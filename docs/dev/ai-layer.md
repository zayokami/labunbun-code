# Design notes: `@labunbun/ai`

`packages/ai` holds the model registry, the prompt cache rules, and the three wire adapters. The agent loop sees one stream protocol, one `StreamFn` shape, and a fixed wrapper order (`packages/ai/src/index.ts:294`). A wire is one provider's HTTP message format, and the stream protocol is the neutral event sequence the adapters produce. The transport is the full pipeline of wrappers around one adapter. This document keeps the long-form design notes that were in the source comments.

## Purpose

- Give the agent loop one stream protocol for the three wires: `anthropic-messages`, `openai-completions`, and `openai-responses` (`packages/ai/src/types.ts:188`).
- Keep the model list small and hand-written. Users add OpenAI-compatible providers from settings (`packages/ai/src/model.ts:1305`).
- State what each provider does about the prompt cache. Measure the traffic the provider reports back (`packages/ai/src/cache.ts:2`).
- Turn a retryable failure, a stalled stream, and a dead model into one terminal `error` event. A caller never sees a throw cross the stream boundary (`packages/ai/src/retry.ts:2`).
- Watch the bytes of every request, so a prefix rewind cannot happen quietly (`packages/ai/src/cache-tracker.ts:2`).

## Behavior

### The stream protocol

- The protocol is event-based. An error never throws across the stream boundary. It arrives as a terminal `error` event with a finalized `AssistantMessage` (`packages/ai/src/types.ts:96`).
- `start` comes first, exactly once. Then `text_*`, `thinking_*`, and `toolcall_*` events arrive in start/delta/end triples. Each triple shares one `contentIndex`. One terminal event comes last: `done` or `error` (`packages/ai/src/types.ts:316`).
- Every event carries the accumulated `partial` message snapshot. Consumers render from it directly and never reduce deltas again.
- Tool arguments arrive as raw JSON fragments, and `toolcall_end` hands the buffered text on unparsed (`packages/ai/src/message-builder.ts:89-101`). The agent layer parses it once at dispatch, where an unparseable payload becomes an invalid-input tool error rather than a stream failure.
- An abort is an `error` event whose `stopReason` is `aborted` (`packages/ai/src/message-builder.ts:123`).
- `MessageBuilder` owns that partial snapshot for all adapters. `#snapshot` copies only the block that changed. The builder shares untouched blocks, because consumers treat blocks as immutable. That copy-on-write keeps a whole content-array copy off the hot path (`packages/ai/src/message-builder.ts:136`).
- `#ensure` fills gaps with empty text blocks when a wire skips an index (`packages/ai/src/message-builder.ts:143`).
- `#get` throws when an index holds the wrong kind of block. Its message names the index and both kinds (`packages/ai/src/message-builder.ts:151`).
- `parseToolArguments` maps an empty string, malformed JSON, and a non-object value to `{}` (`packages/ai/src/message-builder.ts:161`).
- `StopReason` has `refusal` on purpose. A refusal is a deliberate answer with no content and no tool calls. Folded into `stop`, it looks like a normal turn that happened to say nothing (`packages/ai/src/types.ts:59`).
- `Usage.input` is the uncached part of the prompt, on the Anthropic interpretation. The wires disagree: Anthropic's `input_tokens` drops the cached prefix, and OpenAI's `prompt_tokens` keeps it. Adapters normalize to the Anthropic interpretation, so the four channels sum to the true token count (`packages/ai/src/types.ts:69`).
- `Usage.cacheWriteTtl` records write tokens per TTL bucket, where the provider states one. Anthropic does. It is the only evidence that a one-hour TTL took effect. A provider that accepts the field and writes a five-minute entry reports the same `cacheWrite` either way (`packages/ai/src/types.ts:79`).
- `Usage.promptTotal` counts every token in the prefix, cached or not. It is the number to compare against a context window. It is also the only count that means the same thing on both APIs. Messages recorded before the adapters reported it do not have it (`packages/ai/src/types.ts:87`).
- `errorKind` names the failure kinds a caller can act on: `context_overflow`, `rate_limit`, `overload`, and `auth`. The fallback walk is the one reader. A `context_overflow` marks a refusal about size: the same request again, or the next model in a fallback chain, changes nothing, so the walk ends with the message as it stands. A `rate_limit`, an `overload`, or an `auth` names a failure another model may answer, so the chain descends on it. An absent kind is an unclassified failure, and the chain keeps it: provider wordings that match no rule have always earned the next model (`packages/ai/src/types.ts:115`).
- `AssistantMessage.incomplete` marks a turn whose text is real but unfinished: an abort kept the streamed part, a mid-stream failure was sealed with content, or the output ladder ran out (`packages/ai/src/types.ts:116-125`). It is written to the session file with the message and never reaches the wire, so a resumed session can still say the answer is partial.
- `ToolResultMessage.interrupted` marks the result the loop writes for a call an abort cut short. `isError` stays true because the wire pairing needs a failed result, but the interface shows an interruption rather than a tool failure (`packages/ai/src/types.ts:146-156`). `repairToolPairing` sets the same marker on the synthetic result it writes, so the distinction survives a resume (`packages/ai/src/transcript.ts:95-116`).
- `THINKING_LEVELS` is the runtime list: `off`, `minimal`, `low`, `medium`, `high`. The settings schema derives its set from this list rather than state it a second time (`packages/ai/src/types.ts:195`).
- `Model.thinkingMode` names the shape a model takes. `adaptive` means the model decides and effort sets depth. `extended` means the caller names a token budget. The wrong shape is a 400 on the first request, not a worse answer. Absent means the adapter has nothing to say on the subject (`packages/ai/src/types.ts:240`).
- `Model.thinkingBlockBinding` marks the few models that check a replayed thought block against its conversation. Only those models can be told what to do when the check fails (`packages/ai/src/types.ts:243`).
- `Model.toolReasoningEffort` names the `reasoning_effort` a model needs on the OpenAI-compatibility wire, when the request carries tools. Absent is not the same as `false`: it says the model never stated a need (`packages/ai/src/types.ts:246`). The field applies only to a request that has tools. Without them there is nothing to protect, and a forced `none` drops the thought depth the session asked for.
- `Model.reasoningEfforts` lists the efforts a model accepts, where that is a proper subset of ours. The adapter leaves a level outside the list out of the request. A round to a near level is a guess about what the session wanted (`packages/ai/src/types.ts:249`). The OpenAI-compatibility field cannot say this, because it names one replacement effort and not a range. The adapter cannot learn the subset from the request it builds, so the row states it.
- `Model.toolCalling: false` marks a row that cannot call tools on its own wire. The row is not broken. It still does not belong in an agent session, because the session sends `tools` on every request (`packages/ai/src/types.ts:260`). The field is a fact about the row, not a filter at the picker. Every place that offers a model to a session reads it. A second place that forgets it re-opens the trap this field closes.
- The four differences between the OpenAI wires are the reason they are separate adapters, not a flag. `openai-responses` puts the system prompt in a top-level `instructions` field, declares tools flat, sends tool results as `function_call_output` items, and streams named events (`packages/ai/src/types.ts:188`).
- `StreamOptions.onRetry` travels with the request options. A retry sequence that backs off to 30 seconds a step runs for minutes, and the request may be per-model. The callback travels with the call that knows which turn it is (`packages/ai/src/types.ts:284`).
- `StreamOptions.onFallback` is called once per step down a model chain, with a `FallbackNotice` naming the model that failed, the one about to be tried, the reason, and the kind when one was classified (`packages/ai/src/types.ts:327-338`). The walk notifies on a pre-content throw (`packages/ai/src/fallback.ts:76`), a stream that ended with no terminal event (`:88`), and a provider error before any content (`:107`). It stays silent on an abort, on `context_overflow`, on a kind it does not descend for, and after content has streamed (`:60-75`, `:92-105`).

### The wrapper order

- `dispatchStreamFn` routes on `model.api` and throws `Unsupported API` for anything else. It checks the absent key first, before it builds a request (`packages/ai/src/index.ts:279`).
- The wrapper order never changes: `withRetry(withStallTimeout(dispatch))` (`packages/ai/src/index.ts:294`).
- The watchdog sits below retry. A stall before the first event is an ordinary failed connection, and the retry policy gives it a second try. A stall after the first event rethrows. The session loop then seals the partial as an errored turn.
- The stall budget is `settings.stallTimeoutMs ?? 120_000` (`packages/ai/src/index.ts:292`).
- `createTrackedStreamFn` wraps the whole transport, retry policy included. It records one entry per request the caller made, not per try below it. A retry that succeeds is the same prefix asked twice (`packages/ai/src/index.ts:308`).
- The tracked variant costs the per-request hashes. An embedder who never reads the report uses `createDefaultStreamFn` and pays nothing (`packages/ai/src/index.ts:301`).
- `createTrackedStreamFn` creates the notices array and hands it to both sides. The Anthropic adapter writes to it and the tracker reads it. The adapter has to exist before the wrapper that owns it (`packages/ai/src/index.ts:300`).
- The Responses adapter gets the same policy but no `onCacheNotice`. It can raise no notice that the wrapper does not already derive, and a callback with nothing to pass states a false hook (`packages/ai/src/index.ts:270`).

### The model registry

The registry is a hand-written list, not a generated mega-catalog. Users extend it through `registerOpenAICompatibleProvider`. In these notes, a row is a record in this list. An entry is a record in another list, such as a cache or a catalog.

- `ANTHROPIC_BASE` is `https://api.anthropic.com` (`packages/ai/src/model.ts:8`).
- `KIMI_BASE` is `https://api.moonshot.ai/v1`, Kimi's international host. The China host serves the same ids under its own keys (`packages/ai/src/model.ts:10`).
- `GOOGLE_OPENAI_BASE` is `https://generativelanguage.googleapis.com/v1beta/openai/`, Google's OpenAI-compatibility shim. Its docs still call that shim beta (`packages/ai/src/model.ts:12`).
- `OPENAI_BASE` is `https://api.openai.com/v1`. The compatibility adapter of this client was written against that API (`packages/ai/src/model.ts:14`).
- `GLM_BASE` is `https://api.z.ai/api/paas/v4`, Z.AI's international host (`packages/ai/src/model.ts:16`).
- `DEEPSEEK_BASE` is `https://api.deepseek.com/v1` (`packages/ai/src/model.ts:18`).
- `MINIMAX_BASE` is `https://api.minimax.io/v1`, and `/chat/completions` on it is OpenAI's wire (`packages/ai/src/model.ts:20`).
- `MISTRAL_BASE` is `https://api.mistral.ai/v1`, with the same `/chat/completions` wire (`packages/ai/src/model.ts:22`).
- `OLLAMA_CLOUD_BASE` (`packages/ai/src/model.ts:24`) is `https://ollama.com/v1`, and the local daemon's default `OLLAMA_LOCAL_BASE` is `http://localhost:11434/v1` (`packages/ai/src/model.ts:26`). The `/v1` is the OpenAI chat wire on both hosts. The native catalog API sits at the root, and the catalog reader takes the suffix back off.
- `OPENROUTER_BASE` (`packages/ai/src/model.ts:28`) is `https://openrouter.ai/api/v1`. One wire, OpenAI's, so the `/v1` stays for the same reason the versioned pair below keeps theirs. The catalog the probe reads is `/models` on that same prefix, and it answers without a key.
- The gateway has two plans on two wires each (`packages/ai/src/model.ts:32`). `OPENCODE_ZEN_BASE` is `https://opencode.ai/zen` and `OPENCODE_GO_BASE` is `https://opencode.ai/zen/go`. `OPENCODE_ZEN_OAI_BASE` is `https://opencode.ai/zen/v1` and `OPENCODE_GO_OAI_BASE` is `https://opencode.ai/zen/go/v1`. Zen is pay-as-you-go, and Go is a $10/month subscription.
- The two spellings of one plan differ only by a path prefix, and the SDK decides which one a wire takes. The Anthropic client appends `/v1/messages` to its base, so it needs the prefix stripped. The OpenAI client appends `/chat/completions` and needs the prefix kept. The unversioned pair is not a typo to tidy up. It is the value the caller has to give the Anthropic wire.
- `GATEWAY_PROVIDERS` (`packages/ai/src/model.ts:52`) holds seven ids: the four gateway spellings `opencode-zen`, `opencode-go`, `opencode-zen-oai`, and `opencode-go-oai`, plus `ollama`, `ollama-cloud`, and `openrouter`. A gateway is a route to a model rather than a home for one. Both plans, both Ollama hosts, and OpenRouter serve models other vendors make, so they sit in one set, and `resolveModel` treats these seven differently for that reason. OpenRouter's rows spell the vendor's own name first, so its refusals are also the first whose refused id contains a slash.
- The set is the seven built-in ids, not a shape. A "looks like a reseller" test also catches a user who registered their own gateway. A gateway a user registers under an id this table has not built in is that user's word, not this set's.

#### Price helpers

- `roundPrice` rounds to four decimals. `10 * 1.25` is 1.25, but `0.1 * 3` is not exact and leaves a visible error in a price table (`packages/ai/src/model.ts:63`).
- `anthropicPricing` derives the two cache channels from the input rate: a read at `0.1x` input and a five-minute write at `1.25x` (`packages/ai/src/model.ts:69`). Anthropic bills cache traffic as a multiplier of the input rate. A rate change moves all three numbers together.
- The read multiplier is a parameter because the vendor prices two rows at `0.025x`: Fable 5.1 and Mythos 5.1, the two ".1" releases. That pair is exactly where a copy-paste error hides. A third row, Opus 5.5, is priced at `0.05x`. Three regimes exist, and the vendor's price page names each one in a footnote.
- `openAIPricing` takes the read rate and derives the write at `1.25x` input (`packages/ai/src/model.ts:85`). Every current OpenAI row publishes a read at a tenth of input. The caller passes in the read, and the code derives the write, because a wrong derived rule produces no report. A wrong write price stays invisible until a cached session gets a bill.

#### Row constructors

- `anthropicCompatModel` builds a row on the Anthropic wire for a host that is not Anthropic's (`packages/ai/src/model.ts:96`). The wire and the vendor are separate questions. A gateway in front of Claude speaks this wire format and is not this vendor. It has its own host, its own credential, and its own price list. The three fields that name the vendor used to be literals inside `anthropicModel`, so a non-Anthropic host had no constructor to call.
- `anthropicCompatModel` takes no `thinkingBlockBinding`. The flag and its beta header travel together, to the four models that run the check. A gateway in front of those models is not evidence that it forwards either one. A model named here sends a parameter whose behavior on the far side is unknown.
- A row with no fallback omits `apiKeyEnvFallbacks` rather than set it empty. So "no other variable works" and "this row never had a second name" stay different (`packages/ai/src/model.ts:118`).
- `anthropicModel` fills in `ANTHROPIC_API_KEY` and the fallback `ANTHROPIC_AUTH_TOKEN`. Proxies and gateways in front of the Anthropic API commonly issue the credential as the token variable instead (`packages/ai/src/model.ts:145`).
- The two OpenAI wires share `openAIModel`. They take the same options and differ only in the `ApiId` on the row (`packages/ai/src/model.ts:159`). Only the options are shared. A field that one wire alone reads must not reach both wires just because it sits beside the shared signature.
- `reasoning` defaults to false on the OpenAI wires and to true on the Anthropic ones.
- The row omits `toolReasoningEffort` rather than default it. Absent says "this model never said". An absent value and a "takes anything" value are different claims. A row that guesses the second about the first sends a `reasoning_effort` that costs the request its tools.
- `reasoningEfforts` lists the efforts a model accepts, where that is a subset of ours. A level the row does not list is a value the model rejects. A choice of the nearest level it does accept is a guess about what the session wanted.
- `openAICompatModel` uses `openai-completions`, the wire every compatibility provider speaks (`packages/ai/src/model.ts:220`).
- `openAIResponsesModel` uses `openai-responses` (`packages/ai/src/model.ts:238`). For the GPT-6 generation this is the only wire that publishes function calls. A row here is what makes the model an agent model rather than a text one. `packages/agent/src/session.ts` sends `tools` on every request, and a wire that takes no tools leaves the agent with nothing to do, and nothing says so.
- `GatewayModel` (`packages/ai/src/model.ts:238`) is a tuple: id, name, window, output cap, price, `toolReasoningEffort`, and `toolCalling`. `toolCalling: false` marks a model whose function calls appear on another endpoint. Only the OpenAI-wire rows read it, because the Anthropic rows are the same models on a different wire.

#### The gateway tables

- `OPENCODE_ZEN_MODELS` and `OPENCODE_GO_MODELS` are two separate transcriptions (`packages/ai/src/model.ts:254`, `packages/ai/src/model.ts:567`).
- The gateway sells the same catalog two ways: Zen, pay-as-you-go, and Go, a subscription. Each plan has its own key, its own host, and its own price list. The two do not agree on a model they share. That is why one table cannot serve both plans.
- `deepseek-v4-pro` is $1.74/$3.84 on Zen and $0.66/$1.98 on Go, so Go is the cheaper plan there. `grok-4.7` is $1.40/$4.20 on Zen and $2.00/$6.00 on Go, so it is the dearer one. Each plan is cheaper and dearer by model, and conversion has no published rule.
- The figures come from models.dev's catalog entries for the two plans, swept 2026-09-28. The check then filtered them against the gateway's own unauthenticated `/v1/models` list the same day. Both sources were re-checked on 2026-10-08.
- Every number is a copy of a published price and must not be derived. Both halves are needed and neither is enough. The gateway proves which ids can be called but publishes no price and no limit. models.dev states the money and the sizes but is hand-edited and drifts in both directions.
- The gateway serves 87 ids on Zen against the 85 priced here, and 43 on Go against 34. The gateway serves every priced, undeprecated row, so nothing known is absent. The foot of the table notes names the ids the gateway serves that models.dev does not price.
- Nothing here goes through `openAIPricing`, which derives its write rate at `1.25x` input. The gateway publishes a write rate for 35 of these 119 rows and states none for the other 84.
- The read rates are not a fixed multiple of input either. `qwen3.8-flash` reads at 0.016 against an input of 0.15, which is `0.107x`. `qwen3.8-max` beside it reads at exactly `0.125x`. A derived figure can pass review and still be wrong in the channel that bills a long session. Where no rate is published the row carries 0, the value the Gemini and MiniMax M3 rows already take.
- Two names here come from the catalog with a promotion removed. It lists Grok 4.7 as `Grok 4.7 (30% Off)` and DeepSeek V4 Pro on Go as `DeepSeek V4 Pro (New)`. A discount that expires does not belong in a model picker.
- `claude-haiku-5-5` entered the table on 2026-10-08, the day after it shipped. The gateway lists it and models.dev prices it, and the figures match the vendor page's 100k-and-under band. No Go twin exists. The Go list carries no Claude id at all, so both Go tables stay silent. models.dev prices the model on the Go plan too.
- `claude-sonnet-5-5` entered the table on 2026-09-29, the day after it shipped. The gateway lists it, and models.dev prices it at the same figures as its own predecessor, which are also the vendor's. Three sources agree, so this row is a copy and not a derivation. It is the first row added on a re-check of the list rather than on the 09-28 sweep.
- `gpt-6.1-sol` sorts after `gpt-6-sol` because `-` (0x2D) precedes `.` (0x2E). The same byte order puts `gpt-5-codex` before `gpt-5.1` earlier in the table.
- OpenRouter's seven are not a transcription like the two tables above. The host lists hundreds of ids; the seven are a sweep of flagship rows, pinned beside the tables in `BUILT_IN_MODELS` and sourced from the host's own unauthenticated listing on 2026-10-12, except `moonshotai/kimi-k3.1-pro`, added 2026-10-24, the day it shipped. Everything else the host serves arrives through discovery, which works here because its listing states both limits per id — prices still do not travel that road, so a discovered row is unpriced until a user declares one.
- `gpt-6.1-sol` carries no `toolReasoningEffort`, for the same reason its first-party row carries none. Both the constraint and the absent value ride through the reseller. Go sells no `gpt-6.1-*` id, so there is no row to add there.
- `gpt-6.1-sol` is the one gateway row with `toolCalling: false`. Its first-party counterpart sits on `openai-responses`, because that is where OpenAI publishes the model's function calls. This row stays on Chat Completions because that is the only wire Zen's list proves it answers. A row on a wire nobody asked about is a row that 404s. The cost is that the model is text-only here, so the picker does not offer it for a session that expects a tool call.
- On Go, `qwen3.6-plus` carries a 1M window where Zen's entry states 262,144. Each plan's row carries the figure its own catalog states, because nothing says which figure the model itself takes.
- On Go, `space-bunny` replaced `space-bunny-free`, checked 2026-10-08. The Go list serves it at $0.15/$0.60 with $0.03 reads and $0 writes. models.dev's Go entry still lists both ids, but the list is the source that can reject a request. The Zen table still serves `space-bunny-free`, so the plans no longer agree on the id. An old Go reference no longer resolves, and no row forwards it. `RETIRED_MODEL_IDS` is for ids no row carries, and Zen's row still carries this one. It is a plan rename, not a retirement.
- `kimi-k3.1-pro` entered the Go table on 2026-10-24, the day it shipped. Go's listing serves it and models.dev prices it at the vendor's own figures: $2/$10 with a $0.20 read and a $2 write, on the same 1M window and 131k default output as the first-party row. It is the only K3.1 id on the gateway: Zen's list does not serve it, and `kimi-k3.1-pro-highspeed` is first-party only, so neither plan has a row for the twin. The OpenRouter row is not this one; it is pinned in `BUILT_IN_MODELS` and carries the host's own 943,718 output cap and a zero write channel.

#### The built-in table and its provenance

- The last sweep, on 2026-09-27, checked every row against the vendor's own page (`packages/ai/src/model.ts:684`). A date on that line means "as of", not "covers every row below it".
- Rows added between sweeps name a later date in their own note: `claude-opus-5-5` (2026-09-23), `gpt-6-sol`, and `gpt-6-luna`.
- Also `glm-5.3-flashx` and the five MiniMax rows (2026-09-27), `claude-sonnet-5-5` (2026-09-29), `claude-haiku-5-5` (2026-10-08), and the Kimi K3.1 Pro pair (2026-10-24): each note carries its own date.
- The 09-27 sweep changed none of the current prices. It added eight rows and re-confirmed the rest. That includes the DeepSeek V4 Pro and Kimi K2.6 rows that third-party aggregators listed as changed.
- Anthropic's and DeepSeek's figures are the vendors' USD figures. The table derives the cache channel from the documented multipliers rather than copies it. A hand-copied third number is where such a table goes stale first. Sonnet 5 is $2/$10, and the vendor cancelled the increase to $3/$15 that it planned for 2026-09-01.
- The 119 gateway rows are the exception to "the vendor's own page", and they say so. A gateway has no price list of its own: its resellers price what it sells, so those figures are a third-party catalog's. Treat them as a tier below the rows around them, and re-sweep them sooner.
- The OpenAI-compatible rows are worth less than the Anthropic ones, because they differ per host. DeepSeek bills peak and off-peak rates since 2026-08-16, and the figures are the peak ones. A session outside 01:00-04:00 and 06:00-10:00 UTC on a weekday pays half of what the table says.
- Cache writes are the channel the vendors agree on least, so each row says what its vendor says (`packages/ai/src/model.ts:684`). Nothing for DeepSeek and the Kimi K2 series, whose caches fill at ordinary input rates. Nothing today for Z.AI, whose price page calls cache storage "limited-time free" rather than free. `1.25x` input for OpenAI. K3.1 Pro's and K3's own stated write prices. Nothing for MiniMax M3, the one row on its vendor's table with no write rate at all while its M2.x rows state one. Nothing for Google, which meters cache storage by the hour instead, a charge this table cannot express. That last gap makes a Gemini row a floor rather than a cap.
- Two published regimes are time-boxed, and the table carries the current one. Google's Flash prices roughly double on 2027-01-01. OpenAI bills 2x input and 1.5x output across a whole request over 272K input tokens. The second is a premium no per-token table can express at all.
- MiniMax is a third shape: M3's rates double over 512k input, and its `priority` service tier adds 1.5x on top. Its row carries the standard rate at 512k or under. Claude Haiku 5.5 is a fourth: its rates step up fivefold over 100k input tokens, so its row carries the rate at 100k or under.
- When a price matters, for a proxy, a negotiated rate, or a newer model, declare it under `pricing` in `settings.json`. That declaration overrides this table.

#### The Anthropic rows

- Every model from the 4.6 generation on carries the full 1M-token window, and all but one are billed the same at any prompt length. The price page names Haiku 5.5 as the exception, priced by prompt length. Its row carries the band at 100k input tokens or under, and the note carries the rest.
- `thinkingMode` is the capability the rows disagree on, and every row states it rather than takes a default. From 4.7 on, and on the vendor's recommendation for the 4.6 pair too, the only shape these models take is adaptive thought. `output_config.effort` sets the depth, and they refuse `enabled` with `budget_tokens` outright. Haiku 4.5 is the reverse and rejects `adaptive`. The wrong shape for a row is a 400 on the first request. That is why a row that guesses is worse than one that says nothing.
- `claude-opus-5-5` runs the thought-block check and is one of the four flagged models. Its cache read is the `0.05x` regime, between the `0.025x` pair and the standard tenth (`packages/ai/src/model.ts:688`).
- `claude-fable-5-1` and `claude-mythos-5-1` are the `0.025x` pair, and they are the only two rows whose cache reads are not a tenth of input. The flag marks only Fable 5.1. Mythos 5.1 records the same signatures but runs no such check, so it is deliberately not flagged (`packages/ai/src/model.ts:699`).
- Fable 5 is legacy. It is still served, and a settings file may still name it.
- The 4.6-generation rows are legacy too, still served, and they are what a settings file written before the 5 series names. Opus kept its $5/$25 across the generation, and Sonnet 4.6 is still at the $3/$15 that Sonnet 5 cut to $2/$10.
- The 4.6 pair is the one place the regime is a choice. The endpoint accepts both shapes, `enabled` is deprecated, and the vendor's guidance is adaptive.
- `claude-sonnet-5-5` was checked against the vendor's model page on 2026-09-29, the day after it shipped. Its change notes say the API checks a replayed thought block against the conversation that produced it. The check is the default for accounts created on or after 2026-08-31. So this row runs it and belongs beside the pair above (`packages/ai/src/model.ts:757`).
- That flag is not inferred from "the newest model": Mythos 5.1 is newer than the pair and runs no check. The price is unchanged from Sonnet 5, and the vendor, models.dev's `anthropic` entry, and models.dev's Zen entry all state the same four figures. #### Retired ids and declared prices

- `RETIRED_MODEL_IDS` maps ids that no row carries to the row that answers to them now (`packages/ai/src/model.ts:1287`). A model id written into a settings file outlives the model. When a vendor retires one, the choice is between a map to the replacement and a broken reference. The second turns a good configuration into "no such model" while the model the user picked is still served under a new name.
- The map is one-way: nothing writes these ids back out, and nothing lists them, because there is nothing left to choose. Retirement is the usual reason an id lands here, not the only one. Vendors also keep compatibility aliases alive long after the release they named. An alias the table cannot match is as unreachable as a retired id.
- The forward does not keep the price. A target is chosen for family and tier. Where a family is gone, as with Kimi's moonshot-v1 ids, the retirement notice is the only guide. What a session costs can change with the reference, which is the reason to write the map down rather than guess at it twice.
- The Anthropic rows follow the replacement each notice named, a 4.6-generation id or later in every case. The map leaves out the ids whose notice named a whole group's successors rather than their own (`claude-2.x` and `claude-3-sonnet`). A reference that fails loudly beats one forwarded to a guess.
- DeepSeek retired the chat/reasoner pair on 2026-07-24, and both modes live on under the flash id. The two V4 flash ids are different: the API still answers them as compatibility aliases, at flash prices. They name the same row, so a reference to either resolves to it.
- Kimi is where the line of succession ran twice. The K2 previews and K2.5 stay in the family, since K2.6 is the member that survives at the price they had. The moonshot-v1 ids have no survivor to land on and follow their notice to K3, a far more expensive model than the one they named.
- `pricingOverrides` holds prices declared in settings, by reference (`packages/ai/src/model.ts:1272`). The built-in table is a dated snapshot of public list prices, and nobody's bill is the list price. A gateway, a negotiated rate, or a repriced model all make it wrong. A bare model id applies to every provider that serves it, the same way `resolveModel` reads a bare id.
- `OpenAICompatibleProviderSpec` (`packages/ai/src/model.ts:1287`) describes a provider from settings: `id`, `baseUrl`, `apiKeyEnv`, and models with `id`, `name`, `contextWindow`, `maxOutputTokens`, `reasoning`, and `pricing`. The figures are USD per million tokens. An omitted price means tokens count but add no cost.

#### Resolution and the environment

- `allModels` answers everything this process knows about, and that includes models a provider no longer lists (`packages/ai/src/model.ts:1479`). Resolution reads it, not `listModels`. A model a vendor retired today is still the model yesterday's session recorded. That transcript has to resolve and cost with the row in force when the session wrote it. Discovery narrows what can be chosen. It never narrows what can be named. A dynamic provider's template is not in it. The template is a wire and a base URL rather than a model, and it must never resolve.
- `listModels` is the enumeration behind the `/model` picker: everything known, minus what a provider's own list disowns (`packages/ai/src/model.ts:1490`).
- `baseUrlEnvVar` builds `<PROVIDER>_BASE_URL`, with every character outside `A-Z0-9` replaced by an underscore (`packages/ai/src/model.ts:1500`). `ANTHROPIC_BASE_URL` is the example.
- `applyBaseUrlOverrides` points a model at a proxy or gateway through that variable (`packages/ai/src/model.ts:1524`). It runs on the `resolveModel` path so every consumer sees the redirected URL. Both provider adapters build their client from `model.baseUrl`, so nothing downstream needs to know an override happened.
- `resolveApiKey` tries `apiKeyEnv` first, then `apiKeyEnvFallbacks` in order. A row that names no variable contributes no names, because `apiKeyEnvNames` leaves the absent field out. It answers `undefined` when the environment holds none, so callers can tell "absent" apart from "empty" (`packages/ai/src/model.ts:1536`).
- `resolveModel` reads `provider/model` as an exact match on provider and id. A bare id matches at the vendor that makes the model (`packages/ai/src/model.ts:1566`). The code tries a reference that matches nothing once more against the retired ids.
- A bare id means the vendor that makes the model, and only that vendor. Two ways a row breaks that promise, both created by the gateway tables and neither visible in the row itself.
- A bare id a vendor retired still means the retirement, even where some other host sells a model of that name today. The session wrote the reference when exactly one row carried it. An answer from a reseller's row moves the session to another vendor, host, and price. Nobody asked for that. `deepseek-v4-flash` is exactly the case. DeepSeek retired it in favor of `deepseek-flash`, and four gateway providers sell it under its own name and its own rates.
- An id that no first-party vendor carries resolves to nothing at all rather than to the gateway. `gpt-5-codex` is the case that shaped this rule. Before the gateway tables it was an unknown model, which is a fact a migration reports. With them it is a Zen row. A user's `model` setting then turns into a subscription plan on a host whose prices are not OpenAI's. The user may hold no key for that plan. The only symptom is a request that fails at the auth header.
- The picker already shows the rule worth a copy here: choose a model at a gateway under the name that gateway offers. Nothing about `gpt-5-codex` says "on the Zen plan".
- A qualified reference is exempt from both rules, and has to be. `opencode-zen/deepseek-v4-flash` names the reseller, and an answer from DeepSeek is the guess this whole function exists to avoid.
- `lookupReplacement` counts a provider-qualified reference only when it names the provider that serves the replacement (`packages/ai/src/model.ts:1595`). `deepseek/deepseek-chat` is the id this table retired. `gateway/deepseek-chat` is a model somebody else may still serve, and an answer from ours is a guess.
- `gatewayProvidersFor` answers the gateway providers that sell a model under exactly this bare id. It feeds a "no such model, but it is here" message (`packages/ai/src/model.ts:1506`). It exists because of the rule `resolveModel` enforces and cannot itself report. A bare id no vendor makes resolves to nothing, while the `/model` picker lists it a screen away as `opencode-zen/gpt-5-codex`. Without the hint, the message says the model is unknown and the picker shows it.
- The answer is empty whenever the bare name works, in two cases beyond the obvious one. The first is a model a first-party vendor makes: the gateway sells `claude-opus-5-5` too, and the bare name is the one the user keeps. The second is an id that forwards to its replacement. The contract is "consult this after a resolution has already failed". A hint that fires when it must not is worse than none: it sends a user off to buy a plan they do not need.
- A qualified reference needs no guard of its own. The id is compared whole, so `opencode-ze/gpt-5-codex` matches no row and a correct reference already returned empty. An earlier version spelled `includes("/")` out here to be safe against a model id that held a slash. If one ever does, the guard suppresses a hint that is the right thing to give, so the guard is not worth its cost.
- The code raises `MissingApiKeyError` before it builds a request, in place of an empty key passed to the provider's SDK (`packages/ai/src/model.ts:1551`). The SDKs report an empty key as an authentication failure, which reads like something a later try can get past. No try can supply a credential the environment does not hold. The type is what lets the retry wrapper end the turn on the first try and say which variable is absent.
- Its message names the provider and the variables: `Missing API key for <provider>: set <VAR> or <VAR> in your environment.`

### Prompt caching policy

The cache module holds two things, apart from the adapters that use them. The first is what each provider caches: capability, minimum prefix, granularity, and knobs. The second is how the code measures a cached prefix once the provider reports it back (`packages/ai/src/cache.ts:2`). Both halves are pure, so a test can pin them without a network and without a provider.

The measurement half exists because the numbers were invisible. `prompt_cache_hit_tokens`, and the top-level `cached_tokens` some providers put on the usage object, were never read. The report recorded a session that read 99 percent of its prompt from cache as one that read none of it. A hit rate that nobody records cannot improve.

- `CacheMode` is `explicit` when the caller marks the prefix, and `automatic` when the provider decides by itself (`packages/ai/src/cache.ts:7`).
- `CacheCapability.minPrefixTokens` is a floor the provider documents. A prefix below it is not cached at all, so a marker placed there is a write that never becomes a read (`packages/ai/src/cache.ts:13`).
- `incrementTokens` is the granularity a hit rounds to. OpenAI matches the first 1024 tokens exactly and then in steps of 128 tokens, so a 1100-token prefix reads back 1024.
- Both are floors and granularities, not promises. The real numbers come back in `usage`, which is the reason this module also knows how to read them.
- The `ANTHROPIC` row is the one provider that needs the caller to mark the prefix. Its 512-token floor is only the fallback for a model id that is not in the table below (`packages/ai/src/cache.ts:29`).
- The `openai` row records 1024, the low end of the documented 1024-to-2048 range. That figure only decides whether the report calls a prefix cacheable (`packages/ai/src/cache.ts:48`). A low error there says "the provider may have chosen not to" rather than "the provider had no such option".
- The `deepseek` row records a floor of 0 rather than a number invented to look precise. DeepSeek cuts cache units at request boundaries, not at a length (`packages/ai/src/cache.ts:49`).
- The `kimi` row records the documented position: automatic, a 256-token minimum, and no key for the router (`packages/ai/src/cache.ts:57`). Kimi's own guide describes its cache as automatic and says the previous prompt must go above 256 tokens. It documents no key for the router. Third-party clients forward `prompt_cache_key` to the Kimi presets for code and report it as mandatory there. Independent tests on the same endpoint report it as a no-op. The documentation does not settle the question, so the row follows the documentation and `promptCacheKey: "on"` sends one anyway.
- `glm` records 500 and `google` records 1024 (`packages/ai/src/cache.ts:58`). A provider nobody measured is read as `UNKNOWN`: automatic, a 1024 floor, and nothing else (`packages/ai/src/cache.ts:63`).

#### The Anthropic floor table

- `ANTHROPIC_MIN_PREFIX` is a table rather than a family rule, because the spread is not something a rule can express (`packages/ai/src/cache.ts:73`). The floor is 512 on Opus 5, 1024 on Sonnet 5, and 4096 on Haiku 4.5. Then it is 512 again on Sonnet 5.5, a floor that went down inside a family whose rows are prefixes of one another.
- Haiku 5.5 is the same slide one generation later: 512 where Haiku 4.5 needs 4096.
- An earlier inference, "the Haiku family needs twice as much", got both ends wrong. It refused to mark short prefixes that current models cache happily. It also marked Haiku prefixes at half the size Haiku accepts, and the provider then ignored those marks without a report.
- The table runs most-specific-first, and a test checks it with a start anchor, because the ids are prefixes of one another. `claude-opus-4-5` must match before `claude-opus-4`, or an Opus 4.5 request is held to the wrong floor.
- The module exports the table only for the test that keeps it Anthropic's. A pattern added for another vendor's id cannot be caught by an assertion on the floor a lookup returns. The fallback is 512, and so is half this table. A mutant that adds a `gpt-6` pattern at 512 is invisible from the outside. A test that reads the patterns is the only form of that assertion which holds whatever floor is chosen.
- `ANTHROPIC_UNKNOWN_MIN` is the lowest floor anyone documents, deliberately (`packages/ai/src/cache.ts:107`). The two ways to be wrong are not symmetric. A floor set too low places a breakpoint the provider ignores. That shows at once as `cache_creation: 0` in the usage, and it costs one of four breakpoint slots. A floor set too high declines to mark a prefix the provider can cache. That is a hit rate of zero, with no error anywhere. A low error is free and easy to find. A high error is silent and expensive.
- `cacheCapability` reads a provider with no row through `model.api` rather than `model.provider` (`packages/ai/src/cache.ts:120`). A self-registered gateway that speaks `anthropic-messages` still gets breakpoints. The wire format decides whether the provider accepts a marker, and this wire says it does.

#### The TTL and the knobs

- `CachePolicy.explicitBreakpoints` off is a real choice, not a switch for tests. A caller whose prompts never repeat writes an entry on every request and reads none of them back. That caller pays the write premium for the privilege (`packages/ai/src/cache.ts:137`).
- `ttl: "auto"` resolves to the long one, and the cost argument looks wrong at first (`packages/ai/src/cache.ts:175`). The provider bills a one-hour write at twice the input price, against 1.25x for five minutes, but only for the tokens written at that breakpoint. In a conversation those are the few tokens added since the last request. So the premium applies to the delta, and the read discount applies to everything behind it. The shorter TTL buys an entry that is gone after a five-minute pause. The next turn is then a full-price replay of the whole transcript. For a goal measured in hit rate, the long TTL is not a close call.
- `promptCacheKey: "auto"` follows the provider's documentation, which is the only thing that can decide it (`packages/ai/src/cache.ts:184`). An OpenAI-compatible endpoint that never heard of `prompt_cache_key` can reject the request for it. `"on"` is for an endpoint that turns out to want one anyway, a judgement about someone else's gateway that only its operator can make.
- `promptCacheRetention` unset means the field is not sent, and that is the right default rather than a cautious one (`packages/ai/src/cache.ts:194`). On OpenAI an organization without zero-data-retention already gets the long retention. A `"24h"` send repeats the default, and `"in_memory"` shortens it. Only a caller who read their own organization's setting can want either.
- The `PromptCacheRetention` values are deprecated on the newest models. A TTL field replaces them, and that field exists only on a beta surface this adapter does not speak (`packages/ai/src/cache.ts:158`). Models that support neither reject it outright, which is why nothing goes out unasked.
- `resolveCacheTtl` turns `"auto"` into `"1h"` (`packages/ai/src/cache.ts:175`).
- `resolvePromptCacheKey` answers `"on"` with true, `"off"` with false, and `"auto"` with the provider's documented answer and nothing else (`packages/ai/src/cache.ts:180`). A key sent to a gateway that does not know the field is a 400 on every request. A key sent to one that ignores it is a field that means nothing. Neither is a thing to do on a guess.
- `resolvePromptCacheRetention` depends on the provider rather than on a list of model ids (`packages/ai/src/cache.ts:193`). One vendor documents the field. That vendor's models disagree about which values they take, and a value a model does not support is a 400. The caller opts in, and the provider must be the one that documents the field. A gateway never receives it, however the policy reads.

#### The identity of a stable prefix

- `hash64` concatenates two FNV-1a passes with different offset bases (`packages/ai/src/cache.ts:203`). It is not a cryptographic hash and does not try to be. The job is to tell two byte strings apart within one session, where a 32-bit hash is already adequate. Two passes make a collision very unlikely.
- `prefixIdentity` is the wire format, the model, the tools, and the system prompt, joined by `\x00` (`packages/ai/src/cache.ts:218`). Those four stay fixed for the whole life of a prefix, and a provider keys its cache on them. Messages are deliberately absent: they are what grows. A key that moved with them names a different cache on every turn, the opposite of what a cache router wants.
- The same string serves the cache key below and the tracker's notion of a family. So the prefix a report calls one conversation and the prefix a provider is asked to route are the same prefix by construction.
- `promptCacheKeyFor` is the readably-prefixed hash of that identity: `labunbun-` plus the hex (`packages/ai/src/cache.ts:224`). It is readable because the key turns up in a provider's own logs. A support conversation goes better when the key says whose it is. It is a hash because the identity is a whole system prompt and tool schema, not something to paste into a header-sized field. Same prefix, same key, across turns, processes, and a resumed session. The docs describe that case: requests that share a long prefix route to the machine that already has it.
- `CacheNotice` records something a provider did to the cache settings (`packages/ai/src/cache.ts:234`). A refused setting leaves no trace in `usage`. Without a notice the user sees a lower hit rate and no cause, while every later request runs on the fallback. Its fields are the TTL asked for, the TTL now in force, and the provider's own words.
- `cacheHitRate` answers `undefined` rather than 0 when the request did not report a prompt total (`packages/ai/src/cache.ts:246`). A provider that does not report the field and a request that genuinely read nothing are different answers. A printed 0 percent for both is how a cache that works looks broken.
- `cachedTokensFrom` reads the cached token count out of whichever of four spellings a provider used (`packages/ai/src/cache.ts:254`). OpenAI's Chat Completions nests it under `prompt_tokens_details.cached_tokens`. Moonshot puts it at the top level of `usage`. DeepSeek reports `prompt_cache_hit_tokens` beside the nested copy. The Responses wire renames both halves to `input_tokens_details.cached_tokens`. The report recorded a Kimi session that hit its cache about 99 percent of the time as a miss. A read of one spelling alone causes that. A skipped fourth spelling is the same failure one wire over.
- Where more than one spelling is present and they disagree, the largest wins. They name the same quantity, so the smaller one under-reports. That under-report is the failure this code fixes. A first-wins read brings it back the moment a gateway emits a stale `cached_tokens: 0` beside a correct count.

#### Estimating a prefix

- The estimate counts about four characters per token for prose and three for JSON schema, which is denser (`packages/ai/src/cache.ts:275`).
- `messageChars` counts only text. Images need a rule of their own, and a guess produces a number that looks measured. To leave them out is an underestimate, and every decision this estimate feeds compares against a floor (`packages/ai/src/cache.ts:280`).
- `estimatePrefixTokens` is the estimated input tokens of the whole request (`packages/ai/src/cache.ts:298`). It has the same shape as the compaction threshold in `packages/agent/src/compaction.ts`, for the same reason. The last assistant message carries the provider's own count of the prompt that produced it. The unknown part is only what came after. That part is mostly plain text, and division by four is close enough to answer whether this exceeds a thousand tokens. The code bills nothing on this estimate.
- `PrefixTiers` gives the prefix length at each tier a provider caches separately, cumulative at each boundary (`packages/ai/src/cache.ts:304`). Anthropic rejects the whole request if the `tools` tier changes, and only the system tier and below if `system` does. So its breakpoints sit on tier boundaries, and each boundary has its own length against its own minimum.
- One number for the whole prompt cannot answer whether one position is worth a mark. A 900-token system prompt under a 60k transcript clears no minimum on its own. The same system prompt at the end of the transcript does. A breakpoint on the system prompt caches the tools as well, which is why the numbers are cumulative.
- `prefixTierTokens` counts the tool schema at three characters per token, the system prompt at four, and then adds `estimateMessageTokens` (`packages/ai/src/cache.ts:320`).
- `estimateMessageTokens` moves back to the newest assistant message that reported usage (`packages/ai/src/cache.ts:320`). It takes the provider's prompt count as the anchor, adds that message's output, and estimates the appended text at four characters per token. The estimator skips a message with no prompt total and no input tokens. With no anchor at all, the estimate is the plain character count of everything, divided by four.

#### How good a session cache can be

- `cacheCeiling` computes the best hit rate a sequence of requests can achieve (`packages/ai/src/cache.ts:343`). A request can read only what an earlier request wrote, and a prompt only grows. Request `t` can read at most the prompt of request `t-1`, so the best possible rate is `sum(P[t-1]) / sum(P[t])`. The number falls as a conversation grows, because the newest prompt is always the biggest one.
- The cap turns "we are at 96 percent" from a verdict into a diagnosis. At the cap the machinery is perfect and the workload is the limit. Below it, tokens were thrown away.
- The cap comes from the provider's own prompt counts, in order. The cap skips requests that did not report one, rather than estimate them, because a made-up cap excuses a real gap.
- Fewer than two known prompt counts yields `undefined`. The first request has nothing before it to read, so it adds to the denominator and nothing to the numerator.
- `promptTotalsOf` collects one prompt count per assistant message that reported one, in order (`packages/ai/src/cache.ts:363`). The assistant message is what the provider answered a request with, so its usage is that request's usage.
- `cacheTotals` sums the four token channels and the request count over the assistant messages (`packages/ai/src/cache.ts:381`). `totalsHitRate` is `read / (read + write + input)`, or `undefined` for an empty session (`packages/ai/src/cache.ts:395`).

### Cache tracking

The hit-rate number alone cannot say why a cache missed. A request that reads nothing can be a cold start, because no earlier request wrote the prefix. It can be a TTL that expired. It can be a genuine rewind, where the bytes changed in the middle and everything after that point was charged at full price. It can be a different conversation, a subagent or a model fallback.

The tracker answers that question. It remembers the wire-visible bytes of each request and compares the next request against them (`packages/ai/src/cache-tracker.ts:2`).

- The tracker is a `StreamFn` wrapper rather than part of the agent session, deliberately. The session sees only its own loop, while compaction and subagent requests go through the same `StreamFn` the app hands out. A tracker inside the session reports those requests as absent. Worse, it compares them against the main loop transcript and calls every one a rewind.
- Two requests are comparable only when they share a cache namespace and a prefix: same model, same tools, same system prompt. This is the notion of a family (`packages/ai/src/cache-tracker.ts:145`).
- A subagent has its own system prompt and a filtered tool list, so its request starts a new family. The first request in a family is a cold start by definition, never a rewind.
- A model switch or a fallback starts a new family for the same reason. A cache belongs to one model, so the new model has nothing to read no matter how stable our bytes were.
- The hash covers only the bytes the adapters actually put on the wire: role, text, block kinds, tool ids, and arguments (`packages/ai/src/cache-tracker.ts:99`). The hash leaves out `timestamp`, `usage`, and anything else that moves every turn but never goes out on the wire. A hash of the whole neutral message reports rewinds the provider never sees.
- The tracker compares the neutral transcript, not the post-merge wire array. The Anthropic adapter merges consecutive tool results into one user turn, and that transform is stable. So a divergence in the neutral list shows at or before its wire position. The indices below are message indices, the unit a person can look up in the transcript.
- `MAX_FAMILIES` is 8, one per model-plus-prompt shape in play (`packages/ai/src/cache-tracker.ts:13`). The main loop and a handful of subagent flavours is the realistic cap. A family that falls out of the window starts over, and its next request is a cold start, exactly as a fresh family is.
- `MAX_RECORDS` is 500 (`packages/ai/src/cache-tracker.ts:21`). A long session issues thousands of requests, and each one costs a few hashes and some counters. The bound keeps the report readable rather than about memory, because `/cache` summarises all of it and lists the tail.
- `CacheRequestRecord.kind` separates four cases (`packages/ai/src/cache-tracker.ts:44`). `"first"` is the family's first request, the one request with nothing before it to read. `"extension"` is the healthy grown prefix. `"rewind"` is a changed prefix. `"reask"` is the same prefix presented again, such as a retry after a failure or a second try with a different output cap. Those last two ask the provider to read the same bytes, so neither wastes a cache opportunity and neither grows the conversation. That is exactly why they are not extensions.
- `outcome: "cancelled"` covers both an aborted turn and a consumer that walked away mid-stream. `"failed"` is a throw from the client before any event arrived (`packages/ai/src/cache-tracker.ts:63`). Neither is a prefix problem, so neither is a `cause`. A rewrite nobody registered must stay visible as one.
- `CacheTracker.note` registers a deliberate rewrite, and the next request recorded takes it (`packages/ai/src/cache-tracker.ts:68`). `records` answers oldest first. `families` answers in most-recently-used order. `reset` forgets everything, and it runs when resume or `/clear` replaces a session (`packages/ai/src/cache-tracker.ts:82`).
- `notices` sits apart from `records` because it is not about a request. A refused TTL changes every later request. A report that folds the refusal into one turn's numbers shows the symptom but not the cause (`packages/ai/src/cache-tracker.ts:81`).
- `CacheTrackerOptions.notices` is a list the tracker reads from, filled by whoever owns the transport (`packages/ai/src/cache-tracker.ts:89`). The direction is unusual, because the notices come from inside the adapter, and the adapter is built before this wrapper can exist. The transport gets the array itself, rather than a setter, so it stays the only writer.
- `messageText` reduces one message to the bytes an adapter sends (`packages/ai/src/cache-tracker.ts:99`). The hash includes a thought block's signature because Anthropic sends it back and rejects a transcript whose signature does not match. The hash includes a tool call's arguments because they are the model's own output, replayed.
- `contextFingerprints` returns tools at unit 0, the system prompt at unit 1, and one unit per message (`packages/ai/src/cache-tracker.ts:118`). Tools and system are units rather than one folded key, because a divergence there has a different fix from a divergence in the transcript. The tool list is frozen for the session. A change to it means something added tools mid-conversation, such as `/mcp approve`, and that invalidates every tier below it. An empty system prompt and an absent tool list hash to constants, so they still compare cleanly.
- `firstDivergence` answers the first unit at which the next request no longer extends the previous one (`packages/ai/src/cache-tracker.ts:131`). A longer list that starts with the old one is the healthy case, because the conversation grew. Anything else is a rewind, because the bytes at that index changed and every token after it is a fresh write. A shorter list that the old one starts with is a truncation, and it lands in the same place for the same reason.
- `withCacheTracker` wraps a `StreamFn` so the tracker records every request it makes (`packages/ai/src/cache-tracker.ts:158`). It sees logical requests. A failed try that the retry policy retries away is the retry policy's business. The tracker records the try that succeeds as a reask, because that is what the cache sees.
- Usage comes from the terminal `done` or `error` event. A stream abandoned before one still produces a record with `reported: false`. A request that reached the provider and got nothing back is exactly the kind of thing a cache report must not hide. The wrapper never throws on its own account, because its own records must not be the reason a turn fails.
- The tracker updates the family before the request goes out. If the stream throws, the next request must still compare against what went out. A stale prefix that this try already replaced is the wrong comparison (`packages/ai/src/cache-tracker.ts:222`).
- The record's kind is `"first"` with no previous family, `"rewind"` when a divergence appears, `"extension"` when `extendsPrev` holds, and `"reask"` otherwise (`packages/ai/src/cache-tracker.ts:207`). No divergence and no growth can only mean the same bytes twice.
- There is no `finally` block. The default outcome is `"cancelled"`, which is what is left when the loop neither finished nor threw. That covers a consumer that walked away from an aborted turn (`packages/ai/src/cache-tracker.ts:250`). A caught error records `"failed"` when the provider reported nothing, and then rethrows. This wrapper sees the stream, and it does not own what happens to it.
- `extendsPrev` answers whether the next list is strictly longer than the previous one and starts with it (`packages/ai/src/cache-tracker.ts:262`).

### Retries, stalls, and fallbacks

#### The retry wrapper

The retry wrapper is the throw boundary of the stream protocol. Adapters let SDK and network exceptions go up. This wrapper catches them, retries with exponential backoff while it emitted nothing downstream, and turns the final failure into a terminal `error` event (`packages/ai/src/retry.ts:2`). After it forwards any event to the consumer, exceptions go up unchanged. The stream can take no safe retry, and the agent loop owns the mid-stream failure. It seals the partial as an errored turn.

- The defaults are `maxAttempts` 10, `baseDelayMs` 500, `maxDelayMs` 30_000, and `overloadedMaxAttempts` 3 (`packages/ai/src/retry.ts:30`).
- `overloadedMaxAttempts` caps the tries for a 529 response, which means the provider is overloaded (`packages/ai/src/retry.ts:23`).
- `random` is the jitter source for the backoff, injectable so a test can pin it (`packages/ai/src/retry.ts:27`).
- `statusCodeOf` reads a status from `error.status` or from `error.response.status`, and answers `null` for anything else (`packages/ai/src/retry.ts:38`).
- `isRetryableStatus` is true for 408, 409, 429, and every status of 500 or above (`packages/ai/src/retry.ts:47`).
- `OVERFLOW_PATTERNS` holds the provider wordings for "this request is bigger than the model's window" (`packages/ai/src/retry.ts:58`). They all arrive as a 400, which is indistinguishable from a malformed request unless the code reads the message. The difference matters: one is worth a fix that sends less, and the other is not worth a request.
- The patterns carry their vendors: `maximum context length` for OpenAI and the OpenAI-compatible clones, `prompt is too long` for Anthropic, `exceeds the maximum number of tokens` for Google, and three more.
- `isOverflowStatus` accepts 400, 413, and 422, the statuses a provider uses to refuse a body it considers too large (`packages/ai/src/retry.ts:68`).
- `looksLikeContextOverflow` also reads in-stream error text (`packages/ai/src/retry.ts:73`).
- `isContextOverflowError` is true when the provider refused the request as too large to send (`packages/ai/src/retry.ts:79`). A retry gains nothing, because the request does not shrink on its own. A replay against the next model in a fallback chain gains nothing either. That is how an oversized context turns into a generic error on every later turn. Only the caller can make it smaller.
- A 413 answers true with no check of the text, because a gateway's "Request Entity Too Large" needs none. The remedy is the same: send less.
- `isAbortError` matches the names `AbortError` and `APIUserAbortError` (`packages/ai/src/retry.ts:97`). An abort is the user's own cancel, not a provider fault. A retry overrides the user's cancel, and the fallback chain tries every model before it gives up. Callers rethrow it so the session loop maps it to stop reason `"aborted"`.
- `isNetworkError` matches a `TypeError`, which is how a `fetch` failure surfaces. It also matches a message that names a network condition such as `ECONNREFUSED` or `socket` (`packages/ai/src/retry.ts:103`).
- `headerValue` reads one header off an error, whichever container the SDK used (`packages/ai/src/retry.ts:112`). It handles a real `Headers` instance and a plain record, in both spellings.
- `retryAfterMsOf` reads the wait a `Retry-After` response asks for, in milliseconds, or `null` (`packages/ai/src/retry.ts:125`). The SDKs attach a real `Headers` instance, and an earlier version read it like a plain record, so the header never fired in production. Only the hand-rolled fixture in this repo ever had the right shape.
- Three forms are legal, and the code reads all three. `retry-after-ms` comes first, because a seconds value rounds it off, then seconds, then an HTTP date (`packages/ai/src/retry.ts:128`). Negative values clamp to zero, rather than a sleep backwards.
- An empty header counts as absent. `Number("")` is 0, and a header that says nothing must not count as "retry at once" (`packages/ai/src/retry.ts:136`).
- In the retry loop, a stream that ends with no terminal event is an error (`packages/ai/src/retry.ts:192`). A stream with no events at all throws, so the catch below can retry it. A stream that emitted events but no terminal event yields a terminal `error` event instead.
- After anything went downstream, the catch rethrows at once, because the consumer already saw partial output (`packages/ai/src/retry.ts:198`).
- A user interrupt rethrows at once, so the session loop sees the abort, not a sequence of retries (`packages/ai/src/retry.ts:202`).
- `MissingApiKeyError` yields one terminal `error` event with the error's own message, labelled `errorKind: "auth"`, and returns (`packages/ai/src/retry.ts:208`). A credential the environment does not hold is not something a later try can produce. It arrives without a status, like the unknown errors that earn one more try. Without this guard it takes the whole retry sequence, two minutes, to report a key that was never there. The label keeps the fallback walk alive: another provider holds its own key.
- An error that says a new sign-in is needed fails the same fast way: a `ClaudeOAuthError` marked `invalidGrant` yields one terminal `error` event with its own message, labelled `errorKind: "auth"`, and returns (`packages/ai/src/retry.ts:222`). The reason is the missing key's reason. The mark is deliberately narrow. A token endpoint having a bad day arrives with `invalidGrant` false and earns the full ladder, because waiting is exactly what fixes that.
- `retryable` is true for a network error, a retryable status, or no status at all. An unknown error before the first byte earns one more try (`packages/ai/src/retry.ts:234`).
- The overloaded cap is the smaller of `overloadedMaxAttempts` and `maxAttempts`, and it counts only overloaded tries (`packages/ai/src/retry.ts:236`).
- A context overflow is terminal on the first try, and the status-less case that otherwise earns a retry is included (`packages/ai/src/retry.ts:244`). The request does not get smaller because it is sent again.
- The terminal message for an overflow is `The request is larger than <model>'s context window: <message>`, with `errorKind: "context_overflow"` (`packages/ai/src/retry.ts:247`). Every other final failure reads `Request failed after <n> attempt(s): <message>`, and carries the kind its status names where one does: `rate_limit` for an exhausted 429, `overload` for a 529 at its cap, `auth` for a 401 or 403 (`packages/ai/src/retry.ts:155`).
- The backoff is `min(baseDelayMs * 2 ** (attempt - 1), maxDelayMs)`, and the jitter keeps half of it fixed and randomizes the other half (`packages/ai/src/retry.ts:264`). Retries from parallel sessions on the same schedule otherwise synchronize with each other, and a delay that can shrink to nothing retries at once. The jitter applies to the exponential backoff only, because a `Retry-After` is the server's own number. Both live under the caller's cap.
- A `Retry-After` value wins over the jittered backoff, and the code clamps the result to `maxDelayMs` (`packages/ai/src/retry.ts:266`).
- The notice goes to `streamOptions.onRetry` first, then to the wrapper's own `onRetry` (`packages/ai/src/retry.ts:275`). The caller that knows which turn is on retry is also the one with a place to say so.
- The backoff wait passes through `sleepUnlessAborted`, so the caller's signal can end it (`packages/ai/src/retry.ts:276`). The loop read the signal nowhere inside the wait before that, and a wait can run to `maxDelayMs` — thirty seconds, which is also the number a `Retry-After: 30` asks for. An interrupt during the backoff went unseen until it ran out.
- `sleepUnlessAborted` races the sleep against that signal and throws its reason (`packages/ai/src/retry.ts:299`). `abortErrorOf` keeps the reason the caller passed, and shapes anything else into the platform's `AbortError`, the name `isAbortError` reads as the interrupt (`packages/ai/src/retry.ts:283`).

#### The stall watchdog

`withStallTimeout` is the idle watchdog between the consumer and the wire (`packages/ai/src/stall-timeout.ts:2`). The failure it exists for is the request that never ends and never fails. A provider or a proxy took the connection and then went silent. Timeouts inside the SDK cover a slow response, not a dead one. The retry layer sees only failures, so a connection that goes quiet triggers no retry and ends no turn. This wrapper turns "no event for N ms" into a thrown `StreamStallError`.

- `StreamStallError` carries the message `Provider stream stalled: no event arrived for <ms>ms` (`packages/ai/src/stall-timeout.ts:13`). It is deliberately not an `AbortError`. Every layer above reads an aborted signal as the user's interrupt, and a stalled connection is a provider fault.
- The wrapper sits under retry, as `withRetry(withStallTimeout(dispatch))` (`packages/ai/src/stall-timeout.ts:25`). A stall before any event flowed is a failed connection and earns a second try. A stall after events flowed is terminal, and the session loop seals the partial as an errored turn.
- The stall must reach the wire, so the request under it stops (`packages/ai/src/stall-timeout.ts:38`). The wrapper aborts its own controller for that, composed with the caller's signal so Esc still cancels. An abort of the caller's own signal reads as the user's interrupt in every layer above.
- The wrapper takes the explicit iterator rather than the iterable. The watchdog paces `next()` itself instead of a `for await` over the whole stream (`packages/ai/src/stall-timeout.ts:41`).
- Each `next()` races a timer (`packages/ai/src/stall-timeout.ts:61`). The timer aborts first and then rejects, so the connection stops in the turn the watchdog gives up. It does not wait while the error travels up through the wrappers.
- Both promises settle and the race uses one. The loser's rejection still needs a handler, or it surfaces as an unhandled rejection (`packages/ai/src/stall-timeout.ts:58`).
- The outer `finally` closes the inner generator, because the consumer can walk away mid-stream, by an interrupt or an early break (`packages/ai/src/stall-timeout.ts:74`). The close is not awaited: an inner generator suspended on a promise that never settles can hang this cleanup. The cascade abort is what actually stops a real request.

#### The composed signal

Each adapter hands the SDK a custom `fetch`. The SDK calls it with its own signal on the `init`. Its per-request timer aborts through that one. The caller's signal, the user's Esc, travels beside it (`packages/ai/src/signals.ts:2`). A request must answer to both. A pass-through of one where two exist means the dropped one can no longer cancel anything.

- `composeSignals` answers an `AbortSignal` that aborts when either input does (`packages/ai/src/signals.ts:6`).
- With no SDK signal there is nothing to combine, and the caller's signal goes back as it is. A manufactured wrapper adds only a listener that outlives the call.
- On a runtime without `AbortSignal.any`, the caller's signal passes through alone. That is the behavior from before composition, kept rather than emulated.

#### The fallback chain

`withModelFallback` retries the turn with the next model in the chain on a provider error that arrives before any content streamed (`packages/ai/src/fallback.ts:2`). An auth failure, an unavailable model, and a rate limit past the retries all qualify. An error after content started to flow goes up unchanged. A fallback replays the turn the user already watched, and the agent loop seals the partial as an errored turn.

- The chain is the model itself, then `resolveChain(model)` without any entry that names the same id and provider (`packages/ai/src/fallback.ts:38`).
- The loop yields events as they come and watches for a terminal event (`packages/ai/src/fallback.ts:68`). The `start` event does not count as content.
- A pre-content throw falls through to the next model, except for an abort (`packages/ai/src/fallback.ts:75`). The abort must go up even then, or the chain tries every model before the abort takes effect.
- A stream that ends with no terminal event is an error for the last model in the chain. For every other model it is a reason to try the next one (`packages/ai/src/fallback.ts:82`).
- A terminal `error` walks on only when its kind says another model may answer: `rate_limit`, `overload`, or `auth` (`packages/ai/src/fallback.ts:22`). A `context_overflow` goes up at once (`packages/ai/src/fallback.ts:96`): the context is too large for this model, so it is too large for every model after it with the same window, and for the ones that take it, the caller asked the wrong question. The walk turns one explainable refusal into a generic error per model. A kind this version does not know goes up at once too, and an error with no kind keeps the walk, the resilience that predates any classification.
- A terminal `done`, any content, or the last model in the chain all yield the terminal event and return (`packages/ai/src/fallback.ts:101`). Otherwise the error came before any content, and the next model gets a silent try. Its own `start` event re-anchors the consumer's partial state.

### The Anthropic adapter

- The adapter is three pieces. `buildAnthropicRequest` maps the `Context` to wire params, `mapAnthropicStream` maps raw SSE events to `AssistantMessageEvent`, and `createAnthropicStreamFn` wires the official SDK client to both (`packages/ai/src/providers/anthropic.ts:2`).
- Tool-call arguments arrive as `input_json_delta` fragments. The mapper buffers them raw and parses them once at block end, which avoids an O(n²) parse of partial JSON.
- The raw wire types are a local structural subset of the SDK's stream events. They stay local so the mapper is testable with plain fixtures (`packages/ai/src/providers/anthropic.ts:29`).
- `AnthropicStopDetails` carries a refusal reason as far as the API will say (`packages/ai/src/providers/anthropic.ts:77`). `category` is the machine-readable half and `explanation` is the prose. Both are nullable and either can arrive alone. A beta endpoint has more categories and more fields, and this reader takes the GA shape and ignores additions rather than a guess at them.
- `THINKING_BUDGETS` is 1024, 4096, 16384, and 32768 for `minimal` through `high` (`packages/ai/src/providers/anthropic.ts:86`).
- `THINKING_EFFORT` is the depth dial for the adaptive models, and it replaced the budget (`packages/ai/src/providers/anthropic.ts:95`). Those models pace themselves, and effort is the only say left to the caller. `off` lands on the lowest level rather than on nothing, because there is nothing to switch off there. Thought is not optional on these models. The vendor's guidance for a request that once asked for a small budget is the lowest effort. `minimal` joins `low` for the same reason, because the scale has no level below it.
- The two levels above `high` are deliberately unreachable. The session's `ThinkingLevel` is exactly four levels plus `off`, and a map onto anything past it invents a setting nobody asked for.
- `AnthropicEffort` names the five effort levels the wire accepts: `low`, `medium`, `high`, `xhigh`, and `max` (`packages/ai/src/providers/anthropic.ts:104`).
- `THINKING_BLOCK_BINDING_BETA` is `thinking-binding-controls-2026-08-01`, and its two halves work only together (`packages/ai/src/providers/anthropic.ts:113`). The beta header lives on the client call and `thinking.block_binding` lives in the body. The field without the header is itself a 400. The header on a model that runs no prefix check asks it to honor a parameter it does not know. Both travel together, and only to the models flagged `thinkingBlockBinding`.
- The module exports `anthropicBetaHeaders` because the headers ride on the client call rather than in the body. `buildAnthropicRequest`, the pure piece the tests drive, cannot see them (`packages/ai/src/providers/anthropic.ts:132`).
- `AnthropicRequestParams` spells `output_config` out even though the index signature lets any key through (`packages/ai/src/providers/anthropic.ts:157`). That signature is exactly why an omission is invisible to the compiler, and this field is what the whole adaptive path hangs on.

#### The API version

- The adapter pins `anthropic-version` on both SDK clients, through the options that `defaultClient` and `defaultModelsClient` share. Version 2023-06-01 is still supported. SDK 1.x sends 2026-10-21 unless told otherwise, so the wire version would otherwise change with a dependency bump. The pin keeps that choice in this repository, where a migration can be reviewed and tested.
- Version 2026-10-21 removes `temperature`, `top_p`, and `top_k`: any of the three is a 400 even at its default. It also rejects a `document` block directly in an assistant message and a non-empty `citations` array on a text block in a user message. This build sends none of them. The request builder assigns no sampling field, and the neutral content model has no document or citation block. The sampling fields are typed `never` on the request params, so a future addition fails to compile rather than at the API.
- `ANTHROPIC_API_VERSION` overrides the version for first-party rows, which is how to try 2026-10-21 without a source change. Reseller rows keep the pinned version, because a gateway speaks the wire shape it was built for. A value that is not a date is refused when the client is built.
- A request under the override can still carry `oauth-2025-04-20` and the thinking-binding beta. The release notes do not say whether either beta remains valid under 2026-10-21, so a live check is part of trying the new version. The pinned default is what ships until that check happens.
- The Admin API and Claude Enterprise Analytics field renames in the same release do not apply: this package calls neither API.
- The build runs `@anthropic-ai/sdk` 1.x. That line sends the API key as `Authorization: Bearer` and sends no `X-Api-Key`. A first-party row keeps that shape. A reseller row also carries `X-Api-Key` with the same key, because a gateway built against 0.x reads the old header; the SDK's header and the gateway's header then both work. The subscription path carries no api key, so it adds no such header.
- The SDK's `credentials` client option is still the `AccessTokenProvider` shape: a provider returning `{ token, expiresAt }` and accepting `forceRefresh`. `ClaudeTokenProvider` matches it structurally, so the subscription path needed no change. A 401 still forces a refresh through the same option.

#### The four breakpoint slots

- `AnthropicBreakpointPlan` names four positions: `tools`, `system`, `previous`, and `tail` (`packages/ai/src/providers/anthropic.ts:184`). Anthropic orders its tiers `tools`, then `system`, then `messages`, and a change at one level invalidates that level and everything below it. So the four positions are the longest prefixes that do not change between the requests of one conversation.
- `tools` covers the tool definitions, frozen when the session was built.
- `system` covers the tools plus the system prompt, which changes only when the app rebuilds it, at a resumed session or a change of directory. Its separation from `tools` means a changed system prompt still reads the tools tier back.
- `previous` is where the request before this one ended.
- `tail` is where this one ends, written for the next one to read.
- `previous` needs the justification. A read is an exact hash match at a breakpoint, and when that fails the API searches back at most 20 positions. In an ordinary tool loop the previous request's tail is two or three positions back. An assistant turn and a run of tool results sit between, and the API counts each of those as one position. So the search finds it and the extra breakpoint changes nothing. It exists for the case where the tail moved past what the search reaches. There a breakpoint on the position, rather than a search for it, turns a full miss into a full read.
- The plan spends all four slots when all four positions clear their minimum, in the order the tiers need (`packages/ai/src/providers/anthropic.ts:207`). There is no reserve. Anything added later must take a slot from this list rather than be appended to it. That includes a request-level automatic breakpoint or a marker an app wants to place itself.
- The plan checks every position against its own minimum. A breakpoint below the model's floor is not cached. Unlike a breakpoint that is simply shorter, it says nothing in the response except that nothing happened.
- `previousRequestTail` finds where the request before this one ended, and how long its prompt was (`packages/ai/src/providers/anthropic.ts:195`). The prompt that produced the newest assistant message was everything before it, and a transcript grows only at the end. So the message immediately before that assistant message is exactly where that prompt ended. The function needs no state across requests, which matters for a process restart and a resumed session, where a remembered index does not survive.
- The token count comes from that message's own usage, because it is the prompt the provider billed, and therefore exact (`packages/ai/src/providers/anthropic.ts:201`). That doubles as the correctness condition. A message with no usage came from a request that never answered. So the code cannot know of a write at the position before it, and there is nothing worth a breakpoint.
- `planAnthropicBreakpoints` checks all four positions against the minimum, from `prefixTierTokens` for the tiers and `previousRequestTail` for `previous` (`packages/ai/src/providers/anthropic.ts:208`).
- `buildAnthropicRequest` adds the `previous` mark first and the tail mark last, so on a one-message request the tail position wins (`packages/ai/src/providers/anthropic.ts:229`). The tail is the one that writes the entry this turn will read.

#### The thought shape

- A model takes exactly one of two shapes. On the oldest rows that shape is `enabled` with a budget, and from 4.7 on it is `adaptive` with an effort (`packages/ai/src/providers/anthropic.ts:264`). The wrong shape is a 400 on the first request. That is why the choice is a per-model capability rather than a default with an exception.
- The adapter honors the session's level only on a row that declares a thought shape: `reasoning: true` or a `thinkingMode` (`packages/ai/src/providers/anthropic.ts:262`). A row that declares neither says the endpoint is not known to think. A level handed to it puts a `thinking` field on the request, and the model can refuse that field. On a gateway row whose id is a 4.6-or-later Claude model, `{type: "enabled", budget_tokens}` is exactly the 400 this path exists to avoid. A forced `off` there sends no thought field at all, and for those rows that is the only request known to work.
- On an adaptive row, the adapter sets `display: "summarized"`, and the setting is not cosmetic (`packages/ai/src/providers/anthropic.ts:274`). Left off, these models return thought blocks whose text is empty. The panel goes blank, and so does the narration between tool calls, on every turn, with no error to explain it. The beta option is not the way out. `display: "updates"` empties the thought blocks and fills only the progress-update ones, so it buys back the narration and gives up the thought. `summarized` fills both and is the richer of the two.
- `block_binding` goes out only for the flagged models (`packages/ai/src/providers/anthropic.ts:275`).
- The adapter sends `output_config.effort` even for a level that once meant "think less" (`packages/ai/src/providers/anthropic.ts:281`). To compare the effort against the default and then skip the field saves nothing, because the prompt carries the resolved setting either way.
- On the `enabled` path the budget is `min(THINKING_BUDGETS[level], max_tokens - 1)`, and it goes out only when it stays at 1024 or above (`packages/ai/src/providers/anthropic.ts:283`).

#### The answer's shape

- `StreamOptions.outputSchema` carries a JSON Schema from the host to every adapter (`packages/ai/src/types.ts:318`). The session forwards it on each request (`packages/agent/src/session.ts:483`), so the constraint applies to every answer rather than only the last one.
- Each wire has its own spelling. Anthropic puts the schema in `output_config.format` beside the effort, not in place of it, because `output_config` is one object (`packages/ai/src/providers/anthropic.ts:386`). Chat Completions uses `response_format` (`packages/ai/src/providers/openai-compat.ts:126`), and Responses uses `text.format` (`packages/ai/src/providers/openai-responses.ts:169`). Both OpenAI wires send `strict: true`, the default Codex uses: the schema is a constraint, not a hint. A schema outside the provider's strict subset is a 400 that names the field.
- The host gates the flag to those four wires (`packages/coding-agent/src/headless.ts:246`). The Gemini Code Assist wire has no field for a schema, so a run on it refuses the flag before the first request (`packages/coding-agent/src/headless.ts:353`) rather than sending a request that would ignore it.

#### Message conversion

- `convertMessages` merges consecutive tool results into one user message of `tool_result` blocks. The API needs tool use and its results paired inside user turns (`packages/ai/src/providers/anthropic.ts:294`).
- Thought blocks round-trip with their signature, which the API needs before it takes them back at all. The API returns them, and that is not the same as their effect. Some models check a block against the conversation that produced it. On those models an in-place edit of the history, which is what compaction does, leaves a signature that no longer matches. The `drop_block` opt-in keeps that a dropped block rather than a 400 on the next request.
- A user message's text goes out as a block array even when a bare string fits (`packages/ai/src/providers/anthropic.ts:345`). The two forms are the same prompt. One message carries a breakpoint on the turn it arrives and none on the turns after it. A breakpoint can attach only to a block. So blocks throughout mean the bytes of a message never depend on whether it is the tail.
- The exception is an empty message. It has no block to attach to and no tokens to cache, and it keeps the bare form (`packages/ai/src/providers/anthropic.ts:341`).
- The `marks` are indices into the neutral message array, not the wire array (`packages/ai/src/providers/anthropic.ts:310`). The merge changes the positions, so the two do not line up. A rewind report that said "wire message 7" then describes something the reader cannot find.
- The adapter parses an assistant `toolCall` block on the way out with `parseToolArguments`. That is the same function the dispatcher parses it with on the way in (`packages/ai/src/providers/anthropic.ts:378`). The API schema wants an object there, and `ToolCall.arguments` is the model's JSON text. The type system accepted the string, because the field is untyped in `AnthropicRequestParams`, and no test rejected it. So a transcript with a tool call was impossible to replay.

#### Stream mapping

- The mapper lets exceptions from the wire iterator go up, because the retry wrapper is the throw boundary, not this mapper (`packages/ai/src/providers/anthropic.ts:439`).
- A `signature_delta` arrives as its own delta event before block stop. The mapper buffers it per index and attaches it when the thought block closes. Without it the block comes back unsigned, and no later request can carry an unsigned block (`packages/ai/src/providers/anthropic.ts:449`).
- `message_start` maps the usage: input tokens, output tokens, the two cache channels, and the TTL breakdown when `cache_creation` is present (`packages/ai/src/providers/anthropic.ts:461`). `promptTotal` is input plus `cacheRead` plus `cacheWrite`.
- `content_block_start` for `tool_use` also handles a complete inline `input` object, which some models send instead of deltas (`packages/ai/src/providers/anthropic.ts:483`). A `redacted_thinking` block is opaque and has no deltas, so the mapper records only its type.
- `STOP_REASON_MAP` maps `end_turn` and `stop_sequence` to `stop`, `tool_use` to `toolUse`, and `max_tokens` to `length` (`packages/ai/src/providers/anthropic.ts:406`).
- `pause_turn` maps to `stop`, and the map names it rather than leaves it to a fallback. The server handed the turn back mid-flight and can take it again with the same messages. Nothing here resumes a paused turn, so it ends the way an ordinary stop does. The decision not to resume these is written down on purpose.
- The mapper handles `refusal` and `model_context_window_exceeded` where it reads them, not in the map, because each needs more than a one-word translation.
- A `refusal` becomes `stopReason: "refusal"` with `refusalMessage` as the error message (`packages/ai/src/providers/anthropic.ts:530`). A refusal is an answer, and an empty one: no content, no tool calls, and the same `stop_reason` a normal turn sends. Folded into `stop`, it files as a successful turn that happened to say nothing. That leaves the user with an empty reply and nothing to act on.
- `refusalMessage` uses the explanation, or the category as `Claude declined this request (<category>)`, or nothing (`packages/ai/src/providers/anthropic.ts:427`). An invented sentence puts the words in two places, and one of them must speak even when the wire said nothing.
- `model_context_window_exceeded` becomes `stopReason: "error"` with `errorKind: "context_overflow"` and the message `The model's context window was exceeded` (`packages/ai/src/providers/anthropic.ts:537`). The turn ran out of room, and unlike a `max_tokens` stop, no follow-up request fixes it, because the request itself is at the window. This is the same error the thrown form produces, so callers reach for the one remedy that works: send less.
- A stop reason the map does not know becomes `stopReason: "error"` with `Unrecognized stop reason: <value>` (`packages/ai/src/providers/anthropic.ts:565`). An unknown reason is not a normal finish. A default of `stop` is how a refusal went unnoticed for so long. The failure it hides, an empty turn filed as a successful one, is invisible by construction. The value in the message is the difference between a bug report and a mystery.
- `message_stop` yields `done`, with `stop` substituted when the reason is still `pending` (`packages/ai/src/providers/anthropic.ts:558`).
- An `error` event is classified in the mapper too. An in-stream refusal never becomes a throw, so the retry layer above cannot see it (`packages/ai/src/providers/anthropic.ts:565`).
- A stream that ends without `message_stop` yields `Anthropic stream ended without message_stop`, or `Anthropic stream produced no events` when nothing arrived at all (`packages/ai/src/providers/anthropic.ts:575`).

#### The live function and the TTL fallback

- `ttlLadder` is the list of TTLs to try, and the code tries each entry only because the provider refused the one above it (`packages/ai/src/providers/anthropic.ts:609`). The first entry is what the policy asked for. Below it the short TTL, and below that no `ttl` field at all, because a gateway that rejects the field outright rejects either value. So the third entry is a request any Anthropic-shaped endpoint accepts. A policy with `explicitBreakpoints: false` yields a single entry with no TTL.
- Each entry costs one failed request, once per process, and then never again. The entry index is process-wide on purpose. A provider that does not take the long TTL does not take it for the next session either. To learn that again on every request costs one failed request to be told the same thing (`packages/ai/src/providers/anthropic.ts:624`).
- `looksLikeCacheSettingRejection` is true for a 400 whose message mentions cache, TTL, ephemeral, or beta (`packages/ai/src/providers/anthropic.ts:619`). A 400 that mentions none of those is a genuinely malformed request and must go up. A retry without a `ttl` turns a real error into a silent one. The text check separates the two, and it is deliberately narrow.
- The downgrade happens below `withRetry`, because a 400 is not a status that wrapper retries, and it is right not to (`packages/ai/src/providers/anthropic.ts:695`). So this code must fix the one class of 400 it can handle before the first event goes out. That is where the catch sits.
- A refusal fires `onCacheNotice` with the old TTL, the new one, and the provider's own words, then takes the next entry (`packages/ai/src/providers/anthropic.ts:701`).
- The adapter applies the beta headers per request rather than on the client. So a model without the flag does not carry a header meant for another one. The subscription's `oauth-2025-04-20` beta joins them only while the request rides a sign-in, and the model's beta headers win a header-name collision against the caller's (`packages/ai/src/providers/anthropic.ts:673`).
- `defaultClient` sets `maxRetries: 0`, because the retry wrapper owns retry policy, and composes both abort signals in a custom `fetch` (`packages/ai/src/providers/anthropic.ts:760`). Both signals must reach the request, because the SDK puts its own on the `init` and its timeout timer aborts through that one. A replacement with the caller's signal alone leaves the timeout with no listener.

#### The Anthropic catalog

- `listAnthropicModels` reads `GET /v1/models` page by page (`packages/ai/src/providers/anthropic.ts:795`). The endpoint answers 20 rows at a time unless asked for more, and `MODELS_PAGE_SIZE` is 1000, its own maximum. `MAX_MODEL_PAGES` is 10.
- A list cut off at the page cap claims the models past it do not exist, so `complete` reports whether all of them were seen. A partial list is still worth a read for its limits, but it must never be used to conclude that something is gone.
- When more rows exist but the response carries no cursor, the result is a fragment, and it stays marked as one (`packages/ai/src/providers/anthropic.ts:823`).
- `defaultModelsClient` sets no retries and no timeout of its own. How long to wait is the caller's policy, and the caller says so with the signal it passes (`packages/ai/src/providers/anthropic.ts:831`).

### The Claude subscription

`anthropic-oauth.ts` speaks the console's OAuth handshake and mints the bearer token that a subscription session sends in place of an API key. The endpoints and the client id are the console's own, and they live here as constants (`packages/ai/src/providers/anthropic-oauth.ts:18`).

- The authorize URL is `https://claude.com/cai/oauth/authorize`, and the token endpoint is `https://platform.claude.com/v1/oauth/token` (`packages/ai/src/providers/anthropic-oauth.ts:21`). There is no client secret, which is what the PKCE pair is for.
- `CLAUDE_OAUTH_SCOPES` asks for five scopes: `user:profile`, `user:inference`, `user:sessions:claude_code`, `user:mcp_servers`, and `user:file_upload` (`packages/ai/src/providers/anthropic-oauth.ts:30`).
- The manual flow ends on an HTTPS callback page rather than a local port (`packages/ai/src/providers/anthropic-oauth.ts:27`). The page shows the authorization as `code#state`, and `parseClaudeAuthorizationInput` keeps the first two segments and drops any tail (`packages/ai/src/providers/anthropic-oauth.ts:117`). An empty paste and a state-only paste are nothing.
- `createPkce` makes a 43-character base64url verifier from 32 random bytes, and the S256 challenge is its SHA-256 digest (`packages/ai/src/providers/anthropic-oauth.ts:75`). The challenge is computed from the verifier and never the other way around, because that derivation is the whole handshake. The state is its own 32 bytes and not a slice of the verifier (`packages/ai/src/providers/anthropic-oauth.ts:81`).
- `claudeAuthorizeUrl` pins the console's parameter order, from `code=true` through `state`, and a `login_hint` goes last (`packages/ai/src/providers/anthropic-oauth.ts:96`). The order is the one property of the URL a host cannot tell us is wrong, so a test holds it.
- `exchangeClaudeCode` posts the code and the verifier as JSON, under a 30-second timeout (`packages/ai/src/providers/anthropic-oauth.ts:242`). A 401 reads `Authentication failed: Invalid authorization code`, and an answer without an access token is refused rather than stored as one. The account e-mail rides along when the endpoint sends it, for the message the login flow shows.
- `refreshClaudeToken` posts the refresh grant with the scopes the login was granted (`packages/ai/src/providers/anthropic-oauth.ts:270`). An answer that omits the rotated refresh token keeps the old one, because the server rotates at will. An omitted lifetime falls back to 30 days, because storing `null` would mean "never expires", the one thing it is not.
- Only a dead grant is marked dead. `invalid_grant` and the reused-token refusal say the session needs a new sign-in; a 500 or a timeout says the endpoint is having a bad day (`packages/ai/src/providers/anthropic-oauth.ts:270`). The mark decides whether the stored credential is cleared, and the split keeps a bad day from logging the user out.
- `claudeRefreshDue` opens a five-minute window before expiry, boundary included (`packages/ai/src/providers/anthropic-oauth.ts:301`). An unknown expiry is never due, because there is nothing to refresh against.
- `ClaudeCredentialStore` is the port, with `load`, `save`, and `clear` (`packages/ai/src/providers/anthropic-oauth.ts:310`). The credential is the app's secret, so the storage form is the app's decision and not this package's.
- The provider matches the SDK's `AccessTokenProvider` shape: a callable that mints, with an `available()` beside it (`packages/ai/src/providers/anthropic-oauth.ts:348`). A fresh token is served without touching the network, a token inside the window refreshes and is saved, and `forceRefresh` ignores the window because the caller knows something the clock does not.
- Concurrent refreshes coalesce into one request, and the join is decided before the first await, because two requests racing the rotation lose one of the two refresh tokens. A forced refresh joins nothing: handed the token the server just rejected, it would fail for the reason it was forced.
- `available()` answers what the next request could actually do (`packages/ai/src/providers/anthropic-oauth.ts:414`). With a refresh token that is true. Without one it is the access token's own clock: true while past the refresh window, false the moment a refresh would be wanted and none is possible. An expired token with no refresh token empties the store and names the login.
- `oauthActive` is the sign-in that could serve this request, and it is false when no subscription is configured, when `available()` says no, or when the caller set a key on the call (`packages/ai/src/providers/anthropic.ts:657`). A per-call key outranks the stored login, which in turn outranks the environment's key.
- The subscription was configured but nothing is signed in and no key can stand in: the adapter says so before a keyless client dials and comes back with the API's own phrasing (`packages/ai/src/providers/anthropic.ts:649`). The error is marked `invalidGrant`, so the retry ladder shows it at once instead of keeping "run /login" off the screen for two minutes.
- `OAUTH_BETA` is `oauth-2025-04-20` (`packages/ai/src/providers/anthropic.ts:123`). The adapter sends it explicitly on a subscription request even though the SDK would add it, because a header the tests can see is a header the tests hold. It rides with the model's own beta headers, and the betas win a header-name collision against the caller's (`packages/ai/src/providers/anthropic.ts:673`).
- One forced refresh is the whole 401 recovery: a second 401 on a token minted moments ago is the account's answer, not a stale token's (`packages/ai/src/providers/anthropic.ts:682`). The forced mint bypasses the freshness window and re-saves, and the retry goes out on the new token. A refresh that fails rethrows the original 401, because it is what the API said.
- The auth trio picks which credential the SDK signs with (`packages/ai/src/providers/anthropic.ts:827`). An explicit key is an API key. The credentials branch passes `apiKey: null` and `authToken: null` so the trio names one credential option. SDK 1.x reads no environment token whenever `credentials` is that one non-null option, and a second non-null option throws before a request.

### The ChatGPT subscription

`chatgpt-oauth.ts` speaks the codex backend's OAuth handshake and mints the bearer that the `chatgpt-responses` adapter sends in place of a key — a subscription is the only way onto this wire, because its rows name no key variable. The endpoints and the client id are the reference client's own (`packages/ai/src/providers/chatgpt-oauth.ts:22`).

- The issuer is `https://auth.openai.com`, and the authorize page and the token endpoint hang off it (`packages/ai/src/providers/chatgpt-oauth.ts:25`). The client id is public, which is what the PKCE pair is for (`packages/ai/src/providers/chatgpt-oauth.ts:29`).
- `CHATGPT_OAUTH_SCOPE` asks for the identity trio, `offline_access`, and the two connector scopes (`packages/ai/src/providers/chatgpt-oauth.ts:32`).
- `chatGptAuthorizeUrl` pins the reference client's parameters and its order, including the three knobs of its own flow: ask the ID token for organization claims, use the simplified flow, and identify the requesting client as `codex_cli_rs` (`packages/ai/src/providers/chatgpt-oauth.ts:102`).
- `createChatGptPkce` and `createChatGptOAuthState` make the same 32-byte derivations the Claude module makes (`packages/ai/src/providers/chatgpt-oauth.ts:84`). The state is its own bytes, not a slice of the verifier.
- The account lives in the ID token: `chatgpt_account_id` and `chatgpt_plan_type` under the `https://api.openai.com/auth` claim, the e-mail from the top-level claim or the profile claim behind it (`packages/ai/src/providers/chatgpt-oauth.ts:157`). A token that is not a JWT at all is `undefined` — an empty claim set is a login this layer knows nothing about, not an error.
- `ChatGptOAuthCredential` keeps `accountId: string | null`, because the API cannot be called without the header that carries it. `expiresAt` is the access token's own `exp` claim and may be null; `lastRefreshAt` then becomes the refresh clock, the reference client's 8-day fallback (`packages/ai/src/providers/chatgpt-oauth.ts:196`).
- `exchangeChatGptCode` posts the code as a form, exactly as the reference client does (`packages/ai/src/providers/chatgpt-oauth.ts:281`). An answer missing any of the three tokens is refused rather than stored as half a login, and a 401 is the invalid-code shape the retry wrapper must let out at once.
- `refreshChatGptToken` posts the refresh grant as JSON — the same endpoint takes the two encodings — and what the answer omits survives from `previous` (`packages/ai/src/providers/chatgpt-oauth.ts:338`). The dead-grant rule is shared with the Claude module: a 401, an `invalid_grant` word, or a body naming an expired, reused, or invalidated refresh token (`packages/ai/src/providers/chatgpt-oauth.ts:258`).
- `chatGptRefreshDue` opens the same five-minute window as its Claude twin (`packages/ai/src/providers/chatgpt-oauth.ts:394`).
- `ChatGptCredentialStore` is the port and `createChatGptTokenProvider` the minting provider, under the same rules as the Claude pair: coalesced refreshes, a forced refresh joining nothing, and `available()` derived from the refresh token or the clock.
- The device flow is the fallback for machines whose loopback no browser can reach. `requestChatGptDeviceCode` returns the one-time code and the page (`packages/ai/src/providers/chatgpt-oauth.ts:555`). The poll treats 403 and 404 as "not approved yet" (`packages/ai/src/providers/chatgpt-oauth.ts:623`). On approval the server hands over the PKCE pair to use itself, and the exchange redirects to the issuer's own device callback.

The adapter is `chatgpt-responses.ts` — a wire of its own rather than a mode of the public Responses adapter, because three shapes differ structurally (`packages/ai/src/providers/chatgpt-responses.ts:2`):

- The system prompt is not a top-level `instructions` field. It is spliced into the input as a developer-role message, after the tool frame.
- The rows the backend's catalog marks lite take their whole tool set inside one `additional_tools` frame item: a single namespace named `functions` with an empty description (`packages/ai/src/providers/chatgpt-responses.ts:45`). A call in the default namespace carries its plain name, which is why the response mapper needs no namespace handling.
- `prompt_cache_retention` does not exist in the request struct the backend's client builds, so this adapter never sends it.
- `buildChatGptRequest` iterates the shared Responses builder's output field by field instead of mutating it, so every field this wire carries is a line someone chose, and a field added upstream does not drift onto a wire nobody verified it against (`packages/ai/src/providers/chatgpt-responses.ts:68`). `tool_choice` is a constant, sent even on a lite request with no top-level tools; `parallel_tool_calls` is `!lite`; and `reasoning.context: "all_turns"` rides lite rows even when no effort does, because it is a property of the wire and not of the session's thinking level.
- `chatGptHeaders` sends `originator: codex_cli_rs`, `ChatGPT-Account-ID` when the grant carries one, and `X-OpenAI-Fedramp` for a FedRAMP account (`packages/ai/src/providers/chatgpt-responses.ts:123`). The caller's headers go under the required ones, because an account id is a requirement of the endpoint, not an incidental value.
- `subscriptionMissingError` is this layer's own refusal, marked `invalidGrant` so the retry wrapper shows "run /login" at once instead of waiting out the ladder (`packages/ai/src/providers/chatgpt-responses.ts:154`).
- `createChatGptStreamFn` carries the same one-forced-refresh 401 recovery as the Anthropic adapter — a second 401 on a token minted moments ago is the account's answer (`packages/ai/src/providers/chatgpt-responses.ts:160`). Its client sets `maxRetries: 0`, because the retry wrapper above owns the ladder (`packages/ai/src/providers/chatgpt-responses.ts:220`).
- The eight rows are off the backend's own catalog, with its base URL as their `baseUrl` (`packages/ai/src/model.ts:20`); seven wrap their tools in the frame and GPT-5.5 does not (`packages/ai/src/model.ts:974`). Discovery skips them (`packages/ai/src/discovery.ts:113`): no listing call exists for this wire — the catalogue is fetched by the backend's own client behind the sign-in — so a probe would return "no answer" by construction, and counting it as an ask would be bookkeeping about a request nobody makes. The retry wrapper's fast path admits this error class beside the Claude one (`packages/ai/src/retry.ts:222`).

### The OpenAI Chat Completions adapter

- This adapter works unchanged against OpenAI, DeepSeek, Kimi, GLM, OpenRouter, and some other providers. Any provider that exposes the `/chat/completions` wire format through a custom `baseUrl` fits the same code (`packages/ai/src/providers/openai-compat.ts:2`).
- Tool calls stream as fragments keyed by array index, with the id and name only on the first fragment of each call. The adapter concatenates the argument pieces raw and parses them once at the finish.
- A model that thinks streams `delta.reasoning_content`. Some providers instead stream `delta.content` as a list of parts during a thought phase, and each part wraps its text one level down.
- Usage arrives only when the request carries `stream_options: { include_usage: true }`.
- `finish_reason` is the terminal signal. The mapper emits `toolcall_end` for all open calls and maps the reason to a `StopReason`.
- `OpenAIRawChunk.usage` lists three spellings of the cached token count. A fixture then proves that each one is understood: Moonshot's top level, and DeepSeek's twice (`packages/ai/src/providers/openai-compat.ts:52`).
- `prompt_cache_key` is a hint to the router, not a cache instruction (`packages/ai/src/providers/openai-compat.ts:84`). It asks the provider to send requests that share the prefix to a machine that already holds it. A key on its own produces no hits, because the prefix still has to match byte for byte.
- `buildOpenAIRequest` asks `cacheCapability` for both cache fields, and a provider with no row gets neither (`packages/ai/src/providers/openai-compat.ts:106`). An unknown endpoint that rejects an unknown field is a 400 on every request. That is worse than a cache with no hits.
- When a caller sets an output cap, both `max_completion_tokens` and `max_tokens` go out (`packages/ai/src/providers/openai-compat.ts:116`). Newer OpenAI models want the first, most compatibility providers understand only the second, and providers ignore an unknown field.
- The adapter never sends `temperature` alongside `reasoning_effort` (`packages/ai/src/providers/openai-compat.ts:133`). DeepSeek-style providers ignore the effort field.
- `model.toolReasoningEffort` wins over the session's level when the request carries tools (`packages/ai/src/providers/openai-compat.ts:135`). The session's level is not negotiable with the wire. Some models publish a function-call ability at one effort only, and the request goes out with `tools` on it either way. An answer at the level asked for there does not degrade the turn, it removes the tools from it.
- Without that field, the level goes out only when it is `low`, `medium`, or `high` (`packages/ai/src/providers/openai-compat.ts:141`).
- `convertMessages` sends the system prompt as a `system` message, and user text as a string or a block list with `image_url` data URLs. A tool result goes out as a `tool` message, and the adapter joins its text blocks with a newline (`packages/ai/src/providers/openai-compat.ts:148`). An assistant's tool call carries its `arguments` or `{}` when they are empty.
- `FINISH_REASON_MAP` maps `stop`, `tool_calls`, `function_call`, `length`, `max_tokens`, `content_filter`, `eos`, and `eos_token` (`packages/ai/src/providers/openai-compat.ts:209`).
- `content_filter` becomes a refusal, the same turn the Anthropic wire names with its own stop reason. `stop` there files the model's refusal as a successful turn that happened to say nothing.
- `eos` and `eos_token` are real terminal values from TGI-style clones. Every unmapped reason is an error now, so those two entries keep the strictness from a false alarm on a provider that works.
- `mapOpenAIStream` emits `start` on the first wire event, not on the connection itself (`packages/ai/src/providers/openai-compat.ts:254`). A connection that the provider accepted and then left quiet must look event-less to the retry layer above. There it earns a second try rather than a terminal turn. The Anthropic mapper always emitted `start` this way, off its first wire event.
- The usage read normalizes the input count to `max(0, promptTotal - cacheRead)` (`packages/ai/src/providers/openai-compat.ts:266`). `prompt_tokens` counts the cached prefix and `input` must not, or the provider bills the cached tokens once as input and again as `cacheRead`.
- The cached count comes from `cachedTokensFrom`, not from `prompt_tokens_details.cached_tokens` alone. Kimi and DeepSeek state the same number elsewhere, and one spelling alone recorded every one of their cache hits as a miss.
- The mapper reads the list shape of `content` part by part (`packages/ai/src/providers/openai-compat.ts:308`). A thought part carries its text one level down, in its own list. The answer's first text part shares that list with the last part of the trace. Once the answer is under way the field is a plain string again. A read as a string alone lands the whole list in `textDelta`. That block of `[object Object]` sits in the middle of the answer, with the trace lost.
- A refusal arrives on its own field too: `delta.refusal` carries the explanation while `content` stays empty (`packages/ai/src/providers/openai-compat.ts:334`). The turn still finishes with `stop`, so a content-less refusal reaches the session as an empty response and the model's own words are thrown away. A turn whose only words are the refusal's therefore becomes a `refusal` with those words as its message, and a turn that streamed text keeps its `stop` (`packages/ai/src/providers/openai-compat.ts:392`).
- The mapper keys each tool fragment by its array slot. An absent id defaults to `call_<slot>`, and a name that arrives on a later fragment fills an empty one (`packages/ai/src/providers/openai-compat.ts:336`).
- A stream that produced no content at all yields `OpenAI-compatible stream produced no content` (`packages/ai/src/providers/openai-compat.ts:363`).
- Open blocks close in creation order, thought first and then text (`packages/ai/src/providers/openai-compat.ts:368`).
- The mapper decides the terminal stop reason before the `toolcall_end` events, so the finalized partial carries the right `stopReason` (`packages/ai/src/providers/openai-compat.ts:396`).
- Three outcomes are told apart on purpose. The mapper respects a known reason. The mapper seals an unknown reason as an error and names it `Unrecognized finish reason: <value>`, because a default of `stop` files it as a successful turn. No reason at all keeps the `stop` guess, and it is a guess. The SDK reads the `[DONE]` sentinel before this mapper sees it. So a clean end and a proxy that dropped the connection after the last content chunk are indistinguishable here. `stop` is the reason the sentinel points to, and the content that did arrive is real either way.
- `defaultClient` threads the caller's abort signal into every request, so Esc cancels an OpenAI-compatible provider the same way it cancels Anthropic (`packages/ai/src/providers/openai-compat.ts:458`). Both signals must reach the request, for the same reason as the Anthropic client.
- `listOpenAIModels` answers almost only ids (`packages/ai/src/providers/openai-compat.ts:493`). Unlike Anthropic's endpoint, this one states no price and no output cap. Only one vendor states a window at all, Kimi as `context_length`. The entries can confirm that an id exists and can report one that does not, plus correct a window where a vendor bothers. That window matters more than it looks. It is the input to the compaction threshold, and this is the one chance to check it against the vendor without a paid call. OpenRouter answers the same endpoint and states more, but it takes the reader right after this one.
- `listOpenRouterModels` is the third reader, for the host whose `/models` answers the same request with more in it (`packages/ai/src/providers/openai-compat.ts:527`). Each entry carries a display name, a window, and an output cap under `top_provider.max_completion_tokens` — both limits, which is a synthesized row's whole requirement. The generic reader above drops the cap, and a row missing either limit is not built at all, so the dispatch is the difference between a browseable catalog and seven pinned rows. Prices in the page are deliberately not read: a discovered row is unpriced by design, and the notice says to declare one. A zero or a null is a field filled in, not a stated limit; an absent field just costs the row that fact.
- The spec leaves the endpoint unpaginated, so whatever comes back is the whole catalog, and the code reports it as complete (`packages/ai/src/providers/openai-compat.ts:505`).

### The Responses adapter

- The Responses wire is the third wire, and the one that carries tool calls for the GPT-6 generation (`packages/ai/src/providers/openai-responses.ts:2`).
- It is a separate adapter rather than a mode flag on Chat Completions, because the two disagree on every shape the agent loop touches. The system prompt is a top-level `instructions` field, and tools are declared flat with no `function` wrapper. A tool result is a `function_call_output` item that references the call. The stream is a sequence of named events, and the terminal event carries the whole response envelope, usage included.
- The `instructions` field is not cosmetic. The cached prefix runs `instructions` first and then `input`. A conversation whose system prompt is rebuilt per turn therefore invalidates the whole prefix, no matter how little else changed.
- The shapes and event names are the vendor's published format, and nothing here was round-tripped against a live endpoint (`packages/ai/src/providers/openai-responses.ts:2`). This checkout cannot make a paid request. The repository has a fixed rule: a claim about the wire is only as good as the evidence for it. The code marks the parts a live request must settle as open where they appear.
- Requests send `store: false` (`packages/ai/src/providers/openai-responses.ts:129`). The transcript of a code session is the user's source code and everything said about it. A default that keeps it on the provider's side is not a decision this adapter gets to make quietly. The flag is also what makes a thought block replayable without an item id.
- `include: ["reasoning.encrypted_content"]` asks for the encrypted thought blob (`packages/ai/src/providers/openai-responses.ts:130`). With `store: false` there is nothing on the provider's side to refer back to. So this is the only thing that makes a thought item replayable. A model that thinks cannot resume a conversation it has no record of, and the caller cannot correct the result.
- `responsesEffort` answers the effort a request can carry, or nothing (`packages/ai/src/providers/openai-responses.ts:101`). An absent result means no `reasoning` field at all. That answer covers three different cases that must stay apart: the session asked for none. The session asked for one this model does not accept. The model says nothing about efforts, and the request carries what was asked for.
- An absent `model.reasoningEfforts` means the model publishes no subset, so everything we can express is on the table (`packages/ai/src/providers/openai-responses.ts:111`). A present list means the row states what it accepts, and `minimal` is not in it. That is an omission, not a round-down to `low`.
- `buildResponsesRequest` sends `instructions`, `max_output_tokens`, and the two cache fields under the same order rule as the other two wires. It also sends the tools flat with `tool_choice: "auto"`, and `reasoning: { effort, summary: "auto" }` (`packages/ai/src/providers/openai-responses.ts:146`).
- `convertInput` reads an assistant turn back in the order the model emitted it: thought, then text, then tool calls (`packages/ai/src/providers/openai-responses.ts:185`). The order is not cosmetic, because the code attributes each item to the turn that produced it.
- A thought block is replayable only when it came back with the encrypted blob (`packages/ai/src/providers/openai-responses.ts:191`). The mapper drops one without the blob rather than send it empty. The wire has no spelling for a thought item with neither readable text nor a verifiable blob. One such item is the request that 400s.
- What is NOT carried is the item `id` (`packages/ai/src/providers/openai-responses.ts:201`). With `store: false` there is nothing on the provider's side for it to name. If the wire turns out to want it, this is where it goes. That is the one claim in this adapter that a live request can falsify and this checkout cannot.
- A tool call becomes a `function_call` item with `call_id`, not the item id. The tool result that comes back names the call, and that name is what has to line up (`packages/ai/src/providers/openai-responses.ts:205`).
- A tool result becomes a `function_call_output` item with `output` (`packages/ai/src/providers/openai-responses.ts:221`). It references the call rather than a turn of its own in the conversation.
- `mapResponsesStream` keys open calls by item id, because that is what the argument deltas carry. It keeps the same states under a second key by wire item id (`packages/ai/src/providers/openai-responses.ts:262`). The mapper keeps content order, so text and thought land where the model put them.
- The mapper emits `start` on the first wire event, not on the connection itself, for the same reason as the Chat Completions mapper (`packages/ai/src/providers/openai-responses.ts:296`).
- `response.output_item.added` prefers `call_id` over the item `id`, and that preference is the whole reason this adapter cannot reuse the Chat Completions one. The item id there produces a request whose every tool result is unmatched (`packages/ai/src/providers/openai-responses.ts:332`).
- On `response.output_item.done`, the mapper captures the blob of a thought item, because the blob arrives on that event and not on the summary deltas. It is what makes the block replayable next turn (`packages/ai/src/providers/openai-responses.ts:359`).
- The mapper uses a `function_call` item's finished arguments only when the deltas produced nothing (`packages/ai/src/providers/openai-responses.ts:366`). A well-formed stream repeats them there. So a stream that omits the event still works, and the mapper repairs one whose deltas did not reassemble.
- A refusal arrives on its own pair of events rather than in the text channel: `response.refusal.delta` carries the explanation and `response.refusal.done` repeats it whole (`packages/ai/src/providers/openai-responses.ts:375`). The done copy fills in only when the deltas produced nothing, like the function-call arguments above. A refusal is a completed turn, so read as an unknown event it lands as a content-less `stop`, and the session seals that as `The model returned an empty response` — the declaration thrown away. So a turn whose only words are the refusal's becomes a `refusal` with those words as its message, and a turn that streamed text keeps its `stop` (`packages/ai/src/providers/openai-responses.ts:440`).
- An unknown event is not an error, because the terminal event is what decides the turn (`packages/ai/src/providers/openai-responses.ts:404`).
- A stream that ends without a status yields `Responses stream ended without a terminal event`, and the absent status is how this code detects the failure (`packages/ai/src/providers/openai-responses.ts:421`). The events that came through can hold a call whose arguments stopped mid-JSON. A close as resolved then dispatches a tool call the model never finished. The terminal events are the only way a status gets set.
- The usage read normalizes the input count the same way Chat Completions does, because `input_tokens` counts the cached prefix and `input` must not (`packages/ai/src/providers/openai-responses.ts:451`).
- A failure yields `error` with the usage attached (`packages/ai/src/providers/openai-responses.ts:461`).
- Tool calls close sorted by content index. So a stream that interleaved two calls closes them in the order the message will be read back in (`packages/ai/src/providers/openai-responses.ts:467`).
- `resolveStopReason` tells a plain answer apart from a turn that ended in tool calls. A Responses terminal event names a status and not a reason (`packages/ai/src/providers/openai-responses.ts:476`). `completed` covers both, so the content of the turn decides. The distinction is not cosmetic. The agent loop stops on `stop` and runs tools on `toolUse`. So an answer that ended in a tool call but reports `stop` is a session that quietly does nothing.
- `incomplete` with `max_output_tokens`, and a plain `incomplete`, both become `length`. `incomplete` with `content_filter` becomes a refusal, the same turn Chat Completions names with that finish reason (`packages/ai/src/providers/openai-responses.ts:490`). A filtered response is a policy outcome, and as `length` the loop sends the turn back after room the model was never going to use. `failed` and `cancelled` become `error`. An absent status becomes `error` too, even though the mapper rejects that case first, so the contract does not depend on the caller (`packages/ai/src/providers/openai-responses.ts:484`).

### The Gemini subscription

The adapter is `gemini-code-assist.ts` — a wire of its own rather than a mode of the `google` rows, because nothing about the request is the OpenAI-compatibility shape those ride: the model, the project, and a per-prompt id sit beside a `request` field that carries the conversation, every stream frame wraps its payload in a `response` envelope, tools ride one `functionDeclarations` list with each schema under `parametersJsonSchema`, and thinking is steered by a camelCase `thinkingConfig` inside a request that is snake_case everywhere else (`packages/ai/src/providers/gemini-code-assist.ts:2`).

- Two things this wire never sends: a prompt-cache field, and a header carrying client metadata (`packages/ai/src/providers/gemini-code-assist.ts:13`). The sign-in's bearer is the whole of the credential — these rows name no key variable.
- The sign-in half is not in this package. The handshake, the credential store, and the bearer provider live in `packages/coding-agent/src/gemini-auth.ts` (documented in gemini-subscription.md). This package consumes the provider: consulted per request, and `forceRefresh` bypasses the freshness window after a 401 (`packages/ai/src/providers/gemini-code-assist.ts:510`).
- `geminiSubscriptionMissingError` is this layer's own refusal — "run /login" — marked `invalidGrant` so the retry wrapper names it at once instead of waiting out the ladder (`packages/ai/src/providers/gemini-code-assist.ts:539`). The retry wrapper's fast path admits this error class beside the Claude and ChatGPT ones (`packages/ai/src/retry.ts:226`).
- `mintGrant` translates the login layer's error shape structurally — an object marked `invalidGrant: true`, rather than a class — so this package does not have to depend on the package that writes the sign-in (`packages/ai/src/providers/gemini-code-assist.ts:626`).
- `codeAssistUrl` posts to `v1internal:streamGenerateContent?alt=sse` under the row's host (`packages/ai/src/providers/gemini-code-assist.ts:546`; the version namespace at `packages/ai/src/providers/gemini-code-assist.ts:39`). `GEMINI_BASE_URL` moves the host, by the generic `<PROVIDER>_BASE_URL` rule the resolver applies to every provider (`packages/ai/src/model.ts:1681`, the read at `packages/ai/src/model.ts:1705`).
- `codeAssistHeaders` sends the bearer, the JSON content type, and a User-Agent naming the client family — `GeminiCLI/<version>/<model>` (`packages/ai/src/providers/gemini-code-assist.ts:552`). The version is a literal, not a build stamp: the endpoint reads the field as "which client is calling", and a version from this repo would name a client the backend has never heard of (`packages/ai/src/providers/gemini-code-assist.ts:46`).
- `buildCodeAssistRequest` sends the model id, the project when the sign-in onboarded one, and a fresh `user_prompt_id` on every request (`packages/ai/src/providers/gemini-code-assist.ts:158`). The body carries no session id: the upstream request type has the field, but this wire holds no session identity to give it.
- Tools ride one `functionDeclarations` list, each schema under `parametersJsonSchema` — raw JSON Schema, not the backend's own Schema dialect (`packages/ai/src/providers/gemini-code-assist.ts:174`).
- Thinking is steered per family. The 2.5 family takes a budget: the one cap the chat traffic runs at, `DEFAULT_THINKING_BUDGET` 8192, or 0 for off (`packages/ai/src/providers/gemini-code-assist.ts:270`; the cap at `packages/ai/src/providers/gemini-code-assist.ts:53`). The 3.x and Gemma families take a level: `low` and `minimal` land on LOW, everything else on HIGH, and off is answered by not asking for the thoughts at all, because no rung below LOW exists to ask for (`packages/ai/src/providers/gemini-code-assist.ts:275`).
- A replayed assistant turn drops its thinking blocks — the wire replays neither the thought text nor the signature it minted — and puts the stand-in signature on its first function call, the one position the backend validates (`packages/ai/src/providers/gemini-code-assist.ts:224`; the stand-in at `packages/ai/src/providers/gemini-code-assist.ts:62`). A tool result becomes one `functionResponse` part: `error` for a failed call, `output` for text, and an empty object for a call that said nothing — which is not the same as an error (`packages/ai/src/providers/gemini-code-assist.ts:234`). Consecutive same-role turns coalesce into one (`packages/ai/src/providers/gemini-code-assist.ts:243`).
- `parseCodeAssistSse` accumulates `data:` lines to a blank line, then parses one JSON document (`packages/ai/src/providers/gemini-code-assist.ts:294`). Two readings are deliberate: a frame whose JSON does not parse is skipped rather than fatal, so one bad frame does not cost the turn the frames around it, and a trailing event whose terminating blank line never arrived is dropped — an unflushed buffer is not a frame.
- `mapCodeAssistStream` emits `start` on the first wire event, not on the connection itself, the same rule as the other mappers: a connection accepted and then gone silent must look event-less to the retry layer above (`packages/ai/src/providers/gemini-code-assist.ts:380`). A call arrives whole — arguments included — inside a single part, where the OpenAI wires stream it as fragments, so the mapper emits its three events back to back; an absent call id is minted so the result can name the call it answers (`packages/ai/src/providers/gemini-code-assist.ts:416`; the mint at `packages/ai/src/providers/gemini-code-assist.ts:420`).
- The usage read normalizes input to `max(0, prompt − cached) + toolPrompt` (`packages/ai/src/providers/gemini-code-assist.ts:404`): `promptTokenCount` counts the cached prefix, and a frame's own total counts the tool frame separately, so the tool prompt joins both prompt figures. Output adds the thought count, and `reasoning` is the thought count (`packages/ai/src/providers/gemini-code-assist.ts:406`).
- `STOP` is the stop, `MAX_TOKENS` is a length, and the safety family — `SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, and the two image variants — is read as one class: a refusal, because "stop" would file a blocked turn as one that happened to say nothing (`packages/ai/src/providers/gemini-code-assist.ts:337`). `MALFORMED_FUNCTION_CALL` and `UNEXPECTED_TOOL_CALL` are protocol failures with their own wording, and every other unmapped reason is an error, because a reason this adapter cannot name must not seal as a successful stop (`packages/ai/src/providers/gemini-code-assist.ts:475`).
- A stream that ends without a finish reason is an error: a cut-off answer that closed cleanly is the one case the stall watchdog cannot see, so filing it as a stop would be the one way a truncated turn reports success (`packages/ai/src/providers/gemini-code-assist.ts:463`). A call-bearing turn whose reason is a plain STOP becomes `toolUse` — the calls are what make it a tool turn (`packages/ai/src/providers/gemini-code-assist.ts:485`), and a refusal's own message is its explanation (`packages/ai/src/providers/gemini-code-assist.ts:488`).
- `createCodeAssistStreamFn` carries the one-forced-refresh 401 recovery the other subscription wires carry (`packages/ai/src/providers/gemini-code-assist.ts:583`). A refresh that fails leaves the original 401 as the better answer, because it is what the API said (`packages/ai/src/providers/gemini-code-assist.ts:603`).
- The twelve rows name provider `gemini`, api `gemini-code-assist`, no key variable, and a zero price on all four channels — the subscription convention (`packages/ai/src/model.ts:286`; the rows from `packages/ai/src/model.ts:1065`). The Gemini rows carry 1,048,576 for both window and output cap and the two Gemma rows 256,000, because no output cap is stated anywhere upstream and the output column carries the window (`packages/ai/src/model.ts:1062`). The block sits after the `google` rows, so a bare id both hosts serve answers at the public API first (`packages/ai/src/model.ts:1051`). Discovery skips these rows (`packages/ai/src/discovery.ts:115`): no listing call exists for this wire, so a probe would return "no answer" by construction.
- The package root carries the credential: `StreamFnOptions.geminiCredentials` (`packages/ai/src/index.ts:320`), built once per transport (`packages/ai/src/index.ts:381`) and dispatched on the model's api (`packages/ai/src/index.ts:389`).

### The faux provider

- `fauxProvider` is the scripted fake provider for tests, the core of the zero-network test strategy (`packages/ai/src/providers/faux.ts:1`). Each `stream()` call takes the next script step. A step gives shorthand, such as `text` or `toolCalls`, or a raw event list, and it can assert on the `Context` it receives.
- `FAUX_MODEL` is a fake model on the `anthropic-messages` wire with a 200_000 window, 8_192 output tokens, and `reasoning: false` (`packages/ai/src/providers/faux.ts:19`).
- `FauxToolCallSpec.arguments` is a JSON object rather than a string, and the provider stringifies it into the raw arguments (`packages/ai/src/providers/faux.ts:35`).
- `FauxStep.stopReason` is every reason a real adapter can end a turn with, minus `pending`, the one that means "not ended yet" (`packages/ai/src/providers/faux.ts:52`). A double that cannot express a reason cannot test what the loop does with it. `FauxStep.errorKind` is typed as the message's own field, so a scripted failure can drive every kind the fallback walk distinguishes (`packages/ai/src/providers/faux.ts:57`).
- `assertContext` throws a mismatch when the call receives the wrong context (`packages/ai/src/providers/faux.ts:60`). `throwError` throws instead of a clean end, which simulates a network or SDK failure. `delayMs` pauses before the events, which lets a test fire a timer mid-stream. `abortIfSignaled` simulates an abort signal that already fired.
- The provider emits text in three chunks, to exercise the delta path, and splits tool arguments into two fragments, to exercise reassembly (`packages/ai/src/providers/faux.ts:127`).
- A refusal explains itself on the message, beside the stop reason, rather than through a separate `error` event. That is how the real adapters deliver one, and the loop reads it from there (`packages/ai/src/providers/faux.ts:167`).

### The package root

- `AI_PACKAGE_VERSION` is `0.1.0.2` (`packages/ai/src/index.ts:1`).
- `StreamFnOptions.policy` carries the cache settings, and the defaults are the ones this app ships (`packages/ai/src/index.ts:199`).
- `onCacheNotice` travels with the transport rather than with `StreamOptions`. It describes the connection and not the request, and the answer outlives the call that provoked it (`packages/ai/src/index.ts:201`).
- `responsesClientFactory` is an injection point, for the same reason each adapter takes one. A test that wants to prove which adapter a model's `api` reaches needs a network call or an injection point. Without one, the only available proof is that the call fails. That result is indistinguishable from a branch that does not exist (`packages/ai/src/index.ts:209`).
- `credentials` names where a Claude subscription's bearer token comes from (`packages/ai/src/index.ts:224`). It travels with the transport for the same reason `onCacheNotice` does: one account per process, and the refresh policy it carries outlives any one request. The adapter consults it per request, and when its `available()` says no, the API-key path stands.
- `stallTimeoutMs` bounds the failure no SDK timeout covers: a connection that the provider accepted and then left quiet (`packages/ai/src/index.ts:225`).
- `missingApiKey` returns the error a model fails with when no key resolves, or `undefined` when one does (`packages/ai/src/index.ts:243`). Without it the adapters hand the SDK an empty key and let it complain about authentication. That error reads like a failure a retry can get past. The pre-flight is the whole difference, so it is exported. A test that reaches a provider tests the provider. A `subscription` argument stands the whole check aside: a subscription session holds a credential the environment does not, and the adapter's own gate owns the message a user without one sees.
- `dispatchStreamFn` is not exported. The retry policy and the cache record are what callers choose between, and both wrap this rather than be it (`packages/ai/src/index.ts:263`).
- The Responses adapter is built with the same policy and no `onCacheNotice` (`packages/ai/src/index.ts:276`). The notices it can raise are the two the wrapper already derives. It has nothing to say about a Responses request that the Chat Completions one can refuse. A callback with no notice to pass states a false hook.
- `createTrackedStreamFn` creates the notices list and hands it to both sides. The adapter must exist before the wrapper that otherwise belongs to it (`packages/ai/src/index.ts:300`).

### Discovery

- The catalog in `model.ts` is a hand-written snapshot of a date. Vendors retire ids and move context windows without a word to anyone, and the only way to find out is to ask them (`packages/ai/src/discovery.ts:2`). This module asks once, at startup, in the background, and no caller waits for it.
- What cannot be discovered is the price (`packages/ai/src/discovery.ts:2`). None of these APIs returns one. The models endpoints report ids, and an Anthropic endpoint also reports a name, a context window, and an output cap. So a price is still either the table's or the user's own `settings.pricing` declaration. A claim to the contrary is how a cost report goes quietly wrong.
- Every failure mode ends the same way (`packages/ai/src/discovery.ts:35`). No key where the provider takes one, a rejected request, a timeout, and an empty list all mean the module simply does not probe the provider. The table then stands exactly as it did before this module existed.
- `DISCOVERY_TIMEOUT_MS` is 5_000. A catalog read is a nicety, and five seconds of a background nicety is already generous (`packages/ai/src/discovery.ts:20`).
- `DiscoveredListing.complete` is false when the list can omit ids, and an incomplete list then hides nothing (`packages/ai/src/discovery.ts:27`).
- `CatalogProbe` answers `undefined` when the answer cannot be used, which is the same outcome as a rejection. It is injectable so a test can answer without a network (`packages/ai/src/discovery.ts:35`).
- `refreshModelCatalog` returns what changed, or `undefined` when nobody answered, in which case nothing changed and there is nothing to report (`packages/ai/src/discovery.ts:52`). It never throws, because a probe that blows up is one provider that did not answer.
- One deadline covers the whole refresh, combined with the caller's signal. The app aborts at exit, and a probe in flight must not hold the process open after the user quits (`packages/ai/src/discovery.ts:64`).
- An empty list is a provider that did not answer, not one that serves nothing. To hide the whole catalog behind a blank response is the worst way to read it (`packages/ai/src/discovery.ts:83`).
- `providersToProbe` picks one model per provider (`packages/ai/src/discovery.ts:103`). The probe needs a base URL and, where the provider takes one, a credential, and every model of a provider answers the same list. A provider whose rows name no key variable is asked anyway: the local daemon serves the one catalog that exists nowhere but its own answer, and its template stands in for a row.
- A Claude subscription does not turn the Anthropic probe on (`packages/ai/src/discovery.ts:103`). The gate here is `resolveApiKey` — the environment and the settings — and the subscription is a credential the app injects on the streaming path only; this module never sees it. A subscription-only setup therefore probes nothing for Anthropic and keeps the table as written. The cost is a newer id the vendor serves; a price was never discoverable here in any case.
- `probeProvider` is exported, with an injected client, for one reason (`packages/ai/src/discovery.ts:115`). Which wire a model answers its catalog on is a per-model decision made here, and `refreshModelCatalog` already lets a caller replace the whole function. Without a way to reach this one, the only test available is that the refresh returns nothing. That result is indistinguishable from a branch that does not exist. That distinction is not theoretical. `providersToProbe` picks one model per provider. So a provider whose first row sits on a wire this function does not handle is never probed at all. The catalog then stops its refresh for that provider with no report. The Ollama pair is the dispatch that shows why: those rows speak the OpenAI chat wire, but their catalog lives on the native API at the root, and `/v1/models` there states no limit and no thinking flag. The OpenRouter branch is the same shape one layer along: the rows speak the OpenAI chat wire, but the host states a name and both limits on that same endpoint (`packages/ai/src/discovery.ts:127`), and the generic reader would keep the id and drop everything else.
- One lister serves both OpenAI wires, because the catalog is not part of either. `GET /models` is the same request on both and answers the same shape. So a split by wire needs a second copy of an endpoint that does not differ (`packages/ai/src/discovery.ts:144`).
- `listOllamaModels` (`packages/ai/src/providers/ollama.ts:49`) is the native catalog reader, and it is the reason the dispatch above branches on the provider rather than on the wire. `GET /api/tags` names the models, and one `POST /api/show` per model states the detail. A capability list that exists and omits `completion` marks an embedding model, and the reader excludes it: a picker row that can only fail is worse than an absent one. A capability list that exists states thinking too, and `reasoning` is read from it. A show page that stays silent claims nothing, so its row carries no flag rather than a `false`. A window is read only from a `context_length` key holding a positive number, under whatever architecture prefix the model uses. A show page that refuses loses that model's detail, not the model.
- An API this module cannot list is one it cannot check, so the probe answers `undefined` (`packages/ai/src/discovery.ts:147`).
- `NOTICE_LIMIT` is 3, and `nameRefs` adds `and N more` past it (`packages/ai/src/discovery.ts:152`).
- `formatCatalogNotice` gives one line about what the refresh changed, or `undefined` when it changed nothing (`packages/ai/src/discovery.ts:161`). A background refresh that found nothing new must say nothing, because a startup notice that appears every single time is a notice nobody reads. Both halves explain themselves, because each one is a surprise on its own. A model that leaves the picker while it stays usable needs a notice to stay useful. A model that appears with no price needs a notice that says the price has no value yet.
- The two messages read `... not listed by the provider any more — hidden from /model, still usable by name` and `... added from the provider's listing — no price, declare one in settings.json`, joined into `Model catalog refreshed: ...` (`packages/ai/src/discovery.ts:158`).

#### What discovery records in the registry

- The registry keeps three discovery stores beside the hand-written table. `providerCatalogue` holds only listings that came back complete and non-empty, because the empty set is what hides a model. The registry must not record an unreachable provider as one that serves nothing (`packages/ai/src/model.ts:1378`).
- `liveLimits` holds the limits a provider stated, keyed `provider/id`, and a stated limit beats the table. A list can restate one limit and stay silent on the other, so the entries are partial. Kimi publishes a window and no output cap, and a window on its own has value. It is what the compaction threshold is measured against, and a stale one is worse than an absent one (`packages/ai/src/model.ts:1382`).
- `synthesizeModel` builds a row from a list only when the provider stated both limits. A window we must guess is a threshold we guess at, and a wrong threshold is worse than an absent row. In practice Anthropic's unknowns are added and the OpenAI-compatible ones are not. The rule is about the data, not about which vendors are trusted. A provider with no table row at all, the local daemon, gets its row built on the template instead: the template supplies the wire and the base URL, and the listing supplies the limits and the thinking flag. The row carries no price. The honest answer is "not priced", which the cost report can print, rather than $0, which reads as free (`packages/ai/src/model.ts:1389`).
- `dynamicProviders` (`packages/ai/src/model.ts:1333`) holds the templates for providers whose catalog exists only in their own answer. The local Ollama daemon is the one such provider: only the daemon knows which models the user pulled, so no row can be written down ahead of time. The entry is a template, not a model. It is never listed in `/model` and never resolves. `dynamicProviderTemplates` hands it to the two callers that need one: the discovery probe, which needs a wire and a base URL to speak with, and `synthesizeModel`, which needs something to build a row on.
- `setProviderCatalogue` replaces a provider's entry rather than grows it, because the list describes what the provider serves now. A list cut short by the page cap still carries usable limits, because each row describes itself. It can miss some ids, so it must not hide anything. The function returns the ids the visible catalog gained and lost (`packages/ai/src/model.ts:1411`).
- `withLiveLimits` applies a stored entry on top of a row, and the entry names only the limits the list stated. That is what lets the table's other number stand. The store is the only writer. `clearDiscovery` undoes all three stores, for tests that need to start from the table alone (`packages/ai/src/model.ts:1462`).

### Pricing and transcript repair

- `computeCost` multiplies each of the four token channels by its per-Mtok price and sums the four (`packages/ai/src/pricing.ts:12`). `MTOK` is 1_000_000. A model with no declared price yields a zero breakdown.
- `formatCost` shows two decimals at a dollar or above, four decimals below that, and `$0` for zero (`packages/ai/src/pricing.ts:30`).
- `repairToolPairing` repairs a stored transcript before any request carries it (`packages/ai/src/transcript.ts:53`). A conversation read back from disk, converted from another tool's history, or reassembled after a damaged line can be no longer well-formed. That list of messages needs a repair. The provider is the judge of that, and its verdict is a 400 with no message index and no explanation. So the repair happens here, where the structure is still in hand.
- An unpaired tool call is answered, not deleted (`packages/ai/src/transcript.ts:33`). The messages API rejects a transcript with a call and no result on the next request, so the call stays — with the assistant turn's own words around it — and a synthetic `isError` result is placed immediately after it. The wording is `INTERRUPTED_TOOL_RESULT_TEXT`, shared with the live loop so a resumed transcript and a live one read alike. The result reuses the owning turn's timestamp, and its `synthetic: true` marker is memory-only: the session file records an ordinary error result. A result that lost its call upstream is still dropped, because there is no call for it to answer.
- A call with an empty id names nothing, so it is filtered as before, and a turn left with no content goes too (`packages/ai/src/transcript.ts:85`).
- The function returns the repaired list and three counts: `dropped` (blocks removed and turns emptied — the count the migration reports have always used), `synthesized` (interrupted calls answered, one per call id), and `droppedMessages` (input messages absent from the output) (`packages/ai/src/transcript.ts:119`). A second pass over the output adds nothing, removes nothing, and is byte-identical: the repair is idempotent.

## Why it is like this

- One stream protocol serves every wire, so the agent loop never learns which provider it talks to (`packages/ai/src/types.ts:2`).
- The retry wrapper is the only place an adapter throw becomes an `error` event. A stream that already emitted partial output cannot take a safe replay (`packages/ai/src/retry.ts:2`).
- The watchdog sits below retry, so an early stall earns a retry and a late stall ends the turn (`packages/ai/src/stall-timeout.ts:25`).
- The tracker wraps the whole transport, so its records match the requests the caller made rather than the tries underneath (`packages/ai/src/index.ts:308`).
- A subscription is a credential and not a wire. The flow mints the same bearer token that an API key already is, so one adapter serves both (`packages/ai/src/providers/anthropic-oauth.ts:324`).
- Cache behavior comes from the provider's own usage numbers. A hit rate that nobody records cannot improve (`packages/ai/src/cache.ts:246`).
- The model table is hand-written and dated, because a generated catalog cannot say where a number came from (`packages/ai/src/model.ts:684`).
- The code marks a claim about an unverified wire as open. A claim about the wire is only as good as the evidence for it (`packages/ai/src/providers/openai-responses.ts:2`).

## Known traps

- `MessageBuilder.toolCallEnd` carries a JSDoc that says the code parses the buffered JSON there. The body only copies the block, and the parse lives in the consumers, such as `packages/ai/src/providers/anthropic.ts:378`. A reader who trusts the comment looks in the wrong function.
- The cached token count has four spellings, and the largest wins. A gateway that emits a stale zero beside a correct count cannot mask the hit (`packages/ai/src/cache.ts:267`).
- OpenAI's `prompt_tokens` counts the cached prefix, so `input` is `max(0, promptTotal - cacheRead)`, or those tokens bill twice (`packages/ai/src/providers/openai-compat.ts:266`).
- A stall error is not an `AbortError`, because every layer above reads an abort as the user's interrupt (`packages/ai/src/stall-timeout.ts:10`).
- A TTL downgrade runs below `withRetry`, because a 400 is not retryable, and the fix must land before the first event (`packages/ai/src/providers/anthropic.ts:695`).
- The SDK's own 401 recovery is dead under `maxRetries: 0`, so the adapter runs the one forced refresh itself (`packages/ai/src/providers/anthropic.ts:682`). A reader who counts on the SDK's credentials retry waits for something this configuration disables.
- The `apiKey: null` and `authToken: null` in the credentials branch are explicit bookkeeping (`packages/ai/src/providers/anthropic.ts:833`): SDK 1.x reads no environment token when `credentials` is the one non-null credential option, and two non-null options throw. The old trap — `ANTHROPIC_AUTH_TOKEN` silently outranking the provider — no longer exists; the nulls keep the trio readable rather than load-bearing.
- `invalidGrant` on `ClaudeOAuthError` means a retry cannot repair the session, not that a grant was refused (`packages/ai/src/providers/anthropic-oauth.ts:49`). The empty-store mint and the adapter's gate carry the mark too, and the retry ladder reads it to fail fast.
- On Kimi, a key from the China platform needs `KIMI_BASE_URL=https://api.moonshot.cn/v1`, and the two platforms do not share keys (`packages/ai/src/model.ts:811`).
- `gpt-6.1-sol` halves only its cache read against Sol, so "half of the 6-generation row" is wrong in the other three channels (`packages/ai/src/model.ts:874`).
- A bare model id resolves to its maker and not to a gateway. A caller reaches the Zen copy of `gpt-5-codex` as `opencode-zen/gpt-5-codex` and not by the bare name (`packages/ai/src/model.ts:1566`).
- The MiniMax `maxOutputTokens` column holds the window, and both consumers clamp it, so no value above 32k behaves differently (`packages/ai/src/model.ts:945`).
- Google meters cache storage by the hour, so a Gemini row states a floor rather than a cap (`packages/ai/src/model.ts:929`).
