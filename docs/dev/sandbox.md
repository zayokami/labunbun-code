# Sandbox and network policy

The sandbox has three axes: the mode, the filesystem sandbox, and the network sandbox. Two pure modules in `packages/agent/src` define the policy as a value (`sandbox-policy.ts` and `network-policy.ts`). The modules under `packages/tools/src/sandbox/` translate that value for the platform and carry out the parts a program can do on its own (`packages/tools/src/sandbox/index.ts:1`).

## Purpose

- Describe what a command may touch as data, so every back end reads one value (`packages/agent/src/sandbox-policy.ts:118`).
- Keep the filesystem axis and the network axis in separate fields of that value (`packages/agent/src/sandbox-policy.ts:65`).
- Translate the policy for macOS seatbelt, Linux bwrap, and a Windows AppContainer profile (`packages/tools/src/sandbox/index.ts:386-390`, `packages/tools/src/sandbox/index.ts:341-354`).
- Decide each network request in one pure function that tests on any machine (`packages/agent/src/network-policy.ts:289`).
- Report what confines a command in fact, not what the policy asked for (`packages/tools/src/sandbox/index.ts:453`).

## Behavior

### The policy value

`packages/agent/src/sandbox-policy.ts` builds one `SandboxPolicy` from a mode and a few call options. It stays pure: it reads no filesystem and starts no process (`packages/agent/src/sandbox-policy.ts:1`).

The policy is a value, not a check. Three translators read it. macOS seatbelt and Linux bwrap are real, and bwrap needs an install as well. The third is a Windows layer that the tools simulate in their own process (`packages/agent/src/sandbox-policy.ts:1`). A subprocess started outside the tools is not subject to the third one.

On all three platforms the network axis works through a proxy. That is a convention, not kernel enforcement (`packages/agent/src/sandbox-policy.ts:1`). Where no back end exists, on Windows or on Linux without bubblewrap, the proxy and the environment variables are the whole of the network story. `describeNetworkPolicy` says which case a session is in (`packages/agent/src/sandbox-policy.ts:1`). `networkConfinement` lives in `@labunbun/tools` because the agent package cannot see whether the machine has bubblewrap (`packages/agent/src/sandbox-policy.ts:1`). A mechanism that reads as enforced by the OS when it is not is worse than no mechanism (`packages/agent/src/sandbox-policy.ts:1`).

`canonicalPolicyPath` is the one spelling every comparison uses. It replaces `\` with `/`, and every downstream comparison starts with `startsWith` on that form (`packages/agent/src/sandbox-policy.ts:8`). A backslash entry widens a check, and a test caught that, so the builder canonicalises the entry first (`packages/agent/src/sandbox-policy.ts:8`). The function deliberately does not resolve paths. A resolve needs filesystem access, and a relative path resolved against the real filesystem moves a fixture's `/w/repo` onto a real drive (`packages/agent/src/sandbox-policy.ts:8`).

`FileSystemAccessMode` has `write`, `read`, and `deny` (`packages/agent/src/sandbox-policy.ts:17`). A `write` entry implies `read` (`packages/agent/src/sandbox-policy.ts:17`). `deny` is unambiguous on seatbelt, which has a deny rule, and in the simulated layer, which refuses the read in `decideRead` (`packages/agent/src/sandbox-policy.ts:17`). On bwrap the mode is purely constructive, so the strongest form bwrap can express is a read-only bind. `bwrap.ts` documents the gap (`packages/agent/src/sandbox-policy.ts:17`). `buildSandboxPolicy` emits only `write` and `read` entries (`packages/agent/src/sandbox-policy.ts:17`).

`WritableRootKind` separates a project root from a data root (`packages/agent/src/sandbox-policy.ts:21`). A project root derives a `<root>/.git` protected path whether or not that directory exists. A data root does not, because caches and scratch directories have no version-control metadata in them (`packages/agent/src/sandbox-policy.ts:21`). The caller carries the distinction. The kind is never read off the path (`packages/agent/src/sandbox-policy.ts:21`). The builder treats an unknown kind as `project`, the conservative side (`packages/agent/src/sandbox-policy.ts:21`).

A bare string writable root means `project` on purpose (`packages/agent/src/sandbox-policy.ts:25`). Any other shape is an error the builder drops (`packages/agent/src/sandbox-policy.ts:25`). The failure this avoids is a silent increase in access that looks like a refactor (`packages/agent/src/sandbox-policy.ts:25`). `normalizeWritableRoot` does that conversion (`packages/agent/src/sandbox-policy.ts:35`).

`NETWORK_SANDBOX_POLICIES` is the list of network values, and the settings schema derives its enum from that list (`packages/agent/src/sandbox-policy.ts:39`). A hand-written `z.enum` is a copy that drifts (`packages/agent/src/sandbox-policy.ts:39`).

`FileSystemSandboxEntry` carries a `path` and a `missingPathBehavior` (`packages/agent/src/sandbox-policy.ts:51`). The path is absolute and forward-slash, and the builder enforces both halves (`packages/agent/src/sandbox-policy.ts:51`). A measurement covered them: before the enforcement, `isWritePermitted` answered true for `<ws>/.git/config` in either spelling (`packages/agent/src/sandbox-policy.ts:51`). `missingPathBehavior: "skip"` marks an entry whose absence is not a broken session, such as self-referential entries (`packages/agent/src/sandbox-policy.ts:55`). The caller drops those entries, not the back end, because the translators are pure (`packages/agent/src/sandbox-policy.ts:55`). The mark is essential on Linux, where bwrap refuses to start when a `--bind` source is absent (`packages/agent/src/sandbox-policy.ts:55`).

`SandboxPolicy` holds the filesystem entries, the network rules, and the protected paths (`packages/agent/src/sandbox-policy.ts:65`). The network rules sit on the policy so the network axis arrives as one value. A caller cannot assemble it from two arguments that disagree (`packages/agent/src/sandbox-policy.ts:68`). An empty rule list means the mode alone decides (`packages/agent/src/sandbox-policy.ts:68`).

`protected` is its own field rather than deny entries appended to the entry list (`packages/agent/src/sandbox-policy.ts:71`). An append approach needs "deny after every allow" on each back end, which repeats one promise once per back end. A back end that forgets is the bug shape, and the tests assert the order per back end (`packages/agent/src/sandbox-policy.ts:71`). Today the protected paths are the `.git` directories. The containment check stops the Edit and Write tools, and a shell is not subject to it. Agent mode allowed an `rm .git/config` through Bash before this layer existed (`packages/agent/src/sandbox-policy.ts:71`).

`BuildSandboxPolicyOptions` gives the builder its inputs (`packages/agent/src/sandbox-policy.ts:76`). The caller discovers `protectedPaths`, because the module stays pure (`packages/agent/src/sandbox-policy.ts:81`). `writableRoots` is the list of roots the mode allows (`packages/agent/src/sandbox-policy.ts:87`). `readOnlyRoots` becomes read entries that are not writable (`packages/agent/src/sandbox-policy.ts:95`).

The network policy is not derived from the sandbox mode (`packages/agent/src/sandbox-policy.ts:97`). A collapse cuts the network for the `workspace-write` default and breaks `npm install` and `git fetch`. It defaults to enabled (`packages/agent/src/sandbox-policy.ts:97`).

The builder copies `networkRules` rather than references, so a later change by the caller cannot change the policy a back end already holds (`packages/agent/src/sandbox-policy.ts:100`).

### What the builder produces

`buildSandboxPolicy` returns an empty policy for `danger-full-access`, not one that allows everything (`packages/agent/src/sandbox-policy.ts:118`). A back end can recognize an empty policy and refuse to wrap. A test can tell an unconfined run from a very wide sandbox (`packages/agent/src/sandbox-policy.ts:118`).

The workspace is the one path entry the builder always adds, with kind `write` (`packages/agent/src/sandbox-policy.ts:132`). Its `missingPathBehavior` is deliberately not set: a workspace that does not exist is a broken session, not a policy to skip past (`packages/agent/src/sandbox-policy.ts:132`). The builder canonicalises every entry once (`packages/agent/src/sandbox-policy.ts:138`).

The writable roots each become a `write` entry with the skip mark (`packages/agent/src/sandbox-policy.ts:142`). A read-only root is not emitted where the platform reads everything by default. The builder records it anyway, because the Windows simulated layer has no default for readable paths (`packages/agent/src/sandbox-policy.ts:145`).

`protectedFor` receives the workspace and the project roots, not the data roots (`packages/agent/src/sandbox-policy.ts:157`). Only a project root derives a `.git`. A data root holds caches and scratch files (`packages/agent/src/sandbox-policy.ts:159`). The Linux translator creates an empty read-only directory for a protected path that is absent. A directory that appears for nobody is the wrong result of a `.git` derived for a cache root (`packages/agent/src/sandbox-policy.ts:159`).

### Protected paths from a scan

`protectedFor` derives `<root>/.git` for every writable root of kind `project` (`packages/agent/src/sandbox-policy.ts:170`). The derivation is the point: the scan has limits it cannot see past, and a `.git` the scan misses stays writable (`packages/agent/src/sandbox-policy.ts:170`). The scan limits are a depth of four and a skip of `node_modules` (`packages/agent/src/sandbox-policy.ts:170`). Those limits are wrong for the one directory everybody knows. A repository created after the first Bash call, or a `.git` five levels down, was writable. The write went through, and the tool reported success (`packages/agent/src/sandbox-policy.ts:170`).

The code used to cache the scan for the life of the process, and the cache was a hole of its own. A measurement showed it: a moved `.git` stayed listed at the old path (`packages/agent/src/sandbox-policy.ts:170`). The cache is gone. The only limit left is the reach of the scan (`packages/agent/src/sandbox-policy.ts:170`).

The builder derives only `.git`. The builder deduplicates the list. An absent path is still derived, which is why bwrap needs the empty-directory recipe. The protection is stronger when the directory appears later (`packages/agent/src/sandbox-policy.ts:170`).

`gitRoots` is the set of roots that asked for a `.git` derivation. The caller filters on kind. `WorkspacePolicyOptions` passes the temp and cache roots with kind `data` (`packages/agent/src/sandbox-policy.ts:170`).

The builder joins `root` and `.git` and then canonicalises. The join is what puts `\` on Windows, and canonicalisation turns it into the one spelling (`packages/agent/src/sandbox-policy.ts:172`).

### The write question without a filesystem

`isWritePermitted` answers lexically, with no filesystem access (`packages/agent/src/sandbox-policy.ts:185`). The kernel back ends do not use it, because the kernel is the check (`packages/agent/src/sandbox-policy.ts:185`). The Windows simulated layer does not use it either. `decideWrite` has its own containment test, takes the case rule as a parameter, and canonicalises the root itself (`packages/agent/src/sandbox-policy.ts:185`).

The export has no production caller. Tests use it. An earlier comment claimed the simulated layer used it, and that was false (`packages/agent/src/sandbox-policy.ts:185`).

The question is directional: an answer may only narrow access, never widen it (`packages/agent/src/sandbox-policy.ts:185`). Both sides are already canonical. On macOS, `/var/folders` and `/private/var/folders` name the same directory, and a "no" for that pair is the wrong direction (`packages/agent/src/sandbox-policy.ts:185`). That is why `decideWrite` is the production answer (`packages/agent/src/sandbox-policy.ts:185`).

The code checks the protected list first (`packages/agent/src/sandbox-policy.ts:187`). A helper that must never widen access must not discard the narrower rule (`packages/agent/src/sandbox-policy.ts:188`). Then an unrestricted policy answers true. Then the code tests the entries with `canWrite` and the containment check (`packages/agent/src/sandbox-policy.ts:187`).

`isWithin` needs both sides in canonical absolute forward-slash form (`packages/agent/src/sandbox-policy.ts:198`). `buildSandboxPolicy` enforces the separator half, because it runs everything through `canonicalPolicyPath` (`packages/agent/src/sandbox-policy.ts:198`). The absolute half is still a convention. The choice to fold case belongs to the caller (`packages/agent/src/sandbox-policy.ts:198`). On Windows and macOS this comparison is too strict: `.GIT/config` slips past a `.git` root (`packages/agent/src/sandbox-policy.ts:198`). `decideWrite` takes the platform's answer instead (`packages/agent/src/sandbox-policy.ts:198`).

### The resolver: five outcomes

`packages/tools/src/sandbox/index.ts` turns one policy into one run: a program, its arguments, and the status of what confines it (`packages/tools/src/sandbox/index.ts:318`).

A resolution has five outcomes, not two (`packages/tools/src/sandbox/index.ts:1`). They are `native`, `appcontainer`, `simulated`, `unavailable`, and `unconfined` (`packages/tools/src/sandbox/index.ts:38`). `appcontainer` is the Windows back end, and it is not an argv wrapper: the confinement is the child process's own token. The AppContainer package SID comes from the workspace, and an ACL grant covers the writable roots. The child starts through FFI in `appcontainer.ts`. The code reaches this outcome only with the network axis enabled (`packages/tools/src/sandbox/index.ts:335`, `packages/tools/src/sandbox/index.ts:341`).

The last three outcomes all mean "not confined by this layer", and the distinction exists for the report, not for the argv (`packages/tools/src/sandbox/index.ts:1`). An unavailable back end still runs the command. A refusal of every command on a machine that never installed bubblewrap is a worse failure than an unconfined one (`packages/tools/src/sandbox/index.ts:1`). A collapse of the outcomes makes a simulated run read as a real one (`packages/tools/src/sandbox/index.ts:1`).

The `reason` field on a resolution has no production reader. Both production readers, `operations.ts` and `background.ts`, test `kind` alone (`packages/tools/src/sandbox/index.ts:3`). The sentence a user reads about a back end comes from `describeSandboxBackend` on the same two inputs, and `/permissions` is its one caller. The disclosure follows from those inputs, so it is not absent (`packages/tools/src/sandbox/index.ts:3`).

`SandboxExecution` is what a caller spawns: the program, its arguments, and the policy (`packages/tools/src/sandbox/index.ts:22`). The argv replaces nothing: the builder appends the shell and its arguments after `--` (`packages/tools/src/sandbox/index.ts:22`). The wrapper wraps the shell, and a `bash -c` re-execs, so background jobs escape the wrapper (`packages/tools/src/sandbox/index.ts:22`). Both translators emit the command last, after `--` (`packages/tools/src/sandbox/index.ts:22`).

`SandboxResolution` has an `appcontainer` variant (`packages/tools/src/sandbox/index.ts:40`). It carries the workspace the profile derives from, and `grantRoots`: every root the ACL grant must cover. The workspace leads the list, and each path appears once (`packages/tools/src/sandbox/index.ts:48`). A real session names the home caches and the temp directory there. An un-granted container child cannot write any of them (`packages/tools/src/sandbox/index.ts:48`).

The code carries the list and does not derive it twice, because two spawn paths must give one answer (`packages/tools/src/sandbox/index.ts:48`). Its network flag is `true` always, because this branch runs only with the network axis enabled (`packages/tools/src/sandbox/index.ts:71`).

`ResolveSandboxOptions` injects the two probes (`packages/tools/src/sandbox/index.ts:77`). The caller injects `hasNativeBackend` so tests reach every branch on any machine (`packages/tools/src/sandbox/index.ts:118`). The caller injects `hasAppContainer` because a pair of DLL loads breaks purity, and its default of false follows the safe direction. A wrong `true` sends a command down a container path whose profile and grant were never established. A wrong `false` is the simulated status quo (`packages/tools/src/sandbox/index.ts:121`).

The caller injects `exists` and the code consults it for two decisions: the `missingPathBehavior` filter and the bwrap protected path (`packages/tools/src/sandbox/index.ts:128`).

`policyFor` accepts writable roots and used to drop them on the floor: every caller got a policy without them (`packages/tools/src/sandbox/index.ts:155`). That failure was narrower than requested, not a leak, but the root user was told the root was writable when it was not (`packages/tools/src/sandbox/index.ts:158`). The type still allowed the argument, so no error pointed at the loss (`packages/tools/src/sandbox/index.ts:159`).

`hasNativeSandboxBackend` answers false on Windows, and that does not change in this build (`packages/tools/src/sandbox/index.ts:175`). The two ways to change it are a helper program with a Windows service, or an MXC container runner. The user ruled both out (`packages/tools/src/sandbox/index.ts:168-174`). `nativeSandboxProgram` names the program for a platform: `sandbox-exec` on macOS, `bwrap` on Linux (`packages/tools/src/sandbox/index.ts:180`). `detectNativeBackend` treats `sandbox-exec` as present, because its fixed absolute path is part of the OS, and scans `PATH` for `bwrap`. "Not installed here" is a real state (`packages/tools/src/sandbox/index.ts:186`, `packages/tools/src/sandbox/index.ts:185`).

`SandboxRuntime.hasAppContainer` means what the selection probe answered for this session, not whether the API loads (`packages/tools/src/sandbox/index.ts:212`). The back end works: the profile spawns, the ACL grant holds, and the kernel refuses a write beyond the grant. Whether it is selected is a question about this machine's shell and toolchain, and `appcontainer-probe.ts` answers it (`packages/tools/src/sandbox/appcontainer-probe.ts:1`).

The probe asks by acting: it writes the grant production would write — the workspace and the toolchain roots — and runs the session's shell once inside a live container (`packages/tools/src/sandbox/appcontainer-probe.ts:207`). A decline is a measured answer, not caution. An msys shell dies at process start — `BaseNamedObjects`, which the container denies and no grant restores (`packages/tools/src/sandbox/appcontainer-probe.ts:133`) — and a toolchain root the user cannot rewrite the ACL of has no path into the container, measured on an elevated `D:\Program Files` (`packages/tools/src/sandbox/appcontainer-probe.ts:212`).

The README warning is per machine rather than per platform: a machine whose shell and toolchain the container can run selects the back end, and every other Windows machine keeps the simulated layer, with the machine's own why — the probe's reason when it declined, the network axis when that is the gate (`packages/tools/src/sandbox/index.ts:366`). `sandbox-wiring.test.ts` drives the container branch with an injected flag, which is what keeps the branch reachable on machines the probe declines.

`detectRuntime` does one `PATH` scan on every platform, and on Windows it also runs the selection probe — one real spawn of the session's shell, classified — and carries the answer (`packages/tools/src/sandbox/index.ts:247`). A per-process cache keyed on the probe's own inputs keeps that once per machine state, because the default constructors this feeds run per tool set (`packages/tools/src/sandbox/index.ts:274-283`). `appContainerAvailable` stays exported, from `appcontainer.ts` now, as the honest, narrower answer tests ask about (`packages/tools/src/sandbox/appcontainer.ts:1556`).

### The order inside the resolver

`resolveSandboxExecution` takes `hasNativeBackend` as an option so every branch is reachable on any machine (`packages/tools/src/sandbox/index.ts:119`). A real caller passes the probe result, and `sandbox-wiring.test.ts` asserts that both call sites pass it. An earlier comment named `operations.test.ts`, a file that never existed (`packages/tools/src/sandbox/index.ts:317`).

`danger-full-access` short-circuits first (`packages/tools/src/sandbox/index.ts:326`). The mode is not a sandbox with a very wide allow list. It is the absence of one (`packages/tools/src/sandbox/index.ts:322`). The network half does not change it, and the reason string is not the old one.

The old text scoped the problem to the container branch (`packages/tools/src/sandbox/index.ts:341`). In fact every restricted command on a native back end is meant to reach the proxy, and the platform now splits the answer by mechanism (`packages/tools/src/sandbox/index.ts:459`). On macOS the seatbelt profile denies every route off the machine and then permits the proxy's own loopback ports, one rule per port, so the proxy stays reachable and allowed domains stay reachable through it (`packages/tools/src/sandbox/seatbelt.ts:228`). On Linux the namespace denies every route off the machine, the proxy included — except the loopback bridge: a process inside the namespace listens on the proxy's own ports and forwards over a Unix socket to the host, so the proxy stays reachable there too, by the bridge (`packages/tools/src/sandbox/bridge.ts:1`).

One change was deliberately not made on Linux, while a narrower one was made on macOS — and the property pair it was skipped for is had through the bridge instead. The Linux change considered then was the removal of the OS denial so the proxy becomes the boundary; it would have turned restricted from "the kernel denies" into "the proxy program can ignore" (`packages/tools/src/sandbox/index.ts:459`). The macOS change keeps the denial and adds the proxy's ports to it, so the kernel still denies and the proxy is still the only route that answers (`packages/tools/src/sandbox/seatbelt.ts:228`). The bridge needs no such trade: the namespace still denies every route, and the loopback bridge — a process inside, listening on the proxy's own ports and forwarding over a Unix socket — is the one route left (`packages/tools/src/sandbox/bridge.ts:1`).

The `exists` predicate answers three questions on the same machine (`packages/tools/src/sandbox/index.ts:328`). The resolver drops an absent entry marked `skip` before the translators see it. The AppContainer grant list drops it for the same reason: a grant on an absent path fails (`packages/tools/src/sandbox/index.ts:333`). The resolver keeps an absent protected path, and it becomes an empty read-only mount. A drop of it quietly removes protection (`packages/tools/src/sandbox/index.ts:329`).

The AppContainer branch sits after the short-circuit and before the `hasNativeBackend` check, which answers false on win32 (`packages/tools/src/sandbox/index.ts:341`). Its conditions are win32, `policy.network === "enabled"`, and `hasAppContainer` (`packages/tools/src/sandbox/index.ts:341`). The tests measured the reason for the network condition. A proxy that listens on loopback enforces a restricted network, and a container child cannot reach loopback even with `privateNetworkClientServer`. A confinement of a restricted command breaks its network. An enabled network starts no proxy and needs no loopback (`packages/tools/src/sandbox/index.ts:360`).

Inside the branch, the workspace is the first `write` entry without the skip marker (`packages/tools/src/sandbox/index.ts:343`). The grants cover every writable root, not only the workspace, which is the real session shape. `policyFor` fixed that half-grant failure once (`packages/tools/src/sandbox/index.ts:345`). The workspace leads the list because the profile and its refcount derive from it (`packages/tools/src/sandbox/index.ts:345`). Read-only roots are absent from the grant list. The reason used to be that the child reads outside the grant by default; the 2026-10-15 record below measured the opposite — a confined child reads nothing outside its grants — so the grant list is the complete picture of what a confined child can read, and a root it must read joins that list (`packages/tools/src/sandbox/index.ts:350`). The builder reads the grant list from the filtered present entries, because a skip-marked absent root fails the grant (`packages/tools/src/sandbox/index.ts:333`).

The simulated fallback is the default case (`packages/tools/src/sandbox/index.ts:376`). `installed` is `options.hasNativeBackend ?? true` (`packages/tools/src/sandbox/index.ts:386`). It defaults to installed. A guess of "not installed" produces `unavailable` and no wrapper, which is fail-open. A guess of "installed" gives a spawn error, which is the fail-closed side, the correct one.

No production caller reaches the default: `packages/tools/src/operations.ts:541` passes the runtime value (`packages/tools/src/sandbox/index.ts:386`). The `unavailable` return is its own outcome, and the command still runs (`packages/tools/src/sandbox/index.ts:389`).

The program and its arguments are named in this one place and nowhere else (`packages/tools/src/sandbox/index.ts:394`). The program is absolute for `sandbox-exec`, because `PATH` resolution is how a wrapper gets substituted (`packages/tools/src/sandbox/index.ts:395`). Only bwrap gets the `exists` predicate (`packages/tools/src/sandbox/index.ts:390`). An absent protected path is harmless under seatbelt: a subpath filter that matches no file grants nothing (`packages/tools/src/sandbox/index.ts:400`).

`presentEntries` exists because both translators are pure and both say so (`packages/tools/src/sandbox/index.ts:408`). A comment that names a contract the caller has not carried out is worse than no comment (`packages/tools/src/sandbox/bwrap.ts:2`, `packages/tools/src/sandbox/seatbelt.ts:2`). On Linux the filter is not cosmetic: bwrap fails on an absent `--bind` source (`packages/tools/src/sandbox/index.ts:390`). The builder leaves entries not marked `skip` alone, because a nonexistent workspace is a broken session (`packages/tools/src/sandbox/index.ts:413`).

`SandboxBackend` has four values, not three: `simulated` and `appcontainer` cannot share a name (`packages/tools/src/sandbox/index.ts:420`, `packages/tools/src/sandbox/index.ts:420`). A string cannot narrow after the fact (`packages/tools/src/sandbox/index.ts:420`). `sandboxBackendFor` is a function of the platform, so "Linux without bubblewrap" is reachable from any test (`packages/tools/src/sandbox/index.ts:424`). Its default of false follows the safe direction (`packages/tools/src/sandbox/index.ts:427`).

### Network confinement, reported

`networkConfinement` in `packages/tools/src/sandbox/index.ts` derives a six-way answer from the same facts it always took, plus the platform (`packages/tools/src/sandbox/index.ts:451`). Its order is the whole function (`packages/tools/src/sandbox/index.ts:457`):

1. `network === "enabled"` gives `network-left-open`.
2. `danger-full-access` gives `filesystem-axis-off`.
3. A native back end gives `proxy-ports` on macOS and `proxy-bridge` everywhere else (`packages/tools/src/sandbox/index.ts:459`), `unavailable` gives `backend-missing` (`packages/tools/src/sandbox/index.ts:460`), and anything else gives `no-os-backend` (`packages/tools/src/sandbox/index.ts:464`).

An unreported back end reads as the weakest answer (`packages/tools/src/sandbox/index.ts:464`). The appcontainer backend joins `no-os-backend` on the restricted axis, for a measured reason. The resolver's container branch is reachable only with the enabled axis. A restricted command therefore resolves simulated and runs on the proxy (`packages/tools/src/sandbox/index.ts:461`).

`describeSandboxBackend` writes the user sentence per case, not one hedged sentence for all of them (`packages/tools/src/sandbox/index.ts:474`). The code treats an undefined back end as simulated, since there is nothing to point at (`packages/tools/src/sandbox/index.ts:486`). The code asks `danger-full-access` first, because it is true in all three back-end cases (`packages/tools/src/sandbox/index.ts:483`).

The native case makes a write-only claim (`packages/tools/src/sandbox/index.ts:487`). Both back ends start from an already-readable baseline: bwrap with `--ro-bind / /`, seatbelt with `(allow file-read*)` (`packages/tools/src/sandbox/index.ts:489`). The string describes the mode, not the policy. `Reads are unrestricted` is one mechanism's answer under the other's name (`packages/tools/src/sandbox/index.ts:492`).

The claim that the back end refuses every write to version-control metadata holds for every policy `buildSandboxPolicy` produces. `protectedFor` adds `join(root, ".git")` for every writable root unconditionally, and the scan only ever adds more (`packages/tools/src/sandbox/index.ts:490`). The `danger-full-access` early return is the one branch with an empty protected list, and it never reaches this case (`packages/tools/src/sandbox/index.ts:483`). The process-tree sentence is a different claim from the open `mv` question in the bwrap header (`packages/tools/src/sandbox/index.ts:492`).

### A failure that reads as a refusal

The Bash tool prints one hedge line after the exit line of a failed command when the failure reads like a kernel refusal (`packages/tools/src/bash.ts:205`). The read is `likelySandboxDenied` (`packages/tools/src/sandbox-denial.ts:67`). The gate is asked first: only a `native` or `appcontainer` run is a candidate (`packages/tools/src/sandbox-denial.ts:72`), and a clean exit or a command that never ended is never a denial (`packages/tools/src/sandbox-denial.ts:73`). A run that no kernel backend confined cannot have failed *because of* the sandbox, and the tool-layer refusals have already said their own name in words — a hedge there would blame a backend that was not present.

Past the gate the read is a keyword set — the errno spellings, the syscall-layer names, and the Windows spelling of a denied write — matched against both streams, case-insensitively (`packages/tools/src/sandbox-denial.ts:25`, `packages/tools/src/sandbox-denial.ts:83`). It is joined by the platform's own exit spelling of `SIGSYS`: 128+31 on Linux and 128+12 on macOS, because the signal number is the platform's and the other platform's spelling is a different signal (`packages/tools/src/sandbox-denial.ts:79`). The quick-reject codes are never consulted as codes; `127 command not found` is a fact about the shell, and only a refusal word in the output makes a quick-reject exit count.

The hedge is a label and not a verdict (`packages/tools/src/bash.ts:204`). It names the axes from the policy the tool built — the same policy the run executes under — and points at `/permissions` and at `/mode`, which is the door that can turn the sandbox off (`packages/tools/src/bash.ts:206`). The narrow reading is deliberate: the `!` passthrough runs under the same axes as the tool, resolved per run (`packages/coding-agent/src/interactive.ts:1116`), so it is not a way around a refusal. `isError` is whatever the exit code said, and a killed run keeps its own story and gets no hedge (`packages/tools/src/bash.ts:205`). The fact behind it travels on the result: `ExecResult.sandboxBackend` is the resolution's own kind, read once in `exec` and absent when nothing confined the run (`packages/tools/src/operations.ts:96`, `packages/tools/src/operations.ts:567`).

### Finding protected paths

`packages/tools/src/sandbox/protected-paths.ts` holds the walk (`packages/tools/src/sandbox/protected-paths.ts:1`). Two shapes are real: a directory (a checkout) and a file (a worktree or submodule gitdir pointer) (`packages/tools/src/sandbox/protected-paths.ts:1`). ### macOS: seatbelt

`seatbelt.ts` builds a sandbox profile and the `-D` parameters for `/usr/bin/sandbox-exec` (`packages/tools/src/sandbox/seatbelt.ts:1`). It is pure (`packages/tools/src/sandbox/seatbelt.ts:1`).

The shape is `[-p profile -DKEY=value ... -- command]` (`packages/tools/src/sandbox/seatbelt.ts:3`). The caller prepends `/usr/bin/sandbox-exec`, which must be the system binary (`packages/tools/src/sandbox/seatbelt.ts:3`). `PATH` resolution is how an attacker substitutes a wrapper, and the check belongs next to the spawn (`packages/tools/src/sandbox/seatbelt.ts:3`).

Paths travel as `-D` parameters and never as profile text (`packages/tools/src/sandbox/seatbelt.ts:3`). A path placed into the profile can carry `") (allow file-write* (subpath "/` and close the string. Rules of its own can then follow (`packages/tools/src/sandbox/seatbelt.ts:3`).

The parameters are safe because `sandbox-exec` substitutes a `-D` value as an opaque string and does not lex it again as SBPL (`packages/tools/src/sandbox/seatbelt.ts:3`). That premise was not checked from a Mac, and it is the essential assumption of this file (`packages/tools/src/sandbox/seatbelt.ts:3`). If a future `sandbox-exec` lexed parameter values again, a path replaces the `.git` rule with an allow of the attacker's choice (`packages/tools/src/sandbox/seatbelt.ts:3`). Denies come last (`packages/tools/src/sandbox/seatbelt.ts:3`). The last rule wins, so a deny before a broad allow is dead text that reads as protection (`packages/tools/src/sandbox/seatbelt.ts:3`). The builder assembles the profile in order: base, read baseline, writable roots, network, deny entries, protected paths, and nothing after the protected block (`packages/tools/src/sandbox/seatbelt.ts:3`).

This port trimmed `BASE_POLICY` from a 116-line base policy (`packages/tools/src/sandbox/seatbelt.ts:6`). The S6 wave ran on 2026-10-16 (Windows 11, build 26200, no elevation) through this module's own DACL writer and a synthetic `.git` of 7,473 files, the size of this repository's. It settled the shape the `.git` protection ships:

- The reconciling writer is stewarded and the raw one is not. `SetNamedSecurityInfoW` corrects an ACE that still carries the inherited flag back to the ancestor's version, so a narrowed inherited copy evaporates in the very write that lands it — the reason every earlier narrowing write answered success and changed nothing (`packages/tools/src/sandbox/appcontainer.ts:714`). The same writer re-adds a fresh inherited copy of any ancestor ACE missing from the written list, beside what was written (`packages/tools/src/sandbox/appcontainer.ts:714`). `SetFileSecurityW` is not stewarded: it neither rewrites, propagates, nor descends (`packages/tools/src/sandbox/appcontainer.ts:754`).
- The protection bit blocks ancestry, not descent. A `.git` pinned before the grant receives no copy of the parent's ACE at all — measured: the child could not even read `.git/config` — while a descent that starts at a protected node still flows down (`packages/tools/src/sandbox/appcontainer.ts:912`).
- The shipped shape is two writes at the protected directory: the raw writer pins the narrowed list with `SE_DACL_PROTECTED`, then one reconciling write of the same list starts the engine's tree walk below the pin (`packages/tools/src/sandbox/appcontainer.ts:942`). One walk narrows every stale full copy in the subtree and removes the copies whose source ACE is gone. This runs after the grant is on disk, so the ACE that narrows is the grant's own copy (`packages/tools/src/sandbox/appcontainer.ts:1743`).
- The semantics hold on a `.git` whose `config` predates the grant: the child reads it, and an append, a create, and a delete inside `.git` all fail, while the host keeps full access through its own ACE (`packages/tools/test/appcontainer.test.ts:902`). Release writes the original list back through the raw writer and sweeps the directory (`packages/tools/src/sandbox/appcontainer.ts:1781`): the reconciling write that restores the list re-fuses inheritance for the subtree, and ten acquire and release rounds leave the `.git` DACL byte for byte where they found it (`packages/tools/test/appcontainer.test.ts:965`).
- Cost, measured on the synthetic `.git`: a per-object FFI walk ran 4.13 s to acquire and 3.97 s to release, about 550 µs per object, dominated by the security write's kernel time. The two-write form runs 2.25 s and 2.33 s, about 150 µs per object per kernel tree walk, with the FFI round-trips gone (`packages/tools/src/sandbox/appcontainer.ts:942`). The cost runs once per command — the acquire before the spawn, the release in the `finally` (`packages/tools/src/operations.ts:596`) — and it scales with the size of `.git`, not with the command.
- The narrowing reaches `.git` and nothing else. `protectDirForGrant` refuses any path outside every grant root before it reads anything (`packages/tools/src/sandbox/appcontainer.ts:915`), and a protected directory the grant never reached is an error that rolls the whole acquire back, not a silent skip (`packages/tools/src/sandbox/appcontainer.ts:939`).

### Windows: the simulated layer

`simulated.ts` is the Windows filesystem sandbox that is not a sandbox, and says so (`packages/tools/src/sandbox/simulated.ts:1`). It is not OS-level enforcement, and a subprocess outside the tools is not subject to it (`packages/tools/src/sandbox/simulated.ts:1`). A result from it reads as `the Write or Edit tool call was refused by this process` (`packages/tools/src/sandbox/simulated.ts:1`). It never reads as a claim that the write was impossible (`packages/tools/src/sandbox/simulated.ts:1`).

The header used to also claim there was nowhere else to go (`packages/tools/src/sandbox/simulated.ts:1`). It said real Windows confinement "compiles two helper binaries and registers a Windows service" (`packages/tools/src/sandbox/simulated.ts:1`). It also said there is "no user-mode equivalent of macOS seatbelt" (`packages/tools/src/sandbox/simulated.ts:1`). The first half is about one design. The second half was false in the expensive direction: it named a capability as absent that exists (`packages/tools/src/sandbox/simulated.ts:1`).

The Windows SDK 10.0.26100.0 headers confirmed the claim: `CreateAppContainerProfile` at `userenv.h:1398`, `DeriveAppContainerSidFromAppContainerName` at `userenv.h:1550`, `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` at `WinBase.h:3591`, and `SECURITY_CAPABILITIES` at `winnt.h:12671` (`packages/tools/src/sandbox/simulated.ts:1`). The SDK documents them all as user-mode, with no driver, service, or elevation needed (`packages/tools/src/sandbox/simulated.ts:1`). The kernel checks an AppContainer child's package SID on every file access, which is a real write boundary (`packages/tools/src/sandbox/simulated.ts:1`). What is absent is not the mechanism and not the connection (`packages/tools/src/sandbox/simulated.ts:1`).

`appcontainer.ts` holds the whole back end, from the profile lifecycle to the confined spawn and the refcounted ACL grant (`packages/tools/src/sandbox/appcontainer.ts:1-5`). The resolver has the branch, and the exec consumer grants before the spawn and releases in a `finally` (`packages/tools/src/sandbox/index.ts:341-354`, `packages/tools/src/operations.ts:596`). The tests run all of it for real on Windows (`packages/tools/test/appcontainer.test.ts:628`). Production selects that back end through the probe's one real answer, and a decline carries the probe's reason into this layer's sentence (`packages/tools/src/sandbox/index.ts:478`).

A confined child reaches what its grants name and what the machine's own DACLs already admit to application packages: the system drive's program directories carry `ALL APPLICATION PACKAGES:(RX)`, so a toolchain under them needs no grant written at all (`packages/tools/src/sandbox/appcontainer.ts:790`). This paragraph's earlier premise — a child reads outside its grant by default — was corrected on 2026-10-15: an un-granted user directory is refused for reads too (`packages/tools/src/sandbox/appcontainer.ts:6`). A toolchain on another volume with no such ACE — measured: an elevated `D:\Program Files` — cannot be granted at all, and the probe declines instead of confining every command into a container that cannot run `git status` (`packages/tools/src/sandbox/appcontainer-probe.ts:212`).

Measured on this machine (2026-10-09, no elevation, no helper binary): create, derive, and delete succeed (`packages/tools/src/sandbox/simulated.ts:1`). Derivation is a pure function of the name, so the grant names the same SID that the next run derives again (`packages/tools/src/sandbox/simulated.ts:1`). One `(OI)(CI)(F)` allow ACE gives the confined child read and write on the subtree and nothing outside (`packages/tools/src/sandbox/simulated.ts:1`). The kernel refuses a write beyond the grant with access-denied (`packages/tools/src/sandbox/simulated.ts:1`). Without the grant the child cannot read the workspace at all, so it fails closed (`packages/tools/src/sandbox/simulated.ts:1`).

Directory enumeration is fine, and this note retracts the old reason for the other belief (`packages/tools/src/sandbox/appcontainer.ts:302-312`). `FindFirstFile` consumers such as `git status` and `ls` in bash list a granted tree (`packages/tools/src/sandbox/appcontainer.ts:302-312`). `.git` is protected by the container half through the allow side, and the 2026-10-15 replay settled why the first attempt failed: a deny ACE for the package SID never reaches the container's access check — the same shape aimed at the user SID refuses immediately — so the refusals once read as the deny working hold with no deny anywhere (`packages/tools/src/sandbox/appcontainer.ts:6`). The route that works narrows the package SID's own ACE on `.git` to read and execute and protects the DACL, which held 10 of 10 replays; the module writes it now, as `protectDirForGrant`, and the 2026-10-16 record above measures the shipped two-write form (`packages/tools/src/sandbox/appcontainer.ts:912`).

The container has no network that a session can use: it denies loopback even with `privateNetworkClientServer`, measured (`packages/tools/src/sandbox/simulated.ts:1`). What changed with the kernel-held route is who can act on it: before the bridge, a command on Linux reached nothing at all — the listed domains were what the web tools may fetch, not what a command may reach — and now the shell's reach matches the web tools', through the proxy (`packages/tools/src/sandbox/bridge.ts:2`). The detail states that reach for both kernel-held cases, because the sentence is the same once the route exists (`packages/agent/src/network-policy.ts:433`).

The port clause on the allowlist branch is a disclosure, not a defect (`packages/agent/src/network-policy.ts:427`). Both call sites that decide a request, `decideUpstream` in the proxy and `refuseByNetworkPolicy` in the web tools, pass a bare host to `decideNetworkRequest` (`packages/tools/src/sandbox/proxy.ts:62`, `packages/tools/src/web.ts:115`). `normalizeHost` strips any `:port` off before the rule engine sees it, so a rule cannot distinguish ports (`packages/agent/src/network-policy.ts:56`). A rule that allows a domain allows it on every port (`packages/agent/src/network-policy.ts:56`).

That is the intended model, with a domain-based table like Codex's (`packages/agent/src/network-policy.ts:427`). But a sentence about listed domains reads like a host allowlist tight enough to pin a service's port (`packages/agent/src/network-policy.ts:433`). A user who relies on that is wrong (`packages/agent/src/network-policy.ts:433`). The text states the granularity, because that is cheaper than to let the reader infer a restriction the code does not apply (`packages/agent/src/network-policy.ts:437`).

With `restricted` and no allow rule, the detail says nothing is reachable and the rules allow no domain (`packages/agent/src/network-policy.ts:436`). Otherwise the restricted detail says commands may reach only the listed domains, on any port, and that the list names domains, not ports (`packages/agent/src/network-policy.ts:437`). With `enabled` the detail says traffic goes through a local proxy that refuses the denied patterns (`packages/agent/src/network-policy.ts:438`).

The caveat appears per case rather than as one sentence for all six (`packages/agent/src/network-policy.ts:440`). `the OS holds the rest of the boundary` and `nothing but the proxy holds it` are opposite facts, and to average them is how a proxy-only boundary starts to read as a kernel-held one (`packages/agent/src/network-policy.ts:440`). The two kernel-held cases name the proxy too; what changes between them is which of the proxy's routes the kernel left standing — the proxy's own loopback ports, or the namespace's loopback bridge to them (`packages/agent/src/network-policy.ts:441`). This is the same obligation the filesystem half carries in `describeSandboxBackend` (`packages/agent/src/network-policy.ts:440`). It used to be wrong for the same reason (`packages/agent/src/network-policy.ts:440`).

The code keyed off `process.platform` (`packages/agent/src/network-policy.ts:440`). So a Linux box without bubblewrap and a Mac with `sandbox-exec` both printed the sentence for a machine that has one (`packages/agent/src/network-policy.ts:440`). That sentence claims the OS holds something (`packages/agent/src/network-policy.ts:440`).

The text states the scope of the gap as carefully as the gap itself (`packages/agent/src/network-policy.ts:440`). `A program that ignores the proxy environment` names subprocesses, and a user who reads only that may conclude the caveat covers the model's own tools (`packages/agent/src/network-policy.ts:440`). That was false until `WebFetch` and `WebSearch` came under this same table (`packages/agent/src/network-policy.ts:453`). They are named explicitly because the caveat's silence about them was an overclaim in its own right (`packages/agent/src/network-policy.ts:453`). It disclosed one bypass and let the reader assume there was not another (`packages/agent/src/network-policy.ts:451`).

The `proxy-bridge` caveat names the second half of the kernel-held story: the bridge is the only route the denial leaves, and when it cannot start the namespace refuses everything, the proxy included (`packages/agent/src/network-policy.ts:450`). That is what makes its detail sentence true rather than aspirational (`packages/agent/src/network-policy.ts:433`). Its absence is what let the old dead-network words — a shell that reaches nothing, allowed or denied — stand as the whole truth for Linux (`packages/tools/src/sandbox/bridge.ts:2`).

The `proxy-bridge` caveat says the OS sandbox denies the command every route off the machine except the loopback bridge into the proxy (`packages/agent/src/network-policy.ts:450`). To ignore the proxy environment gains a program nothing: the bridge is the one route back, and it leads to the proxy (`packages/agent/src/network-policy.ts:450`). And when the bridge cannot start, even a command bound for an allowed host meets a refusal, because the namespace refuses everything, the proxy included (`packages/agent/src/network-policy.ts:450`).

The other four share one caveat: the reason, then the statement that the proxy is the whole network boundary (`packages/agent/src/network-policy.ts:451`). A program that opens a socket and ignores the proxy environment is not subject to it (`packages/agent/src/network-policy.ts:451`). All four cases share the final tail (`packages/agent/src/network-policy.ts:453`). This covers the web tools too, since they fetch in this process where the proxy is not in the path (`packages/agent/src/network-policy.ts:453`).

### The network proxy

`packages/tools/src/sandbox/proxy.ts` is a local HTTP and SOCKS5 proxy that refuses what the domain policy refuses (`packages/tools/src/sandbox/proxy.ts:1`). It is the part of the network axis that touches a socket, and the decision it enforces is a pure function in `@labunbun/agent` (`packages/tools/src/sandbox/proxy.ts:3`). Every connection goes through one gate, `decideUpstream`, the address blocklist and then the domain rules, before the code opens an upstream socket (`packages/tools/src/sandbox/proxy.ts:3`). That order is the property that makes this a filter rather than a logger (`packages/tools/src/sandbox/proxy.ts:3`).

No MITM, deliberately (`packages/tools/src/sandbox/proxy.ts:3`). An `https://` URL reaches this proxy as `CONNECT host:443` followed by a byte pipe (`packages/tools/src/sandbox/proxy.ts:3`). The proxy sees the hostname and then stops (`packages/tools/src/sandbox/proxy.ts:3`). That is exactly the trade this build makes: it can refuse a destination, and it cannot read the traffic (`packages/tools/src/sandbox/proxy.ts:3`).

The other option is a locally generated CA with a man-in-the-middle in front of it (`packages/tools/src/sandbox/proxy.ts:3`). It buys content checks and costs the user a certificate in their trust store that whoever gets one file write can use (`packages/tools/src/sandbox/proxy.ts:3`). The trade is not made, and that is in the plan's not-delivered list (`packages/tools/src/sandbox/proxy.ts:3`). It is a real limitation, not an oversight (`packages/tools/src/sandbox/proxy.ts:3`). A domain on the allow list can exfiltrate through a request this proxy cannot read (`packages/tools/src/sandbox/proxy.ts:3`).

What this does not stop (`packages/tools/src/sandbox/proxy.ts:3`). Proxy environment variables are a convention (`packages/tools/src/sandbox/proxy.ts:3`). A program that calls `connect` and ignores them is not routed here and is subject to no rule in this file (`packages/tools/src/sandbox/proxy.ts:3`). Where an OS sandbox back end is actually installed, it closes that gap (`packages/tools/src/sandbox/proxy.ts:3`). Where none is, on Windows or on Linux without bubblewrap, nothing in this build does (`packages/tools/src/sandbox/proxy.ts:3`). `describeNetworkPolicy` says so per case rather than in a footnote nobody reads (`packages/tools/src/sandbox/proxy.ts:3`).

Two ports, because the tools differ (`packages/tools/src/sandbox/proxy.ts:3`). `HTTP_PROXY` and `HTTPS_PROXY` speak the HTTP proxy protocol, and `ALL_PROXY` speaks SOCKS5 (`packages/tools/src/sandbox/proxy.ts:3`). Both point at the same decision (`packages/tools/src/sandbox/proxy.ts:3`). A client handed only one of them is a client this proxy cannot filter (`packages/tools/src/sandbox/proxy.ts:3`). So both start together rather than one as an option (`packages/tools/src/sandbox/proxy.ts:3`).

The SOCKS5 reply codes are `0x00` success, `0x02` refused, and `0x07` command unsupported, from RFC 1928 §6 (`packages/tools/src/sandbox/proxy.ts:21`). The refused code is the policy answer, and the proxy is CONNECT only, so `0x07` answers any other command (`packages/tools/src/sandbox/proxy.ts:24`).

`socksReply` writes a complete ten-byte reply whole, not from a placeholder and a `subarray` (`packages/tools/src/sandbox/proxy.ts:29`). The assembled version shipped one byte too long, because the placeholder's own VER survived into the middle (`packages/tools/src/sandbox/proxy.ts:29`). The extra byte sat in the client's read buffer (`packages/tools/src/sandbox/proxy.ts:29`). Everything the tunnel then carried was off by one byte (`packages/tools/src/sandbox/proxy.ts:29`). It answered every reply test correctly, because those tests read the first ten bytes (`packages/tools/src/sandbox/proxy.ts:29`).

`NetworkProxyOptions` holds the inputs (`packages/tools/src/sandbox/proxy.ts:34`). They are the network mode behind the decision, the domain table, the loopback host to bind on, and the connect timeout (`packages/tools/src/sandbox/proxy.ts:35`). An empty table is meaningful under `restricted`, where it reaches nothing (`packages/tools/src/sandbox/proxy.ts:37`). The host is overridable so a test can pick a free port (`packages/tools/src/sandbox/proxy.ts:39`). The connect timeout gives up on an upstream that has not answered `connect` in that time (`packages/tools/src/sandbox/proxy.ts:41`).

`isBlockedHost` is injectable for one narrow reason (`packages/tools/src/sandbox/proxy.ts:43`). A test that wants to watch an allowed connection happen has to connect somewhere (`packages/tools/src/sandbox/proxy.ts:44`). Every address this build refuses is a loopback address, the only kind the test machine has (`packages/tools/src/sandbox/proxy.ts:44`). An injection point lets those tests run against a stand-in, and the real table stays on (`packages/tools/src/sandbox/proxy.ts:44`). The tests that pin the real table deliberately do not pass this option (`packages/tools/src/sandbox/proxy.ts:44`).

`decideUpstream` is the one gate, and every upstream connection in the file goes through it (`packages/tools/src/sandbox/proxy.ts:58`). It runs the address blocklist before the domain rules rather than after (`packages/tools/src/sandbox/proxy.ts:58`). The order is the whole point (`packages/tools/src/sandbox/proxy.ts:58`). The rules are a user's configuration, and a user can write `*` (`packages/tools/src/sandbox/proxy.ts:58`). That pattern answers `allowed: true` for `127.0.0.1` and for `169.254.169.254` (`packages/tools/src/sandbox/proxy.ts:58`). So the blocklist has to be the thing that can still say no (`packages/tools/src/sandbox/proxy.ts:58`).

That is also why `blocked_address` is its own reason code (`packages/tools/src/sandbox/proxy.ts:58`). A refusal from here that reported `no_matching_allow_rule` sends the user to the allowlist (`packages/tools/src/sandbox/proxy.ts:58`). The entry they need there is one they cannot add (`packages/tools/src/sandbox/proxy.ts:58`).

It is one function rather than a check pasted into three handlers (`packages/tools/src/sandbox/proxy.ts:58`). Three copies is how `handleHttp` ends up with a table `handleSocks` does not have (`packages/tools/src/sandbox/proxy.ts:58`). With a SOCKS client the only evidence it got is a single byte, so a missed gate there is invisible from the outside (`packages/tools/src/sandbox/proxy.ts:58`).

The `NetworkProxy` value holds the two URLs, the environment a child process needs for its traffic to arrive here, and `close` (`packages/tools/src/sandbox/proxy.ts:65`). `httpUrl` is the endpoint `HTTP_PROXY` and `HTTPS_PROXY` name, and `socksUrl` is the endpoint `ALL_PROXY` names (`packages/tools/src/sandbox/proxy.ts:66`). `close` stops the servers and drops every connection this proxy opened (`packages/tools/src/sandbox/proxy.ts:79`).

A request in origin-form reaches this listener when the client does use a proxy (`packages/tools/src/sandbox/proxy.ts:279`). That client wrote the request line in the direct form, or connected here by hand (`packages/tools/src/sandbox/proxy.ts:279`). It is not a URL this can place, so `new URL` throws and it fails as a malformed host (`packages/tools/src/sandbox/proxy.ts:279`). That failure is right, because there is no host to decide against and to invent one is the dangerous move (`packages/tools/src/sandbox/proxy.ts:279`).

It is worth care about what bounds such a client, because the obvious answer is wrong on two of three platforms (`packages/tools/src/sandbox/proxy.ts:279`). A client that ignores `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY` does not reach this listener at all (`packages/tools/src/sandbox/proxy.ts:279`). It opens its own socket, and this proxy is not in that path (`packages/tools/src/sandbox/proxy.ts:279`). Where an OS sandbox back end is actually installed, it closes that gap (`packages/tools/src/sandbox/proxy.ts:279`). Where none is, on Windows or on Linux without bubblewrap, nothing in this build does, and the connection is simply direct (`packages/tools/src/sandbox/proxy.ts:279`). The file says so at the top, and this paragraph used to imply the opposite without a platform qualifier (`packages/tools/src/sandbox/proxy.ts:279`).

The client sent the proxy's own `Host`, and the origin needs its own (`packages/tools/src/sandbox/proxy.ts:295`). The upstream request carries the target hostname, its port or 80, the method, and the path with its query (`packages/tools/src/sandbox/proxy.ts:289`). The headers carry that origin's own `Host` (`packages/tools/src/sandbox/proxy.ts:296`). The proxy relays the response with its status code, or 502 when there is none (`packages/tools/src/sandbox/proxy.ts:299`). An upstream error answers 502 as well (`packages/tools/src/sandbox/proxy.ts:303`).

`splitHostPort` keeps an unbracketed IPv6 literal intact (`packages/tools/src/sandbox/proxy.ts:311`). To split at the first colon is the one line of code that turns `::1` into an empty host (`packages/tools/src/sandbox/proxy.ts:311`). The code then refuses that host as malformed (`packages/tools/src/sandbox/proxy.ts:311`). That is a fail-closed accident rather than a decision (`packages/tools/src/sandbox/proxy.ts:311`). It is the kind of accident that gets fixed later by someone who reads the failure as the bug (`packages/tools/src/sandbox/proxy.ts:311`).

`handleSocks` runs the SOCKS5 handshake in RFC 1928 order (`packages/tools/src/sandbox/proxy.ts:351`). The server offers only no-authentication, because this proxy authenticates nothing and a client told to offer more has nothing to offer (`packages/tools/src/sandbox/proxy.ts:334`). The code checks the first message for the version and for the no-authentication method (`packages/tools/src/sandbox/proxy.ts:351`). A command other than CONNECT gets the command-unsupported reply and the end of the connection (`packages/tools/src/sandbox/proxy.ts:346`). The code reads the address by its type octet: four bytes, a length byte with a name, or 16 bytes (`packages/tools/src/sandbox/proxy.ts:351`). The port is two big-endian bytes (`packages/tools/src/sandbox/proxy.ts:352`).

The reply to a policy refusal is a code with no reason attached, and that is the protocol rather than an oversight (`packages/tools/src/sandbox/proxy.ts:356`). RFC 1928's reply carries a code and nothing else (`packages/tools/src/sandbox/proxy.ts:357`). So a blocked address, a denied domain, and an unmatched allow rule are one byte apart to a SOCKS client (`packages/tools/src/sandbox/proxy.ts:358`). `handleConnect` answers in a header because HTTP has somewhere to put it (`packages/tools/src/sandbox/proxy.ts:359`).

On success the upstream opens, the reader releases, the success reply goes out, and both pipes start (`packages/tools/src/sandbox/proxy.ts:366`). The reader's `data` listener has to go first (`packages/tools/src/sandbox/proxy.ts:367`). Otherwise a handshake that already finished buffers the tunnel bytes, while `pipe` tries to read the same bytes (`packages/tools/src/sandbox/proxy.ts:368`). The catch path releases the reader before it rethrows (`packages/tools/src/sandbox/proxy.ts:375`).

`byte` reads one byte of a wire buffer, or throws (`packages/tools/src/sandbox/proxy.ts:381`). `noUncheckedIndexedAccess` makes every index into a `Buffer` a `number | undefined` (`packages/tools/src/sandbox/proxy.ts:381`). This file reads a protocol whose whole job is to fail on a malformed message (`packages/tools/src/sandbox/proxy.ts:381`). The three ways out of that are all worse than a throw (`packages/tools/src/sandbox/proxy.ts:381`).

One is an `!` the linter forbids (`packages/tools/src/sandbox/proxy.ts:381`). One is a `?? 0` that turns a truncated first message into a plausible one (`packages/tools/src/sandbox/proxy.ts:381`). One is a comparison against `undefined` that quietly does the right thing for every value except its intended one (`packages/tools/src/sandbox/proxy.ts:381`).

`uint16` reads two bytes big-endian, for the same reason and as its only use (`packages/tools/src/sandbox/proxy.ts:388`). `readAddress` reads the destination in whichever of the three address forms the client used (`packages/tools/src/sandbox/proxy.ts:393`).

`formatIpv6` writes the eight groups as a hostname, with the longest run of zeros collapsed to `::` per RFC 5952 (`packages/tools/src/sandbox/proxy.ts:402`). A run has to be two or more to take that form (`packages/tools/src/sandbox/proxy.ts:403`). A `::` that stands for one zero group is a different string (`packages/tools/src/sandbox/proxy.ts:404`).

`byteReader` keeps one `data` listener for the whole handshake (`packages/tools/src/sandbox/proxy.ts:431`). To attach and remove a listener per read looks equivalent and is not (`packages/tools/src/sandbox/proxy.ts:431`). With no listener attached the socket keeps whatever its buffer already holds (`packages/tools/src/sandbox/proxy.ts:431`). The socket drops bytes that arrive in the gap between two awaits (`packages/tools/src/sandbox/proxy.ts:431`).

The first SOCKS5 message is 2+N+method bytes sent in one write (`packages/tools/src/sandbox/proxy.ts:431`). The gap is exactly where the rest of that message is (`packages/tools/src/sandbox/proxy.ts:431`). `release()` removes the listener before it hands the socket to `pipe`, which is the other half of the same hazard (`packages/tools/src/sandbox/proxy.ts:431`).

The code annotates the buffer and does not infer it (`packages/tools/src/sandbox/proxy.ts:433`). `Buffer.alloc` narrows to a buffer over `ArrayBuffer`, and the `data` event hands over the wider `Buffer` type (`packages/tools/src/sandbox/proxy.ts:435`). Without the annotation the first concatenation does not type-check (`packages/tools/src/sandbox/proxy.ts:434`).

In `flush` the code has to read the waiter from the queue before it removes the waiter (`packages/tools/src/sandbox/proxy.ts:449`). An ask for `waiters[0]` again after the shift answers for the next caller (`packages/tools/src/sandbox/proxy.ts:450`). The loop form with a `break` replaces a condition on `waiters[0].count`, because that index is optional under `noUncheckedIndexedAccess` (`packages/tools/src/sandbox/proxy.ts:452`). The only other ways to use it are an assertion the linter forbids or a default that answers 0 for an empty queue (`packages/tools/src/sandbox/proxy.ts:453`).

`fail` drains the queue with a splice rather than a shift loop (`packages/tools/src/sandbox/proxy.ts:463`). So the loop variable is the waiter itself, the value that needs the rejection (`packages/tools/src/sandbox/proxy.ts:464`). A client that closes the socket during the handshake rejects every waiter with `client closed during the SOCKS5 handshake` (`packages/tools/src/sandbox/proxy.ts:473`).

`openUpstream` opens the upstream socket for an allowed destination, with a connect deadline (`packages/tools/src/sandbox/proxy.ts:494`). A timeout destroys the socket and rejects with `connecting to HOST:PORT timed out` (`packages/tools/src/sandbox/proxy.ts:503`).

`ListeningServer` is what `http.Server` and `net.Server` share, and all this file calls on either (`packages/tools/src/sandbox/proxy.ts:513`). To declare it structurally is what lets the SOCKS5 listener be a `net.Server` (`packages/tools/src/sandbox/proxy.ts:513`). No helper above needs a union or a cast for it (`packages/tools/src/sandbox/proxy.ts:513`). The event methods come from `EventEmitter` rather than from a long list in the declaration (`packages/tools/src/sandbox/proxy.ts:513`). A hand-written `on(event: string, ...)` is not assignable from Node's typed overloads (`packages/tools/src/sandbox/proxy.ts:513`).

`listen` binds on port 0 and the given host, and `portOf` reads the port back from the address (`packages/tools/src/sandbox/proxy.ts:520`). An address of `null` or a string throws, because the server did not report a port (`packages/tools/src/sandbox/proxy.ts:546`). `trackServer` accepts connections onto the live set so `close` can drop them (`packages/tools/src/sandbox/proxy.ts:555`). `closed` turns the server's close callback into a promise (`packages/tools/src/sandbox/proxy.ts:562`). `close` destroys every live socket and waits for both servers to close (`packages/tools/src/sandbox/proxy.ts:194`).

### The Linux loopback bridge

`packages/tools/src/sandbox/bridge.ts` is the one route back into a `--unshare-net` namespace (`packages/tools/src/sandbox/bridge.ts:1`). The proxy environment inside a restricted command names loopback ports the namespace cannot reach, so a process inside the namespace listens on those same ports and forwards every connection over a Unix socket to the host, where `NetworkProxy` serves the other end (`packages/tools/src/sandbox/bridge.ts:2`). The socket file is the entire rendezvous: it rides the filesystem the two namespaces share, and nothing else crosses the boundary (`packages/tools/src/sandbox/bridge.ts:6`). The ports are the proxy's own on both sides, which is why the proxy environment needs no rewriting for the confined command (`packages/tools/src/sandbox/bridge.ts:16`).

The proxy publishes the host side when, and only when, the bridge is wanted: `unixBridge` opens one socket per listening port under a fresh temp directory, named `port-<n>.sock` (`packages/tools/src/sandbox/proxy.ts:218`, `packages/tools/src/sandbox/proxy.ts:222`), and the executor asks for it on Linux alone — the one platform whose back end gets `--unshare-net` (the other two platforms' ports reach their profiles directly, so a socket would be a second, unused path) (`packages/tools/src/sandbox/operations.ts:486`). `networkBridgeFor` is the read side the resolver consumes, next to `networkEnvFor`, so the host half of the bridge is up before the spawn, the same way the macOS profile names the proxy's ports before its argv is built (`packages/tools/src/sandbox/operations.ts:536`).

The argv that starts a bridge under this same executable has two shapes, told apart in one place: a source checkout runs the script beside the module, and a compiled binary re-enters its own entry point with `__bridge`, because a compiled binary reports a virtual `import.meta.dir` and the join would not exist under it (measured) (`packages/tools/src/sandbox/bridge.ts:39`). The script shape is `bridge-main.ts`, three lines that hand their argv to `runBridge` (`packages/tools/src/sandbox/bridge-main.ts:5`). The compiled shape is a branch at the top of the CLI's `main`, before argument parsing, that dynamically imports `@labunbun/tools` and hands the remaining argv to the same function (`packages/coding-agent/src/main.ts:329`). `runBridge` parses the pairs and serves until the namespace it lives in is torn down, which is what a never-settling await expresses: there is nothing to do after this and no exit path to run (`packages/tools/src/sandbox/bridge.ts:134`).

`wrapWithBridge` is what a confined command's argv becomes (`packages/tools/src/sandbox/bridge.ts:65`). It declines — the caller then keeps the bare argv, which in a restricted namespace is the dead network the build had before the bridge existed — when there are no pairs to bridge or no `/bin/bash` to run the wrapper (`packages/tools/src/sandbox/bridge.ts:70`). The wrapper is one `bash -c` script: bring loopback up — belt and braces rather than the mechanism, because bubblewrap's own `loopback_setup()` raises `lo` on every `--unshare-net` and exits if it cannot (measured against 0.9.0, the version CI installs), so the `ip` line only covers older bubblewrap's namespaces, where `lo` stays down (`packages/tools/src/sandbox/bridge.ts:83`) — start the bridge in the background with its stderr attached, because a bridge that cannot listen says so there and nowhere else (`packages/tools/src/sandbox/bridge.ts:87`), and poll both ports with `/dev/tcp` until a connect succeeds — the only evidence that matters, because it is exactly what the confined command will do (`packages/tools/src/sandbox/bridge.ts:91`). On timeout it says so on stderr, then the bridge's own state — `still running` or `has exited`, a different machine each — and runs the command anyway: fail closed, like every other unavailable-network path, rather than refusing a command the user asked for (`packages/tools/src/sandbox/bridge.ts:92`). The command itself is passed through as positional arguments and `exec`ed, with a placeholder as the shell's `$0` so nothing in the command's own argv can be read as an option to `bash` (`packages/tools/src/sandbox/bridge.ts:93`).

The bwrap half grants `--cap-add CAP_NET_ADMIN` only when a bridge is actually in the argv: the wrapper's `ip` fallback for older bubblewrap — bringing this namespace's own loopback up — is what takes the capability, and on current bubblewrap (which raises `lo` itself) the grant sits unused rather than being wrong (`packages/tools/src/sandbox/bwrap.ts:75`). The bridge only ever wraps a command the namespace is about to cut off: on an open axis there is no namespace and nothing to bridge, and with no bridge the argv is the bare `--unshare-net` command either way (`packages/tools/src/sandbox/bwrap.ts:23`). The report side is `proxy-bridge` (`packages/tools/src/sandbox/index.ts:459`), and `/permissions` treats it as kernel-held: the proxy is not the whole boundary there, so the same predicate that covers `proxy-ports` covers it (`packages/coding-agent/src/doctor.ts:253`).

The tests hold each piece still: `parseBridgeArgs` reads socket/port pairs in the order the wrapper writes them, `bridgeRuntime` holds both argv shapes, `wrapWithBridge` pins the command verbatim after the placeholder, the loopback-up/probe script, the two post-failure state lines, and the stderr that stays attached, and `runBridge` is exercised over a real socket round trip (`packages/tools/test/sandbox-bridge.test.ts:21`, `packages/tools/test/sandbox-bridge.test.ts:43`, `packages/tools/test/sandbox-bridge.test.ts:59`, `packages/tools/test/sandbox-bridge.test.ts:132`). The wiring tests pin the two directions that meet in `operations`: a restricted policy's bridge lands on the ports its environment names, and a policy that confines no network opens no bridge at all (`packages/tools/test/sandbox-wiring.test.ts:2077`, `packages/tools/test/sandbox-wiring.test.ts:2106`).

The 2026-10-16 CI record is the bridge row's first real-machine run, and the failure it produced was the row's own harness: the upstream server stands in the test process, `spawnSync` froze the event loop that had to accept and answer the bridge's connection, and the run measured exactly that deadlock — bun's 5000 ms watchdog killed `bwrap` as a dangling process with both streams empty. The bridge was never in question, and the reproduction that settled it ran in WSL: bubblewrap 0.9.0 extracted from its own `.deb` (no root, user-namespace mode), bun 1.3.5, and the argv generated verbatim from these two modules. The same driver with the synchronous spawn reproduced the CI shape to the byte (15018 ms, `ETIMEDOUT`, both streams empty), and with an asynchronous spawn the same argv answered `PING` in 73 ms. The row now spawns asynchronously (`packages/tools/test/sandbox-bwrap-smoke.test.ts:733`), with its own 15 s kill budget inside a 25 s test budget, so the kill lands inside the row and the assertions get to report what happened (`packages/tools/test/sandbox-bwrap-smoke.test.ts:769`) — the wrapper's two changes from the same record, stderr attached and the post-failure state line, are what would have made the original failure readable.

## Why it is like this

- **Why the policy is a value and not a mechanism.** The filesystem and network halves are separate data (`packages/agent/src/sandbox-policy.ts:3`). Three translators read it, and the platform picks which one runs (`packages/agent/src/sandbox-policy.ts:3`). A test can assert what a mode means without a spawn (`packages/agent/src/sandbox-policy.ts:3`).
- **Why the network half is a proxy on all three platforms.** The proxy sees the hostname and then stops, because it can refuse a destination and cannot read the traffic (`packages/tools/src/sandbox/proxy.ts:3`). A locally generated CA buys content checks and costs a certificate in the user's trust store (`packages/tools/src/sandbox/proxy.ts:3`).
- **Why the two halves are layered rather than merged.** Where a native back end exists, it closes the gap the proxy cannot (`packages/agent/src/sandbox-policy.ts:3`). Where one is not, the proxy is the whole of it, and the report says which (`packages/agent/src/sandbox-policy.ts:3`). A mechanism that reads as OS-enforced when it is not is worse than no mechanism (`packages/agent/src/sandbox-policy.ts:5`).
- **Why Windows still gets a tool-layer decision.** The original reason — that no user-mode confinement existed to reach for — was false, and the container back end is the correction (`packages/agent/src/sandbox-policy.ts:3`). The decision remains because the container is selected per machine and can decline: wherever it declines, a subprocess that goes around the tools is not subject to the decision either (`packages/agent/src/sandbox-policy.ts:3`).
- **Why the blocklist runs before the rules.** A user can write `*`, and that pattern answers `allowed: true` for `127.0.0.1` and for `169.254.169.254` (`packages/tools/src/sandbox/proxy.ts:58`). The blocklist has to be the thing that can still say no (`packages/tools/src/sandbox/proxy.ts:58`).
- **Why `deny` beats `allow` regardless of list order.** The order of the first two rules is the security property (`packages/agent/src/network-policy.ts:288`). A table where a later `allow` rescues an earlier `deny` is order-sensitive in the one direction that matters (`packages/agent/src/network-policy.ts:288`).
- **Why the proxy starts for `enabled` with rules.** Either the mode forbids by default, or the rules narrow something open by default (`packages/agent/src/network-policy.ts:306`). Both are one decision seen from two sides, which is why one function answers (`packages/agent/src/network-policy.ts:306`).
- **Why a confinement answers with a reason and not a boolean.** Four of the six answers are a no, for four different reasons (`packages/agent/src/network-policy.ts:312`). The code owes the user the reason, and it is the reason a user acts on (`packages/agent/src/network-policy.ts:349`).
- **Why one claim string serves four cases.** A reader who sees a differently-worded claim in one case has no way to know it means the same thing (`packages/agent/src/network-policy.ts:349`). Only the reason may differ (`packages/agent/src/network-policy.ts:349`).
- **Why the two kernel-held cases get their own detail.** Every shared sentence would be false for them, in opposite directions on either side of the kernel-held line (`packages/agent/src/network-policy.ts:430`). The one detail true for both says the allowlist governs a command's traffic through the proxy, the one route the kernel left standing (`packages/agent/src/network-policy.ts:423`): the macOS profile leaves exactly the proxy's ports standing, and the Linux namespace exactly the loopback bridge to them, so in both cases the allowlist governs what rides through (`packages/agent/src/network-policy.ts:433`).
- **Why the web tools are named in the caveat.** The silence about them was an overclaim in its own right (`packages/agent/src/network-policy.ts:453`). It disclosed one bypass and let the reader assume there was not another (`packages/agent/src/network-policy.ts:451`).
- **Why the port clause is stated.** `normalizeHost` strips any `:port` before the rule engine sees it, so a rule cannot tell ports apart (`packages/agent/src/network-policy.ts:56`). A rule that allows a domain allows it on every port, and the sentence says so (`packages/agent/src/network-policy.ts:420`).
- **Why the splitter counts colons.** An unbracketed IPv6 literal has several colons (`packages/agent/src/network-policy.ts:66`). A split at the first colon turns `::1` into an empty host, and the code refuses that host (`packages/agent/src/network-policy.ts:67`).
- **Why the tool keys are pinned rather than stripped.** To strip `PIP_PROXY` removes pip's only proxy setting and sends it out directly, which is the same bypass by the other road (`packages/tools/src/sandbox/proxy.ts:106`). There is no version of that removal that is safe here (`packages/tools/src/sandbox/proxy.ts:106`).
- **Why `NO_PROXY` is empty.** To put `localhost` or `127.0.0.1` there is the conventional thing to do, and it is a documented bypass (`packages/tools/src/sandbox/proxy.ts:118`). An empty value routes even loopback through the decision (`packages/tools/src/sandbox/proxy.ts:118`).
- **Why the ten-byte reply is written whole.** The assembled version shipped one byte too long (`packages/tools/src/sandbox/proxy.ts:29`). The extra byte sat in the client's read buffer (`packages/tools/src/sandbox/proxy.ts:29`).
- **Why one `data` listener covers the handshake.** With no listener attached the socket keeps whatever its buffer already holds (`packages/tools/src/sandbox/proxy.ts:431`). The socket drops bytes that arrive in the gap between two awaits (`packages/tools/src/sandbox/proxy.ts:431`). The first SOCKS5 message is one write, so the gap is exactly where the rest of it is (`packages/tools/src/sandbox/proxy.ts:431`).
- **Why the real blocklist stays on in tests.** A test that wants to watch an allowed connection happen has to connect somewhere (`packages/tools/src/sandbox/proxy.ts:44`). An injection point lets those tests run against a stand-in, and the real table stays on (`packages/tools/src/sandbox/proxy.ts:44`).
- **Why both halves share one address table.** The proxy matcher and the web tools ask the same question (`packages/agent/src/network-policy.ts:96`). One import means no second table for two halves to drift apart over (`packages/agent/src/network-policy.ts:96`).

## Known traps

- `127.0.0.1` has six spellings, and a `deny` rule caught one of them before `canonicalIpLiteral` (`packages/agent/src/network-policy.ts:31`). The other five were `127.0.0.01`, `127.1`, `0177.0.0.1`, `0x7f000001`, and `2130706433` (`packages/agent/src/network-policy.ts:31`).
- The two blocklist halves can disagree about what is loopback. A comment once claimed they agreed, and measurement said the `web.ts` half answered false for the hex spelling (`packages/agent/src/network-policy.ts:115`).
- The `fe80::/10` check read `startsWith("fe80:")`, which is a single /16 of a /10. Seven of the sixteen link-local blocks came back unblocked (`packages/agent/src/network-policy.ts:159`).
- NAT64 prefixes other than the well-known `64:ff9b::/96` are not decoded (`packages/agent/src/network-policy.ts:225`). A deployment that uses one has a real gap (`packages/agent/src/network-policy.ts:225`).
- A user can write `{allow: "*"}` and believe every host is open. `127.0.0.1` and `169.254.169.254` are still refused, and the code `blocked_address` is the clue (`packages/tools/src/sandbox/proxy.ts:58`).
- A rule for a domain covers every port on it, because `normalizeHost` strips the port first (`packages/agent/src/network-policy.ts:56`).
- Seven of the ten per-tool variables are not set, and the same list reads as one gap and is two (`packages/tools/src/sandbox/proxy.ts:106`). Yarn is not checked here, and Bundler is an open question rather than a verdict (`packages/tools/src/sandbox/proxy.ts:106`).
- A client that ignores `HTTP_PROXY` does not reach the proxy at all. It opens its own socket, and only a native back end closes that gap (`packages/tools/src/sandbox/proxy.ts:279`). On Windows, or on Linux without bubblewrap, the connection is direct (`packages/tools/src/sandbox/proxy.ts:279`).
- Under `restricted` with a Linux native back end, the one route left is the loopback bridge, and the bridge is user space (`packages/tools/src/sandbox/bridge.ts:1`): when it cannot start, the namespace refuses everything, the proxy included, and a command bound for an allowed host meets a refusal (`packages/agent/src/network-policy.ts:330`). The macOS side of the same line is the profile's own trap: the enforcing proxy's own loopback ports are the only route left standing, so the allowlist sentence is true for a command there too (`packages/tools/src/sandbox/seatbelt.ts:228`).
- A port that is absent defaults to 443 on the `CONNECT` path (`packages/tools/src/sandbox/proxy.ts:271`).
- A SOCKS5 refusal carries a code with no reason (`packages/tools/src/sandbox/proxy.ts:357`). A blocked address, a denied domain, and an unmatched allow rule are one byte apart to the client (`packages/tools/src/sandbox/proxy.ts:358`).
- The `data` listener has to go first, or a handshake that already finished buffers the tunnel bytes (`packages/tools/src/sandbox/proxy.ts:367`). `release()` removes the listener before it hands the socket to `pipe`, which is the same hazard from the other side (`packages/tools/src/sandbox/proxy.ts:431`).
- A throw refuses a malformed first message (`packages/tools/src/sandbox/proxy.ts:381`). Three worse options exist (`packages/tools/src/sandbox/proxy.ts:381`). One is an `!` the linter forbids (`packages/tools/src/sandbox/proxy.ts:381`). One is a `?? 0` that turns a truncated first message into a plausible one (`packages/tools/src/sandbox/proxy.ts:381`). One is a comparison against `undefined` (`packages/tools/src/sandbox/proxy.ts:381`).
- An empty `NO_PROXY` looks like a mistake and is the design (`packages/tools/src/sandbox/proxy.ts:118`). A stale lowercase `no_proxy=localhost` from the ambient environment otherwise wins on half the tools (`packages/tools/src/sandbox/proxy.ts:118`).
- MSYS and Cygwin cannot start inside an AppContainer at all: the runtime creates its shared memory under `\BaseNamedObjects`, which a container token cannot reach by construction, and the process dies with `0xC0000142` before any grant is consulted (`packages/tools/src/sandbox/appcontainer-probe.ts:133`). No ACL arrangement is the fix; the shell itself is the wrong shell for the container.
- A container child can be started from a path the container cannot read. `CreateProcessW` opens the image in the launching process's context, so a successful launch is not evidence of reachability — everything after the image is the child's own (`packages/tools/src/sandbox/appcontainer.ts:6`).
- The refusal read is a keyword hedge over output the command controls. A test suite about sandboxes that fails for its own reason exits nonzero under a wrapped run, carries the word `sandbox`, and reads as a refusal (`packages/tools/src/sandbox-denial.ts:83`). The hedge says *may* for exactly that reason; `/permissions` states the axes, and the hedge only points at it (`packages/tools/src/bash.ts:204`).
- Line references inside comments drift when another file changes. The refs in this document were re-derived at the end. The ones inside the source comments are not all current.
