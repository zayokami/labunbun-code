# Sandbox and network policy

The sandbox has three axes: the mode, the filesystem sandbox, and the network sandbox. Two pure modules in `packages/agent/src` define the policy as a value (`sandbox-policy.ts` and `network-policy.ts`). The modules under `packages/tools/src/sandbox/` translate that value for the platform and carry out the parts a program can do on its own (`packages/tools/src/sandbox/index.ts:1`).

## Purpose

- Describe what a command may touch as data, so every back end reads one value (`packages/agent/src/sandbox-policy.ts:118`).
- Keep the filesystem axis and the network axis in separate fields of that value (`packages/agent/src/sandbox-policy.ts:65`).
- Translate the policy for macOS seatbelt, Linux bwrap, and a Windows AppContainer profile (`packages/tools/src/sandbox/index.ts:170`).
- Decide each network request in one pure function that tests on any machine (`packages/agent/src/network-policy.ts:289`).
- Report what confines a command in fact, not what the policy asked for (`packages/tools/src/sandbox/index.ts:280`).

## Behavior

### The policy value

`packages/agent/src/sandbox-policy.ts` builds one `SandboxPolicy` from a mode and a few call options. It stays pure: it reads no filesystem and starts no process (`packages/agent/src/sandbox-policy.ts:1`).

The policy is a value, not a check. Three translators read it. macOS seatbelt and Linux bwrap are real, and bwrap needs an install as well. The third is a Windows layer that the tools simulate in their own process (`packages/agent/src/sandbox-policy.ts:1`). A subprocess started outside the tools is not subject to the third one.

On all three platforms the network axis works through a proxy. That is a convention, not kernel enforcement (`packages/agent/src/sandbox-policy.ts:1`). Where no back end exists, on Windows or on Linux without bubblewrap, the proxy and the environment variables are the whole of the network story. `describeNetworkPolicy` says which case a session is in (`packages/agent/src/sandbox-policy.ts:1`). `networkConfinement` lives in `@labunbun/tools` because the agent package cannot see whether the machine has bubblewrap (`packages/agent/src/sandbox-policy.ts:1`). A mechanism that reads as enforced by the OS when it is not is worse than no mechanism (`packages/agent/src/sandbox-policy.ts:1`).

`canonicalPolicyPath` is the one spelling every comparison uses. It replaces `\` with `/`, and every downstream comparison starts with `startsWith` on that form (`packages/agent/src/sandbox-policy.ts:8`). A backslash entry widens a check, and a test caught that, so the builder canonicalises the entry first (`packages/agent/src/sandbox-policy.ts:8`). The function deliberately does not resolve paths. A resolve needs filesystem access, and a relative path resolved against the real filesystem moves a fixture's `/w/repo` onto a real drive (`packages/agent/src/sandbox-policy.ts:8`).

`FileSystemAccessMode` has `write`, `read`, and `deny` (`packages/agent/src/sandbox-policy.ts:17`). A `write` entry implies `read` (`packages/agent/src/sandbox-policy.ts:17`). `deny` is unambiguous on seatbelt, which has a deny rule, and in the simulated layer, which refuses the read in `decideRead` (`packages/agent/src/sandbox-policy.ts:17`). On bwrap the mode is purely constructive, so the strongest form bwrap can express is a read-only bind. `bwrap.ts` documents the gap (`packages/agent/src/sandbox-policy.ts:17`). `buildSandboxPolicy` emits only `write` and `read` entries (`packages/agent/src/sandbox-policy.ts:17`).

`WritableRootKind` separates a project root from a data root (`packages/agent/src/sandbox-policy.ts:21`). A project root derives a `<root>/.git` protected path whether or not that directory exists. A data root does not, because caches and scratch directories have no version-control metadata in them (`packages/agent/src/sandbox-policy.ts:21`). The caller carries the distinction. The kind is never read off the path (`packages/agent/src/sandbox-policy.ts:21`). The builder treats an unknown kind as `project`, the conservative side (`packages/agent/src/sandbox-policy.ts:21`).

A bare string writable root means `project` on purpose (`packages/agent/src/sandbox-policy.ts:25`). Any other shape is an error the builder drops (`packages/agent/src/sandbox-policy.ts:25`). The failure this avoids is a silent increase in access that looks like a refactor (`packages/agent/src/sandbox-policy.ts:25`). `normalizeWritableRoot` does that conversion (`packages/agent/src/sandbox-policy.ts:35`).

`NETWORK_SANDBOX_POLICIES` is the list of network values, and the settings schema derives its enum from that list (`packages/agent/src/sandbox-policy.ts:39`). A hand-written `z.enum` is a copy that drifts (`packages/agent/src/sandbox-policy.ts:39`).

`FileSystemSandboxEntry` carries a `path` and a `missingPathBehavior` (`packages/agent/src/sandbox-policy.ts:51`). The path is absolute and forward-slash, and the builder enforces both halves (`packages/agent/src/sandbox-policy.ts:51`). A measurement covered them: before the enforcement, `isWritePermitted` answered true for `<ws>/.git/config` in either spelling (`packages/agent/src/sandbox-policy.ts:51`). `missingPathBehavior: "skip"` marks an entry whose absence is not a broken session, such as self-referential entries (`packages/agent/src/sandbox-policy.ts:55`). The caller drops those entries, not the back end, because the translators are pure (`packages/agent/src/sandbox-policy.ts:55`). The mark is essential on Linux, where bwrap refuses to start when a `--bind` source is absent (`packages/agent/src/sandbox-policy.ts:55`).

`SandboxPolicy` holds the filesystem entries, the network rules, and the protected paths (`packages/agent/src/sandbox-policy.ts:65`). The network rules sit on the policy so the network axis arrives as one value. A caller cannot assemble it from two arguments that disagree (`packages/agent/src/sandbox-policy.ts:68`). An empty rule list means the mode alone decides (`packages/agent/src/sandbox-policy.ts:68`).

`protected` is its own field rather than deny entries appended to the entry list (`packages/agent/src/sandbox-policy.ts:71`). An append approach needs "deny after every allow" on each back end, which repeats one promise once per back end. A back end that forgets is the bug shape, and the tests assert the order per back end (`packages/agent/src/sandbox-policy.ts:71`). Today the protected paths are the `.git` directories. The containment check stops the Edit and Write tools, and a shell is not subject to it. Agent mode allowed an `rm .git/config` through Bash before this layer existed (`packages/agent/src/sandbox-policy.ts:71`).

`BuildSandboxPolicyOptions` gives the builder its inputs (`packages/agent/src/sandbox-policy.ts:76`). The caller discovers `protectedPaths`, because the module stays pure (`packages/agent/src/sandbox-policy.ts:81`). `writableRoots` is the list of roots the mode allows (`packages/agent/src/sandbox-policy.ts:87`). `readOnlyRoots` becomes read entries that are not writable (`packages/agent/src/sandbox-policy.ts:95`).

The network policy is not derived from the sandbox mode (`packages/agent/src/sandbox-policy.ts:97`). A collapse cuts the network for the `workspace-write` default and breaks `npm install` and `git fetch`. It defaults to enabled (`packages/agent/src/sandbox-policy.ts:97`).

The builder copies `networkRules` rather than references, so a later change by the caller cannot change the policy a back end already holds (`packages/agent/src/sandbox-policy.ts:100`).

### What the builder produces

`buildSandboxPolicy` returns an empty policy for `danger-full-access`, not one that allows everything (`packages/agent/src/sandbox-policy.ts:118`). A back end can recognize an empty policy and refuse to wrap. A test can tell an unconfined run from a very wide sandbox (`packages/agent/src/sandbox-policy.ts:118`).

The workspace is the one path entry the builder always adds, with kind `write` (`packages/agent/src/sandbox-policy.ts:132`). Its `missingPathBehavior` is deliberately not set: a workspace that does not exist is a broken session, not a policy to skip past (`packages/agent/src/sandbox-policy.ts:132`). The builder canonicalises every entry once (`packages/agent/src/sandbox-policy.ts:138`).

The writable roots each become a `write` entry with the skip mark (`packages/agent/src/sandbox-policy.ts:142`). A read-only root is not emitted where the platform reads everything by default. The builder records it anyway, because the Windows simulated layer has no default for readable paths (`packages/agent/src/sandbox-policy.ts:145`).

`protectedFor` receives the workspace and the project roots, not the data roots (`packages/agent/src/sandbox-policy.ts:157`). Only a project root derives a `.git`. A data root holds caches and scratch files (`packages/agent/src/sandbox-policy.ts:159`). The Linux translator creates an empty read-only directory for a protected path that is absent. A directory that appears for nobody is the wrong result of a `.git` derived for a cache root (`packages/agent/src/sandbox-policy.ts:159`).

### Protected paths from a scan

`protectedFor` derives `<root>/.git` for every writable root of kind `project` (`packages/agent/src/sandbox-policy.ts:170`). The derivation is the point: the scan has limits it cannot see past, and a `.git` the scan misses stays writable (`packages/agent/src/sandbox-policy.ts:170`). The scan limits are a depth of four and a skip of `node_modules` (`packages/agent/src/sandbox-policy.ts:170`). Those limits are wrong for the one directory everybody knows. A repository created after the first Bash call, or a `.git` five levels down, was writable. The write went through, and the tool reported success (`packages/agent/src/sandbox-policy.ts:170`).

The code used to cache the scan for the life of the process, and the cache was a hole of its own. A measurement showed it: a moved `.git` stayed listed at the old path (`packages/agent/src/sandbox-policy.ts:170`). The cache is gone. The only limit left is the reach of the scan (`packages/agent/src/sandbox-policy.ts:170`).

The builder derives only `.git`. The builder deduplicates the list. An absent path is still derived, which is why bwrap needs the empty-directory recipe. The protection is stronger when the directory appears later (`packages/agent/src/sandbox-policy.ts:170`).

`gitRoots` is the set of roots that asked for a `.git` derivation. The caller filters on kind. `WorkspacePolicyOptions` passes the temp and cache roots with kind `data` (`packages/agent/src/sandbox-policy.ts:170`).

The builder joins `root` and `.git` and then canonicalises. The join is what puts `\` on Windows, and canonicalisation turns it into the one spelling (`packages/agent/src/sandbox-policy.ts:172`).

### The write question without a filesystem

`isWritePermitted` answers lexically, with no filesystem access (`packages/agent/src/sandbox-policy.ts:185`). The kernel back ends do not use it, because the kernel is the check (`packages/agent/src/sandbox-policy.ts:185`). The Windows simulated layer does not use it either. `decideWrite` has its own containment test, takes the case rule as a parameter, and canonicalises the root itself (`packages/agent/src/sandbox-policy.ts:185`).

The export has no production caller. Tests use it. An earlier comment claimed the simulated layer used it, and that was false (`packages/agent/src/sandbox-policy.ts:185`).

The question is directional: an answer may only narrow access, never widen it (`packages/agent/src/sandbox-policy.ts:185`). Both sides are already canonical. On macOS, `/var/folders` and `/private/var/folders` name the same directory, and a "no" for that pair is the wrong direction (`packages/agent/src/sandbox-policy.ts:185`). That is why `decideWrite` is the production answer (`packages/agent/src/sandbox-policy.ts:185`).

The code checks the protected list first (`packages/agent/src/sandbox-policy.ts:187`). A helper that must never widen access must not discard the narrower rule (`packages/agent/src/sandbox-policy.ts:188`). Then an unrestricted policy answers true. Then the code tests the entries with `canWrite` and the containment check (`packages/agent/src/sandbox-policy.ts:187`).

`isWithin` needs both sides in canonical absolute forward-slash form (`packages/agent/src/sandbox-policy.ts:198`). `buildSandboxPolicy` enforces the separator half, because it runs everything through `canonicalPolicyPath` (`packages/agent/src/sandbox-policy.ts:198`). The absolute half is still a convention. The choice to fold case belongs to the caller (`packages/agent/src/sandbox-policy.ts:198`). On Windows and macOS this comparison is too strict: `.GIT/config` slips past a `.git` root (`packages/agent/src/sandbox-policy.ts:198`). `decideWrite` takes the platform's answer instead (`packages/agent/src/sandbox-policy.ts:198`).

### The resolver: five outcomes

`packages/tools/src/sandbox/index.ts` turns one policy into one run: a program, its arguments, and the status of what confines it (`packages/tools/src/sandbox/index.ts:168`).

A resolution has five outcomes, not two (`packages/tools/src/sandbox/index.ts:1`). They are `native`, `appcontainer`, `simulated`, `unavailable`, and `unconfined` (`packages/tools/src/sandbox/index.ts:247`). `appcontainer` is the Windows back end, and it is not an argv wrapper: the confinement is the child process's own token. The AppContainer package SID comes from the workspace, and an ACL grant covers the writable roots. The child starts through FFI in `appcontainer.ts`. The code reaches this outcome only with the network axis enabled (`packages/tools/src/sandbox/index.ts:1`, `packages/tools/src/sandbox/index.ts:187`).

The last three outcomes all mean "not confined by this layer", and the distinction exists for the report, not for the argv (`packages/tools/src/sandbox/index.ts:1`). An unavailable back end still runs the command. A refusal of every command on a machine that never installed bubblewrap is a worse failure than an unconfined one (`packages/tools/src/sandbox/index.ts:1`). A collapse of the outcomes makes a simulated run read as a real one (`packages/tools/src/sandbox/index.ts:1`).

The `reason` field on a resolution has no production reader. Both production readers, `operations.ts` and `background.ts`, test `kind` alone (`packages/tools/src/sandbox/index.ts:4`). The sentence a user reads about a back end comes from `describeSandboxBackend` on the same two inputs, and `/permissions` is its one caller. The disclosure follows from those inputs, so it is not absent (`packages/tools/src/sandbox/index.ts:4`).

`SandboxExecution` is what a caller spawns: the program, its arguments, and the policy (`packages/tools/src/sandbox/index.ts:19`). The argv replaces nothing: the builder appends the shell and its arguments after `--` (`packages/tools/src/sandbox/index.ts:19`). The wrapper wraps the shell, and a `bash -c` re-execs, so background jobs escape the wrapper (`packages/tools/src/sandbox/index.ts:19`). Both translators emit the command last, after `--` (`packages/tools/src/sandbox/index.ts:19`).

`SandboxResolution` has an `appcontainer` variant (`packages/tools/src/sandbox/index.ts:36`). It carries the workspace the profile derives from, and `grantRoots`: every root the ACL grant must cover. The workspace leads the list, and each path appears once (`packages/tools/src/sandbox/index.ts:36`). A real session names the home caches and the temp directory there. An un-granted container child cannot write any of them (`packages/tools/src/sandbox/index.ts:36`).

The code carries the list and does not derive it twice, because two spawn paths must give one answer (`packages/tools/src/sandbox/index.ts:36`). Its network flag is `true` always, because this branch runs only with the network axis enabled (`packages/tools/src/sandbox/index.ts:187`).

`ResolveSandboxOptions` injects the two probes (`packages/tools/src/sandbox/index.ts:59`). The caller injects `hasNativeBackend` so tests reach every branch on any machine (`packages/tools/src/sandbox/index.ts:59`). The caller injects `hasAppContainer` because a pair of DLL loads breaks purity, and its default of false follows the safe direction. A wrong `true` sends a command down a container path whose profile and grant were never established. A wrong `false` is the simulated status quo (`packages/tools/src/sandbox/index.ts:59`).

The caller injects `exists` and the code consults it for two decisions: the `missingPathBehavior` filter and the bwrap protected path (`packages/tools/src/sandbox/index.ts:59`).

`policyFor` accepts writable roots and used to drop them on the floor: every caller got a policy without them (`packages/tools/src/sandbox/index.ts:105`). That failure was narrower than requested, not a leak, but the root user was told the root was writable when it was not (`packages/tools/src/sandbox/index.ts:105`). The type still allowed the argument, so no error pointed at the loss (`packages/tools/src/sandbox/index.ts:105`).

`hasNativeSandboxBackend` answers false on Windows, and that does not change in this build (`packages/tools/src/sandbox/index.ts:117`). The two ways to change it are a helper program with a Windows service, or an MXC container runner. The user ruled both out (`packages/tools/src/sandbox/index.ts:117`). `nativeSandboxProgram` names the program for a platform: `sandbox-exec` on macOS, `bwrap` on Linux (`packages/tools/src/sandbox/index.ts:123`). `detectNativeBackend` treats `sandbox-exec` as present, because its fixed absolute path is part of the OS, and scans `PATH` for `bwrap`. "Not installed here" is a real state (`packages/tools/src/sandbox/index.ts:128`, `packages/tools/src/sandbox/index.ts:130`).

`SandboxRuntime.hasAppContainer` means whether production picks the container path, not whether it can load. The back end works: the profile spawns, the ACL grant holds, and the kernel refuses a write beyond the grant. The session toolchain does not work inside it (`packages/tools/src/sandbox/index.ts:141`).

A confined child's token runs only what the grant names its package SID. `System32` does. `git`, `node`, and `bun` from `D:\Program Files` and the user profile come back `not recognized`, and an absolute path gives `Access is denied`. A copy inside the granted workspace runs, and that is what separates the two cases (`packages/tools/src/sandbox/index.ts:141`).

To pick the back end for production confines every default-mode command into something that cannot run `git status` (`packages/tools/src/sandbox/index.ts:141`). The README line "simulated on Windows" stays true until the toolchain reaches the child. `sandbox-wiring.test.ts` drives the container branch with an injected flag (`packages/tools/src/sandbox/index.ts:141`).

`detectRuntime` does one `PATH` scan at construction (`packages/tools/src/sandbox/index.ts:159`). It deliberately does not probe AppContainer (`packages/tools/src/sandbox/index.ts:159`). `appContainerAvailable` stays exported as the honest, narrower answer tests ask about (`packages/tools/src/sandbox/index.ts:159`).

### The order inside the resolver

`resolveSandboxExecution` takes `hasNativeBackend` as a parameter so every branch is reachable on any machine (`packages/tools/src/sandbox/index.ts:168`). A real caller passes the probe result, and `sandbox-wiring.test.ts` asserts that both call sites pass it. An earlier comment named `operations.test.ts`, a file that never existed (`packages/tools/src/sandbox/index.ts:168`).

`danger-full-access` short-circuits first (`packages/tools/src/sandbox/index.ts:174`). The mode is not a sandbox with a very wide allow list. It is the absence of one (`packages/tools/src/sandbox/index.ts:174`). The network half does not change it, and the reason string is not the old one.

The old text claimed the problem only touched this branch (`packages/tools/src/sandbox/index.ts:174`). In fact `workspace-write` with a restricted network reaches `--unshare-net` or a deny-default profile today, with the same result (`packages/tools/src/sandbox/index.ts:174`). The command's only route to the proxy is loopback, and both of those take loopback away (`packages/tools/src/sandbox/index.ts:174`). That situation is what a restricted network means on a native back end (`packages/tools/src/sandbox/index.ts:174`).

One change was deliberately not made: the removal of the OS denial so the proxy becomes the boundary. That change turns restricted from "the kernel denies" into "the proxy program can ignore" (`packages/tools/src/sandbox/index.ts:174`). To get both properties at once needs a bridge that routes, such as a Unix socket forwarder, and this build ships none (`packages/tools/src/sandbox/index.ts:174`).

The `exists` predicate answers three questions on the same machine (`packages/tools/src/sandbox/index.ts:180`). The resolver drops an absent entry marked `skip` before the translators see it. The AppContainer grant list drops it for the same reason: a grant on an absent path fails (`packages/tools/src/sandbox/index.ts:180`). The resolver keeps an absent protected path, and it becomes an empty read-only mount. A drop of it quietly removes protection (`packages/tools/src/sandbox/index.ts:180`).

The AppContainer branch sits after the short-circuit and before the `hasNativeBackend` check, which answers false on win32 (`packages/tools/src/sandbox/index.ts:187`). Its conditions are win32, `policy.network === "enabled"`, and `hasAppContainer` (`packages/tools/src/sandbox/index.ts:187`). The tests measured the reason for the network condition. A proxy that listens on loopback enforces a restricted network, and a container child cannot reach loopback even with `privateNetworkClientServer`. A confinement of a restricted command breaks its network. An enabled network starts no proxy and needs no loopback (`packages/tools/src/sandbox/index.ts:187`).

Inside the branch, the workspace is the first `write` entry without the skip marker (`packages/tools/src/sandbox/index.ts:187`). The grants cover every writable root, not only the workspace, which is the real session shape. `policyFor` fixed that half-grant failure once (`packages/tools/src/sandbox/index.ts:187`). The workspace leads the list because the profile and its refcount derive from it (`packages/tools/src/sandbox/index.ts:187`). Read-only roots are absent on purpose: the child reads outside the grant by default, and the policy refuses only writes (`packages/tools/src/sandbox/index.ts:187`). The builder reads the grant list from the filtered present entries, because a skip-marked absent root fails the grant (`packages/tools/src/sandbox/index.ts:187`).

The simulated fallback is the default case (`packages/tools/src/sandbox/index.ts:204`). `installed` is `options.hasNativeBackend ?? true` (`packages/tools/src/sandbox/index.ts:212`). It defaults to installed. A guess of "not installed" produces `unavailable` and no wrapper, which is fail-open. A guess of "installed" gives a spawn error, which is the fail-closed side, the correct one.

No production caller reaches the default: `packages/tools/src/operations.ts:471` passes the runtime value (`packages/tools/src/sandbox/index.ts:212`). The `unavailable` return is its own outcome, and the command still runs (`packages/tools/src/sandbox/index.ts:216`).

The program and its arguments are named in this one place and nowhere else (`packages/tools/src/sandbox/index.ts:226`). The program is absolute for `sandbox-exec`, because `PATH` resolution is how a wrapper gets substituted (`packages/tools/src/sandbox/index.ts:226`). Only bwrap gets the `exists` predicate (`packages/tools/src/sandbox/index.ts:226`). An absent protected path is harmless under seatbelt: a subpath filter that matches no file grants nothing (`packages/tools/src/sandbox/index.ts:226`).

`presentEntries` exists because both translators are pure and both say so (`packages/tools/src/sandbox/index.ts:235`). A comment that names a contract the caller has not carried out is worse than no comment (`packages/tools/src/sandbox/index.ts:235`). On Linux the filter is not cosmetic: bwrap fails on an absent `--bind` source (`packages/tools/src/sandbox/index.ts:235`). The builder leaves entries not marked `skip` alone, because a nonexistent workspace is a broken session (`packages/tools/src/sandbox/index.ts:235`).

`SandboxBackend` has four values, not three: `simulated` and `appcontainer` cannot share a name (`packages/tools/src/sandbox/index.ts:247`, `packages/tools/src/sandbox/index.ts:249`). A string cannot narrow after the fact (`packages/tools/src/sandbox/index.ts:249`). `sandboxBackendFor` is a function of the platform, so "Linux without bubblewrap" is reachable from any test (`packages/tools/src/sandbox/index.ts:251`). Its default of false follows the safe direction (`packages/tools/src/sandbox/index.ts:253`).

### Network confinement, reported

`networkConfinement` in `packages/tools/src/sandbox/index.ts` derives a five-way answer from the same two inputs (`packages/tools/src/sandbox/index.ts:263`). Its order is the whole function (`packages/tools/src/sandbox/index.ts:265`):

1. `network === "enabled"` gives `network-left-open`.
2. `danger-full-access` gives `filesystem-axis-off`.
3. A native back end gives `os-namespace`, `unavailable` gives `backend-missing`, and anything else gives `no-os-backend`.

An unreported back end reads as the weakest answer (`packages/tools/src/sandbox/index.ts:265`). The appcontainer backend joins `no-os-backend` on the restricted axis, for a measured reason. The resolver's container branch is reachable only with the enabled axis. A restricted command therefore resolves simulated and runs on the proxy (`packages/tools/src/sandbox/index.ts:265`).

`describeSandboxBackend` writes the user sentence per case, not one hedged sentence for all of them (`packages/tools/src/sandbox/index.ts:280`). The code treats an undefined back end as simulated, since there is nothing to point at (`packages/tools/src/sandbox/index.ts:280`). The code asks `danger-full-access` first, because it is true in all three back-end cases (`packages/tools/src/sandbox/index.ts:280`).

The native case makes a write-only claim (`packages/tools/src/sandbox/index.ts:294`). Both back ends start from an already-readable baseline: bwrap with `--ro-bind / /`, seatbelt with `(allow file-read*)` (`packages/tools/src/sandbox/index.ts:294`). The string describes the mode, not the policy. `Reads are unrestricted` is one mechanism's answer under the other's name (`packages/tools/src/sandbox/index.ts:294`).

The claim that the back end refuses every write to version-control metadata holds for every policy `buildSandboxPolicy` produces. `protectedFor` adds `join(root, ".git")` for every writable root unconditionally, and the scan only ever adds more (`packages/tools/src/sandbox/index.ts:294`). The `danger-full-access` early return is the one branch with an empty protected list, and it never reaches this case (`packages/tools/src/sandbox/index.ts:294`). The process-tree sentence is a different claim from the open `mv` question in the bwrap header (`packages/tools/src/sandbox/index.ts:294`).

The appcontainer case does not repeat the `.git` promise, because the deny ACE is out until the anomaly is understood (`packages/tools/src/sandbox/index.ts:300`). A confined command can write `.git` inside its grant. Only the tool layer refuses it (`packages/tools/src/sandbox/index.ts:300`). The fixed string states the restricted-axis gap, because the function is not handed the axis (`packages/tools/src/sandbox/index.ts:300`).

The simulated case is the default, and its string embeds `SIMULATED_SANDBOX_DISCLAIMER` (`packages/tools/src/sandbox/index.ts:308`). "Calls that arrive through the tools" means the Write and Edit tools, not Bash (`packages/tools/src/sandbox/index.ts:308`). Bash builds the same policy and hands it to `exec`, which drops it unread when the resolution is not native (`packages/tools/src/sandbox/index.ts:308`).

### The workspace policy

`workspace-policy.ts` is the one place that builds the workspace `SandboxPolicy` (`packages/tools/src/sandbox/workspace-policy.ts:1`). Bash and the file tools ask the same question and get the same answer. Two builders mean one refusal in one tool and a success in the other (`packages/tools/src/sandbox/workspace-policy.ts:1`).

`protectedPathsFor` re-derives `.git` on every call (`packages/tools/src/sandbox/workspace-policy.ts:8`). This was a cache, and the cache was the hole (`packages/tools/src/sandbox/workspace-policy.ts:8`).

The sequence: Bash runs `mv /w/repo/sub /w/repo/relocated`. The cached list still names the old path. A later spawn re-derives, `exists` is false, and the protection lands nowhere. `/w/repo/relocated/.git` receives no mount, and the write succeeds (`packages/tools/src/sandbox/workspace-policy.ts:8`). Both steps must happen. Neither alone is enough (`packages/tools/src/sandbox/workspace-policy.ts:8`).

### Windows: the simulated layer

`simulated.ts` is the Windows filesystem sandbox that is not a sandbox, and says so (`packages/tools/src/sandbox/simulated.ts:1`). It is not OS-level enforcement, and a subprocess outside the tools is not subject to it (`packages/tools/src/sandbox/simulated.ts:1`). A result from it reads as `the Write or Edit tool call was refused by this process` (`packages/tools/src/sandbox/simulated.ts:1`). It never reads as a claim that the write was impossible (`packages/tools/src/sandbox/simulated.ts:1`).

The header used to also claim there was nowhere else to go (`packages/tools/src/sandbox/simulated.ts:1`). It said real Windows confinement "compiles two helper binaries and registers a Windows service" (`packages/tools/src/sandbox/simulated.ts:1`). It also said there is "no user-mode equivalent of macOS seatbelt" (`packages/tools/src/sandbox/simulated.ts:1`). The first half is about one design. The second half was false in the expensive direction: it named a capability as absent that exists (`packages/tools/src/sandbox/simulated.ts:1`).

The Windows SDK 10.0.26100.0 headers confirmed the claim: `CreateAppContainerProfile` at `userenv.h:1398`, `DeriveAppContainerSidFromAppContainerName` at `userenv.h:1550`, `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` at `WinBase.h:3591`, and `SECURITY_CAPABILITIES` at `winnt.h:12671` (`packages/tools/src/sandbox/simulated.ts:1`). The SDK documents them all as user-mode, with no driver, service, or elevation needed (`packages/tools/src/sandbox/simulated.ts:1`). The kernel checks an AppContainer child's package SID on every file access, which is a real write boundary (`packages/tools/src/sandbox/simulated.ts:1`). What is absent is not the mechanism and not the connection (`packages/tools/src/sandbox/simulated.ts:1`).

`appcontainer.ts` holds the whole back end, from the profile lifecycle to the confined spawn and the refcounted ACL grant (`packages/tools/src/sandbox/simulated.ts:1`). The resolver has the branch, and the exec consumer grants before the spawn and releases in a `finally` (`packages/tools/src/sandbox/simulated.ts:1`). The tests run all of it for real on Windows (`packages/tools/src/sandbox/simulated.ts:1`). The reason production stays off it comes from measurements, not caution (`packages/tools/src/sandbox/simulated.ts:1`).

A confined child's token runs only what the grant names its package SID (`packages/tools/src/sandbox/simulated.ts:1`). `git`, `node`, and `bun` live outside every grant on this machine (`packages/tools/src/sandbox/simulated.ts:1`). The branch confines every default-mode command into something that cannot run `git status` (`packages/tools/src/sandbox/simulated.ts:1`). The branch is reachable from a test that injects the flag, and `SandboxRuntime.hasAppContainer` carries the full measurement (`packages/tools/src/sandbox/simulated.ts:1`).

Measured on this machine (2026-10-09, no elevation, no helper binary): create, derive, and delete succeed (`packages/tools/src/sandbox/simulated.ts:1`). Derivation is a pure function of the name, so the grant names the same SID that the next run derives again (`packages/tools/src/sandbox/simulated.ts:1`). One `(OI)(CI)(F)` allow ACE gives the confined child read and write on the subtree and nothing outside (`packages/tools/src/sandbox/simulated.ts:1`). ### The network policy

`packages/agent/src/network-policy.ts` decides which hosts a confined command may reach (`packages/agent/src/network-policy.ts:1`). The decision is pure, like `sandbox-policy.ts` next door (`packages/agent/src/network-policy.ts:3`). The proxy that enforces it is the only part that touches a socket (`packages/agent/src/network-policy.ts:3`). So a test can assert the decision on any machine, the Windows development machine included (`packages/agent/src/network-policy.ts:3`). The shape is a table of host pattern to `allow` or `deny` (`packages/agent/src/network-policy.ts:3`). This build leaves out the pieces it does not have rather than write stubs: unix sockets, remote config, and MITM (`packages/agent/src/network-policy.ts:3`).

This file states once what the word `enforced` means here (`packages/agent/src/network-policy.ts:3`). This file decides what the proxy allows (`packages/agent/src/network-policy.ts:3`). It does not stop a program that opens a socket and ignores the proxy environment (`packages/agent/src/network-policy.ts:3`). `HTTP_PROXY` is a convention that most developer tools honour, not a kernel boundary (`packages/agent/src/network-policy.ts:3`). Where the platform has one, the OS sandbox is what closes that gap, and the two layers stay distinct rather than confused (`packages/agent/src/network-policy.ts:3`).

The cases, per platform (`packages/agent/src/network-policy.ts:3`):

- macOS and Linux with `enabled`: the OS confines the filesystem and leaves the network open (`packages/agent/src/network-policy.ts:3`). The proxy is still the whole of the network boundary (`packages/agent/src/network-policy.ts:3`). A program that ignores the environment gets out, and the report says `network-left-open` rather than a kernel-held line (`packages/agent/src/network-policy.ts:3`).
- macOS and Linux with `restricted`: the OS denies the command every route off the machine (`packages/agent/src/network-policy.ts:3`). This is not loopback only, and that difference is worth a plain sentence (`packages/agent/src/network-policy.ts:3`). The seatbelt profile starts from `(deny default)` and adds no network rule at all (`seatbelt.ts`) (`packages/agent/src/network-policy.ts:3`). `--unshare-net` puts the command in an empty network namespace (`bwrap.ts`) (`packages/agent/src/network-policy.ts:3`). The effect is the opposite of what the setting sounds like (`packages/agent/src/network-policy.ts:3`). The proxy is unreachable from the shell too (`packages/agent/src/network-policy.ts:3`). So this domain list governs the web tools, which fetch in this process (`packages/agent/src/network-policy.ts:3`). It does not govern a command run through Bash (`packages/agent/src/network-policy.ts:3`). A shell command reaches nothing, allowed or denied (`packages/agent/src/network-policy.ts:3`).
- Windows: there is no such back end, so this file and the proxy are the whole of the network story (`packages/agent/src/network-policy.ts:3`). `/permissions` and `/doctor` say so rather than paper over it, for the same reason the filesystem half does (`packages/agent/src/network-policy.ts:3`).

That middle bullet used to say the code narrowed the profile to loopback, so only the proxy was reachable (`packages/agent/src/network-policy.ts:3`). No code did that, on either platform, and the sentence described a design rather than the build (`packages/agent/src/network-policy.ts:3`). A seatbelt profile narrowed to loopback is expressible (`packages/agent/src/network-policy.ts:3`). The equivalent is not available for `--unshare-net` (`packages/agent/src/network-policy.ts:3`). That namespace has no route to the host's loopback at all without a bridge in user space (`packages/agent/src/network-policy.ts:3`).

A loopback-narrowed macOS profile beside an unreachable-proxy Linux one is two behaviours under one setting (`packages/agent/src/network-policy.ts:3`). So the code does neither, and the setting means what it does (`packages/agent/src/network-policy.ts:3`).

### The network proxy

`packages/tools/src/sandbox/proxy.ts` is a local HTTP and SOCKS5 proxy that refuses what the domain policy refuses (`packages/tools/src/sandbox/proxy.ts:1`). It is the part of the network axis that touches a socket, and the decision it enforces is a pure function in `@labunbun/agent` (`packages/tools/src/sandbox/proxy.ts:3`). Every connection goes through one gate, `decideUpstream`, the address blocklist and then the domain rules, before the code opens an upstream socket (`packages/tools/src/sandbox/proxy.ts:3`). That order is the property that makes this a filter rather than a logger (`packages/tools/src/sandbox/proxy.ts:3`).

No MITM, deliberately (`packages/tools/src/sandbox/proxy.ts:3`). An `https://` URL reaches this proxy as `CONNECT host:443` followed by a byte pipe (`packages/tools/src/sandbox/proxy.ts:3`). The proxy sees the hostname and then stops (`packages/tools/src/sandbox/proxy.ts:3`). That is exactly the trade this build makes: it can refuse a destination, and it cannot read the traffic (`packages/tools/src/sandbox/proxy.ts:3`).

The other option is a locally generated CA with a man-in-the-middle in front of it (`packages/tools/src/sandbox/proxy.ts:3`). It buys content checks and costs the user a certificate in their trust store that whoever gets one file write can use (`packages/tools/src/sandbox/proxy.ts:3`). The trade is not made, and that is in the plan's not-delivered list (`packages/tools/src/sandbox/proxy.ts:3`). It is a real limitation, not an oversight (`packages/tools/src/sandbox/proxy.ts:3`). A domain on the allow list can exfiltrate through a request this proxy cannot read (`packages/tools/src/sandbox/proxy.ts:3`).

What this does not stop (`packages/tools/src/sandbox/proxy.ts:3`). Proxy environment variables are a convention (`packages/tools/src/sandbox/proxy.ts:3`). A program that calls `connect` and ignores them is not routed here and is subject to no rule in this file (`packages/tools/src/sandbox/proxy.ts:3`). Where an OS sandbox back end is actually installed, it closes that gap (`packages/tools/src/sandbox/proxy.ts:3`). Where none is, on Windows or on Linux without bubblewrap, nothing in this build does (`packages/tools/src/sandbox/proxy.ts:3`). `describeNetworkPolicy` says so per case rather than in a footnote nobody reads (`packages/tools/src/sandbox/proxy.ts:3`).

Two ports, because the tools differ (`packages/tools/src/sandbox/proxy.ts:3`). `HTTP_PROXY` and `HTTPS_PROXY` speak the HTTP proxy protocol, and `ALL_PROXY` speaks SOCKS5 (`packages/tools/src/sandbox/proxy.ts:3`). Both point at the same decision (`packages/tools/src/sandbox/proxy.ts:3`). A client handed only one of them is a client this proxy cannot filter (`packages/tools/src/sandbox/proxy.ts:3`). So both start together rather than one as an option (`packages/tools/src/sandbox/proxy.ts:3`).

The SOCKS5 reply codes are `0x00` success, `0x02` refused, and `0x07` command unsupported, from RFC 1928 §6 (`packages/tools/src/sandbox/proxy.ts:17`). The refused code is the policy answer, and the proxy is CONNECT only, so `0x07` answers any other command (`packages/tools/src/sandbox/proxy.ts:20`).

`socksReply` writes a complete ten-byte reply whole, not from a placeholder and a `subarray` (`packages/tools/src/sandbox/proxy.ts:25`). The assembled version shipped one byte too long, because the placeholder's own VER survived into the middle (`packages/tools/src/sandbox/proxy.ts:25`). The extra byte sat in the client's read buffer (`packages/tools/src/sandbox/proxy.ts:25`). Everything the tunnel then carried was off by one byte (`packages/tools/src/sandbox/proxy.ts:25`). It answered every reply test correctly, because those tests read the first ten bytes (`packages/tools/src/sandbox/proxy.ts:25`).

`NetworkProxyOptions` holds the inputs (`packages/tools/src/sandbox/proxy.ts:30`). They are the network mode behind the decision, the domain table, the loopback host to bind on, and the connect timeout (`packages/tools/src/sandbox/proxy.ts:31`). An empty table is meaningful under `restricted`, where it reaches nothing (`packages/tools/src/sandbox/proxy.ts:33`). The host is overridable so a test can pick a free port (`packages/tools/src/sandbox/proxy.ts:35`). The connect timeout gives up on an upstream that has not answered `connect` in that time (`packages/tools/src/sandbox/proxy.ts:37`).

`isBlockedHost` is injectable for one narrow reason (`packages/tools/src/sandbox/proxy.ts:39`). A test that wants to watch an allowed connection happen has to connect somewhere (`packages/tools/src/sandbox/proxy.ts:40`). An injection point lets those tests run against a stand-in, and the real table stays on (`packages/tools/src/sandbox/proxy.ts:40`). The tests that pin the real table deliberately do not pass this option (`packages/tools/src/sandbox/proxy.ts:40`).

`decideUpstream` is the one gate, and every upstream connection in the file goes through it (`packages/tools/src/sandbox/proxy.ts:45`). It runs the address blocklist before the domain rules rather than after (`packages/tools/src/sandbox/proxy.ts:45`). The order is the whole point (`packages/tools/src/sandbox/proxy.ts:45`). The rules are a user's configuration, and a user can write `*` (`packages/tools/src/sandbox/proxy.ts:45`). That pattern answers `allowed: true` for `127.0.0.1` and for `169.254.169.254` (`packages/tools/src/sandbox/proxy.ts:45`). A client that cannot read the reason for its refusal says connection failed (`packages/tools/src/sandbox/proxy.ts:171`). The one line here is the difference between two users (`packages/tools/src/sandbox/proxy.ts:173`). One user knows their allow list lacks a domain, and the other thinks the network is down (`packages/tools/src/sandbox/proxy.ts:174`). On an allow it splits `host:port`, opens the upstream, answers `200 Connection Established`, writes the head if the client sent any, and pipes both ways (`packages/tools/src/sandbox/proxy.ts:180`). A port that is absent defaults to 443 (`packages/tools/src/sandbox/proxy.ts:180`).

`handleHttp` answers absolute-form requests, the shape `HTTP_PROXY` clients use (`packages/tools/src/sandbox/proxy.ts:188`). A request in origin-form reaches this listener when the client does use a proxy (`packages/tools/src/sandbox/proxy.ts:188`). That client wrote the request line in the direct form, or connected here by hand (`packages/tools/src/sandbox/proxy.ts:188`). It is not a URL this can place, so `new URL` throws and it fails as a malformed host (`packages/tools/src/sandbox/proxy.ts:188`). That failure is right, because there is no host to decide against and to invent one is the dangerous move (`packages/tools/src/sandbox/proxy.ts:188`).

It is worth care about what bounds such a client, because the obvious answer is wrong on two of three platforms (`packages/tools/src/sandbox/proxy.ts:188`). A client that ignores `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY` does not reach this listener at all (`packages/tools/src/sandbox/proxy.ts:188`). It opens its own socket, and this proxy is not in that path (`packages/tools/src/sandbox/proxy.ts:188`). Where an OS sandbox back end is actually installed, it closes that gap (`packages/tools/src/sandbox/proxy.ts:188`). Where none is, on Windows or on Linux without bubblewrap, nothing in this build does, and the connection is simply direct (`packages/tools/src/sandbox/proxy.ts:188`). The file says so at the top, and this paragraph used to imply the opposite without a platform qualifier (`packages/tools/src/sandbox/proxy.ts:188`).

The client sent the proxy's own `Host`, and the origin needs its own (`packages/tools/src/sandbox/proxy.ts:204`). The upstream request carries the target hostname, its port or 80, the method, and the path with its query (`packages/tools/src/sandbox/proxy.ts:198`). The headers carry that origin's own `Host` (`packages/tools/src/sandbox/proxy.ts:205`). The proxy relays the response with its status code, or 502 when there is none (`packages/tools/src/sandbox/proxy.ts:208`). An upstream error answers 502 as well (`packages/tools/src/sandbox/proxy.ts:212`).

`splitHostPort` keeps an unbracketed IPv6 literal intact (`packages/tools/src/sandbox/proxy.ts:220`). To split at the first colon is the one line of code that turns `::1` into an empty host (`packages/tools/src/sandbox/proxy.ts:220`). The code then refuses that host as malformed (`packages/tools/src/sandbox/proxy.ts:220`). That is a fail-closed accident rather than a decision (`packages/tools/src/sandbox/proxy.ts:220`). It is the kind of accident that gets fixed later by someone who reads the failure as the bug (`packages/tools/src/sandbox/proxy.ts:220`).

`handleSocks` runs the SOCKS5 handshake in RFC 1928 order (`packages/tools/src/sandbox/proxy.ts:234`). The server offers only no-authentication, because this proxy authenticates nothing and a client told to offer more has nothing to offer (`packages/tools/src/sandbox/proxy.ts:243`). The code checks the first message for the version and for the no-authentication method (`packages/tools/src/sandbox/proxy.ts:247`). A command other than CONNECT gets the command-unsupported reply and the end of the connection (`packages/tools/src/sandbox/proxy.ts:255`). The code reads the address by its type octet: four bytes, a length byte with a name, or 16 bytes (`packages/tools/src/sandbox/proxy.ts:260`). The port is two big-endian bytes (`packages/tools/src/sandbox/proxy.ts:261`).

The reply to a policy refusal is a code with no reason attached, and that is the protocol rather than an oversight (`packages/tools/src/sandbox/proxy.ts:265`). RFC 1928's reply carries a code and nothing else (`packages/tools/src/sandbox/proxy.ts:266`). So a blocked address, a denied domain, and an unmatched allow rule are one byte apart to a SOCKS client (`packages/tools/src/sandbox/proxy.ts:267`). `handleConnect` answers in a header because HTTP has somewhere to put it (`packages/tools/src/sandbox/proxy.ts:268`).

On success the upstream opens, the reader releases, the success reply goes out, and both pipes start (`packages/tools/src/sandbox/proxy.ts:275`). The reader's `data` listener has to go first (`packages/tools/src/sandbox/proxy.ts:276`). Otherwise a handshake that already finished buffers the tunnel bytes, while `pipe` tries to read the same bytes (`packages/tools/src/sandbox/proxy.ts:277`). The catch path releases the reader before it rethrows (`packages/tools/src/sandbox/proxy.ts:284`).

`byte` reads one byte of a wire buffer, or throws (`packages/tools/src/sandbox/proxy.ts:290`). `noUncheckedIndexedAccess` makes every index into a `Buffer` a `number | undefined` (`packages/tools/src/sandbox/proxy.ts:290`). This file reads a protocol whose whole job is to fail on a malformed message (`packages/tools/src/sandbox/proxy.ts:290`). The three ways out of that are all worse than a throw (`packages/tools/src/sandbox/proxy.ts:290`).

One is an `!` the linter forbids (`packages/tools/src/sandbox/proxy.ts:290`). One is a `?? 0` that turns a truncated first message into a plausible one (`packages/tools/src/sandbox/proxy.ts:290`). One is a comparison against `undefined` that quietly does the right thing for every value except its intended one (`packages/tools/src/sandbox/proxy.ts:290`).

`uint16` reads two bytes big-endian, for the same reason and as its only use (`packages/tools/src/sandbox/proxy.ts:297`). `readAddress` reads the destination in whichever of the three address forms the client used (`packages/tools/src/sandbox/proxy.ts:302`).

`formatIpv6` writes the eight groups as a hostname, with the longest run of zeros collapsed to `::` per RFC 5952 (`packages/tools/src/sandbox/proxy.ts:311`). A run has to be two or more to take that form (`packages/tools/src/sandbox/proxy.ts:312`). A `::` that stands for one zero group is a different string (`packages/tools/src/sandbox/proxy.ts:313`).

`byteReader` keeps one `data` listener for the whole handshake (`packages/tools/src/sandbox/proxy.ts:340`). To attach and remove a listener per read looks equivalent and is not (`packages/tools/src/sandbox/proxy.ts:340`). With no listener attached the socket keeps whatever its buffer already holds (`packages/tools/src/sandbox/proxy.ts:340`). The socket drops bytes that arrive in the gap between two awaits (`packages/tools/src/sandbox/proxy.ts:340`).

The first SOCKS5 message is 2+N+method bytes sent in one write (`packages/tools/src/sandbox/proxy.ts:340`). The gap is exactly where the rest of that message is (`packages/tools/src/sandbox/proxy.ts:340`). `release()` removes the listener before it hands the socket to `pipe`, which is the other half of the same hazard (`packages/tools/src/sandbox/proxy.ts:340`).

The code annotates the buffer and does not infer it (`packages/tools/src/sandbox/proxy.ts:342`). `Buffer.alloc` narrows to a buffer over `ArrayBuffer`, and the `data` event hands over the wider `Buffer` type (`packages/tools/src/sandbox/proxy.ts:344`). Without the annotation the first concatenation does not type-check (`packages/tools/src/sandbox/proxy.ts:343`).

In `flush` the code has to read the waiter from the queue before it removes the waiter (`packages/tools/src/sandbox/proxy.ts:358`). An ask for `waiters[0]` again after the shift answers for the next caller (`packages/tools/src/sandbox/proxy.ts:359`). The loop form with a `break` replaces a condition on `waiters[0].count`, because that index is optional under `noUncheckedIndexedAccess` (`packages/tools/src/sandbox/proxy.ts:361`). The only other ways to use it are an assertion the linter forbids or a default that answers 0 for an empty queue (`packages/tools/src/sandbox/proxy.ts:362`).

`fail` drains the queue with a splice rather than a shift loop (`packages/tools/src/sandbox/proxy.ts:372`). So the loop variable is the waiter itself, the value that needs the rejection (`packages/tools/src/sandbox/proxy.ts:373`). A client that closes the socket during the handshake rejects every waiter with `client closed during the SOCKS5 handshake` (`packages/tools/src/sandbox/proxy.ts:382`).

`openUpstream` opens the upstream socket for an allowed destination, with a connect deadline (`packages/tools/src/sandbox/proxy.ts:403`). A timeout destroys the socket and rejects with `connecting to HOST:PORT timed out` (`packages/tools/src/sandbox/proxy.ts:412`).

`ListeningServer` is what `http.Server` and `net.Server` share, and all this file calls on either (`packages/tools/src/sandbox/proxy.ts:422`). To declare it structurally is what lets the SOCKS5 listener be a `net.Server` (`packages/tools/src/sandbox/proxy.ts:422`). No helper above needs a union or a cast for it (`packages/tools/src/sandbox/proxy.ts:422`). The event methods come from `EventEmitter` rather than from a long list in the declaration (`packages/tools/src/sandbox/proxy.ts:422`). A hand-written `on(event: string, ...)` is not assignable from Node's typed overloads (`packages/tools/src/sandbox/proxy.ts:422`).

`listen` binds on port 0 and the given host, and `portOf` reads the port back from the address (`packages/tools/src/sandbox/proxy.ts:429`). An address of `null` or a string throws, because the server did not report a port (`packages/tools/src/sandbox/proxy.ts:439`). `trackServer` accepts connections onto the live set so `close` can drop them (`packages/tools/src/sandbox/proxy.ts:448`). `closed` turns the server's close callback into a promise (`packages/tools/src/sandbox/proxy.ts:455`). `close` destroys every live socket and waits for both servers to close (`packages/tools/src/sandbox/proxy.ts:151`).

## Why it is like this

- **Why the policy is a value and not a mechanism.** The filesystem and network halves are separate data (`packages/agent/src/sandbox-policy.ts:3`). Three translators read it, and the platform picks which one runs (`packages/agent/src/sandbox-policy.ts:3`). A test can assert what a mode means without a spawn (`packages/agent/src/sandbox-policy.ts:3`).
- **Why the network half is a proxy on all three platforms.** The proxy sees the hostname and then stops, because it can refuse a destination and cannot read the traffic (`packages/tools/src/sandbox/proxy.ts:3`). A locally generated CA buys content checks and costs a certificate in the user's trust store (`packages/tools/src/sandbox/proxy.ts:3`).
- **Why the two halves are layered rather than merged.** Where a native back end exists, it closes the gap the proxy cannot (`packages/agent/src/sandbox-policy.ts:3`). Where one is not, the proxy is the whole of it, and the report says which (`packages/agent/src/sandbox-policy.ts:3`). A mechanism that reads as OS-enforced when it is not is worse than no mechanism (`packages/agent/src/sandbox-policy.ts:5`).
- **Why Windows gets a tool-layer decision.** There is no user-mode equivalent of seatbelt, and the plan rules out a helper program (`packages/agent/src/sandbox-policy.ts:3`). A subprocess that goes around the tools is not subject to that decision (`packages/agent/src/sandbox-policy.ts:3`).
- **Why the blocklist runs before the rules.** A user can write `*`, and that pattern answers `allowed: true` for `127.0.0.1` and for `169.254.169.254` (`packages/tools/src/sandbox/proxy.ts:45`). The blocklist has to be the thing that can still say no (`packages/tools/src/sandbox/proxy.ts:45`).
- **Why `deny` beats `allow` regardless of list order.** The order of the first two rules is the security property (`packages/agent/src/network-policy.ts:288`). A table where a later `allow` rescues an earlier `deny` is order-sensitive in the one direction that matters (`packages/agent/src/network-policy.ts:288`).
- **Why the proxy starts for `enabled` with rules.** Either the mode forbids by default, or the rules narrow something open by default (`packages/agent/src/network-policy.ts:306`). Both are one decision seen from two sides, which is why one function answers (`packages/agent/src/network-policy.ts:306`).
- **Why a confinement answers with a reason and not a boolean.** Four of the five answers are a no, for four different reasons (`packages/agent/src/network-policy.ts:312`). The code owes the user the reason, and it is the reason a user acts on (`packages/agent/src/network-policy.ts:326`).
- **Why one claim string serves four cases.** A reader who sees a differently-worded claim in one case has no way to know it means the same thing (`packages/agent/src/network-policy.ts:326`). Only the reason may differ (`packages/agent/src/network-policy.ts:326`).
- **Why `os-namespace` gets its own detail.** The sentence the other four use is false there (`packages/agent/src/network-policy.ts:350`). A command cannot reach the proxy, so it reaches nothing, allowed host or not (`packages/agent/src/network-policy.ts:354`).
- **Why the web tools are named in the caveat.** The silence about them was an overclaim in its own right (`packages/agent/src/network-policy.ts:366`). It disclosed one bypass and let the reader assume there was not another (`packages/agent/src/network-policy.ts:366`).
- **Why the port clause is stated.** `normalizeHost` strips any `:port` before the rule engine sees it, so a rule cannot tell ports apart (`packages/agent/src/network-policy.ts:354`). A rule that allows a domain allows it on every port, and the sentence says so (`packages/agent/src/network-policy.ts:354`).
- **Why the splitter counts colons.** An unbracketed IPv6 literal has several colons (`packages/agent/src/network-policy.ts:66`). A split at the first colon turns `::1` into an empty host, and the code refuses that host (`packages/agent/src/network-policy.ts:67`).
- **Why the tool keys are pinned rather than stripped.** To strip `PIP_PROXY` removes pip's only proxy setting and sends it out directly, which is the same bypass by the other road (`packages/tools/src/sandbox/proxy.ts:73`). There is no version of that removal that is safe here (`packages/tools/src/sandbox/proxy.ts:73`).
- **Why `NO_PROXY` is empty.** To put `localhost` or `127.0.0.1` there is the conventional thing to do, and it is a documented bypass (`packages/tools/src/sandbox/proxy.ts:85`). An empty value routes even loopback through the decision (`packages/tools/src/sandbox/proxy.ts:85`).
- **Why the ten-byte reply is written whole.** The assembled version shipped one byte too long (`packages/tools/src/sandbox/proxy.ts:25`). The extra byte sat in the client's read buffer (`packages/tools/src/sandbox/proxy.ts:25`).
- **Why one `data` listener covers the handshake.** With no listener attached the socket keeps whatever its buffer already holds (`packages/tools/src/sandbox/proxy.ts:340`). The socket drops bytes that arrive in the gap between two awaits (`packages/tools/src/sandbox/proxy.ts:340`). The first SOCKS5 message is one write, so the gap is exactly where the rest of it is (`packages/tools/src/sandbox/proxy.ts:340`).
- **Why the real blocklist stays on in tests.** A test that wants to watch an allowed connection happen has to connect somewhere (`packages/tools/src/sandbox/proxy.ts:40`). An injection point lets those tests run against a stand-in, and the real table stays on (`packages/tools/src/sandbox/proxy.ts:40`).
- **Why both halves share one address table.** The proxy matcher and the web tools ask the same question (`packages/agent/src/network-policy.ts:96`). One import means no second table for two halves to drift apart over (`packages/agent/src/network-policy.ts:96`).

## Known traps

- `127.0.0.1` has six spellings, and a `deny` rule caught one of them before `canonicalIpLiteral` (`packages/agent/src/network-policy.ts:31`). The other five were `127.0.0.01`, `127.1`, `0177.0.0.1`, `0x7f000001`, and `2130706433` (`packages/agent/src/network-policy.ts:31`).
- The two blocklist halves can disagree about what is loopback. A comment once claimed they agreed, and measurement said the `web.ts` half answered false for the hex spelling (`packages/agent/src/network-policy.ts:115`).
- The `fe80::/10` check read `startsWith("fe80:")`, which is a single /16 of a /10. Seven of the sixteen link-local blocks came back unblocked (`packages/agent/src/network-policy.ts:159`).
- NAT64 prefixes other than the well-known `64:ff9b::/96` are not decoded (`packages/agent/src/network-policy.ts:225`). A deployment that uses one has a real gap (`packages/agent/src/network-policy.ts:225`).
- A user can write `{allow: "*"}` and believe every host is open. `127.0.0.1` and `169.254.169.254` are still refused, and the code `blocked_address` is the clue (`packages/tools/src/sandbox/proxy.ts:45`).
- A rule for a domain covers every port on it, because `normalizeHost` strips the port first (`packages/agent/src/network-policy.ts:354`).
- Seven of the ten per-tool variables are not set, and the same list reads as one gap and is two (`packages/tools/src/sandbox/proxy.ts:64`). Yarn is not checked here, and Bundler is an open question rather than a verdict (`packages/tools/src/sandbox/proxy.ts:64`).
- A client that ignores `HTTP_PROXY` does not reach the proxy at all. It opens its own socket, and only a native back end closes that gap (`packages/tools/src/sandbox/proxy.ts:188`). On Windows, or on Linux without bubblewrap, the connection is direct (`packages/tools/src/sandbox/proxy.ts:188`).
- Under `restricted` with a native back end, the kernel denies the command the proxy as well (`packages/agent/src/network-policy.ts:314`). A command then reaches nothing, even for an allowed host (`packages/agent/src/network-policy.ts:314`). A user who misreads the allowlist sentence expects the opposite (`packages/agent/src/network-policy.ts:314`).
- A port that is absent defaults to 443 on the `CONNECT` path (`packages/tools/src/sandbox/proxy.ts:180`).
- A SOCKS5 refusal carries a code with no reason (`packages/tools/src/sandbox/proxy.ts:266`). A blocked address, a denied domain, and an unmatched allow rule are one byte apart to the client (`packages/tools/src/sandbox/proxy.ts:267`).
- The `data` listener has to go first, or a handshake that already finished buffers the tunnel bytes (`packages/tools/src/sandbox/proxy.ts:276`). `release()` removes the listener before it hands the socket to `pipe`, which is the same hazard from the other side (`packages/tools/src/sandbox/proxy.ts:340`).
- A throw refuses a malformed first message (`packages/tools/src/sandbox/proxy.ts:290`). Three worse options exist (`packages/tools/src/sandbox/proxy.ts:290`). One is an `!` the linter forbids (`packages/tools/src/sandbox/proxy.ts:290`). One is a `?? 0` that turns a truncated first message into a plausible one (`packages/tools/src/sandbox/proxy.ts:290`). One is a comparison against `undefined` (`packages/tools/src/sandbox/proxy.ts:290`).
- An empty `NO_PROXY` looks like a mistake and is the design (`packages/tools/src/sandbox/proxy.ts:85`). A stale lowercase `no_proxy=localhost` from the ambient environment otherwise wins on half the tools (`packages/tools/src/sandbox/proxy.ts:85`).
- Line references inside comments drift when another file changes. The refs in this document were re-derived at the end. The ones inside the source comments are not all current.
