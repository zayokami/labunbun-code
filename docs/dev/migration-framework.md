# Migration framework

The migration framework reads the files that another agent left on this machine and writes them into labunbun's own files. It covers nineteen sources and three categories: settings, assets and history. This document records what the framework does, the reason for each decision, and which traps the source comments name.

## Purpose

A user moves from another agent and wants to keep the work they built up there. The framework carries over settings, MCP servers and permission rules. Skills, agents, commands and rules carry over too. It can also carry past conversations, as session files that `--continue` can resume. It runs from the CLI as `labunbun migrate` and from the REPL as `/migrate`. A run plans by default and writes only with `--apply`.

## Behavior

### Migration pipeline

`packages/coding-agent/src/migrate.ts` is the hub. It turns raw per-source reads into a plan, and the plan into writes.

- The framework has three phases: read, plan and apply. Read does the I/O that touches disk. Plan holds every decision on target values and does no I/O. Apply does the I/O that writes.
- Two invariants hold. The framework reads a source tree and never writes it, so a re-run is always safe. Nothing lands unless `apply: true`.
- `readSources` takes `cwd` as a required argument and does not default the value. A default of `process.cwd()` lets a caller that forgot the argument read the process directory, and the failure is not reproducible. Ten of the sources read only from the home, and Cursor and Trae also read a project half. The plan options take the same `cwd`. A test against a fake home does not read the project half of Cursor and Trae from its own checkout. More than fifty call sites each give `cwd` in one word.
- `planMigration` reads `RawSources`, the parsed options and `existing`, the user's current user-tier settings. When an imported value collides with one already there, the plan keeps the one already there.
- The plan holds `items` and `writes`. An item names its source, the value it came from, the target, an action, a detail line, and whether the target holds a secret.
- The three actions are `map`, `downgrade` and `skip`. The framework reports each skip to the user and never drops one without a report.
- The categories are settings, assets and history. `--only` filters by category. An excluded category yields one skip item whose text reads `excluded by the category filter — nothing from this category was imported`.
- The claim helpers are `claimScalar`, `claimModePair`, `claimPermissionList`, `addPermissionRules`, `claimHooks` and `claimEnv`. A claim turns one target key into one reported decision.
- The plan demotes a superseded claim. When a second source claims the same target key, only the second claim lands, and the first item becomes a skip. The report no longer shows two green ticks for one value.
- `claimModePair` writes both halves of the mode, `permissionMode` and `sandbox`, even when the source names only one half.
- `claimPermissionList` unions rules. It does not assign them. The plan skips an item whole when not all of its rules parse.
- `addPermissionRules` lets a later source add rules to the list. The rules already there stay.
- `claimHooks` unions hook entries per event and writes the key once at the end.
- `claimEnv` covers sources whose environment variable scope is narrower than `settings.env`.
- The settings write uses `JSON.stringify(merged, null, "\t")` plus one newline.
- The MCP write merges the imported servers with the file already on disk, so the user's own servers stay.
- `planPromptHistory` writes the recall list in one whole-file write. Imported prompts go before the prompts already in the file. A prompt already present is never written again, so a second run writes nothing. This file has no `--force`.
- `planHistory` derives the target session id from the source session id. A second run over the same session names the same file and reports `already imported`.
- `applyMigration` does the planned writes. The run collects a failed write and reports it with its path and its error.
- `runMigration` is the entry point that the CLI subcommand and the REPL command share. A bad option value comes back with an empty plan and the error. This step, not the planner, reads the transcripts.
- The report groups lines by source. The action icons are `✓`, `!` and `·`. The counts line reads `N mapped, N downgraded, N skipped`. A dry run ends with `Re-run with --apply to write these files`. The report lists targets that hold or will hold secrets at the end, under `Credentials are copied verbatim`.
- `--from` chooses sources and `--only` chooses categories. `--history-limit` caps sessions per source, and zero is a valid answer that imports no sessions. `--history-scope` is `cwd`, `all` or `none` and defaults to `cwd`. `--force` overwrites a value that the run keeps by default. `--apply` writes.

The order drives the wizard's list and the `--from` argument, and a new source goes at the end. The layout of each source is:

- `qoder`: `$QODER_CONFIG_DIR` when set, else `$QODER_CLI_HOME` (or home) plus `$QODER_CONFIG_DIR_NAME`, which defaults to `.qoder`. The Electron userData root `%APPDATA%\alma` on Windows holds `chat_threads.db`, opened read-only for `app_settings.settings_data`, `providers` and the thread count. `~/.alma` holds `bin/`, `npm-cache/`, `activity-records/` and `cache/`. `~/alma` with no dot at the front holds the stable copy of the browser extension and `worktrees/`. Settings are one SQLite row. The importer reads three keys: `chat.defaultModel`, `general.theme` and `security.autoApproveToolRequests`. The importer whitelists the blob, and does not scrub it.

### History file

The import writes session files for past conversations below `~/.labunbun/projects`, in the directory of the project they ran in. `packages/coding-agent/src/migrate-history.ts` holds all of the conversion.

- The conversion is lossy on purpose. The reader drops encrypted thought text. It drops sidechains and subagent threads, and counts each. A tool call left without its result, or a result without its call, loses both halves. A shorter transcript is better than one that fails the API on the first `--continue`.
- Two phases hold the design. `listHistory` lists candidates and opens no transcript. `readHistory` converts the chosen ones. `collectHistory` runs both with the user's choice between them.
- The scope is `cwd`, `all` or `none`, and it defaults to `cwd`. Under `none` a source gives back nothing at all. The sentences `the user said no` and `there was nothing` must print differently.
- `DEFAULT_HISTORY_LIMIT` is 20 sessions per source. `DEFAULT_PROMPT_HISTORY_LIMIT` is 500 prompts, and `PROMPT_HISTORY_BYTES` is 4 MiB.
- `narrowCandidates` applies the scope. `selectHistory` applies the user's choice before the cap, so a choice of twenty from the picker is not cut down again.
- `readHistory` converts each chosen candidate. The run counts a candidate that it cannot convert. The reader's own reason comes first, so a result explained by its reader never becomes a bare count.
- `renderHistorySession` writes the JSONL that `SessionStore` reads: a header with version 1, then one entry per line, each linked to the previous by id. See `packages/agent/src/session-store.ts:151`.
- Ids come from the session id and the entry index, so the same source produces the same bytes and a second `--apply` changes nothing.
- `importedSessionId` reads `imported-<source>-<first 8 hex digits of sha256(sourceId)>`. `historyPath` places the session file for the candidate's `cwd`.
- A compaction entry carries `preTokens` from the source, `postTokens` 0, `model` "imported", `trigger` "manual" and `preservedFiles` []. Its summary message comes from the same `compactionBoundary` builder that a native session uses.
- Prompt history is labunbun's own recall list, `~/.labunbun/history.jsonl` (`packages/coding-agent/src/history.ts:15`). The import merges into it and never replaces it.
- `mergeNotes` sums the counts for the same reason and keeps the first-seen order. `parseHistoryScope` defaults to `cwd` and rejects any other value with an error that lists the valid ones.
- The session list reads a bounded head of each file rather than the whole file. A line that does not fit the window is not returned, because half a JSON object is not the object it came from. The first line is the exception. A Codex rollout opens with the `session_meta` line, which carries the whole base instruction set and is routinely larger than any head window.
- The prompt list reads a bounded tail of the file, because a prompt history only grows at the end. A read from the front carries the oldest prompts on the machine. A `truncated` flag says the window was smaller than the file. The report can then admit that something before it went unread, rather than imply the count is all of it.
- A rollout is named `rollout-*.jsonl`, and a recompressed old rollout keeps that name with `.zst` appended. Both spellings still parse, because the id and the timestamp come from the name and not from the file.
- The Codex walk covers `sessions/` and `archived_sessions/`, and each candidate carries which of the two it came from.
- An archived session does not become a skip. The importer writes it with the flag. The run counts and skips a subagent session (`parent_id` set).
- The prompt layer tells an empty list from a list that is not there. `absent` carries the reason when the source has no prompt list anywhere. `cwdSubstitute` marks entries filed under the current project because the source records no directory.

### Types and dialects

`packages/coding-agent/src/migrate-core.ts` holds the helpers, and `packages/coding-agent/src/migrate-types.ts` holds the shared types. A helper lives here when more than one source needs it, and its callers, not its first neighbor, decide that. `isRecord` used to sit next to the Codex planner and is called 149 times.

- `MigrationAction` is `map`, `downgrade` or `skip`. `PlannedWrite.kind` is one of `settings`, `mcp`, `skill`, `rule`, `memory`, `agent`, `history` or `prompt-history`. `MigrationCategory` is `settings`, `assets` or `history`, and `categoryOfKind` maps a kind to its category.
- `SECRET_ENV_MARKERS` lists `TOKEN`, `KEY`, `SECRET`, `PASSWORD` and `CREDENTIAL`. The match ignores case and applies to any text in the name, so it catches every `*_API_KEY` spelling. `looksLikeSecretName` is the check built on it.
- `MODEL_ALIASES` maps four short names. `opus` maps to `anthropic/claude-opus-5`, `sonnet` to `anthropic/claude-sonnet-5`, `haiku` to `anthropic/claude-haiku-4-5` and `fable` to `anthropic/claude-fable-5-1`. `resolveModelReference` is the lookup.
- `STATE_TELEMETRY_KEYS` names three keys of `~/.claude.json`: `tipsHistory`, `promptQueueUseCount` and `cachedChangelog`.
- `CLAUDE_SETTINGS_HANDLED` lists what the importer claims from `~/.claude/settings.json`: `env`, `model`, `permissions`, `sandbox`, `hooks`, `fallbackModel`, `effortLevel` and `enabledPlugins`. `CLAUDE_STATE_HANDLED` lists what it claims from the state file: `env`, `model`, `mcpServers`, `projects` and the telemetry keys.
- The two write targets are `~/.labunbun/settings.json` and `~/.labunbun/.mcp.json`.
- `readJson` gives back null for a malformed file. The run goes on with the other sources.
- `parseJsonc` and `stripJsonc` remove the line comments, the block comments and the end commas in one scan. The scan honors the backslash escape and never looks inside a string. A block comment keeps its newlines, because a dropped newline joins two lines and moves every column number in a parse error. A comma at the end goes away only when the next character the scan sees closes an object or an array. Comments and spaces do not count in that check. A hand-edited JSONC file often ends with a comment, and a whitespace-only lookahead left the comma in place. That is the silent loss this function exists to stop.
- Skills: `SKILL_EXCLUDED_DIRS` skips `.git`, `node_modules`, `__pycache__`, `.venv` and `venv`. `MAX_ATTACHMENT_BYTES` is 256 times 1024, and `MAX_ATTACHMENTS` is 200.
- `readAttachments` reads the files beside `SKILL.md`, sorted by name. The report counts the files that it leaves behind, with a reason: `more than 200 files`, `not part of the skill (dependencies or VCS data)`, `unreadable`, `larger than 256 KB` and `binary file`.
- `readCommandFiles` flattens a nested path into one name, so `fix/bugs.md` becomes the command `fix-bugs`. `MAX_COMMAND_NAME` is 64 characters.
- `readAgentFiles` reads agent definitions. A model name in an agent resolves when a subagent starts, against the models this build knows. A name that does not resolve falls back to the session's model and says so at the spawn. The note therefore names the model to expect, not a field the build ignores. The old note read `is not honoured`, and that sentence became false when the resolution landed.
- `requoteNumericKeyPaths` repairs a TOML document that writes `[model.grok-4.6]`. The repair quotes the segments, so the id stays one key. A document that needs no repair gives back null.
- `countTreeEntries` counts the children of a directory of any kind, or zero when it is unreadable. `readDirectoryNames` lists entry names, sorted.
- `HOOK_MATCHER_METACHARACTERS` holds the pattern characters a source matcher may use. It names the twelve characters: `.`, `+`, `^`, `$`, `{`, `}`, `(`, `)`, `|`, `[`, `]` and `\`. The target cannot reproduce any of them. `HOOK_MATCHER_NAME` accepts only letters, digits, `_`, `:`, `-` and `*`. `MAX_HOOK_TIMEOUT_MS` is 600000 and `DEFAULT_HOOK_TIMEOUT_MS` is 60000.
- `normalizeClaudeHandler` converts a timeout from seconds to milliseconds and clamps it to the range 1 to 600000. It counts the converted, the clamped and the untimed handlers.
- `normalizeClaudeHooks` keeps only the events the target runs, only `command` handlers, and only matchers this build can reproduce. An `A|B` alternation splits into names when every part is a plain name. Otherwise the scan drops it.
- `urlCredentialProblem` checks an MCP server URL for two credential shapes: userinfo (`https://alice:hunter2@host/sse`) and a credential-named query parameter (`?access_token=`, `?api_key=`, `?sig=`). It reads the URL by hand and never calls `new URL`. It names the kind and never the value.
- `nameSegments` splits a name on separators and camelCase. `safeDecode` decodes a percent-encoded name before the check. The check looks at the last segment of the name and matches whole words, not text inside a word.
- `CREDENTIAL_URL_SEGMENTS` holds `token`, `key`, `secret`, `password`, `passwd`, `pwd`, `credential`, `credentials`, `sig`, `signature`, `auth`, `authz`, `authorization`, `bearer` and `jwt`. `CREDENTIAL_URL_NAMES` holds joined spellings such as `apikey`, `accesskey`, `accesstoken`, `clientsecret` and `privatekey`.
- `reportUnhandledKeys` turns the rest of a source document into skip items. A key is either carried across or named. The values are never printed.
- `placeholderNames` finds `${VAR}` names in an env or header block. `placeholderNote` turns them into the downgrade reason.
- `planAssetTrees` maps skills to `.labunbun/skills/<name>/SKILL.md`, agents to `.labunbun/agents/<name>`, and a memory document to a rule named `imported-<source>.md`.
- `UNHONORED_COMMAND_KEYS` lists the command keys this build reads past: `allowed-tools`, `model`, `argument-hint`, `disable-noninteractive` and `skills`.
- `commandAsSkill` turns a command into a skill whose body is byte for byte the same. The description collapses onto one line. `commandAsSkill` substitutes `$ARGUMENTS`, and leaves `$1` through `$9` alone.
- `planMemoryAsRule` imports a memory document as a rule. `mergeProviderSpecs` merges provider tables and reports a collision rather than a silent overwrite.
- `ASSUMED_MAX_OUTPUT_TOKENS` is 8192. `summarizeNames` joins up to five names and adds `+N more`.
- `tildePath` renders a path under the home directory with `~` at the front. `collectFileWrites` and `collectAttachmentWrites` build one write line per file.

### Settings schema

`packages/coding-agent/src/settings.ts` defines the settings file and the load order.

- The tiers are user, then project, then local, then policy and flag, in that merge order. Objects merge recursively. Arrays and scalars replace. Project and local values come from files inside the project checkout and pass through `stripUntrustedKeys` before the merge.
- The merge loses track of which tier a value came from. So `LoadedSettings` also carries `sources`, `perSource` (one parsed settings object per tier) and `ignoredKeys`. `sources` feeds the view that `/permissions` shows.
- `PROJECT_TIER_KEY_POLICY` classifies every key of the settings schema as honored or denied for the project and local tiers. From those tiers, the code honors only `deny` under `permissions`. The filter drops `allow` and `additionalDirectories`.
- `LEGACY_MODE_SUGGESTIONS` maps each retired mode to a whole replacement pair. `default`, `manual`, `acceptEdits` and `dontAsk` become `permissionMode` "ask". `bypassPermissions` becomes `permissionMode` "agent" together with `sandbox` "danger-full-access".
- `PermissionModeSchema` reads the same list as the runtime. A legacy value that is stale produces the sentence `"<value>" is no longer a permission mode. Write <pair> instead`.
- `SandboxModeSchema`, `NetworkDomainRuleSchema`, `ModelPricingSchema` and `OpenAICompatibleProviderSchema` cover the other value shapes. A network domain rule is a bare string, or an object with a `domain` and an `action` of `deny`. A price is in USD per million tokens, keyed by `provider/model` or by model id alone.
- The schema also holds `fallbackModels`, `thinkingLevel`, `sandbox`, `networkAccess`, `networkDomains`, `theme`, `vimMode`, `emacsMode`, `trimOldToolResults`, `modelDiscovery`, `backgroundShellNotifications`, `permissions`, `gamepad`, `env`, `allowManagedPermissionRulesOnly`, `disableBypassPermissionsMode` and `providers`. The rest are `cache`, `pricing`, `beetle`, `hooks` and `mcpServers`.
- The `gamepad` block holds `enabled`, `allowApprove`, `device`, `deadzone`, `bindings`, `phrases`, `rumble` and `lightbar`. The `cache` block holds `explicitBreakpoints`, `ttl` (one of `auto`, `5m`, `1h`), `promptCacheKey` (one of `auto`, `on`, `off`) and `promptCacheRetention` (one of `in_memory`, `24h`). The `beetle` block holds `models`, `maxTurns`, `maxCostUSD` and `stallNoticeMinutes`.
- `settingsPath` names the user settings file. `readJsonFile` strips a byte-order mark before the parse, so a file saved by a Windows editor loads.
- `mergeSettings` merges two parsed tiers. `loadSettings` reads user, project, local and policy, and puts the flag tier last with the source name `--settings`. The code skips a tier it cannot parse. A total failure prints `Warning: invalid settings ignored` and gives back the defaults.
- `formatIgnoredKeysNotice` produces the notice for filtered repo keys: `Ignoring repo-controlled settings (<list>): these can only be set from your own settings files (~/.labunbun/settings.json, managed-settings.json, or --settings), not from files inside the project`.
- `UserChoiceKey` names the keys a user picks with a command: `theme`, `model`, `vimMode`, `emacsMode`, `gamepad` and `thinkingLevel`. `shadowingTier` reports the highest-precedence tier that already sets one, among `flag`, `policy`, `local` and `project`. `shadowedChoiceNotice` says when another tier undoes a write to the user file.
- `collectPermissionRules` reads the tiers in hierarchy order, so a later tier wins on the allow rules. A deny rule always wins. Under `allowManagedPermissionRulesOnly`, the policy file is the only grantor.
- `RULE_SOURCE_BY_SETTINGS_SOURCE` maps each settings source to the rule source name shown by `/permissions`: `userSettings`, `projectSettings`, `localSettings`, `policy` and `cliArg`.
- `resolveMode` turns `permissionMode` and `sandbox` into one effective pair, and reports a reason when the policy tier downgrades an unrestricted sandbox.
- `networkAxisFrom` is the one place that turns `networkAccess` and `networkDomains` into the network configuration. An unset access value defaults to enabled. `applySettingsEnv` copies `settings.env` into the process environment, lets a real variable from the shell win, and gives back the names it applied, never the values.

### Wizard flow

`packages/coding-agent/src/migrate-wizard.ts` runs the interactive `/migrate` command, and every answer it gathers becomes an argument to `runMigration`.

- The wizard asks questions and does not decide. Its questions end at the same `runMigration` call the command line makes, so it cannot import anything `labunbun migrate` refuses.
- The first question is a shortcut. `Import everything` answers the source question with every source found and the category question with every category, and skips to the plan.
- The wizard asks about the history of one source at a time. That answer decides how much of the user's past it reads, and the wizard does not guess a default for it.
- A question is radio-style and answers with the chosen label. A picker scrolls a long list and answers with one index. So the source question is one yes-or-no per source, and the session question is a picker whose first entry stands for the whole list.
- The category questions are `Bring settings, MCP servers and permissions across?`, `Bring skills, agents and rules across?` and `Import past conversations?`.
- The history question offers `Only this project (N)`, `Everything (N)`, `Choose sessions…` and `Skip history`. The picker behind `Choose sessions…` starts with `All of them (newest N)`, so the cap does not become a question of its own.
- The recall list follows the session scope. `Only this project` sets the prompt scope to `cwd` as well.
- The picker labels a session with `title || sourceId.slice(0, 8)`, its project, and its date, which is a locale date string or `unknown date`.
- The wizard skips a source with nothing to list, and reads nothing from it. A source whose list converts to nothing reports `no sessions imported` and the reason from its notes.
- The wizard lists each source's history with scope `all`, and asks the plan with `historyScope: "all"`. The per-source scope rides on the entries themselves.
- The confirm dialog reads `Apply these N file(s)?`, with `write them now` and `keep the dry run` as the two answers. A plan with no writes stops earlier with `Nothing to write — the report above says why`.
- The cancel paths read `Migration cancelled — nothing was read or written`, `No source selected — nothing to import` and `No category selected — nothing to import`.
- A successful apply ends with `Restart to pick up the imported configuration`.
- The dialog bridge is a structural slice of the REPL's app handle. The TUI's handle type satisfies it, and neither package imports the other's types.
- `MigrationWizardContext` carries the dialog, the `cwd`, an optional `home` and `report`, where the output of each step goes. The REPL passes `pushInfo`.

## Why it is like this

The comments in these six files are mostly the record of what each choice was chosen against. That record is a shape that someone tried, a measured failure, or the defect that added the rule. This section keeps that record next to the behavior it explains. Do not undo a rule here before you check that its reason no longer holds.

### Migration pipeline

The shape is `read` (I/O), then `plan` (a pure function of its input), then `apply` (I/O). Every decision that maps a value lives in the plan step, so the decisions are testable without a real home directory. The `--apply` step has nothing left to decide.

- Sources are never written. A run leaves the configuration of the source byte for byte as it was. That is what makes a first run safe to try and safe to repeat.
- Nothing lands without `--apply`. The dry run prints the same plan that the apply step runs.
- The plan merges over what is already there. `planMigration` reads the current user-scope settings and MCP servers into `existing`, and the default conflict answer is keep. A conflict line names the key, shows the current value, and points at `--force`.
- A claim is a settings write that another claim can collide with. Every helper that writes a claimable key exists to close a specific hole:
  - `claimScalar` demotes an earlier claim on the same key. Only the second claim lands. Before the demotion the report showed two green ticks and a past-tense sentence that said the run imported the first claim's value. The written file held one value. No one can find the collision at the time of the first claim. `existing` is the file from before the run and cannot see a write from a moment ago. So the code rewrites the earlier line where the collision is a fact, and the scan goes by target key rather than by source. The scan walks `items` backward. A report line that skipped its own write is the same lie one step later, so the scan stops before it.
  - `claimModePair` is the only path that writes a mode. A foreign tool's mode is one value with two jobs, and this build splits it into `permissionMode` and `sandbox`. A hand call of `claimScalar` in each mapper is how one of them writes the mode and forgets the sandbox. A session that approves everything and still enforces a sandbox is a combination the user never chose, and the report does not name it. Both halves are claimed even when the source names only one. A claim of "the source had no opinion about the sandbox" is not the same as "import nothing". The report line names the half the source never mentioned.
  - `claimPermissionList` unions rather than assigns, because two sources can each decide something about what may run unasked. A later claimant that replaces the list drops the first source's rules while its report item still says the run wrote them. A rule the target cannot parse is not a rule, so the scan drops it with a counted skip line (`written by hand would mean written to no effect`). A list that is empty at the target is not a decision to protect, because the run loses nothing when it fills the list.
  - `addPermissionRules` accumulates the whole list that the migration leaves behind, not only the new part. The run writes the value once at the end, and a list without the user's own rules drops them on the way through. A new rule never removes one. The detail line counts a rule that already sits there, rather than a second claim.
  - `claimHooks` unions per event, because a `Stop` hook from one source and a `PreToolUse` hook from another describe one configuration rather than two rival ones. In the earlier shape each source wrote the key. The last one reached erased the first, while the report line of each still said its hooks landed.
  - `claimEnv` lets a later source win over an earlier one. First-wins makes the outcome depend on source order in a way the report does not show. The detail defaults to `credential copied verbatim` when the variable name looks like a secret.
- `--force` must mean one thing for a whole key. Hooks are the place where the recursive merge blurs that rule. `mergeSettings` merges objects key by key, so a forced `hooks` keeps every event the target already had. The skip line that told the user to run `--force` then describes a merge. The code assigns the hook config after the merge, in the forced case only, and touches no other key.
- The permission and hook accumulators carry the target's own lists in as well. So a shallow merge cannot drop a rule or a hook through an overwrite.
- The plan turns history off loudly. Under `--history-scope none` the plan holds a skip item that says history import is off rather than an absence the report cannot explain.
- The report keeps a tally of map, downgrade and skip lines. A permission list that arrived in another shape is not a faithful copy, and the tally is where a user notices.
- `runMigration` reads the transcripts, not the planner. Their read is the one expensive input, and the planner is meant to be a pure function of its input. A bad option value gives back an empty plan and the error, so a refused run writes nothing.

### Source registry

The union order matters. The arms run in `MIGRATION_SOURCE_IDS` order, and every rule where a later source wins (`env`, MCP name collisions) depends on it.

- `claude-code`: the global memory document is the one every other source imports. This source did not import it, which left the most widely used instructions of the six on disk and the report silent.
- `codex`: paths go through `codexAt` because `$CODEX_HOME` can put the tree anywhere. A label that says `~/.codex/config.toml` for a tree that is not there points the user at a file nobody read. The grok source renders its paths the same way. The report names `memoryShadowed` because Codex reads one of the two memory names and the other is not in force. A user who wrote both keeps the one they believed was overridden, or loses the one they forgot Codex reads.
- `cursor` and `trae` share one arm shape. The problem is the same: rules, MCP and a report of the rest, with nothing portable underneath. The code splits out `planCursorAssets` because `planCursor` hangs off `wants("settings")`. A run that asks only for assets reaches the three directories through no path at all, and the code never runs.
- `t3-code`: no asset tree this importer can read, so there is no `wants("assets")` branch. No rules, no skills, no agents, and no MCP server list on disk. The arm states the absence rather than a gap the reader must guess at. `t3-plan.ts` says what "no MCP list" means, because T3 can use MCP servers and the report must not claim it cannot.
- `antigravity`: one arm per category, because `planAntigravity` claims the settings, the MCP servers and the assets. A run that asks only for assets must still reach the skills and workflows without a pass through a settings gate. This is the same reason `planCursor` splits its assets out.
- `qoder`: one arm per category for the same reason. `planQoder` claims a mode, the MCP servers, the hooks, the skills and the rule files. The shape difference against Antigravity is the opposite. There is no `wants("history")` branch, because `planQoder` claims nothing from the sessions and reports the count in its leftover lines instead. `qoder-session.ts` explains why a read of them is a separate batch.
- `codewhale` is the first source whose gate is two roots rather than one. It is a rename of DeepSeek-TUI, and `~/.deepseek` is still a live fallback for some of its readers. `RawCodewhale.present` is true when either tree holds something, and the arm asks the reader's own question rather than one of its own. One arm rather than one per category: `planCodewhale` claims two mode axes, the permission rules, the hooks, the MCP servers, the skills and rule files. A run that asks only for assets still reaches the skills and the instruction documents without a settings gate. **No `claimModePair`**, because Codewhale names `approval_policy` and `sandbox_mode` as two separate root keys, so it claims the pair per field.
- `mimocode-code`: one arm per category is not needed, because `planMiMoCode` reaches its skills and memory through no settings gate. The gate is on the call, not on the parts. There is no `claimModePair` and no `claimHooks`, and both absences come from the product. `permission` in MiMo Code is a rule map whose unmatched default is `ask`. No mode key appears anywhere in its 41-key document, so there is no mode-and-sandbox pair to claim and no posture to write.
- `openclaw`: one arm per category for the same reason as Qoder's. `planOpenClaw` claims a mode, the MCP servers, the hooks, the managed skills and the workspace instruction document. Unlike Qoder's, this one does reach `openclaw-session.ts`. The importer knows the transcript format, so the history branch converts a chosen session rather than a count.
- `alma`: gated on `present` rather than `settings !== null`, deliberately. Alma with a `skills/` tree, an `mcp.json` or four identity documents and no settings row is a real state with things in it. It is the state of a user who installed the CLI and never opened the desktop app. Alma claims a model, a theme, a mode pair, the MCP servers, the hooks, the skills and the memory. The arm is Qoder's shape rather than Antigravity's. `planAlmaAssets` reaches the skills and the memory through no settings gate of its own. The conversation half runs through `alma-session.ts`. Alma's transcripts are rows in a SQLite table, and the importer knows the record shape. So this source converts the chosen sessions rather than counts.

### History file

- An import runs in three phases: list, ask the user, then convert. They stay separate because the middle one is the user's. A picker needs the list before it can ask, and only the chosen sessions are worth a convert.
- The choice applies before the cap, because it is a decision about which sessions matter. A picker that offered twenty choices must not quietly drop half of them to the default limit afterwards.
- `--history-scope` defaults to `cwd`, the conservative value. For a run, the scope compares against the directory the user runs from, because the import puts sessions into their own project's directory.
- Scope `none` returns nothing at all rather than an empty result per source. "The user said no" and "there was nothing" print differently in the report, and only one of them needs an explanation.
- The prompt scope is the same question as the session scope. The wizard asks it once per source: what of mine comes across. A user who asked for this project's history did not ask for every prompt that they ever typed. A user who said no to history did not mean "except the recall list".
- A source whose reader finds nothing wrong still needs a second question: is the tree there at all? `historySourcePresent` is that gate. Each arm records a fact:
  - The shallow question (`present`) goes to Grok, to kimi, to minimax, to step and to opencode on purpose. Grok's prompt history lives under `sessions/`, so a home with pruned sessions still has prompts to offer. A gate that asks for a session to exist drops them without a report. The walk over a home with neither is one `readdir` that fails and returns nothing. Step adds its own reason: its transcripts sit under `<agent dir>/sessions/<cwd bucket>/`, and the buckets are named after directories that may not exist any more. Step keeps no prompt list on disk, so a deeper count costs a walk that rescues nothing. MiniMax and OpenCode answer the same way. A database gate guards the deeper count in both cases (MiniMax's sessions live four directories deep under `v2/`).
  - `deepseek-harness` asks for `present` and a count. The root is there as soon as dsh runs once, and what makes the walk worth it is that transcripts exist. The count also carries the answer past the reader of the other source that reads the same tree.
  - `t3-code` asks whether its state directory exists. `RawT3Code` spells the answer `stateDir` rather than `present`. The reader's own two answers are the settings documents and the skips, and a bare flag is one too many. **This arm was once absent, and the absence was silent.** Without it the function fell through to `raw.agents.present`, so a T3 install with no agents tree got a plan with no sessions. The T3 history tests all passed, because all of them call `listHistory`/`readHistory` directly and never come through this gate. The lesson is the reason the gate exists: a reader tested only at its own level is not evidence that anything calls it.
  - `antigravity` asks the question its reader already answered. The Gemini CLI shares `~/.gemini`, so `present` alone offers every Gemini CLI user a walk over a tree with no `brain/` in it. `dataDir` is the reader's own answer to "one of the two roots holds something", so this gate cannot drift from the reader.
  - `qoder` uses `present`, deliberately not `settings !== null`. A Qoder CLI-only home has skills and memory and no settings document, and that is a real state with things in it. A home with none of the three has nothing to import, and an offer costs the user a read and a keystroke.
  - `codewhale` uses the reader's own `sessionCount` of `<id>.json` files rather than `present`. A home with settings and skills and no session has nothing for `--history-scope` to fetch. A history phase that runs anyway produces an empty list that reads as "you had no sessions". The count reads no files, and it counts whichever root the product reads, so a home whose sessions never migrated off `~/.deepseek` still passes.
  - `mimocode-code` uses `present`, which its reader answers as "any of the four roots holds something". Its config and data roots are separate directories rather than nested ones, and either one alone can be the only populated one. A TUI user without a single conversation has an empty data root and a populated config root, and the reverse state exists too. **This arm carries weight that the reader's tests cannot see.** Without it the function falls through to `raw.agents.present`, another source's flag, with the same silent zero-session outcome as the `t3-code` arm.
  - `openclaw` asks two questions because both have bitten a migration that asked only one. `present` alone offers a home whose state directory exists but is empty, which is what a first run leaves. Its resolver creates nothing, so "the directory is there" is not evidence. `configDir` alone misses an install whose configuration is elsewhere, which is the normal case for a `.clawdbot` user and for anyone with `OPENCLAW_CONFIG_PATH` set. The two resolvers disagree by design. Either root can answer, and that is enough. A home with history and no settings and a home with settings and no history are both offered.
  - `alma` asks two questions, and the second is the one that matters. `present` alone is true for a home with only `~/.alma` (a CLI install's `bin/` and npm cache), or only `~/alma` (the browser relay). It is also true for a `~/.config/alma` with nothing importable. None has a conversation. `threadCount` alone repeats the `t3-code` failure: every test of the Alma session reader passes while zero sessions plan. So it is `present || threadCount > 0`, and neither half gets an offer just because a directory exists.
  - The fall-through arm is `raw.agents.present` for the `agents` source itself.
- `readHistory` reports each session it cannot open by why it came to nothing, rather than as a session that was empty. "Nothing to import" is a claim about the user's conversation. The reader is in no position to make that claim when the session holds nothing because the file did not open. The same rule runs for grok, kimi, minimax and step. It also runs for t3, antigravity, codewhale and mimocode, and openclaw and alma. For Alma it also covers a thread whose every message was a tool call or an image. `chat_messages.message` there holds a JSON blob, and the reader filters its `parts` to `type === "text"`. The run counts a candidate whose conversion throws once under `session with nothing to import`.
- The qoder branch in `readHistory` is unreachable today, because `listQoderHistory` returns no candidates. It is present rather than left to the silent fall-through. A source whose list half starts to return sessions and whose read half was never wired drops every one of them without a word. This branch says why instead.
- `importedSessionId` derives the target session id from the source session id (`imported-<source>-<sha256 first 8 hex>`). So an import of the same session twice names the same file and the second run is a no-op. `renderHistorySession` derives entry ids from the session id and the entry index rather than invent them. So a re-run over the same source produces the same bytes and a second `--apply` rewrites nothing.
- A compaction entry synthesizes its boundary with the same builder a native session uses, so an imported session resumes like a native one. `postTokens` is 0 and `model` is `imported`. Neither value is recorded by the tools we import from. The report gives a zero and a source label rather than a guess dressed up as a measurement.
- The code carries `cwdSubstitute`. It does not resolve the value. `cwd` already holds the substitute, and all the field does is tell the report which kind of directory it is. The importer leaves it out entirely for the thirteen sources that record a directory. The test `candidate.cwdSubstitute === undefined` tells the untouched ones apart.
- The prompt-history merge is the one path that rewrites a file the user also writes, because `↑` recall appends to it as they type. So the merge is a single whole-file write. Imported prompts go before the ones already there, because the newest entries are what `↑` offers first and those are the ones typed here. An entry already in the file is never written again, which is also what makes a second run write nothing at all.
- There is no `--force` on prompt history. The import merges the file, never replaces it. The only thing that `--force` can add is a second copy of a prompt the user already has. The recall list filters by project, so the dedup key joins the prompt text and the directory. So a prompt typed in two projects is two entries, and the target may hold it in either.
- The `where` sentence in the report is a claim about the entries. A substituted source gets the other sentence, because "`↑` offers them in the directory each was typed in" is false for it. A report that describes behavior the written file does not have is the defect this line exists to avoid. The same distinction covers the session half in the same words, so both halves read alike.
- The over-limit line exists so the user learns the cap did something. Prompts say the recall list is not a transcript, and sessions say to raise `--history-limit` to take the rest.
- The history check in `planHistory` is a `statSync` on the target path only, which is the one directory that function may look at. A source session that is archived says so in its label rather than in a footnote. The transcript is the same kind of thing either way, and a reader who archived it may have forgotten that it exists. The report is where they find out it came across too.
- An empty `cwd` is the value `narrowCandidates` counts under `no working directory recorded` and drops. That is the right verdict for a source that records directories and had one session without one, which is dsh's `_no-cwd` bucket. It is the wrong one for a source that records no directory for any session. It drops every session, and since the default scope is `cwd` it does so on the default run. So the code applies the substitute where the source chose it, and that source says why in a note. The flag survives to the report, so the sentence the user reads can name the difference between `recorded` and `assumed`. This is the same shape the prompt-history path uses for the same reason.
- The bounded head window is not a convenience. To drop the oversized first line turned 115 of 125 rollouts on a real machine into `no session metadata` instead of sessions. That is why the reader takes the first line even when it alone fills the window.
- The reader decompresses a compressed rollout whole, and that cost is worth a line. The list walk reads a bounded head of every rollout, and for a compressed one the window costs a full decode of the file. Codex itself avoids this with a seekable decoder. A stream here is a second reader with its own copy of the head-window rules, and one of those rules keeps an oversized first line. One file, one reader is worth more than the time on a path a user walks once. The frame carries its source size, which Codex pledges on write, and that is what lets a one-shot decompressor size its output.
- The walk skips a compressed rollout when the plain file beside it is still there, which is Codex's own rule (`should_skip_compressed_sibling`). In that state Codex reads the plain file. A list of both puts one session in the picker twice, once under a name with no second copy behind it.
- Codex's own thread list reads `archived_sessions/` under the same rules when someone asks for archived threads. A read of `sessions/` alone leaves every archived session out while the report says the source's history came across.
- Claude Code keeps a per-project auto-memory under `projects/<slug>/memory/`, a `MEMORY.md` and the notes written beside it. It sits in the same directory as the transcripts, so the walk counted it as one more sidechain directory. The report called it a subagent transcript, and described the curated memory document as a conversation nobody needed. It is not imported: this build keeps one memory file for the user, so a note from one project applies to every project.
- A compaction marker that holds no summary says so in words. OpenCode's own reader accepts only a completed pair, where the summary is also finished and unerrored. An interrupted build writes a compaction with no summary. That is exactly this case. A dropped marker imports a transcript that silently claims it was never summarized.
- A subagent session is a task the primary ran, not a conversation the user had. An import of it replays the subagent's turns as though the user typed them. An archived session is a real conversation the user chose to put away. Archived is a place a session went, not a reason it is worth less, and the target records that property too. For MiMo Code the archived flag is a first-class column on the session row, `time_archived`, and the product still archives to it. A session the tool hides or files under an internal kind never reaches the candidates, and the walk counts it and says why.
- OpenCode v2 has no `state.output`. The four arms of its tool state carry an answer in three different places. A completed call has `result`, which the code types as `unknown` and stringifies here, and `content[]` of text and file blocks. A failed one has `error.message`. A call that is not done and not failed holds none of the three. The reader takes `result` first because that is what v1's `output` held, the tool's own answer and not a view of it. `content` is last as the fallback for a tool that filled in only the blocks for the model.
- A compaction marker's position is an index into the message stream, recorded as the stream grew. A repair pass that drops something invalidates those positions, so when the pass drops anything, every marker moves to the end. To land at a position that no longer means what it said is the failure this rule stops. The drop count comes back because the caller reports it, since an unpaired half is a thing left out.
- In v2's message rows, the reader counts three of the eight types and does not make a turn of them. `synthetic` is what the tool itself injected, `system` holds the harness's own words, and `agent-switched` and `model-switched` record a setting change. The imported transcript has three roles, user, assistant and tool result, and no system one. To render one of them as a user turn puts words in the user's mouth. `shell` is the same case: a record of a command the user ran, which carries its output, is not something the user said. Each gets a count under a name that says which. A compaction is the one real message that is not read as a turn, and it becomes a marker. v1 split it across two messages joined by a `parentID` link, and v2 records it as one row with both halves in it.
- The v1 pair forms by link rather than by order. The user's message gains a compaction part, and a separate assistant message carries `summary: true` and names the user message in its `parentID`. OpenCode's own reader finds the pair the same way. It indexes the user messages that hold a compaction part and reaches them from the assistant through that field. A match on adjacency pairs the summary with whichever user message came before it. That is a different message whenever anything landed in between.
- A SQLite-backed source resolves its database path once, and the list half and the read half share that answer. `$MIMOCODE_DB` can put the database anywhere, and `:memory:` puts it nowhere at all. The channel filename of a nightly is a build-time constant that no reader can know. A list half that derives the path differently from the reader reports a source with transcripts that the read phase then finds nowhere.
- The record shape of a MiMo Code session is not inferred, and the strongest evidence is that MiMo Code ships a reader for it. `session/opencode-import.ts` opens an upstream `opencode.db` through `openReadonly` and reads `session`, then `message`, then `part`. The importer parses each `data` column into the same `MessageV2` union it reads. So the data blobs are `MessageV2.Info` and `MessageV2.Part`. The one filter this adds is `agent_id = 'main'`, because MiMo Code's `message` table carries a column that an opencode v1 database does not. See `mimocode-session.ts` for why a reader that omits it duplicates the main thread with the subagent's work.
- A reader takes the session the list half built rather than a rebuild from the candidate's path. The candidate carries a path and nothing else. The reader needs the fields the report speaks about: a session's directory, where the compaction segments are, and its kind and parent. The kind and parent are how a report says that a fork's inherited prefix came along. A wider `HistoryCandidate` for one source's vocabulary puts grok's fields in every other source's way. So the reader looks up the session again. A file that went away between the two phases goes to the report rather than a rebuild from a path.
- `KimiEntry` and `StepEntry` are `HistoryEntry` written out, so entries cross over as they are rather than through a translation that can disagree with either side.
- The Kimi prompt file is named for a hash of the directory. The name is one-way, so the only list the reader can find by itself is the current project's. Scope `all` reaches the others through the sessions: each session records the directory it ran in, and a hash of that finds its file. A project whose sessions are all gone keeps its prompts out of reach. The code counts that rather than skip it, because the format cannot tell the reader which directory an unreachable file belongs to. A line carries its text and nothing else: no timestamp, no directory. The directory is the file's, and time is what the format does not have. The file is append-only, so its order is the only order there is. These entries arrive newest-first with epoch 0, which keeps the per-source limit on the newest end. The list sorts by that timestamp and is stable, so equal keys keep the order they came in.
- A source with an empty prompt list and a source with no prompt list look the same from the entries. The report says which one it was: one means `nothing was typed`, the other `nothing is kept`. Only a source whose tree was actually walked sets that line. It means the reader looked for a list and found none, not that a directory was absent.
- A `PromptEntry` is text, directory and timestamp, and the recall reader drops every line whose directory is not the project that is open. So an entry filed under no directory is one `↑` never offers, and a source whose list records none is normally reported rather than imported. Where such a list is worth an import anyway, the code files the entries under the current project. The list is one the user typed, it is simply not scoped, and the code sets `cwdSubstitute` so the report can say that instead.
- Codex's prompt file names the session, not the directory. The directory comes from that session's rollout, the same metadata the session list reads. A prompt answered in a session the user later archived must still find its project. A prompt whose session has no rollout left on disk cannot find its project. An entry that no directory can recall is not worth a line.
- Grok's prompt file is per directory rather than per home, which is what its own `↑` filters on. The directory comes from where the file sits, because a line does not name one. The scope decides which files are worth an open at all. A directory whose name decodes to no path and which has no `.cwd` sidecar gets a skip and a count. Prompts written into the wrong project's recall list are worse than prompts left behind, and recall is filtered by directory.
- The walk behind the Step session list is the product's own scan. It covers the canonical tree and the pre-rename one, and the configured session directory read in either layout. The scan takes a file that appears in more than one of them once. A file the scan passed over arrives as a note with the reason it did not become a session.
- Cursor's recall list is the one list in the repo that the import takes although it records no directory. `<cli home>/chats/<md5>/view/prompt_history.json` is a flat JSON array of bare strings rather than the JSONL of every other source, which is why it has its own reader. The entries are strings, so there is nowhere in the format to record a directory or a timestamp. Unlike OpenCode's list, nothing in it can be misread. A prompt the user typed deserves a place, so the import files the entries under this run's directory and the report says so. That is a real change in reach, and the report names it as one. `--history-scope` cannot filter this list, because the filter compares an entry's directory against the current project. Every entry's directory is the current project by construction, so the report names the choice rather than let it pass without a note. The order is the file's, because the format has no other. The file is append-only, so the reader reverses the array on the way in. The entries then arrive newest-first with every timestamp 0, which keeps the per-source limit on the newest end. An unsorted middle, an array the CLI rewrote rather than appended to, defeats it, and a list this short is not worth a defensive sort. The path is the one Cursor path with no official citation: a subtree three directories down whose name is a digest of the directory. The `not there` sentence names the exact path that was looked for. A report that says only `no list` is indistinguishable from one that looked in the wrong place. When the reader finds nothing, it reports the source as a source with no list, which is a different statement from an empty one.
- MiniMax has no prompt list, and the reason is specific enough for a line. Three things on its disk can be mistaken for one, and it writes none of them as one. The composer's unsent drafts are text the user never sent. The sessions hold the prompts themselves, and the import turns those into transcripts. The shell's own history is a file that MiniMax protects rather than reads. So the `↑` list gets nothing from this source, while the prompts it does know come across inside their sessions. The report owes that distinction to a reader who asked for MiniMax history.
- Qoder has no prompt list that crosses the sessions either. The sentence is a weaker claim than Step's or MiniMax's, worded to match what the search found. No `promptHistory`, no `history.json`, no `recentPrompts` and no completions store is named anywhere in the desktop bundle. The only per-session record the product keeps is the transcript tree this source counts and does not read. So the `↑` list gets nothing here, and to say so is better than the silent empty the fall-through gives. The report owes the user who pressed `↑` in Qoder the difference between `there was nothing` and `nothing came across`.
- Alma has no prompt list that crosses the sessions either, and the reason is structural rather than a search: the prompts are the message rows. Every user message the importer converts comes with its thread and its timestamp. A recall list is then the sessions' own first user turns read a second time. To say so beats the silent empty the fall-through gives, and here the truth is `nothing came across`.
- MiMo Code's recall list is inside its sessions rather than beside them. The `↑` list gets nothing, while the prompts it does know come across with the transcripts. It is not a case of a file this importer did not find. MiMo Code is an opencode fork, and the opencode it forked writes `<state>/prompt-history.jsonl`. MiMo Code's TUI has no such file. Its prompts live as `user` messages in the same message and part rows this importer already reads as transcripts.
- OpenClaw's recall list is its transcripts, the same shape as MiMo Code's sentence, but the reason is a stronger claim than `no file was found`. OpenClaw keeps one authoritative store, and every prompt is a `user` role message inside it, which this importer already reads as transcripts. The report owes the user who pressed `↑` in OpenClaw the difference between `there was nothing` and `nothing came across`.
- A T3 Code transcript comes without its tool calls. The reason is a constant, because a reader who wonders why is most likely to reword this note. T3 stores a tool call as a row in `projection_thread_activities` with `tone = "tool"`. That row holds a projection for T3's own UI rather than a call with an argument list and a result that pairs with it. The count beside it in the report is how many such rows the offered threads hold.
- A T3 thread with no recorded directory is still offered. The thread row has no directory column, and the effective one comes from a join. A project whose `workspace_root` is empty yields a thread with no path at all. The list takes such a thread with the source's own base directory. It does not leave one out. To drop it hides a conversation the user can see in T3. `narrowCandidates` then decides what the scope means for it.
- T3 records `reasoning` as its own row in the same message table, so a run of it and the reply it produced are adjacent. The reply is what the user read. Two separate assistant messages show a turn that stops to think and then says nothing before another turn answers a question already answered. So the importer keeps a run of consecutive `reasoning` rows and puts them in front of the next assistant message as `thinking` content. The four file-based sources fold their own the same way. A `reasoning` run with no assistant message after it, a turn interrupted mid-thought, becomes its own message rather than dropped. To lose it leaves a transcript that silently omits part of a turn it otherwise carries. That gap is the kind that nobody notices until they try to resume the session. The report gives the empty case a line rather than a failure count, and its reason names the roles. It does not say the thread was empty. Those are different statements. A T3 thread that recorded nothing is a real thing. So is one whose every row is a role this importer does not read.
- No Antigravity conversation carries a directory, and that is a result of the product, not a gap in the reader. The compact transcript has no `cwd` field, and the product's own record type has none. Nothing beside the transcript fills the hole: `swarm.md` and `scratch/` do not name a directory the user worked in. Antigravity does associate conversations with projects, and its settings carry a `project_conversations` field, but where the per-project settings file lives is not established. So every candidate is filed under the directory this run is in, and the report says the directory was assumed. The other value, `cwd: ""`, is the value `narrowCandidates` drops, and here it drops every session rather than one. Since the default scope is `cwd`, it does so on the default run. A history that imports nothing is not a migration that found nothing, and the report must not make the two look alike. The substitute is the user's current project, which is what the Cursor prompt reader does in the same situation. Nothing here claims which project a conversation belonged to. Which data root the reader takes is the same decision it makes. `antigravityDataDirs` orders them by which tree the current build writes to, and the first with content wins.
- The code reads the Antigravity title in the read phase and nowhere else, because the list phase cannot afford it. There is no metadata file beside the transcript, so the title is the first user turn. A user turn is not guaranteed to be the first record: line one is the product's own system prompt. To find one means a scan until a user turn appears. For a list over a whole tree that means a read of every conversation on the machine before the user chose any. The start time has no such problem, because line one carries it and a bounded head reads it at list time. Only the title is blank in the picker.
- The reader reaches OpenClaw's agent store through the state directory, resolved with the product's own precedence and the `.clawdbot` fallback. The reader finds an upgraded install whose state never moved and does not report it absent. `env` defaults to `process.env` for the same reason every other source's does, and every test passes one explicitly.
- The OpenClaw list takes the directory from the transcript header, not from a column: its tables have none. The reader takes the header for every session because it is unconditional. The optional `entry_json` fields are absent on a session that was not spawned. A session with no directory at all is still offered, with the state directory as its `cwd`.
- Codewhale is the one history source whose `cwd` is not a substitute or a hash lookup. A Codewhale transcript records the directory it ran in. `SessionMetadata.workspace` is a `PathBuf` with the serde name `workspace`, and the on-disk fixture confirms the key sits under `metadata`. That is why the list sets no `cwdSubstitute`. The default scope does narrow here. For most sources it silently keeps all of it. The list reads a bounded head of each file, which is enough because the envelope is pretty-printed JSON with `metadata` as the second key. A 256 KB window finds every field the list step needs without a read of a conversation the user has not chosen yet.
- Alma's conversations are rows rather than files. A chosen thread is a second query, not a second read of something already in hand. The reader settles the directory before the read runs. `chat_threads` has no directory column and its `metadata` is `{}` as the application writes it, so the path comes from `workspace_id` to `workspaces.path`. When that link is gone, the list half has already filed the candidate under the configuration root and set `cwdSubstitute`. The report says the directory is an assumed one rather than a recorded one. The read function never invents one. A wrong `cwd` files a conversation under a project it was never had in. That is the one error the rest of the pipeline cannot recover from.

### Types and dialects

`migrate-types.ts` is deliberately a leaf. `migrate-history.ts` needs `MigrationSourceId` and the hub needs all of it, so anything that imports back from either of them cannot live there. That is why `PlanOptions`, the one type that talks about imported history, stays in the hub. The one-way edge is what lets `migrate-history.ts` name the source ids without a cycle between the two files.

- `MIGRATION_SOURCE_IDS` is ordered as the picker and `--from` list it. New sources are appended: the order is what `detectSources` reports, and a reorder silently changes which of two sources that give the same file wins.
- `SOURCE_ROOTS` holds the spellings used to render labels, not to find trees. Several entries record a trap:
  - `opencode` is the only entry that is two directories deep. OpenCode puts its tree under the XDG bases, and `xdg-basedir@5.1.0` has no Windows branch, so on Windows the path is `~/.config/opencode` and not `%APPDATA%`. MiMo Code repeats the same trap, and the product's own README disagrees. It claims `%LOCALAPPDATA%\mimocode\` (`README.md:385`) and `~/Library/Application Support/mimocode/` (`README.md:422`), and neither path is anywhere in the tree.
  - `cursor` and `trae` are the CLI half only. An IDE keeps its state in a profile directory outside the home. So the home-relative spelling misses a user who opened the editor and never ran its CLI. `trae` is the international global home. The home of the China build is `.trae-cn`.
  - `t3-code` is the base directory, not the state directory: the tree a migration reads lives at `<base>/userdata`, which is also where a `$T3CODE_HOME` override lands. The `??` in its `sourceRoot` entry is the fallback for a label rendered against a tree nothing was read from. Detection reports that same state as absent.
  - `antigravity` is `~/.gemini`, and this directory is not Antigravity's alone. The Gemini CLI keeps its own state beside it, so it cannot be a detection root.
  - `qoder` is `~/.qoder`, and unlike `~/.gemini` it is not shared with a foreign tool. `$QODER_CLI_HOME` defaults to the home, and the directory name is appended to it, so anything in there was written by Qoder. The tree also moves on `$QODER_CONFIG_DIR`, a whole-path override used as written, and on `$QODER_CONFIG_DIR_NAME`, a directory name applied under `$QODER_CLI_HOME` or the home.
  - `codewhale` is the first source whose root is not a single directory. Codewhale is a rename of DeepSeek-TUI, and `~/.deepseek` is a live fallback for some of its readers and not for others. `CODEWHALE_LEGACY_FALLBACK` records which is which.
  - `openclaw` has three live spellings that disagree. `resolveStateDir` falls back to `.clawdbot` when `.openclaw` is absent, and `OPENCLAW_PROFILE` puts a named profile in `.openclaw-<name>`. `OPENCLAW_STATE_DIR` replaces the root outright, and `OPENCLAW_HOME` moves the whole tree. A plain relative spelling is wrong for two of the three ways this source installs itself.
  - `alma` is the only one of Alma's four roots that a file is read from. Alma writes to Electron's `userData` (`%APPDATA%\alma`, with `chat_threads.db`). It also writes to `~/.alma` (binaries, an npm cache, screenshots). It writes to `~/alma` with no dot at the front (the stable copy of the browser extension and `worktrees/`).
- `sourceRoot` exists as one function so detection and the readers cannot disagree about which tree a source is. Seven roots move through variables: `$DSH_HOME`, `$GROK_HOME`, `$CODEX_HOME`, `$KIMI_CODE_HOME`, MiniMax's pair, Step's two and `$ZCODE_DATA_BASE_DIR`. A reader that consults `~/` anyway calls the source absent while the importer goes on to import from it. The label direction fails the other way too, where detection finds the tree and the label names a path nobody read.
  - Step's entry is the only one that is not a single expression. The directory name itself is a setting (`$STEPCODE_CONFIG_DIR`), and an agent-directory override moves the tree out of the home. The pre-rename `.step-harness` tree is read when the canonical one holds nothing.
  - The default of ZCode is also a variable, and its CLI half is a second root with a second variable. Detection looks only at the data root, because that is the half a fresh install always has.
  - The `cursor` and `trae` branches are unreachable today and no test covers them, because `detectionRoots` answers both ids first. They are kept because they are the right answer: `~/.trae` is wrong for Trae, whose global rules live in `~/.trae/user_rules`. They are also kept because without them the code falls back to a home-relative join for a source whose root is not a home-relative join. Nothing catches that.
  - Codewhale refuses an unusable override rather than use it. A relative value raises `PathOverrideErrorKind::Relative` in the product, and a silent fallback to `~/.codewhale` imports a tree Codewhale itself rejected.
  - Alma has no environment variable to honor, because its bundle reads none anywhere. Its branch is a plain join that exists to say so in the one place a reader looks.
  - Antigravity needs no branch, and the fall-through is correct. `~/.gemini` is a plain home-relative join, so this is the first source whose tree is unambiguous while its detection is not.
- `detectSources` asks what is in a root, not whether it exists. `~/.agents`, `~/.claude` and `~/.codex` are directories other tools create. An empty one has nothing to import, and an offer costs the user a read and a keystroke. A root that is present but unreadable counts as empty for the same reason.
  - OpenCode needs two detection roots. The product creates its config root at import time, before the user writes a setting. On a stock install that root exists and is empty. A user who ran OpenCode, talked to it, and never touched a setting has sessions in the data root. Detection that looked only at the config root offers a source with nothing in it and hides the one with everything. The sharp case is `OPENCODE_CONFIG_DIR`. The override replaces the config path. The tree appears only when something is written there, while every session sits in the untouched default data root.
  - `cursor` and `trae` each hold two roots because a look at one calls the source absent on half the machines that have it. The import then finds the contents of the other. That is the worse of the two failures.
  - `t3-code` does not repeat that mistake. The state directory an installed build writes and the one a dev build writes are different directories under the same base. So a read of only the production one calls the source absent on every machine whose only T3 is a dev checkout.
  - `antigravity` is the first source whose home-relative root cannot be used for detection at all. A home that has never run Antigravity can still have a busy `~/.gemini`. Detection looks at three directories Antigravity owns: both data roots, and `~/.gemini/config`. Which data root exists depends on whether the user went through the IDE-split wizard. `config` is the customization root the product's own guide names as its machine-local global location (`skills/`, `plugins/`, `mcp_config.json`, `hooks.json`). A user with all three deleted but `config/` populated is real, and the reader handles it. `RawAntigravity.dataDir` is `null` there and every conversation count is zero, which is a report with nothing in it rather than a crash. What this cannot rule out is a home whose only `~/.gemini/config` content is not Antigravity's, which is why `config` is last and not first.
  - `qoder` needs no special case, and that is a fact rather than an omission. A CLI-only home with skills and memory but no `settings.json` is a real state that deserves the offer. Two roots are still checked, both Qoder spellings: the resolved one, and the default home of the China build, `.qoder-cn`. The product picks its build at start-up, and a process cannot see both.
  - `codewhale` has two roots that are two eras, not two builds. `~/.deepseek` is the pre-rename tree and the product still reads it. A home that used Codewhale under its old name has its whole tree there. The reverse is handled rather than assumed away: a post-rename user also has a stale `~/.deepseek` for the paths that still fall back. `CODEWHALE_HOME` narrows detection to one root, and that is the product's own rule. An explicit home is an isolation boundary, and a fallback from an isolated profile reads exactly the data the user isolated themselves from.
  - `openclaw` detection roots are three spellings of one tree. A detector that looked only at `.openclaw` reports "no OpenClaw" for every user who upgraded from the pre-rename build. That user's entire history lives in `.clawdbot`. What this cannot rule out is a profile directory with no `OPENCLAW_PROFILE` set now. A profile name is only discoverable from the variable. A home that ran `openclaw --profile work` once and never exported it has a `~/.openclaw-work` this never looks at. Stated rather than papered over.
  - `alma` has four unrelated roots, and each of the other three is the only root that answers for some real user. `%APPDATA%/alma` holds `chat_threads.db` and `plugin-storage/`, and a user who installed Alma and never opened the settings has it and nothing else. `~/.alma` holds `bin/`, an npm cache, screenshots and a cache directory, none importable. `~/alma` with no dot at the front is the stable copy of the browser extension. The dot at the front is the single most-missed path in the product. A detector that looked for `~/.alma` and `~/.config/alma` reports "no Alma" for every user who runs only the CLI or the browser relay. The `userData` root is `null` on macOS and Linux, where this importer does not guess at `~/Library/Application Support` or the XDG data base. A path this source names but did not read is better than one it names wrongly, and the report says which platform it is on.
  - `mimocode-code` has four roots that sit side by side rather than nested in one another. `resolveMimocodeHome` answers the four XDG bases with `mimocode` appended or, under `$MIMOCODE_HOME`, a `<root>/{config,data,state,cache}` set. So there is no single directory whose non-empty state says "MiMo Code is here". Two of the four are wrong on their own, and one is the sharp case. `config` gets a starter `mimocode.jsonc` written on first run, so it is non-empty early. `data` holds every session and `auth.json`. It is often empty for a user who ran the TUI and kept no conversation. `state` and `cache` hold nothing this importer reads. A look at `config` alone calls the source absent on exactly the machines whose history is the thing to migrate. So all four are checked, and the two that carry content come first.
- `MigrationAction` skips get a report line rather than a silent drop. A setting that vanishes without an explanation reads as a migration bug. The user cannot tell "labunbun has no equivalent" from "the importer missed it".
- The three categories are the chosen granularity because their results differ. Settings change behavior, assets add files to the home directory, and history writes a transcript that resume replays.
- `SECRET_ENV_MARKERS` matches case-insensitively against any text in the name, so the `*_API_KEY` variants are covered. `MODEL_ALIASES` maps a family alias to a `provider/id` reference. Every target is checked against the registry during the plan step. So an alias for a model this build does not carry becomes a reported skip rather than an unusable `model` value. `STATE_TELEMETRY_KEYS` deliberately does not include `projects`: each entry under it holds that project's local-scope MCP servers, and those are configuration. A claim that the whole map is "not configuration" is one the file itself contradicts. The plan reads them one by one in `planClaudeCode`.
- `ClaimEnv` defaults to `map`, which is right when the source's variable and the target's mean the same thing. The eight sources that scope nothing differently say nothing extra. A source that scopes its variables more narrowly passes `downgrade`. T3 Code injects a provider instance's variables into that provider's process, while `settings.env` reaches every tool call. So the value arrives unchanged and its scope does not. A report line that calls that a faithful copy is the kind of imprecision the user notices later. It shows after a shell inherits an endpoint meant for one model provider.
- `ClaimModePair` claims a mode and a sandbox together, as the one decision they are. Every foreign tool's idea of how much it asks the user is one value. The closest equivalent here is often a pair: `bypassPermissions` meant never-ask and unconfined, and `yolo` means the same. Two hand-written scalar claims in eight mappers is how one mapper writes the mode and forgets the sandbox. That combination is one the user never chose, and the report does not name it. Both halves are claimed even when the source named only one. A source with no opinion about the sandbox makes a different claim from one that imports nothing. A pair left half-written reads as a deliberate setting. This is the only way a mode is written.
- `ClaimHooks` stays an accumulator rather than a write. Two sources can each hold hooks. A `Stop` hook from one beside a `PreToolUse` from the other is one configuration, not two rivals. So entries are unioned per event, and the key is written once at the end. A writer that wrote straight into the patch lets the last source reached erase the first, while both report lines say their hooks were written.
- `ClaimableScalarKey` exists as a closed list. A wider list is cheap, while a claim on a key the merge cannot undo is not. That is why permission rules use an accumulator instead.
- `readJson` treats a malformed source file as nothing to migrate rather than as a failed run, because the other sources are still worth an import.
- `parseJsonc` was written for OpenCode, which parses every one of its three settings files with a JSONC parser, not only the one named `.jsonc`. So `// my provider` in `opencode.json` is a legal line. A read with `readJson` throws the whole file away: the catch returns `{}`. The report then says nothing about a file the user can see is full of settings. The failure is silent in the worst direction. The strip step is a scanner rather than a regex, and that is the whole point. `text.replace(/\/\/.*$/gm, "")` mangles `"baseURL": "https://api.example.com"`, because it cuts the value at the `//`, and a Windows path in a `"command"` array loses everything after its separator. The scanner tracks whether it is inside a string and honors `\` as an escape. That keeps a URL's `//` and a Windows path's `\\` intact. Commas at the end of a line go away by the same pass, for the same reason. It is not a general JSONC parser: a string with a literal newline is not repaired. Anything the vendor's parser accepts and this does not costs one settings file, which gets a report line rather than a silent loss.
- A skill is a directory, not a document. Its body points at `references/*.md`, `scripts/` and so on, and a copy of only `SKILL.md` leaves those pointers dead. Text files are carried. Binaries and oversized files are counted and named in the report instead of written. The writer is text-only, and a silent truncation is worse than an explanation. A skill is prose, not an asset store, so the cap is 256 KB per file and 200 files. `SKILL_EXCLUDED_DIRS` names the directories that hold somebody else's files (`.git`, `node_modules`, `__pycache__`, `.venv`, `venv`).
- A commands tree mirrors how the source tool namespaced its commands: `fix/bugs.md` is a different command from `fix.md`, and the two may say different things. The flatten step turns a nested path into the name (`fix-bugs`), because a skill here is one directory per name. A collision is reported as one skill kept. A `README.md` is skipped as "a README, not a command", and a name longer than 64 characters cannot become a directory here.
- `requoteNumericKeyPaths` exists because `[model.grok-4.6]` is TOML 1.0 and is what grok's own user guide writes. It is the path `model.grok-4."6"`: the id with a dot in it becomes three keys. Grok's own pty test says so in as many words, and its parser takes it. `Bun.TOML` does not: a bare segment of digits after a dot is rejected. The rejection costs the whole document, with every other setting, rule and MCP server in the file. The repair quotes the segments, which under the spec produces the same structure. It returns the changed paths so the report explains what grok made of them. Only the key part of a line is touched. Nothing inside a triple-quoted string is, so a description that holds `[model.grok-4.6]` is left as the user wrote it.
- `countTreeEntries` counts both files and directories on purpose. Grok's `personas`, `roles` and `workflows` trees hold `.toml` and `.rhai` files. A count of directories only makes each of them come back as 0, which the caller filters out. So a tree full of the user's own definitions is reported as one grok does not have.
- The hook constants are tied to this build's hook engine on purpose. `matchesPattern` treats `*` as the only wildcard and escapes every other pattern character. So a source matcher written as a regular expression (`mcp__.*__delete.*`) imports as a literal that can never match. `HOOK_MATCHER_METACHARACTERS` must stay equal to the escape list in `hooks.ts`, because that equality is what makes the check honest. A character escaped there and not here is a silent miss. A matcher `A|B` is an alternation in the source and a literal here. One entry per name is what it meant: those are the tools it named, so the split is not a wider rule. An alternation with a part this build cannot express is dropped rather than split, because a split guesses at what the source meant.
- The hook timeout is the one field whose value must change on the way across. The source counts seconds and runs a handler that names none for ten minutes, where this build counts milliseconds and waits a minute. A copy that keeps the number makes `timeout: 30` mean thirty milliseconds, which is thirty thousand times shorter than the source meant. The conversion clamps rather than drops, because the schema rejects an oversized value and takes every hook in the file down with it. `NormalizedHooks` counts every kind of loss, so the report says what did not come across instead of a hook that never fires.
- `urlCredentialProblem` closes the one credential channel the importers copied without a look, and every one of them copied it. A name-based credential scan cannot see it. The credential is not under a key shaped like a secret: it is inside the one string every importer treats as a safe identifier. The report says `containsSecret: false` for a server it copied, so a URL like this is not merely a secret on disk. It is the importer that asserts the opposite of the truth about it, the failure this repository treats as the expensive one. The parse is by hand and never calls `new URL`. A `URL`-based version measured 11 of 16 cases wrong, because the parser is least useful exactly where a credential is most likely. It rejects a space in the host, a port above 65535, an unclosed bracket and a scheme-relative `//user:pass@host`. Every one of those is a hand-edited URL, which is what a pasted credential URL is. "The parser rejected it" is not "it is safe". Scheme-relative URLs, URLs with a space in the host and URLs with an out-of-range port all gave back "no problem". Each of them carried a live password. The scan flags too much on purpose, because the cost matrix is not symmetric. A false positive costs one server, and the user is told which one and why. A false negative writes a live token into `~/.labunbun/.mcp.json` under a report line that says nothing in it is a secret. So `?sortKey=updatedAt` is flagged and `?public_key=` is flagged. The value is never returned, only the two fixed phrases, so the answer can go in a report line.
- The parameter check has three rules that narrow the match, and each buys back a different false positive. The first is whole words: a text match flags `?monkey=1`, `?keyboard=…` and `?hockey=…`. The second is a split on separators and camelCase: `accessToken` becomes `access` and `Token`, and `monkey` stays whole. The third is the last segment only, which separates a credential from the noun it qualifies. `?key_count=3`, `?token_type=bearer` and `?signature_version=4` are a credential word used as an adjective, and none of their values is a secret. A qualifier in front of the credential word (`sortKey`, `public_key`, `hasToken`) is still flagged. There is no way to tell those from `access_token` by name alone, and the direction of that error is deliberate. `sig`, `signature`, `auth`, `authz`, `bearer` and `jwt` are in the segment list and not in `looksLikeSecretName`. Those are the spellings a signed-URL service uses, and a user pastes them out of a vendor's dashboard. `CREDENTIAL_URL_NAMES` is the lowercase spelling of the same rule (`accessToken` splits, `accesstoken` does not) rather than a second opinion about which words are credentials.
- The MCP client of the target does not expand `${VAR}`. No step does it, so a copied value that says `${TOKEN}` stays literal. A server that authenticated before does not authenticate now. `placeholderNote` names the variables and nothing else, so whatever else is in the value is the user's.
- `ASSUMED_MAX_OUTPUT_TOKENS` is 8192 for an imported model whose source does not name a budget. `summarizeNames` joins five names and adds `+N more`, which is enough to act on and short enough to read. `positiveInteger` exists because a token window has no other form.
- `planAssetTrees` takes the commands tree as optional. Only the sources whose reader found a `commands/` directory set it. A source with none has nothing to import and nothing to say.
- `UNHONORED_COMMAND_KEYS` records what dies in the command-to-skill rewrite: `allowed-tools` and `model` do nothing here. ZCode honors `disable-noninteractive` and `skills` where this build reads neither from a skill's header. A key ZCode honors and this build ignores with no report is the one a user is most likely to believe is still in force. So it is named rather than dropped. The body travels byte for byte, because a command is prose the user wrote and only the header has to change. A description spread over several lines is collapsed onto one. The reader takes one line per key, and a header that splits its own value comes back as an empty description. An earlier `detail` stays in front of the new one: that is the plugin provenance, and this rewrite is otherwise the last word on it.
- A command becomes a skill because a command is a named prompt, and a skill here is exactly that. The rewrite is of the header, not a translation. Codex's own importer turns Claude Code commands into skills the same way. That is a sign that this rewrite is the intended one and not merely the convenient one.
- An imported memory document becomes a rule file rather than `MEMORY.md`. `MEMORY.md` is a file the user curates and may already have, and a new document dropped on top of it destroys their own notes. `rules/` is additive by design and is loaded with the same weight.
- `mergeProviderSpecs` reports a collision rather than an overwrite. `id` is what a model reference resolves against, so a silent replace repoints configuration that already worked. The function returns the ids that were taken so the caller does not re-derive which entries survived. Two copies of that small rule is how a report starts to describe a patch that was never written.
- `tildePath` renders a path under the home directory so an item's source and target read at the same scale. A path outside the home is left alone rather than mangled into a relative form that misleads.
- `collectFileWrites` checks the planned writes for a path before it checks the disk. Two sources can hold a skill of the same name, and `existsSync` cannot see a claim that has not been written yet. The message says the first one was kept. Attachment skips go out as one line per file, whatever the mix of reasons. A skill with a dozen images must not turn the report into a directory list. `collectAttachmentWrites` writes beside the file they arrived with, which keeps a skill's internal links real after the move. A file already at the target is kept rather than overwritten. The user may edit it, and `--force` is how they say they did not. Two entries that resolve to one path are guarded, because a double write shows one of them in the report only.
- The branches of `sourceRoot` name their helpers: `dshRoot`, `grokRoot`, `codexRoot`, `kimiRoot`, `minimaxRoot`, `stepRoot`, `opencodeRoots`, `mimocodeRoots`, `cursorUserRoot`, `traeGlobalRulesDir`, `zcodeRoot`, `qoderConfigDir`, `t3Root` and `resolveCodewhaleHome`. `codexRoot`, `t3Root` and `qoderConfigDir` read `process.env` directly, `resolveCodewhaleHome` reads it through a defaulted parameter, and `mimocodeRoots` reads it through its `env` parameter. That is the same trade `opencodeRoots` makes. The reason is the same for all of them. A developer with the variable set gets that tree, and that is the correct answer for their machine. `readMiMoCode` takes the block as an argument instead, and that is what the tests point at a fixture with. `t3Root` is the directory the reader opens, and `t3StateDirs` is the list the label fallback comes from. The OpenClaw branch calls `openclawStateDir`, which quotes all three spellings and takes `process.env` as an argument rather than a read inside that module. `openclaw-home.ts` quotes all five OpenClaw resolvers, and `alma-home.ts` quotes all four Alma roots. The `trae` branch passes `traeEdition(home)` into `traeGlobalRulesDir`. Each `detectionRoots` arm calls the helper its source owns, and `sourceHasContent` is the check `detectSources` runs over every root. ZCode's CLI half is a second root with a second variable, resolved in `zcode-read.ts`.

### Settings schema

- The hierarchy and the merge rule are older than this document: objects merge recursively, arrays and scalars replace, and the later tier wins. What is specific to this repository is trust. Project and local files travel with the repo, so both are filtered through `stripUntrustedKeys` before the merge. Only the tiers the user controls (user, policy, flag) can set the keys that decide what the agent may do or where it sends data. The "local" tier is not a trust boundary either. labunbun never writes an ignore rule for it, so whether it is committed is up to whoever cloned the repo.
- `PermissionModeSchema` used to be a hand-written `z.enum` and a second, independent copy of `PERMISSION_MODES`. The file's own comment claimed the schema read the same list, and it did not. So a mode added to the list was a mode the settings file rejected. The derivation of the schema is what makes the claim true. The legacy branch is why a stale value produces a sentence to act on. The parser's bare "invalid enum value" is not the sentence a user can act on. That text comes from a zod version and is not ours. `SandboxModeSchema` is derived the same way.
- A bare `networkDomains` string is an allow because that is what almost every entry is, and the object form is tedious for the common case. The `{domain, action: "deny"}` shape exists because a deny with no way to express it is a deny nobody writes. Once `allow: "*"` is in a table, the deny is the only thing between it and everything.
- `thinkingLevel` is derived from `THINKING_LEVELS` rather than a restated list, so a level added to the type is a level this file accepts by construction. An unset value leaves the choice to the model. A set value is still bounded by what each model declares. A row that declares no thought shape is sent none, whatever the setting says, because that answer belongs to the adapter. The adapter can see the row and has its own tests.
- `LEGACY_MODE_SUGGESTIONS` stores the whole replacement rather than a mode name, because the answer is a pair. `bypassPermissions` was one value with two jobs: never ask, and no confinement. A suggestion of only the mode sends those users to the sandboxed pair. That is the one change in this batch that can quietly narrow a scripted run.
- `LoadedSettings.perSource` exists because the merged settings can no longer say which tier a value came from. Rule attribution and the policy-tier lockdowns both need that answer. `sources` feeds the `/permissions` view.
- `PROJECT_TIER_KEY_POLICY` is the enforcement of the trust rule, and its reason is concrete. Left unfiltered, a cloned repo can hand itself `bypassPermissions` or register a provider pointed at a host it controls. It can redirect credentials through `env` (`ANTHROPIC_BASE_URL` and friends). It can install a hook that runs on every turn, or connect an MCP server without a pass through the approval gate. It can declare that the model it is about to run costs nothing.
  - `permissions.deny` is deliberately not denied: a tighter rule is always safe, and a repo's own guardrails stay effective against the agent it just configured. `allow` and `additionalDirectories` both widen what the agent may do. The first pre-approves calls, and the second declares more of the disk a workspace.
  - `theme`, `vimMode` and `emacsMode` are cosmetic and have no reach beyond the user's own terminal. `trimOldToolResults` is denied for the opposite reason. It decides how much of the user's own conversation the model keeps. A cloned repository must not make the agent forget on the user's behalf.
  - `gamepad` is denied whole where `permissions` is denied key by key, because there is no sub-key that is safe to keep. `enabled` claims an input device. `device` and `bindings` decide which one and what its buttons mean. `phrases` puts repository-authored text one press away from the prompt. `allowApprove` gives a physical button the power to approve its own tool calls. The argument that a tighter rule is always safe has no analogue here.
  - `allowManagedPermissionRulesOnly` and `disableBypassPermissionsMode` are read only from the policy tier already. They are classified here so the merged settings can never carry a repo-supplied value even if a future reader forgets that rule.
  - `cache` decides how the user's conversation is billed and how much of it hits the cache. It has no effect on the repository at all, so a repo has no legitimate reason to set it. `ttl: "5m"` or `explicitBreakpoints: false` quietly taxes every turn of a session run inside that checkout, which is a strange thing for a checkout to want.
  - The policy is a table rather than an array of denied names. A list of names is a list that drifts, and this one decides what a cloned repository may hand itself. It is typed over `keyof Settings` on purpose. A key added to the schema and not classified here does not compile. So the default for a new field is a question someone answers rather than an omission nobody sees. A test asks the same question at runtime in both directions, for an unclassified key and for a row the schema no longer has.
- `stripUntrustedKeys` removes the keys before the merge, so a dropped key never reaches `merged` and never reaches `perSource` either. `perSource` matters because `collectPermissionRules` reads it for rule attribution, which is the path a project `permissions.allow` uses otherwise to widen access. `formatIgnoredKeysNotice` is the one-line notice that tells the user what a repo tried to set for itself and lost.
- `shadowingTier` exists because `/theme`, `/model` and `/vim` all write the user file, and every other tier is merged on top of it. So a project file, a local override or the managed one quietly undoes the choice at the next startup. The write is fine. The silence about it is what leaves a user setting the same theme again every day. The tiers are ordered by precedence, so the tier reported is the one that actually wins. Only keys with no schema default count, because `theme`, `model` and `vimMode` are all optional. So a value present in a tier's own parsed settings is a value its file really set. The notice stays undefined when nothing outranks the user file, which is the common case and the one that must stay quiet. The format function is passed in so this module knows nothing about `~`.
- `readJsonFile` strips a byte-order mark, because a file saved by a Windows editor is not a parse error. A decision to treat it as one drops a whole tier of settings, and the user never learns why. A parse failure prints `Warning: failed to parse <path>: <message>` in the console and skips the tier.
- `loadSettings` takes `home` as a parameter with a default, not a `homedir()` call in the body. Every other module that resolves one does the same (`loadSkills`, `loadMemoryFiles`, `historyFilePath`, `sessionsRoot`). That is what lets a caller that already knows which home it serves read that home's files. The REPL's `options.home` and a test with a throwaway home are two such callers. A resolve in the body lets the wizard be pointed at one home while the settings load reads another. Project and local data is stripped before the merge so a dropped key cannot win by tier order. Each tier is parsed leniently for `perSource`, because a malformed tier must not take down rule attribution for the well-formed ones. A total failure of the merged result prints `Warning: invalid settings ignored` with the parser message and returns the defaults.
- `collectPermissionRules` reads the tiers in hierarchy order, so a later tier wins among the allows and `/permissions` can show which file a rule came from. Deny rules win regardless of tier, so this order affects allows and the view only. A tier is absent when it had no file or its file did not parse. A tier that is present always carries a permissions block, whose empty arrays contribute no rules. Under `allowManagedPermissionRulesOnly` the policy file is the only grantor. Everything below it is discarded rather than merged, so a project file cannot widen what policy allows. `RULE_SOURCE_BY_SETTINGS_SOURCE` gives each file the rule-source name that attribution and precedence use.
- `resolveMode` is the one place that turns the mode pair into an effective pair. It exists because the policy tier must be able to veto the unrestricted sandbox. `disableBypassPermissionsMode` keeps its name and spelling across the mode rename. It is a policy-tier key, and an admin writes it into the managed settings file. A rename of a key that lives in files we do not control breaks them quietly rather than loudly. The schema strips a field it has never heard of and reports success, so `loadSettings` prints no warning and the lockdown stops. A wrong type under a known key does fail the parse. A renamed key is the silent half. The name is a fossil of the old mode enum, where `bypassPermissions` was one value with two jobs. Of the pair, only "confine nothing" is something a policy file can take away, because the other half is what stops an unattended run. So `danger-full-access` comes back as `workspace-write` and the approval policy is left exactly as asked. A narrower confinement for the machine without new prompts for things it used to run without a prompt is the smaller change. A policy file that wanted both can set them itself. The function returns the reason for a downgrade. So the caller can tell the user why the mode they asked for is not the one they got.
- `networkAxisFrom` is the one place the network keys become a configuration, for the same reason `resolveMode` is the one place for the mode pair. A second place that does this arithmetic is a second answer to "what may this session reach". The two answers only have to differ on the one machine that nobody checks. The default is `enabled` with an empty table, and that is a statement rather than a filler. An empty table under `restricted` reaches nothing. So a `restricted` default turns a settings file that says nothing about the network into a session that cannot fetch anything. That is a silent, invisible break for the many people who never touch these keys. A value of `"networkAccess": "restricted"` is how you ask for that. The union in the schema is a convenience for the file and is collapsed here, so nothing downstream knows a rule has two spellings.
- `applySettingsEnv` lets a real environment variable win, because a settings file must not be able to redirect a key the user exported in their shell. It returns the names it applied and never the values, which are usually credentials.
- The `sandbox` axis is separate from `permissionMode` because the two are separate axes, and `PERMISSION_MODES` in `@labunbun/agent` is the list both sides read. `workspace-write` resolves to an OS-enforced policy on macOS and Linux. On Windows it resolves to a tool-layer one, a weaker guarantee that this build describes as such and not as confinement. Where that description reaches a user: `/permissions`, and only there. An earlier version of this comment said the weaker layer is named in `/doctor` and in the mode's own hint, and neither was true. `/doctor` has no filesystem-sandbox row at all. It calls `sandboxBackendFor` once, to compute the network caveat, and prints that only when the network axis restricts, which is not the default. The mode hints in `MODE_CHOICES` say nothing about the sandbox for `ask`, `plan` or `agent`. The only one that mentions it is `agentNoSandbox`, which describes the axis as off. So on a default-configured Windows install the filesystem layer is disclosed in exactly one place, and that is an under-disclosure rather than an overstatement. This is stated here because the cost of an error in it is a future `/doctor` regression. That regression removes all sandbox disclosure while a comment promises the fact is told elsewhere. `simulated.ts` carries the same fact about its own disclaimer, and gets it right.
- `networkAccess` is not derived from `sandbox`. The two are separate for the same reason the two sandbox keys are separate. A `workspace-write` that silently cut the network breaks `npm install` and `git fetch` for everyone who took the default. Confinement here is something the user asks for by name. The default is `enabled`, which is the behavior today.
- An empty `networkDomains` table under `restricted` reaches nothing, which is the fail-closed answer and the reason it is safe to leave unset. The restriction does not turn on because someone filled the table in. It turns on because someone set `networkAccess`, and by then an empty list is the answer `nothing, yet`.
- `trimOldToolResults` lets the cheap pass run by itself when the context crosses the compaction threshold. Older tool results become previews, and a summarization call happens only if that did not free enough. It is on by default, because the cheap pass only ever runs where the other answer is a summarization. It is a rewrite of text the model has already read, not a deletion of it. The full result stays in the session file, and large outputs are on disk. It costs no model call. Set it false to go straight to the summary, or use `/trim` to do the same thing on request.
- `backgroundShellNotifications` wakes the session when a background shell finishes on its own. On by default: the notice lets a long command run in the background, so the model does not have to ask for updates. The session hears once, with the exit code and the end of the log, and decides what to say. The message travels the follow-up queue, so a completion during a turn waits for the turn's natural end. Set false to leave completions to `BashOutput` and spend no turn on them.
- `gamepad.bindings` is deliberately not an enum. A button name that resolves to nothing becomes a line in `/doctor` and costs that one button. A check here rejects the whole settings file over a typo. That is the same bargain theme files strike for an unknown token.
- The `beetle` block names one model per member of the band. The choice decides what the user's money is spent on, which is the same class as `model` (see `PROJECT_TIER_KEY_POLICY`). A member set to `"session"` follows whichever model the session uses. A saved `models` map is what makes a later `/beetle <task>` skip the picker. Without one, either the block is absent or a hand edit left it empty, the next start asks again. The two budget keys are opt-in guardrails, and unset means unbounded. A band with neither runs until it is stopped by hand, which is the design. `maxTurns` caps each run. A member that wants another turn ends with `max_turns`, and a later message from the user is an explicit new run. `maxCostUSD` stops the whole band once its priced turns cross the amount. Zero and negative values are refused, because `stop before starting` is what `/beetle off` says, not a budget. `stallNoticeMinutes` is the quiet watchdog: a live member silent this long gets one transcript notice that names what it did last. It never stops anything. Unset reads as five minutes, zero turns it off, which is why this key alone accepts zero. Whole minutes only.
- `applyCatalogSettings` makes the providers and prices a settings file declares real. It registers the OpenAI-compatible providers so their models resolve, then applies the declared prices over the catalog's own. Both entry points call it once at startup, before anything resolves a model. A reference to a model that exists only in settings is unknown until it runs. A price is used only by whoever resolves the model afterwards. It is shared rather than written twice, so the two entry points cannot end up with two different costs for one run.

### Wizard flow

- The wizard asks questions, it does not decide: every answer ends up as an argument to `runMigration`, the same call the CLI makes. So the wizard cannot import anything that `labunbun migrate` refuses.
- `Import everything` answers the source and category questions with "every source found, every category" and goes straight to the plan. History is still asked about, because that one answer decides how much of the user's past is read. No default is worth a guess.
- A `null` history answer means leave that source's history alone. It covers three cases: the user said so, the picker was cancelled, or there is nothing to take. The wizard does not ask about a source with nothing to list, and reads nothing from it. Without an answer there is no scope to read under.
- The wizard lives with two facts of the dialog library, both visible in `packages/tui`. A question offers radio-style options and answers with the chosen label, with no multi-choice. A picker scrolls a long list but resolves to a single index. So "which sources?" is one yes-or-no question per source, and "which sessions?" is a picker whose first entry stands for "all of them".
- `MigrationDialogBridge` is structural on purpose: the TUI's `ReplAppHandle` satisfies it, and neither package has to import the other's types for that to hold. `MigrationWizardContext.cwd` is the project the sessions are imported relative to.

## Known traps

- A reader tested only at its own level is not evidence that anything calls it. The `historySourcePresent` gate lost its `t3-code` arm once and the loss was silent. With no arm the function fell through to `raw.agents.present`, another source's flag. So a T3 install with no agents tree got a plan with no sessions, while every direct test of a reader passed. The `mimocode-code` arm carries the same warning for the same reason. When you add a history source, add both its list arm and its gate arm, and test the gate.
- The same shape of failure applies to detection: one root is wrong for any source whose state lives in more than one place. Cursor and Trae have a CLI half and a profile half, and T3 has a production state directory and a dev one. The config root of OpenCode exists and is empty on a stock install. MiMo Code has four roots side by side, Alma has four unrelated ones, and Codewhale has two eras of the same tree. A detector that looks at one root calls the source absent on the machines that have it. Or worse, it offers the source as empty and imports from the other half anyway.
- The Gemini CLI shares `~/.gemini`, so it can never be an Antigravity detection root. The home-relative spelling and the detection answer are not always the same question.
- The reader of an OpenClaw session dispatches on `message.role`, not on the event type. OpenClaw puts the role on the payload rather than the event, and it has three roles where Claude Code has two. A `toolResult` is a first-class message rather than a block inside a user turn. A reader that keys on the wrong field imports no messages, while the report still says the file came across. To hand the same transcript to the Claude reader makes every line fail its `type` test and land in the count of non-conversation entries. The content block vocabulary is the same, so the three conversion helpers are near copies of the Claude ones rather than something new. OpenClaw's `stopReason` includes `error` and `aborted`, which fall through to the tool-call-or-stop default rather than dropped.
- Step keeps no prompt list on disk: its editor holds the last 100 entries in memory and they die with the process. That is why Step has no prompt-history note on disk: the report states its absence rather than an empty list.
- Do not replace the hand parser in `urlCredentialProblem` with `new URL`. The `URL`-based version measured 11 of 16 cases wrong, because the parser is least useful exactly where a pasted credential URL is. "The parser rejected it" is not "it is safe". The scan flags too much on purpose. The cost of a false positive is one server the user can add back by hand. The cost of a false negative is a live token in `.mcp.json` under a report line that says nothing in it is a secret.
- `parseJsonc` is not a general JSONC parser. Anything the vendor's `jsonc-parser` accepts and this scanner does not costs one settings file, which gets a report line rather than a silent loss. Do not "fix" it with a regex. A `//` inside a URL value and a Windows path separator are exactly what the regex version mangles.
- Two claims on one key in one run are invisible when the first claim is made, because `existing` is the file from before the run. The demotion scan in `claimScalar` runs over `items` backward and before the new line joins it. To move it earlier or later brings back the report line that said a superseded value came in.
- `--force` must be applied after the merge for hooks, because `mergeSettings` merges objects key by key. A forced `hooks` that merges like everything else keeps every event the target had. The skip line that told the user to run `--force` then describes a merge.
- Two comments in this tree disagree with the code, and the code leaves both as they are. The JSDoc above `placeholderNames` in `migrate-core.ts` describes a Codex `[mcp_servers.<name>]` rewriter that does not exist there. The comment in `migrate-history.ts` cites line 82 of `history.ts` for the recall filter that lives at `packages/coding-agent/src/history.ts:83`. Read the code, not the line number.
