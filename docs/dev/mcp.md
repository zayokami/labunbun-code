# The MCP client

MCP is the Model Context Protocol: a server process (or an HTTP endpoint) that offers tools, prompts and resources to an agent. The client lives in `packages/mcp/src/client.ts` and connects servers over stdio or StreamableHTTP, adapting their tools into the agent's registry under `mcp__<server>__<tool>` names (`client.ts:1-4`), on top of the official `@modelcontextprotocol/sdk` client (`client.ts:10-17`). The REPL and a `-p` run both connect servers and merge the tools into their sessions — the REPL starts the connect without awaiting it and merges when the tools land (see below), while a `-p` run awaits it, because its first prompt needs the tools (`interactive.ts:927-935`, `headless.ts:502`, `:577`); an editor session (ACP) does not — `session/new`'s `mcpServers` is ignored by design (`acp.ts:28-29`).

## Where servers come from

`loadMcpConfig` (`client.ts:755-775`) reads two files and merges them, project first: `<cwd>/.mcp.json` and `<home>/.labunbun/.mcp.json`. `settings.json`'s `mcpServers` is a third, user-tier source, validated entry by entry through `parseMcpServersRecord` (`:790-810`) — the settings schema keeps the value as `unknown` so one bad entry cannot fail the whole settings load, and an entry that fails is reported rather than dropped: "a server that never appears anywhere else is the one failure the user cannot debug" (`:777-789`). Entries take one of two shapes (`McpServerConfigSchema`, `:20-36`): `stdio` with a non-empty `command`, `args`, optional `env` and `cwd`; or `http` with a `url` and optional `headers`. The non-empty rule is deliberate — a bare `command: ""` used to pass validation and fail at spawn, where the platform's shell answered instead of the config error that names the problem (`:23-26`).

A file that cannot be read is reported, never swallowed: unreadable configs come back in `errors` (`:745-753`), and an invalid-JSON message does not quote the file's text, because that text can hold credentials (`:765-771`). The REPL prints each as `MCP config: <path> — <message>` at startup (`interactive.ts:1993`); a `-p` run prints the same as warnings (`headless.ts:484-486`).

## Connecting and staying fresh

`connectMcpServer` (`client.ts:595-732`) never throws: an invalid config or a failed connect comes back as a connection whose `error` names the problem (`:600-610`, `:722-731`). Two budgets bound it:

- **Connect + discovery: `CONNECT_TIMEOUT_MS = 30_000`** (`:41`). A server that accepts the connection but never answers was a startup hang; the timeout abandons the pending work and closes the transport, so a stdio server does not leave an orphaned child behind for the session's lifetime (`:215-238`, `:657-659`, `:717`).
- **One request: `CALL_TIMEOUT_MS = 60_000`** (`:43-48`). Every request against an already-connected server — a `tools/call`, a list, a read — runs through `withCallBudget` (`:292-324`), which aborts the request rather than racing a timer: the SDK turns the aborted signal into `notifications/cancelled`, so the server is told the request is off (`:296-301`).

Discovery reads every page of both lists (`listToolsFrom`, `listPromptsFrom`, `:240-277`): a server is free to split a list across pages, and reading one page used to look exactly like a complete list — "a server with 200 tools looked exactly like a server with the 50 that fit in page one" (`:245-248`). A server that repeats a cursor is not advancing, so the walk stops and says so instead of busy-waiting: `Warning: <label> repeated the page cursor "<cursor>"; the list from this server is incomplete.` (`:253-276`).

A `tools/list_changed`, `prompts/list_changed` or `resources/list_changed` notification refreshes the connection's snapshot in place (`:664-708`). The handlers are registered *before* the first walk, because the SDK drops a notification that has no handler and a change announced during discovery would otherwise fall into the gap between connect and the walk's end (`:664-670`); the initial walk still must not overwrite a newer snapshot with the one it started from (`:650-655`, `:712-715`). A refresh that fails keeps the last good snapshot — a server that stopped answering one list "has not thereby withdrawn what it already handed out" — and the failure goes to both audiences it has: the `/mcp` row that shows `connection.error`, and stderr (`:630-642`). A later success clears the error again (`:643-649`).

The one list a running session has to be told about is the tools: the agent holds them, so `onToolsChanged` exists for the host to move them into a live session (`:98-107`, `:692`). The REPL's handler is `createMcpToolRefreshHandler` (`packages/coding-agent/src/mcp-tool-refresh.ts:55-65`), wired at `interactive.ts:954-991`: it rewrites the session's list — non-MCP tools kept by name filter, MCP tools rebuilt from the connections' *current* arrays — and notes `mcp tools changed` on the cache tracker, because the tool block sits above the system prompt and one changed tool discards every tier below. The session is read through the host's `() => sessionRef` arrow at the call, never captured: `/resume` swaps it, and a connection outlives the swap; the connections are read at the call too, so a connection `/mcp approve` pushes mid-run counts — as does the startup connect, which is started without being awaited and lands after the mount by design; that landing, plus one refresh call, is what moves a late server's tools into the running session (`interactive.ts:979-999`) — and the command attaches the same handler to the connection it opens (`interactive.ts:3462-3467`) — otherwise that server's later changes would reach the subagent table and the band, which read the connections live, while never reaching the session. Those two tables follow for the same reason: the subagent `allTools` getter (`subagents.ts:179`, read at `:510`) and the band's `mcpTools` getter (`beetle.ts:435`, read in `#memberTools` at `:875`, passed through `beetle-commands.ts:97`/`:323`) resolve at the call — subagents per spawn, the band when `/beetle` constructs it, members and all — so both see a mid-session addition; before this both read a startup snapshot, and a tool the server gained was one they could never call. A `-p` run never sets the hook on purpose — it is one shot and ends before a tool-list change could reach anyone, so there is no live session to move a new list into; it still gets the refreshed `tools` (`headless.ts:512`, `client.ts:99-107`), and its subagent getter (`headless.ts:538`) answers a constant list for the same reason, so a parent's tools and a subagent's stay equal.

## Tool adaptation

`adaptTools` (`client.ts:479-572`) turns one walk of a server's definitions into agent tools. Both callers — initial discovery and the `tools/list_changed` rebuild — go through it, or a tool gained mid-session would be a different tool than the ones that connected (`:479-487`).

- The name is `mcp__<server>__<tool>` and the description falls back to `MCP tool <name> from <server>` (`:495-499`).
- The input schema is translated from JSON Schema to zod by `jsonSchemaToZod` (`:158-213`), as faithfully as JSON Schema allows: `oneOf`/`anyOf` before `type` (`:170-178`), string enums as `z.enum` and primitive enums as literals (`:179-197`), nullability in both spellings the wild uses — `nullable: true` and `"null"` among the type values (`:110-118`) — draft 2020-12 type arrays and tuple-form arrays (`:143-153`, `:198-212`), and `integer` mapped to the same validator as `number`, because JSON draws no line between the two and rejecting `2.0` for an `integer` field would be a false positive on the server's own declared shape (`:136-140`). Object properties pass through rather than strip: a parsed input that silently dropped keys the model sent would hand the server a different call than the one requested (`:130-133`). The only fallback is `z.unknown()` for shapes with no faithful equivalent (`:155`, `:196`, `:205`).
- Execution hints are the server's to declare: `isReadOnly` is `true` only when `annotations.readOnlyHint === true`, and `isConcurrencySafe` follows the same predicate (`client.ts:545-548`). Absent, `false`, or a `destructiveHint`/`idempotentHint`/`openWorldHint` alone keeps the fail-closed default — an unannotated tool is not known to read only, so it is neither admitted as read-only nor run in parallel. Plan mode reads exactly this answer through `collectReadOnlyToolNames` (`packages/agent/src/permissions.ts:534-542`), so an MCP tool the server declares read-only needs no special case. There is deliberately no `maxResultSizeChars` override: results flow through the same pipeline budget as every other tool, so a server cannot outgrow the conversation by answering over the wire, and the same truncation marker says what was cut (`client.ts:549-552`).

A call has two ways out, followed by two signals (`:506-568`): the run's own abort (Esc) and the call's timer. A run cancelled before the call starts never reaches the server — an abort event does not replay for listeners added after it, so the already-aborted case is handled rather than subscribed to (`:507-512`). A timeout reports `<server>/<tool> timed out after <ms>ms` and is the cause named even when both paths ended in an abort (`:542-553`). Every other failure goes through `sanitizeMcpError` (`:50-75`): secret *values* from a stdio server's `env` or an HTTP server's `headers` are redacted — longest first, every occurrence — while key names stay, because config errors quote the value they rejected and connection failures can echo the spawn environment (`:50-58`, `:71-73`).

The failure message also rides the tool-call update channel: `ctx.onUpdate({ mcpError: message })` before the result lands (`:546-552`, `:559-564`), and the TUI renders it as the call's streamed text (`packages/tui/src/ui-state.ts:345-362`) — "dropping that report left a server that timed out saying nothing at all on screen".

## The `/mcp` consumer surface

The four read functions are exported for the REPL: `listPrompts`, `getPrompt`, `listResources`, `readResource` (`packages/mcp/src/index.ts:3-27`), each bounded like a call and each reading the live server rather than the connect-time snapshot ("the answer as of the command is the point of asking", `interactive.ts:3486-3488`).

- `getPrompt` (`client.ts:457-477`) flattens each message's single wire block into `McpPromptBlock`; an unknown block survives as its type name rather than printing nothing, which would read as "the message was empty" (`:431-455`).
- `readResource` (`:382-405`) returns `text` or base64 `blob`, exactly one per entry.

In the REPL (`interactive.ts:3447-3614`): `approve`, then the read subcommands `prompts <server>`, `prompt <server> <name> [key=value ...]`, `resources <server>`, `resource <server> <uri>`. A bare argument is answered with the `key=value` shape rather than passed along (`:3525-3532`); a named-but-unconnected server gets the usage plus "Unknown or unconnected MCP server" (`:4414-4420`); a failed read says so rather than leaving a blank screen (`:4422-4428`). Everything renders as a transcript entry capped at `RESULT_TEXT_CAP` and never enters the conversation (`:4399-4406`). Prompt blocks a terminal cannot show are named and counted — `[image image/png]`, `[binary application/octet-stream, N bytes]` — rather than mangled (`:4438-4447`, `:4482-4486`). The bare `/mcp` view lists each connection as `✓ N tools, N prompts` or `✗ <error>`, then pending approvals and unreadable config files, so the list cannot read as complete when it is not (`:3594-3612`).

## Approvals

A project server ships with the repo's `.mcp.json` — a cloned, untrusted repo could otherwise auto-spawn arbitrary commands or connect to arbitrary URLs with zero user action — so project-scoped servers need one-time approval (`interactive.ts:917-926`). Servers from `settings.json` are the user's own configuration and win over a project entry of the same name, approval gate included (`:909-913`); user-scope `~/.labunbun/.mcp.json` is trusted like any other setting the user wrote (`:901-902`).

The approval is remembered at `~/.labunbun/projects/<cwd-slug>/mcp-approved.json` (`approvalStorePath`, `client.ts:847-849`). That location is the fix for a hole: it used to live in `<cwd>/.labunbun/settings.local.json`, which nothing ever wrote an ignore rule for, so a cloned repo could ship the file and pre-approve its own servers; approvals now live where repo contents cannot reach them, keyed by `sanitizeCwd` exactly as sessions are (`:829-846`). Approvals from the old location are deliberately not read: "re-approving a server costs one `/mcp approve`, reading a repo-controlled file costs everything" (`:839-842`). `approveMcpServer` (`:895-928`) reads-modifies-writes; an unreadable store is not silently overwritten with just the new name — the corrupt file is moved aside (best effort) and the warning says where it went and that earlier approvals are not in effect until re-approved (`:905-922`). The write itself is by replacement, which is `crash-consistency.md`'s territory (`:867-893`).

`connectAllMcpServers` (`client.ts:947-967`) connects in parallel and, when handed an approval set, answers an unapproved server with an `error: "not approved"` row instead of connecting (`:954-962`). The REPL computes the set from the three sources and connects only those (`interactive.ts:918-944`); `/mcp approve <name>` persists the approval, connects the server, merges its tools into the session, attaches the refresh handler to the new connection and notes `mcp tools added` on the cache tracker (`interactive.ts:3449-3483`). A `-p` run cannot approve, so it skips unapproved project servers with a warning naming them and the fix: `Warning: skipping unapproved project MCP server(s) <names> — approve in an interactive session (/mcp approve <name>).` (`headless.ts:493-504`). Pending approvals surface in `/mcp` and in `/status`'s MCP row (`interactive.ts:3240-3243`). Both hosts disconnect every opened connection at teardown, best-effort (`client.ts:974-983`; `headless.ts:817`, `:897`, `interactive.ts:2230`) — the REPL first gives a startup connect still in flight two seconds to land, so a quit right after launch does not orphan servers it had already spawned (`interactive.ts:2229-2230`).
