# Tools

This document describes the built-in tool set in `packages/tools/src`. It covers the shell tools, the file tools, the search tools, the task board, the web tools, and the operations layer below them. The long design comments in the source files moved here. This text keeps their facts, their measured numbers, and their dates.

## Purpose

The package gives every built-in tool one home. Below it sits one backend boundary, the `Operations` interfaces.

Tools call `FileSystemOperations` and `ExecOperations` instead of `node:fs` or `Bun.spawn` directly. This design makes them testable with in-memory fakes. It also lets a remote or container backend slot in later, with no change to the tool logic.

`createAllTools` builds the default set. The order of the tools is frozen there, because the wire-tool list must stay prompt-cache stable. Core file and shell tools come first. The task tools come next. The web tools come last.

The package also holds the parts that must exist once, not once per caller. These parts are the `.gitignore` subset, the path containment guards, and the background shell manager.

## Behavior

### Shell execution and background tasks

The Bash tool runs one command line through the platform shell. On Windows it prefers a POSIX-compatible shell, such as Git Bash or MSYS2, because most agent commands assume POSIX syntax. It falls back to `cmd.exe`. Other platforms use `/bin/bash` with `-c`. On Windows the arguments are `-lc` for bash and `/d /s /c` for `cmd.exe`.

The Windows search order is `LBB_BASH_PATH`, then `C:\Program Files\Git\bin\bash.exe`, then `C:\Program Files\Git\usr\bin\bash.exe`, then `%USERPROFILE%\.bun\bin\bash.exe`, then a PATH scan. The conventional locations come first, because that install is a deliberate one. `LBB_BASH_PATH` comes first of all, because it is where the user pointed the tool.

PATH is the long tail. An install under scoop, chocolatey, or another drive used to be a machine where every command quietly ran through `cmd.exe`. The POSIX-shaped commands then failed one at a time. The PATH scan reads only entries that start with a drive letter. A shell that is itself MSYS hands its children a PATH of POSIX paths, such as `/usr/bin`. No Windows process can open those paths. The same directories sit behind them under their real names.

A `bash.exe` on PATH is rejected when it is the WSL launcher of Windows itself. It answers to the same name and sits in directories that are on every PATH. It starts a Linux VM, and every command this tool runs names Windows paths. The check covers `%SystemRoot%\System32\` and `\Microsoft\WindowsApps\`. `LBB_BASH_PATH` is exempt from that rule, because the user named it. A candidate must also be a file. A directory named `bash.exe` is not a shell.

Bash inputs are `command`, `timeout` in milliseconds, `description`, and `run_in_background`. The timeout default is 120000, the minimum is one and the maximum is 600000. The tool is not read-only and not concurrency safe. Its `overflow` mode is `"spill"`, because command output happens once. A build that fails ends its report with the error. A head-only cut throws that part away.

The live preview pushes at most one update per 100 ms (`BASH_UPDATE_INTERVAL_MS`). The stream is a preview and not a transcript, because the full output arrives with the result either way. Ten updates a second look the same as every chunk. Without the limit, a command that prints thousands of lines a second drives one store update and one React render per line. The preview buffer keeps the last 30000 characters (`MAX_PREVIEW_CHARS`). It is not the result.

The sandbox policy is read per call and not captured at construction. `/mode` can change the sandbox mid-session. A tool that held the value from its build keeps the old one in force. The policy is built before the background branch, because the manager spawns the background path and not `exec`. To leave it out makes `run_in_background: true` a way around the sandbox.

`writableRoots` was gone from that call, and its absence had two results. The policy said "the workspace and nothing else". `mktemp` then had nowhere to create its directory, and `npm install` had nowhere to write its cache, under the mode that every user gets by default. Nothing leaked, and the policy was exactly as narrow as it was built.

`home` and `tempDir` are parameters and not reads of the process. The temp directory and the package caches are per-user paths. This repository's rule is that a reader takes its home as an argument. `os.homedir()` reads only the Win32 environment block. On linux and macOS a reader that calls it reads the real config of the developer. That defect reached CI once, and the `source-env-coverage` test exists to catch it.

With no background manager the tool returns an error result instead of a throw. An unavailable path is an answer the model reads, not an exception it cannot see. The message names the constraint and not the mechanism. A background shell outlives the call that starts it. The Windows container backend runner does not return until the child exits.

Adoption is opt-in, and only when a target for the process exists. A command that outlives the wait is adopted rather than killed. A long build or test run then survives the timeout that gave up on it. It is the same process, not a restart. That is the difference between the work kept alive and the work done twice. With no manager the timeout still kills, because there is no shell id to point a poll at. `adoptedId` and `handedOff` are set together, so the handoff branch is a pair and not a guess. Chunks that arrive after the adoption go to the shell log through `background.append`. They do not go to the preview, because the tool call already returned.

In the result text the spill pointer leads and the exit status sits right behind it. A long result is cut at both ends on its way into the conversation. Two lines must survive any cut. They are the path to the rest of the output and the answer to whether the command worked. The cut in the pipeline recognizes the header and reuses the file from the executor. It does not spill a second copy. Bash itself cuts nothing. The executor bounded the capture. A cut here keeps only what the conversation already has, and it drops output that no file holds.

Both streams over the bound at once put two truncation notices in one result. The pipeline's cut reads only the first, so the second count goes stale. That is accepted. The file holds every character either way, and a marker format with ordinals is not worth the rare case.

The background manager keeps one log file per shell, named `lbb-<id>.log` in the temp directory. Ids have the form `shell_<n>` from a module counter. `MAX_SHELL_OUTPUT_CHARS` is 30000, the most that one read returns. `MAX_RETAINED_SHELLS` is 16.

`readTail` returns the last `maxChars` of a file without a read of the whole file. One character is at most four UTF-8 bytes. A byte window of `4 * maxChars` always holds at least that many characters. The window opens at `bytes - window`. A window that opens in the middle of a character decodes its leftover bytes as a replacement character. That character sits at the front of the window, ahead of everything kept. The text that comes back is a suffix of the file and holds only characters the file has. Two events lose text. The window did not cover the file, or it did and the characters still did not fit.

Log writes are best effort. A shell's output is diagnostic, so a failed append must not take the shell down. An error that surfaces from an event handler does exactly that. A gap in a log is better than a dead shell.

Both spawn paths attach the same completion handlers. The handlers mark the shell ended unless a kill already did. They record the exit code, and they put the code in the log. A reader who only ever saw the file then learns how the shell ended, and not only what it printed along the way. A spawn `error` writes a note and sets exit code 127. `close` sets the real code, with a default of 0.

Only the first end event is acted on. A failed spawn can surface twice, as an `error` and then the `close` behind it. The stamp decides. Whoever arrives first stops the clock and does the work. A second event only updates the record. A killed shell is not a completion, because the user asked it to stop. Nothing is woken to say that it did. Its record is still stamped, because an ended shell is an eviction candidate however it ended. A subscriber's bug must not take the shell record down with it. That is the same stance as the event dispatch of `AgentSession`.

Every shell stays pollable after it ends. BashOutput reads that record, and a caller who missed the announcement catches up there. Ended shells are kept newest-first up to `MAX_RETAINED_SHELLS`. The older ones beyond that are dropped, because the map otherwise keeps a record per command for the life of the process. A shell that runs is never a candidate. Its record is the only handle that can still kill it.

`onComplete` is the hook behind "tell me when it is done" and not "poll it". The code calls it from the end event of the process, before any eviction. The log is then still where the subscriber last saw it. It returns the unsubscribe function.

`start` spawns the shell directly and not through `Operations.exec`. That made it a second, unwrapped spawn path. The moment a filesystem sandbox existed, `run_in_background: true` became a one-word bypass around it. The sandbox then looked active for every command a user ran in the foreground. The wrap is resolved here, because the wrapper must be the parent of the shell. This method is the parent of the shell.

The network half of the policy is resolved here too. That was the second instance of the same bypass. The wrapper comes from the filesystem half of the policy, and the proxy variables were never added to the spawn. A backgrounded command then reached the network unconfined, while every foreground command was held by the proxy. The proxy alone enforces `networkRules`, and no second reader of the domain table exists. Those variables were the whole axis. The method is async because a start of a listener is not something a synchronous spawn can do. A `start` that waits keeps the two spawn paths on one lifecycle instead of one listener each.

The Windows container backend refuses this path. It does not fall through to the bare shell. `bash.ts` named this exact hole when it threaded the policy in. The container kind makes the hole real in a way that the simulated answer never did. A foreground command under the same session policy runs confined. This one runs with nothing around it. The reason to refuse is the runner. `runConfined` is a synchronous FFI wait that does not return until the child exits. A background shell's whole point is a child that outlives the call. Examples are a server, a watcher, or a test suite that reports progress. To hold this method until the process died blocks the session. The only honest options are to confine it through an async rewrite of the spawner, or to refuse to start it. This build does the second.

The proxy variables go last, for the same reason as in `exec`. What confines this command outranks what this process inherited. A manager with no policy spawns with no extra environment of its own.

`adopt` registers a process that already runs. A foreground command arrives in that shape when it outlives its timeout and the executor hands it over rather than kill it. Everything the class already offers works on the adopted process. `output` tails the log, `kill` stops the tree, and `completed` resolves with the exit code. Output is the one thing that is not re-attached, because the exec call's own listeners keep both pipes. A process that is caught mid-stream has no clean point at which to switch readers without a race between the two. Those listeners forward what they read through `append`. Whatever was buffered before the handoff is written first, so the log opens with what the command had already printed.

`append` is the write path for an adopted shell. An unknown id is ignored, which is the same best-effort stance as the log write itself.

`completed` resolves once a shell ends, with its exit code. A caller has no way to learn that a shell finished except through a read of `status`. The only available technique is one poll after another, and a poll needs a budget. A budget is an assertion about the speed of the machine that nothing enforces. Measured on macOS CI: a test that waited on `50 × 100 ms` used the whole budget with the shell still `running`, and it failed. The very next test in the same file spawned and polled the same way, and it passed in 113 ms. The process already announces its own end. `start` installs the handler that marks the shell completed before this method can be called, so `completed` hands that over and does not guess. A shell that already ended resolves at once. A shell that never ends still hangs here, and that is deliberate. The caller owns the timeout, so a hang fails the caller. It is not read as a slow machine. An unknown id resolves with `null`, the same answer that `get` gives. The promise listens for `close` and for `error` and takes whichever arrives first. That matters because `start` marks a spawn with no process behind it as completed with 127. Which event Node emits first for a failed spawn is not claimed here. The claim is only that the promise cannot hang on one.

`output` reads the log from an offset and not whole. A caller polls a shell while it runs, so the log only ever grows. A dev server left up for an hour is otherwise read whole, once per poll, as bytes and again as a string. The poll only needs the last few lines. The read starts at an offset instead. What it skipped is said out loud, together with the path to the whole thing. A tail is a window on the log and not the log itself.

`kill` returns false when the shell is not found or not active. On Windows it runs `taskkill /pid <pid> /T /F`. If `taskkill` itself does not spawn, the method falls back to the direct signal. The process then does not linger after the tool reported it killed.

BashOutput reads the accumulated output of a background shell, and it is safe to call again for progress. Its status line shows the elapsed seconds while the shell runs, and the status with the exit code after it ends. An unknown id is an error. KillBash stops a background shell that runs and kills the whole process tree. A failure reports that the shell was not found or not active.

### Edit, read, write, and file state

The Edit tool does exact string replacement. Two gates sit in front of the write, and a diagnostic behind it says where an edit went wrong. The split of the work is measured, not assumed. The measurement used the history of this repository itself (`edit_probe.ts`, 99 hunks over 60 commits):

```text
UNIQUE, one call   74   74.7%
NON-UNIQUE          1    1.0%
NON-CONTIGUOUS     24   24.2%
```

The 24.2% bucket was decomposed before anything was written (`edit_shape_analysis.ts`, same corpus). All 24 of the 24 are hunks whose removed lines are separated by kept context lines. That means two or more separate edits in one diff hunk. None of the 24 came from quotes or from whitespace. So the honest sense of that bucket is "needs more than one call" and not "impossible". No amount of normalisation in this file moves it. The two strategies below can express one call, and a third fuzzy pass does not reach one of the 24.

Fuzzy match is refused outright. The reference build runs four passes of it. The measured result is a stale patch that lands somewhere plausible-but-wrong instead of a failure. The failure mode of this build is a loud refusal with a diff attached. A confident wrong edit is worse than a wasted turn.

What is left is where a model really loses turns. Those places are the two refusals in front of the write, and the not-found message. In the reference, the not-found message hands the model back its own input plus a boolean. It has no line number, no text around the region, and no statement of what differs. Indentation drift is the single commonest cause of that miss.

`call` returns an `EditToolResult`. `newString` is the replacement text as written to disk, after quote restyle and newline style conversion, if either one ran. `transformations` names every change that moved bytes, and it is empty when none did. `ToolResult` has no room for these two. They are deliberately not in `content`, because the pipeline builds the model-visible message from `content` and `isError` alone (`packages/agent/src/pipeline.ts:41-42`). A field that only the caller can see is a second account of the same edit. The caller that renders a diff reads them. The model reads the text, which repeats the on-disk string whenever that string differs from the request. The reference returns the string from before the transformations. A model can then believe it wrote X while the file holds Y. Here the field and the `content` text are the same string. The tool checks it against a read-back of the file after the write: `readBack.slice(index, index + newString.length) === newString`.

The two transformation names are `quote-style-preserved` and `line-endings-preserved`. Each one is present only when it changed bytes. Transformations are named rather than counted. A model that is told "1 transformation" cannot tell whether its quotes moved.

Gate one asks that this session read the file, and not a page of it. The reference has both checks in code. Before this build they were a prompt line, and a prompt line is a request. A model, or an injected instruction inside a file it never opened, can decline a request. A paged read with `offset` or `limit` is refused outright, not made conditional. The model saw a disjoint slice and has no evidence about the rest of the file, while the replacement applies to all of it. A full read that was cut is a different case, and the tool does not refuse it here. `partialView` marks the 2000-line window, a line over the per-line cap, and a spilled middle. Such a read is an honest prefix of the file. The question worth a check is whether anything touched the file since the read, which is gate two.

Gate two says that the file did not change since the read. `stalenessOf` has two rules, in this order, and the order is the point.

1. Content, when a whole file is there to compare. An uncut full read recorded the file's own bytes, so a difference is proof that the file moved, whatever the clock says. This rule also decides the Windows case in the permissive direction for free. OneDrive, Dropbox and Defender touch mtime on files whose bytes did not move. A gate that refuses on that basis is a gate that users disable. When the bytes are the same, the edit lands on exactly what the model saw. The rule then stops, and it never calls `stat`. That is why the carve-out costs nothing on the common path.
2. mtime, when nothing is there to compare. That means a read that was cut, so `seen.content` is a prefix and not the file. The baseline is the file's own mtime as recorded with the read. The question "did anything touch it" is then asked in one clock: the file's against itself. The old rule compared the file's mtime against the instant of the read. It refuses in both directions in which the two clocks can disagree. A file whose mtime runs ahead reads as changed even when nothing touched it. The causes are skew, coarse timestamps, or a runner mid time-sync, and Windows CI produced that live. When no mtime was recorded, the rule falls back to the read instant. A small positive tolerance absorbs float error there, and the direction stays refuse.

`MTIME_TOLERANCE_MS` is 1. That one millisecond absorbs float error between two clocks and nothing else. The asymmetry is deliberate. A false "changed" costs the model one re-read, and a false "unchanged" costs it a wrong edit. The number is not "one filesystem tick". On a filesystem with coarse timestamps, a rounded-down comparison widens the window in which a real change reads as no change.

Match strategies: exact first, then curly-quote normalisation, and nothing else. Whitespace normalisation is refused for a different reason. It does not make the match correct, it makes the match possible. That is the difference between a loud refusal and a write somewhere plausible-but-wrong.

The length rule matters here. `normalizeQuotes` maps one code unit to one code unit. An offset found in the normalised text is the same offset in the original. `oldString.length` characters from it are the same characters. Every line of the second branch of `findMatches`, and every slice in the splice, rests on that. A normaliser that grew or shrank a string makes every match land at the wrong offset. The shrink happens through a map of `...` to a single ellipsis character, a fold of a ligature, or a strip of a zero-width joiner. The failure is a wrong edit that looks plausible, not an error. The test file asserts the property with `QUOTE NORMALISATION IS LENGTH-PRESERVING`.

`normalizeQuotes` maps the eight curly quotation characters `“ ” „ ‟ ‘ ’ ‚ ‛` to `"` or `'`. Every key is a single code unit inside the BMP, so `normalizeQuotes(s).length === s.length` for every string, astral characters included. A map that changes length breaks every match in the file, silently and plausibly. Such a map is a multi-character replacement or a curly quote outside the BMP.

`locate` returns every occurrence with no overlap, and it steps by the length of the needle. No overlap is what the replacement does: `"aaa".replaceAll("aa", "b")` is `"ba"`, one occurrence. A count of the overlap at index 1 reports a second replacement that never happens.

An empty needle is the one input that silently rewrites a file. With `replace_all` it inserts between every character. Without it, `content.replace("", x)` prepends. `validateInput` rejects an empty `old_string`, but that runs in the tool pipeline and not inside `call`. An embedder that calls `tool.call` directly reaches `locate`. The guard belongs where the loop is, because a caller that cannot reach the pipeline must still be safe. Measured: `findMatches("abc", "")` did not return in 12 seconds and had to be killed. It does not throw, so nothing catches it. The caller learns nothing and the process spins at 100% CPU. The step `from = at + 0` never advances, so the loop appends an index on every pass.

Quote restyle applies to the replacement only, never to the match. `quoteStyleOf` answers `curly`, `straight`, `mixed`, or `none`. A kind of quote that the text does not use cannot outvote the kind that it does. Prose with one straight apostrophe is straight-quoted text and not mixed text. `agreeOnQuoteStyle` gives one style for several regions, or `mixed` when they disagree. With `replace_all` every occurrence is replaced by the same string, so a disagreement means that no restyle can be right for all of them. A `mixed` verdict sends the replacement through unaltered. That is the honest outcome: the bytes of the model, and `transformations` empty to say so.

`toCurlyQuotes` opens on the first occurrence of each kind and closes on the second, in turn. The open and close choice is a heuristic, because a file cannot say which `"` opens a quotation. That is exactly why this function only ever runs on the replacement. It is always named in `transformations`, and it is skipped entirely when the regions disagree. `toStraightQuotes` is `normalizeQuotes`.

`detectLineEnding` picks the style of the file itself by majority: `crlf * 2 > lf ? "crlf" : "lf"`. A file with no newline at all is LF. There is nothing to keep in that case, and the other answer adds a carriage return to a single-line file. The reference rewrites every file it touches to LF. This repository has a recorded CRLF problem, namely no `.gitattributes` with `core.autocrlf=true`. A Windows worktree is then CRLF while the blobs are LF. To copy that default reproduces the problem here, one file per edit. `applyLineEndings` rewrites bare newlines to the style of the file and leaves a lone `\r` alone. Only bare newlines are touched, and only because the model builds its `new_string` with `\n` whatever the file uses. A lone `\r` inside a string literal is far more likely to be a character than a newline that somebody meant.

The splice takes its slices from the original content at the original offsets. Under quote normalisation the spelling of the model is not what is on disk. To replace `input.old_string` literally corrupts the bytes around the match. A deletion also eats the newline that follows it. An `old_string` for a deletion almost never ends in a newline. A model that deletes a block usually quotes it without the blank line at the end. Without this rule every deletion leaves a blank line behind. The rule is scoped to deletions on purpose. A replacement whose old text stops in the middle of a line must not swallow the newline, or the line after it is glued on.

After the write, the tool reads the file back and checks two things, because they can fail apart. The whole file is what the tool composed. The region that is claimed as `newString` really holds that string and not a neighbour of it. The read is cheap, at one read of a file that is already in the OS cache. It is the only thing that turns "the replacement is on disk" from an intention into a fact.

The read record is refreshed after a successful edit, or the second edit in a conversation fails against the output of the first one. A fresh mtime is part of the same refresh. A cut-view record whose baseline predates this write refuses the next edit as changed.

The miss diagnostic is `explainMiss`. The not-found case is the worst-served path in the reference file and the most frequent one. Its cause is indentation drift, and the reference answers with the input of the model and a boolean. This rule is deliberately narrow, because a wrong suggestion costs more turns than no suggestion. A wrong suggestion is re-sent, fails, and leaves the model with two contradictory strings. No suggestion leaves it with the line numbers and the file.

A suggestion is offered only when all of these hold.

- An anchor line was found exactly once in the file, so the region is located and not guessed.
- The file has a line for every line of `old_string` at that offset, so nothing has to be invented at the edges.
- Every line pair is equal modulo whitespace at the start of the line and a `\r` at the end, and nothing else. The model is off by indentation or by the newline style, not by content.
- That string is in the file exactly once, checked with the real matcher. A send of it back can then neither fail nor be ambiguous.

The last condition is what makes the first three safe. The suggestion is literally a slice of the file, so it is correct by construction. Every other cause of a miss is declined and reported as line numbers instead. Those causes are a wrong line, a renamed symbol, or a stale read.

A second route answers one cause: a block that is the text of the file modulo written-out escape sequences. That means a literal `\n`, which is a backslash and the letter `n`, where the file has a real newline, or the reverse. The anchors cannot line up there, because the block has the wrong number of lines before anything is compared. `detectEscapedMiss` respells the block first. The suggestion is that respelled text, which still must pass the uniqueness check. Escapes are reported and never silently unescaped. A matcher that guessed which backslashes the model meant lands plausible-but-wrong edits.

`detectEscapedMiss` handles both directions, and both lose turns in a session. The model can write an escape too literally. That is `\n` turned into the two characters backslash and `n`. The model double-escaped a JSON string, and the file has a real newline. The model can also write one too rarely, as a real newline where the file holds the two characters. That happens when the text under match is itself about escapes, and the test fixtures of this repository are full of them. It also happens when the model unescapes something it copied out of Read. To fire, the respelled block must be in the file exactly once. The code checks that with the real matcher. It then checks the slice itself, because under quote normalisation the matched text can be the spelling of the file rather than the needle. That bar keeps this from a guess. A miss with one plausible other spelling anywhere in the file is reported. A miss with none falls through to the indentation machinery unchanged.

`locateAnchor` tries the first line of the model, then its last line, then a longest-common-prefix scan. That is the order of the reference, for the same reason. A candidate must be in the file exactly once to be used. A repeated line, such as a line with only a brace or a `return`, locates nothing. Alignment on the wrong one of two produces line numbers that are confidently wrong, which is worse than no line numbers. The search tries the line exactly, and then with the indentation at the start dropped. A block whose first line is indented differently from the file is the commonest case there is. The last resort is bounded on both axes. It is the only quadratic pass in the file, and it runs on the failure path of every miss.

The diagnostic bounds are `MAX_REPORTED_DIFFERENCES` 3, `MAX_ANCHOR_CHARS` 400, `MIN_ANCHOR_PREFIX` 8, `MAX_SCAN_LINES` 50000, and `MAX_SCAN_ANCHORS` 32.

- Three lines that differ is the point where a model has enough to act. It is also few enough that the diagnostic fits in the result it is attached to. The suggestion covers the whole block when one can be trusted, so the count is the fallback and not the main channel.
- A "line" longer than 400 characters is a minified file, so the fallback scan ignores it.
- Eight shared characters is the shortest prefix that counts as "this is the line you meant".
- 50000 lines bounds the one pass over anchors and file lines.
- 32 anchor lines is the most that the scan tries.

The diagnostic has one order trap. The check for a `\r`-only difference must come before the equality check. Both sides were stripped on the way in, so a CRLF-only drift arrives as two equal strings. A check that sits after the equality test never sees it. That was the whole bug. The branch written for it sat after the `continue`, so it was dead. A CRLF file then drew the same "the lines are the same bytes, but the block is not contiguous" answer as a genuinely wrong block.

The `\r` at the end of a CRLF line is stripped for the comparison and for the render. A difference that is only the newline style then does not render as two strings that look the same. A `\r`-only difference is named in the notes and not listed among the lines that differ. Two strings that look the same in a differences list is how the bug hid the first time.

Neither note is offered once the block is unrecoverable. `indentOnly` is set by any one line that differs by indentation. A block can differ by indentation on one line and by content on the next. It used to print a note about whitespace directly above a sentence that says no corrected `old_string` is offered. That told the model both things and sent it down the wrong path. A note that contradicts the sentence under it is worse than no note. The escape note takes precedence over both, because the comparisons were made against the escaped spelling. A "whitespace only" or "CRLF" verdict is then about a string that the model did not mean to send.

`renderMiss` adds the three things that the reference omits. They are a line number, the text of the file at that line, and, when one can be trusted, an `old_string` to send back. With no anchor there is no region to point at, and the generic advice is the whole message. The escape diagnostic is the other case, when it respelled the block, and the corrected text is then the useful part. `declined` is non-null whenever `suggestion` is. The fallback text exists so that a future branch cannot render "undefined" into a message that the model must act on. `quoteForDisplay` escapes `\r`, `\n` and `\t`, because a model has to see a space at the end of a line to fix one.

`miniDiff` renders a unified-style hunk around the first replacement. That is enough for the UI to show what changed without a full diff engine. It takes the offset rather than a search for `oldString`. Under quote normalisation the string on disk is not the one the model sent. A search with `indexOf` on the spelling of the model returns -1 for the very edit that needed the diff. Lines are shown without the `\r` at the end. A diff that is rendered in CRLF and pasted into a terminal is a diff with a blank line after every real one. The hunk carries 2 lines of context (`DIFF_CONTEXT_LINES`).

The Read tool returns content with line numbers in `cat -n` style. It reads up to 2000 lines by default, with `offset` and `limit` for long files, and it cuts a line at 2000 characters. The tool marks the cut line with a `…`. `MAX_RESULT_CHARS` is 200000. 2000 lines of ordinary prose is well under it, while 2000 lines of generated JSON on one enormous line is not. Either way the answer to a cut read is a smaller range and not a bigger result.

`readOnlyRoots` are directories outside the workspace that Read may still open. The app's tool-output spill directory is the one in use, where results that are too large for the context are kept in full. Read gets this and nothing else does. Write and Edit go through `guardWritablePath`, which has no such escape. The file that a spilled Bash result points at is a dead end otherwise.

Containment decides the workspace boundary, so "outside workspace" reads the same here as it does for Glob, Grep, LS, Write and Edit. The only way past it is a root that the caller named. That question is asked of a `read` entry and not of a list that this file keeps. A root is then sayable in one place, and the same entry is what stops Write from a write there.

`ctx.sandbox` is deliberately not consulted here. The boundary is the boundary of the application, not of the mode. The same file is readable in Agent and in the mode with no sandbox, just as the write tools' `.git` rule holds in every mode. What the sandbox axis governs is the shell. The kernel confines it on macOS and Linux, and nothing confines it on Windows. See `readableRootsPolicy` for the measured result: a thread of the mode through here widens the roots.

Containment resolves the canonical path before it compares. It collapses `.` and `..` segments, and it resolves the links in the part of the path that exists. `realpath` alone is not enough, because the target of a Write does not exist yet. `realpath` also throws when any segment of the path is absent. The code walks up to the first ancestor that does exist, resolves that one, and appends the rest as written. A symlink or a Windows junction inside the workspace that points outside it, or at a `.git`, is then visible to every check. The checks compare the resolved target, not the spelling that the model named. A Windows realpath can come back with an extended-length prefix. The code strips it, so the result compares equal to the paths that callers pass in.

`describeReadFailure` names which failure Read hit. The message that it replaced, "File does not exist or cannot be read", was three answers under one name. A path with a typo, a directory, and a permission problem all read the same, so the next move of the model was a guess. `ENOENT` and `ENOTDIR` report that the file does not exist. `EISDIR` reports a directory and suggests LS. `EACCES` and `EPERM` report a permission problem. Anything else reports that the file is not readable and includes the code. The codes are the codes of Node, carried through both `Operations` implementations untouched. `EISDIR` is measured on Windows and on POSIX. `EMFILE`, `EBUSY` and the like say nothing about whether the file exists. That branch claims nothing beyond a file that is not readable right now. The rejection value is kept rather than folded into a boolean. `typeof` is used instead of `instanceof Error`, because a rejection value is whatever the executor treats as one.

Read records what the model is about to see, and every error path returns before that point. So an entry means that the read worked. A file that is absent, one that is unreadable, and an offset past the end all leave the previous record alone. None of them showed the model anything. The recorded `content` is the shown lines joined, not the rendered text, because a gate asks whether an `old_string` is in what the model saw. The six-column gutter of Read puts a tab between every pair of lines. The gate then answers that question about a file that the model has not seen. For an unpaged read with nothing cut, that string is the file byte for byte.

Three things make the recorded string something other than the whole file. All three are things that the caller did not request with a page. They are a line over the per-line cap, a file longer than the default window, and a result longer than `maxResultSizeChars`. The default window cuts the long file at 2000 lines with no offset and no limit. The pipeline cuts the last one through the middle before the model sees it. The recorded string is then longer than what arrived, and no comparison can repair that from here. `partialView` is what must carry it.

The mtime is read for the record as the baseline that the staleness check compares for a view it cannot compare by content. A `stat` that loses a race with a deletion costs only the baseline, because the content that the model saw is still what gets recorded.

Write creates the parent directories and writes the whole file. Its two checks are `guardWritablePath` and `decideWrite`, and neither can widen what the other allows. Each one can only refuse. `guardWritablePath` is unconditional. It refuses version-control metadata whatever the mode says. It refuses anything outside the workspace whatever the mode says. It matches on the path, so it catches a `.git` at any depth. A link to a `.git` is caught too, without a scan that has to find it first.

The refusal is about recoverability. `.git/` is inside the workspace, so containment alone passes it, but a write there is not a recoverable edit. A model that tidies up `HEAD` destroys history that the user cannot get back. So does a prompt injection that rewrites `.git/config` or a hook. The refusal does not depend on the mode, on the allow rules, or on how reasonable the request sounds. Read tools keep `guardPathContainment`. A metadata read such as `git log`, `git diff` or `git show` is legitimate work, and `git` is on `PATH` for anything else.

`decideWrite` then asks the session's policy which roots may be written. That is the question the guard has no way to know about, and the one that a shell wrapped in seatbelt or bwrap enforces. The check is not only a read-only-root check. It refuses every path in `policy.protected`. `buildSandboxPolicy` derives `<workspace>/.git` into that list for the workspace itself. Every writable root whose kind is `project` gets a derived `.git` as well (`packages/agent/src/sandbox-policy.ts:180`), whether a scan found it or not. A root whose kind is `data`, such as the temporary directory or a package cache, gets no derived `.git`. So this tool refuses `.git/config` for two reasons. `sandbox-simulated.test.ts` asserts the policy half on its own, with no guard in front of it.

What the policy half does not cover is the rest of the rule of the guard. The gap is a list against a path match. A `.git` under `node_modules` is not in `protected`. Neither is one deeper than the four segments that the scan reads, nor one spelled `".git "` or `".git."`. `decideWrite` allows those, so the guard line is the whole of the protection. Those are exactly the cases that `tools.test.ts` drives through a real Write and Edit. A case that `decideWrite` also refuses still passes if the guard line is deleted.

The guard matches a segment on the raw name. It matches again on the name left once the dots and spaces at its end are removed. Measured on this machine: an earlier check on exact string equality passed both `guardWritablePath(".git /config")` and `(".git./config")`. On Windows those spellings name different directories, `.git ` and `.git.`, and not aliases. The earlier pass left the real `.git` untouched. That is a false negative and not an escape. It is not true everywhere. SMB shares, tar and zip extraction, and the POSIX side of a WSL mount all strip the dots and spaces at the end. The same path there lands inside the real `.git`. To refuse the near-miss spelling costs nothing where it names a different directory, and it closes the gap where it does not. The other option, to strip first and then compare, was rejected, because a path in the output of `git checkout` can end in a dot. The match on the name and on its trimmed form keeps that case allowed.

A Write is the one case in which a file the model never read is still a file whose whole content it knows. The model just authored all of it. Without the record, the Edit gate refuses the next edit to a file that the session created itself. That is the shape of every "create then fix" task. This call is the only production writer of that record, and until it existed the documented rule had no caller. The fresh mtime rides along for the same reason as the content. A pre-write baseline on a record that now describes post-write bytes refuses the next edit as changed.

`ReadFileState` is what the model was really shown by a Read, kept per session. An edit tool can then refuse a file that nobody read. The rule exists in the reference build as code. In `edit.ts` it exists as prose only, and the prompt tells the model to read the file before an edit (`packages/tools/src/edit.ts:62`). Nothing checked it. A prompt line is a request, and a model, or an injected instruction inside a file it never opened, can decline a request. The mechanism is a recorded read, and this is the record.

More than one session is alive in a single process, which is why this is an instance and not a module-level singleton. `/resume` builds a second `AgentSession` around the same tool array (`packages/coding-agent/src/interactive.ts:875`), and every test case that wants a tool set builds its own. A module-level `let` hands the gate content that a different conversation was shown, which is exactly the hole that the gate closes. So this is an ordinary object. `createAllTools` makes one per tool set unless the caller passes its own. The app passes its own precisely so that the `/resume` swap can clear it (`packages/coding-agent/src/interactive.ts:917`). `createReadTool` receives the same instance that the Edit tool is given. Nothing here is reachable without a caller that passes it in.

The lookup key is normalised for separators and for case on the platforms whose filesystem is case-insensitive. On Windows and macOS `Repo/FOO.ts` and `repo/foo.ts` are one file. On Linux they are two files, so a fold there merges records for files that the model never read as one. The path that Edit resolves with `guardWritablePath` and the path that Read resolved with `guardPathContainment` land on the same entry. `caseInsensitivePaths` answers the case question in one place (`packages/tools/src/containment.ts:21`).

The entry is frozen, because a gate cannot rewrite the evidence that it reads. `content` is the text that the model was shown, without the gutter of Read and without its page notice. For a ranged read it is the requested lines only. `timestamp` is `Date.now()` at the moment of the record. `mtime` is the file's own mtime at the read, when the recorder got a stat. `fullRead` is true when neither `offset` nor `limit` was passed. `partialView` is the injection guard.

`mtime` is the baseline for a read that cannot be compared by content. The rule then compares the clock of the file against itself. `timestamp` alone compares two clocks that need not agree. A file whose mtime runs ahead of the clock of this process reads as changed on a file that nothing touched. The causes are a checkout from a machine with skew, coarser filesystem timestamps, or a CI runner in the middle of a time sync.

`partialView` means that the model did not receive the bytes of the file. A page is not the cause. It is the difference between "the model read the file" and "the model read a transformation of it". It is set in three cases. A line was cut at the per-line cap of Read. The default 2000-line window cut a longer file that nobody asked to page. Its arguments mark that read `fullRead`, and `partialView` is what corrects it. The result is longer than `maxResultSizeChars`, and the pipeline cuts its middle before the model sees it. In the last case the recorded string is longer than what reached the model. This flag is the only thing between a gate and an `old_string` taken from the middle that is gone.

`record` replaces any earlier entry and does not add to it. The content is stored without the gutter and the notice. A re-record refreshes the content and the timestamp. It keeps `fullRead` and `partialView` unless the call states them. That is the safe direction to be wrong in. An edit tool that re-records after a successful edit knows the new content. It knows nothing about what the model saw of the rest of the file. A call that carries only `{ content }` must not hand out a whole-file badge on top of a ranged read. To say otherwise, pass `offset` or `limit` or an explicit `partialView`. A record over a path that was never read means that the model authored the content, which is a Write of a new file.

`RecordReadInput.partialView` and `.mtime` default to the values of the previous entry for a path that is already tracked, and to `false` otherwise. A caller that just wrote the file must pass a fresh mtime rather than let the pre-write baseline ride along. `forget` drops one path, and the gate then reads `undefined`, which is the same answer that a file never read gets. `paths` lists every tracked path as recorded, in insertion order. `clear` forgets everything, for a session swap. `/resume` reuses the tool array that it already built. The conversation that arrives otherwise starts able to "recall" reads from the one that is left. Its Edit gate then accepts a file that conversation was never shown. `hotSwapSession` calls `clear` next to `restoreTasks` (`packages/coding-agent/src/interactive.ts:910`), which is the other piece of session state that must follow the conversation and not the process.

### Search tools: Grep, Glob, LS, and ignore files

The Grep tool searches file content. It walks the same tree that Glob walks, and it honours the same `.gitignore` subset.

The header of `grep.ts` once claimed that the tool "spawns ripgrep when available". It never spawned anything, because one pure-JS path was all there was. The claim implied real `.gitignore` support and a non-JS regular expression dialect, and both were visible in the description and absent from the code. The description and the tool now state the same subset in the same words. The walk is the one that Glob runs, so a Grep result and a Glob result differ only when the pattern differs.

The description says: a JavaScript regular expression, matched lines with their file paths and line numbers, indentation intact. Files left out by `.gitignore` or by the skip list are absent too. The walker comes from `glob.ts` and the subset from `ignore.ts`, so each part exists once. The skip list is `node_modules`, `.git`, `dist`, `build`, `.next` and `coverage`.

`MAX_MATCHES` is 200 and `REGEX_TIMEOUT_MS` is 2000. A match at or past the cap sets the truncated flag and stops the search, and the header says how many matches were shown. The deadline exists because a pattern can backtrack without limit. When the deadline passes, the search aborts with a message that names that cause.

`include` is a glob over the path relative to the searched directory, and it has the same semantics as the Glob pattern. Use `**/*.ts` to reach subdirectories. `*.ts` matches at the top level only.

A named file is searched as named. The rules of the walk are statements about trees, and to point Grep at one file is a statement about that file.

Files larger than 1000000 bytes are skipped. So are files that cannot be read and files whose text holds a NUL character. The `\r` of a CRLF line is not part of the line. When it stays in, a pattern anchored with `$` misses, and every quoted line ends in an invisible control character. The indentation of a line is a different case: it is part of what the file says. The old code trimmed it away, and a model that copied a result back out got a string that the file does not hold.

`overflow` is `"spill"`. A search that matched a lot is a search that must be narrowed. The hits are not reproducible by a second ask, because the tree moves on.

The Glob tool finds files by pattern. `MAX_RESULTS` is 200, `MAX_DEPTH` is 15, and the walk stops when the match count passes 5000.

`walkProjectFiles` walks a project tree and returns the matched files as absolute forward-slash paths, newest first. Two callers share it. One is the Glob tool, which filters through a glob pattern. The other is the @-mention completer of the prompt, which relativizes against the session cwd itself. The depth and result caps exist so that a runaway tree cannot stall either caller.

`FileWalkerOps` is deliberately narrower than `Operations`. A caller that only lists files does not need the shell side. `readTextFile` is optional, and the walk needs it only when it honours ignore files. A walker asked to honour a `.gitignore` reads it or stops. Silent ignorance of an unreadable ignore file is the one failure this feature exists to stop. The walk throws in that case, and the presence of the reader doubles as the flag.

`respectGitignore` is opt-in and not automatic. The completer does not pass it. It lists what exists for the user to name. The user may name a file that git ignores, because a path the user can Read is a path worth a completion. A search asks the opposite question: what does the tracked tree say.

The ignore chain: the `.gitignore` of this directory joins the chain before any entry is judged. Its rules apply at and below it, and the code reads them after the sets above, so a deeper file overrides a shallower one. That is the precedence of git, and it is the order in which `isIgnored` folds. To prune a directory that a rule excludes is the semantics of git itself. A file inside an excluded directory cannot be re-included, so nothing below it is worth a descent.

The Glob output is a list of absolute paths sorted by the time of the last write, newest first. Files excluded by `.gitignore` are left out. A long list is cut with a count of what is not shown. The full list goes to a file whose path is the last line. A count alone says only that the list was cut. The list is already in hand, so it goes to a file that the Read tool can open. The caller points the spill directory inside the roots of Read. A write that fails falls back to the count, and the result still says that the list is incomplete, which is the important half.

The LS tool lists one directory. `MAX_ENTRIES` is 200, the same figure as the Glob cap, because it answers the same question. How many names from one directory are worth a place in a conversation? The notice is a count with no file, unlike the Glob notice. A caller with thousands of names works by pattern, and Glob is the tool for that.

The rows are sorted before the cut, so the shown set is the alphabetical head and not whichever entries `readdir` returned first. Only the shown rows are stat'd, so the cap bounds the `stat` calls too. Sizes print as bytes below 1024, as KB with one decimal below 1 MB, and as MB with one decimal above. A file named on the command line gives an error that says it is a file and not a directory. No list follows. An empty directory answers "(empty directory)".

`ignore.ts` holds the `.gitignore` subset that the file walker honours. The tree that a developer searches is the tree that git tracks. A file that git will not show in `git status` is a file that a search result must not quote. The project already said which files those are, in the file it wrote for exactly that purpose. A search that goes past a `.gitignore` makes Grep and Glob report matches from build output and logs that the developer cannot see. That is worse than a miss, because it reads as real.

The subset is exactly this, and the Grep description says the same words.

- Blank lines and lines that start with `#` are skipped.
- `!` re-includes what an earlier rule excluded. The last rule that matches wins.
- A `/` at the end restricts a rule to directories.
- A pattern that holds a slash anywhere is anchored to the directory of its `.gitignore`. The code matches it against the path from there.
- A pattern with no slash is matched against the name, at any depth.
- A directory that a rule excludes is never re-included from inside it. That is the rule of git itself. It is the reason the walker may prune a matched directory instead of a descent to test each descendant.

Deliberately not here: `.git/info/exclude`, the global `core.excludesFile`, escaped spaces at the end of a pattern, and `**` semantics. `Bun.Glob` reads `**` its own way, and the walker does not re-read it. The description claims none of that. Match is case-sensitive everywhere, because the skip list next door is. A guess about the case behavior of the filesystem is one more thing to get wrong.

Nested `.gitignore` files are read, and a deeper one is read after the ones above it, so it overrides them. That is the precedence of git, expressed as the fold in `isIgnored`.

`parseGitignore` drops lines that match nothing. A CRLF `.gitignore` is the normal case on Windows, and the `\r` is not part of any pattern. A lone `!`, a lone `/`, and `!/` leave nothing to match with. `IgnoreRule` holds `negated`, `dirOnly`, `pathType`, `pattern`, and a lazy `Bun.Glob`. That glob is compiled once, on the first match, and not at parse time. `isIgnored` returns the verdict of the last rule that matches. A rule of a deeper file overrides a shallower one exactly when git says it does.

### Operations pipeline and containment

`Operations` is the seam between the tools and the system. The file holds the interfaces, the child-process build of the exec side, and the Node build of the file side.

`CAPTURE_HEAD_CHARS` and `CAPTURE_TAIL_CHARS` are both 30000. The worst case is 120000 characters, with both streams at both caps, against the unbounded string this used to be. The figure matches the default result limit of the pipeline, so the two cuts agree about what "too long" means. Past the cap the middle leaves the window, and from the first drop the whole stream also goes to the spill file. The cap is then a memory bound and not a loss, because everything the window let go is in the file. The `chars` count of the `spill` field is the exact length of the file. It holds every character of both streams in the order of arrival, which is the only order a capture can keep. The bounded `stdout` and `stderr` say how much of each stream is absent, with the marker `... [truncated N chars of output]`.

`ExecResult` reports `exitCode`, `killed`, `handedOff`, and an optional `spill` with a `path` and a `chars` count. `exitCode` is null at a handoff, because no code exists yet.

The options of `ExecOperations.exec` carry the design. `onTimeout` is optional and opts in to a handoff. Without it the timeout kills, exactly as before. A foreground timeout says that the caller stopped its wait. That is not a statement that the command must die. A test suite one second past its budget is a candidate for the background, not for a process-tree kill. `sandbox` is optional because the `!` passthrough sits outside the mode system. `spillDir` is the switch for the capture: with no directory the executor keeps the bounded windows and writes no file. Unset, accumulation is the unbounded string it always was, one per stream. That default suits an executor of an embedder. It does not suit a tool that a model can point at `yes`, which is why the tool set threads a spill directory through. When the directory is absent, the executor creates it. A capture that cannot write reports no spill, and not a path to a half-written file.

`networkEnvFor` gives the proxy environment for a policy. The background manager spawns shells itself, so it must reach the same proxy and not start a second one. One proxy serves each policy. A failure to answer leaves the command unconfined, because a broken proxy must not stop every command in the session.

`sandboxBackend` is optional on the interface, because the `Operations` of an embedder has no backend to report, and required on `ChildProcessExecOperations`, which always has one.

`NodeFileSystemOperations.writeTextFileAtomic` writes a temp file and then renames it. A rename that fails falls back to a direct write of the target. `isFileSync` is the sync check for the shell candidates.

`isWindowsBash` rejects the WSL launcher by its directory, `\system32\` and `\microsoft\windowsapps\`. `LBB_BASH_PATH` is exempt. `pathCandidates` searches PATH for a shell and reads only drive-anchored entries. A shell that is itself MSYS hands its children POSIX paths, and no Windows process can open those. `detectShell` returns the program and the arguments: `-lc` for the conventional bash list, `/d /s /c` for `cmd.exe`, and `/bin/bash -c` on other platforms.

`proxyPolicyKey` is a JSON key for a policy. A hand-joined string was rejected, because it is ambiguous. Join each rule as `permission:pattern`, with a space between rules. The pair `{ allow, x }` and `{ allow, y }` gives the same text as one rule with the pattern `x allow:y`. The second list then runs under the key of the first. The unambiguous form costs one `JSON.stringify` per command, and the other choice costs a policy that is not the policy. The rules stay in their order and the key is not sorted. Two tables that differ only in order then collide, and this file cannot assume that the decision function ignores order. A needless rebuild costs one listener, and a missed rebuild costs enforcement. The same rule covers case and whitespace: no normalisation.

`createExecCapture` keeps three windows over the same chunks. One window per stream holds the text that becomes the result. The third window is combined, and it is the only writer to disk. The combined window is the writer because it is the only one whose bound must cross first. It sees every chunk both streams emit, so it can never overflow later than either single stream. The file then exists, with a lossless seed, before either result stream lets go of a character. `assemble` runs once per outcome, because a close of a file is not repeatable. The timeout snapshot and the final settlement share the one call.

The spill file is deleted for one of two reasons. Both streams fit their windows, so the text holds the whole output and the file is a stray. Each stream past half the shared bound is enough to trip the combined window. Or the file is broken, because the only thing worse than a pointer that is absent is one that points at a maimed file. Either way the delete is best effort, and the spill directory ages out.

`ChildProcessExecOperations` holds the runtime answer, the proxy map `#proxies`, the in-flight start `#starting`, and an epoch. The runtime is asked once at construction, because a PATH scan per command is pure waste. The answer does not change while the process runs. It is injectable, so a test on one machine can reach the wrap branch of another. `sandbox-wiring.test.ts` uses a fake Linux runtime. That fake is the only thing that makes "the wrapper is really around the shell" an assertion and not a hope. The shell is injectable for the same reason, and the reason is not hypothetical. The container-path tests assert what the AppContainer branch spawns. `detectShell` answers with the shell of the machine. That is the `bash.exe` of Git for Windows in its conventional place, on most developer machines and on the GitHub Windows runner. It is `cmd.exe` where no bash is installed. Those two answers are not the same test. One of them cannot run inside the container at all. The injection makes the tests measure the branch and not the Git layout of the machine. `FAKE_LINUX` makes the wrap branch measurable on a Windows box in the same way.

The proxy map holds one proxy per policy key. The key is the fix. One proxy is shared and not one per command, because the rules and the port belong to the session. A fresh loopback port per command reads to a child as a network configuration that changes underneath it. It also breaks anything that caches the proxy URL. The proxy is created on the first command that needs one. The common case of `network: enabled` with no rules must not pay for a socket. The slot was single and unkeyed, so the first restricted command of a session became the authority on destinations for every command after it. The proxy closes over the rules it was built with, so a narrower allowlist mid-session changed nothing. The direction is the bad one: the policy that survives is the older and usually the broader of the two, so this fails open. `sandbox-wiring.test.ts` measures it.

A `null` value in the map is a remembered answer and not an absent one. `network: enabled` with no rules starts nothing, so an unrestricted session otherwise re-enters `startNetworkProxy` and re-asks `needsNetworkProxy` once per command. That is an optimisation with no observable difference. Do not build an assertion on the count of calls. No injection seam can count them, and `networkProxyRunning` is false either way. To remove the `null` costs one function call per command and breaks nothing.

Every proxy stays live until `close`, and a newer one does not retire an older one. `NetworkProxy.close` destroys every open connection of the proxy, and a command started under the previous policy can still run with that port in its environment. To keep them all also means that a session which flips between two policies twice does not churn four listeners. The map grows with the number of distinct policies, which is one per allowlist edit and not one per command. That is a resource characteristic and not a bound. It is written down and not hidden behind an eviction rule, because an eviction closes a proxy that something can still use.

`#starting` shares one in-flight start: two callers that arrive together under the same policy must not start two listeners. A start that fails clears the slot. A rejected promise left in the cache turns one transient `EADDRNOTAVAIL` into a permanently broken `exec`. Callers under different policies wait for each other and do not run together. Two writers race to fill the map, and the proxy of the loser is installed by whichever start resolves last. That entry then names a port built from rules the next caller did not ask for. The wait costs one start of latency in a case that happens once per allowlist edit.

`#epoch` is bumped by `close`. A start that was already in flight when `close` ran can then tell that it is late. `close` clears the map, but it cannot un-start a listener that has not been given a port yet. Without the epoch, the late start installs itself into the empty map, and a proxy then sits on a port that nothing will ever close. That is the same leak that `close` exists to stop, and a quit during a slow start reaches it.

`close` stops every proxy the executor ever started, not only the newest. One left behind keeps the process alive on a port that nothing closes. The call is safe twice, and safe when no command ever needed a proxy.

`networkProxyRunning` skips the remembered `null` answers, because it asks whether a socket is open and not whether the cache is warm. The tests read it to check that a confined command left exactly one listener behind and that `close` took it away. Nothing in the live app reads it. The comment used to claim that `/doctor` does, which was not true of any code in this repository.

`networkEnvFor` is public because the background manager spawns shells itself and must reach the same listener. The point is the shared listener, so the method hands out the environment and keeps the lifecycle private.

`sandboxBackend` is required here and optional on the interface. A caller that asked what holds its commands in must not be told nothing. `describeSandboxBackend` treats an absent answer as `simulated`. The third argument of the resolver is the same fact, read from the same runtime. The sentence that `/permissions` prints and the branch that builds the argv then answer one question.

`exec` has a default timeout of 120000 ms. The wrapper sits outside the shell, so `resolveSandboxExecution` takes a policy and not a finished command. The confinement is then the parent of the process tree, and the shell cannot drop it. With no policy the argv is exactly the two arguments it always was, which is the case of the passthrough shell and of most tests.

The proxy variables go after the caller's variables. A caller that names `HTTP_PROXY` states where its traffic goes, and the policy of this command must win. A proxy that is not active injects nothing at all, so a session that confined nothing keeps the environment it had.

`confinedEnv` filters the `undefined` pseudo-variables of `process.env`, such as `NODE_ENV` and `TZ` on Windows. A literal "undefined" string in an env block reaches the child as a variable set to the text "undefined". The filter belongs here and not in `confinedEnvBlock`, because a silent drop there hides values that the spawn path passes.

The AppContainer branch never falls through to the plain spawn. A ternary that reads "anything not native runs the bare shell" was true while the fifth kind did not exist. That shape is fail-open now that the kind exists. A command that the resolver confined runs with no container at all in that shape. The branch sits after the shell `argv`, the child environment, and the grant roots are decided, because it needs all three. The confined run has four properties, and each one is a difference from the spawn path.

- It is synchronous FFI. `runConfined` does not return until the child exits, and the poll it waits in cannot yield to the event loop. That is measured and not an oversight. The abort check inside reads `signal.aborted`, which the listener of the spawn path sets, and a listener cannot fire while the loop is blocked. An abort that arrives during the run is then not seen. The timeout kill and the abort at entry are seen, and both leave `killed` true. In practice a user who presses Esc mid-command waits for the timeout, exactly as with a hung local terminal. The async rewrite that fixes this is a separate change.
- There is no handoff. The spawn path can hand a live `ChildProcess` to `onTimeout` for background adoption. A confined run owns a raw process handle with no `ChildProcess` around it, so a timeout kills. The Bash tool text that promises that a foreground command past its timeout stays alive in the background is then false under this backend. That text belongs to another round, not to this one.
- The grant outlives the command and not the call. The code gets it before the spawn and releases it in a `finally`. An abort or a spawn failure then cannot leak an ACE onto the workspace. The refcount inside `acquireWorkspaceGrant` means that two commands which run at once do not release the grant of each other.
- A shell that the container cannot run is refused. `detectShell` prefers the `bash.exe` of Git for Windows wherever it is installed. A container child cannot run a program whose runtime sits outside every grant. That child starts and dies at DLL initialization with `0xC0000142`. Four opaque spawn failures on the GitHub Windows runner measured this. The branch checks first with `containerCanExecute` and fails closed with a reason. It does not hand a doomed program to the spawner or fall through to the unconfined spawn. The refusal names the program and the two sets it is not in. It suggests that the user turn the sandbox off for the session, or point `LBB_BASH_PATH` at a path inside a granted root. The check comes before the grant is acquired. A refusal costs nothing. A doomed spawn reads as a command that ran and failed, and not as a backend that cannot start. `CreateProcessW` starts the Git-Bash shell, and the child dies behind it at DLL initialization. The number alone is not actionable. The name of the program and the two sets it is not in are.

A grant that cannot be established fails closed and with a clear message. With no grant the child cannot touch the workspace at all. That is worse than a command which stops before it starts. The cwd of the child goes through the same canonicalisation as the grant roots. The reason is measured. On the GitHub Windows runner the workspace has a short name (`RUNNER~1`). A confined `powershell` whose cwd it was died with the access-denied error of .NET. The runtime resolves its own cwd at start-up and resolved a spelling that the ACE did not cover. A cwd that cannot be resolved is handed over as spelled. A cleanup that fails after the run is reported and not thrown. The command already ran, and its exit code is what the caller acts on. A raise turns a successful command into an exception. The warning goes to `stderr`. A leftover ACE names the container SID, which the next run derives again, so it is reusable and not dangerous.

The spawn path kills the tree on Windows with `taskkill /pid <pid> /T /F` and otherwise with `child.kill()`. Settlement: whichever path arrives first decides, and the rest are no-ops. A spawn `error` settles with 127. `close` settles with 124 when the call already killed the process, and otherwise with the code, default 0. A child that cannot be spawned reports the error through the capture, when a capture exists. The error then lands in the spill file in arrival order like everything else.

With `onTimeout`, the callback runs before the promise settles. The callback then owns the process by the time the caller resumes, and no chunk falls between the two. `settle` detaches the abort listener in the same turn. A process that an embedder adopted must not die when a signal of a later turn fires. One snapshot is used twice: the log of the adopter opens with exactly what the result carries, and a capture is assembled exactly once. A handoff result has `exitCode: null`, `killed: false`, and `handedOff: true`.

`defaultOperations` takes `exec` as a parameter, so a caller can name the executor it owns. A test that must see the proxy under test cannot, if the object it holds is not the one that runs commands. The returned object also keeps one listener: everything routed through it shares the proxy of the executor instead of one proxy each. One listener per policy is what makes that safe. A single listener for the whole session is one set of rules for every command in it. The first restricted command then decides destinations for all the rest. The answers of the executor are forwarded and not recomputed here. They used to be dropped, and the drop was invisible in both directions at once. `sandboxBackend` came back `undefined`, so `/permissions` rendered "simulated, not OS-enforced" on every machine, even on a Mac with `sandbox-exec` present. `networkEnvFor` came back `undefined`, so a spawn that asked this object for the proxy of the policy got nothing and ran unconfined.

### Web fetch and web search

WebFetch turns a URL into readable text. WebSearch uses the DuckDuckGo HTML endpoint and needs no API key. The tests cover `htmlToText` and `parseDuckDuckGoResults` directly.

Both tools obey the network axis of the session. That is not an extra: these two fetch inside this process, so `HTTP_PROXY` is not in the path and the proxy cannot hold them. One tool call alone then reaches any public host, while the same host over Bash was refused by the axis. A network policy that one built-in tool walks around is not a policy, it is a suggestion with a shell.

`MAX_CONTENT_CHARS` is 40000, `FETCH_TIMEOUT_MS` is 30000, and `MAX_RESPONSE_BYTES` is 10000000. `SEARCH_HOST` is `html.duckduckgo.com`, named so that the network axis has something to judge. A literal inline in the fetch URL makes the check read as a comparison against a constant that cannot vary. That is true, and it is the point: the host is fixed, so the decision needs no network round trip. The only variable in the request is the part that must be gated.

`htmlToText` strips HTML down to readable text. It drops the content of `script`, `style`, `noscript` and comments, and turns `br`, `hr` and the close tags of block elements into newlines. Other tags go. The decoder handles `&nbsp;`, `&amp;`, `&lt;`, `&gt;`, `&quot;` and `&#39;`. Runs of spaces and tabs collapse, three or more newlines become two, and the result is trimmed.

`parseDuckDuckGoResults` reads the `result__a` link anchors and the `result__snippet` anchors, pairs them by index, and gives an empty snippet when none is present. `decodeDdgUrl` unwraps the redirect of DuckDuckGo (`/l/?uddg=<encoded>`) and gives `//host/...` an `https:` prefix.

`fetchWithTimeout` aborts through a controller after `FETCH_TIMEOUT_MS`. The cancel of the run must reach the request too, or an interrupted turn stays parked on the network until the timeout expires.

`refuseByNetworkPolicy` gives the answer of the network axis for a hostname, as a refusal string or `null`. `decideNetworkRequest` is the same function that the proxy calls, with the same arguments. One table and one decision then serve both, and no second matcher can disagree with the first. `normalizeHost` runs first, because that is what the proxy applies to a CONNECT target. The two paths must judge the same spelling of the same name the same way.

`HostResolver` gives the addresses of a hostname at the moment of the check. It is injected and not reached for directly, for the reason that `resolveSandboxExecution` takes an `exists`. The one impure call in the guard is the one that a test must be able to state. A test that lets this reach a real resolver asserts about the DNS of the machine and of the moment. That assert is quiet. A name that resolves on a developer laptop and does not resolve in CI fails the test. The failure has nothing to do with the code under test. That is not hypothetical. The header of `web.ts` says that the tests cover the pure helpers, and the lookup in the guard was still a real call. The one test that asserted the network was open passed at home and failed everywhere else. `resolveHostWithDns` is the real resolver and the only place in the module that touches DNS. It uses `lookup` with `all: true`.

`guardPublicUrl` is the SSRF guard. It resolves the hostname and checks every address that comes back. DNS can return several records, with mixed families among them, so every one is checked and not only the first. The checks in order: the URL must parse, the protocol must be `http:` or `https:`, and the network axis must allow the host. Then the host must not be `localhost`, and a literal IP must not be a blocked address. Every resolved address of a name must be public too. A lookup that fails is a refusal and not a pass. A failure to find out where a name points is not evidence that it points somewhere public. The fail-closed sense is the only one for a URL that the model chose. Zero addresses is a refusal for the same reason. An empty list satisfies the loop with nothing to check. A resolver that answers "I know nothing about this name" then turns the guard off for exactly the names it cannot vouch for. The failure is then silent, because a name that resolves to nothing private looks the same as a name that was never checked. The network axis is checked first on the same pass. That check is cheaper, with no DNS lookup, and it is the declared intent of the user. There is then no reason to resolve a name before the answer says that it was never allowed.

What the guard does not do, stated because the other sense is stronger: it does not pin the connection to the address it checked. `fetch()` resolves the name a second time. A name whose answer changes between this lookup and that one is checked against one address and connected to another. The guard narrows that window to the gap between two resolutions, and it does not close it. A close means a connect to the resolved address while the code presents the original `Host` and SNI. That needs a MITM CA and an attribution frame to keep the two apart. This build declined that trade and documented it at the top of `packages/tools/src/sandbox/proxy.ts`. The honest sentence here is the narrow one and not a claim about the backstop.

`readCapped` reads a response body up to a byte cap and cancels the stream once the total passes the cap. A response with no body falls back to `response.text()`.

`fetchGuarded` re-runs the SSRF check on every hop. `redirect: "manual"` stops the runtime from a silent follow of a redirect to a blocked address after the initial URL passed the check. A public URL can answer 302 with a private one. The network axis rides on the same hop loop and is not checked once at the entry. That is the only placement that covers it. A public URL that the axis allows can redirect to a host that it does not. A check outside this loop checks the URL that the model typed and not every host that the fetch visits. The hop limit is five, and the run stops with "Too many redirects".

`createWebFetchTool` details: the URL must be an absolute HTTP(S) URL, and the request carries the user agent `labunbun-code/0.1 (+webfetch)`. `max_chars` is an integer from 1 to 100000 with a default of 40000. A response that is not ok reports the status and the reason. A content type that holds `html` goes through `htmlToText`. Anything else comes back as it was. Text past the cap is cut, and the result says how many characters are gone. An empty page answers "(empty page)" and is not an error. The result starts with the URL, then the text.

`createWebSearchTool` details: the query has a minimum length of 2, and the user agent is `labunbun-code/0.1 (+websearch)`. `max_results` is an integer from 1 to 10 with a default of 5. The tool checks the network axis before it sends anything. The destination is a constant, so this reads like a check that cannot be needed, and that is exactly why it needs one. The query is free text that the model chose, and it leaves the machine inside a URL to a third party. A search is then the shortest exfiltration channel in the tool set, because whatever sits in the query reaches an outside host. A network axis that the search ignores is an axis with a hole in the shape of "ask a question". The refusal message says that WebSearch sends the query to that host. A response that is not ok reports the status and suggests WebFetch on a known URL. Results print as a numbered title, URL and snippet, with a blank line between entries.

### Task board

The task board is a shared in-memory store (`TaskStore`) plus four tools: TaskCreate, TaskList, TaskGet and TaskUpdate. The agent uses these to plan and track multi-step work, and the UI subscribes to the store for the progress strip.

`TASK_BOARD_TOOL_NAMES` holds the four names in one place, because the band filters tool tables by them.

A task has `id`, `subject`, `description`, `status`, `activeForm`, `owner`, `blockedBy`, and `createdAt`. The status is `pending`, `in_progress`, or `completed`. `activeForm` is the progress label that the UI shows. `owner` is who is on the hook, free form, and in band use it is the name of a band member.

`create` gives the next number from the counter. `list` sorts by numeric id. `update` applies a patch and adds dependencies without duplicates. `summary` is the snapshot for the UI strip, and `snapshot` copies every field of every task for a save.

`restore` replaces the whole list with a saved one. Ids come from the saved list and not from `create`, because a restored task is the same task. The conversation can already say "task 2 is in progress", and a new number then quietly means something else. The counter moves past the highest restored id, so the next new task gets a new number. The store keeps a copy, so a later `update` cannot change the array of the caller, which is the contents of a session file.

`blockedHint` is the note appended to a successful TaskUpdate, and it is never a refusal. A move of a blocked task to in_progress is allowed, and the answer names the open dependencies. A dependency id with no task behind it counts as open on purpose, so the note is also the first sign of a typo.

TaskCreate and TaskUpdate are not concurrency safe. TaskList and TaskGet are read-only and concurrency safe. The TaskCreate prompt tells the model to create tasks before multi-step work starts. It says to mark a task in_progress before it starts, and to mark it completed as soon as it finishes. Only one task is in progress at a time. The TaskUpdate description says to mark tasks completed as soon as they are done and not to batch the updates.

### Tool set assembly

`createAllTools` builds the default set, and the order of the tools is frozen there for the cache reason above.

The same executor goes to the background manager. A backgrounded command then joins the proxy of the foreground one, and no second listener opens that nothing closes.

`readState` is one per tool set. `createAllTools` runs once at startup in both entry points (`packages/coding-agent/src/interactive.ts:352`, `packages/coding-agent/src/headless.ts:153`). A second tool set in the same process is then a second call and a second store. A module-level singleton is readable from any conversation. A tool set that outlives its conversation is why the app passes its own and clears it. The `/resume` case inherits the array, so the store must follow the conversation and not the process.

Edit's first gate reads the same store that Read writes. An edit is refused on a file that this session never read. The two tools must look at one store, or the gate refuses everything. Write takes the same read-only root list, and not because it may write there. A root that the policy calls readable only is exactly the root that `decideWrite` must refuse. A policy that only Read knows about is a policy that the shell and the write tools disagree with.

`spillDir` is where a tool that bounds its own output writes what did not fit. The cases are the Bash exec overflow and a Glob match list past its cap. It must sit under a `readOnlyRoots` entry, because a spill that the model cannot read back is a file for nobody. It must sit under the root of tool-output too, so the same retention sweep prunes it. With no `spillDir`, Bash still spills at the pipeline and Glob falls back to a count.

`home` and `tempDir` are parameters and not reads of the process, so a caller can point the whole set at a fixture. `os.homedir()` reads only the Win32 environment block, so on linux and macOS a reader that calls it reads the real home of the developer. That is the defect that the `source-env-coverage` test exists to catch.

`webTools: false` removes WebFetch and WebSearch. Task tools appear only when a `taskStore` is given.

## Why it is like this

`packages/tools/src/containment.ts` never claims to be a security boundary. Nothing here is a boundary. Every function in this package is a policy statement in front of a backend, and the backend is the thing that holds. The tool layer is where a mistake costs a clear error message, and the kernel is where a mistake costs containment. These two layers exist at the same time because they stop different things.

Checks in this layer are preflight. A path check that runs in the same process as the caller cannot stop a hostile caller, and it does not try. It stops mistakes: a wrong path, a stale read, a stray write outside the workspace, a command sent to a host the user refused. The mistake is the case that happens, and the preflight catches it before any bytes move.

The tools also decide and report rather than hide. A cap that cuts output says so. A spill file has a path in the result. A sandbox mode that is simulated says `simulated`. The reader of a result can then tell how far to trust it, which is the property that a silent truncation destroys.

An allow-list needs one entry for each good case, and the set of good cases is small. A deny-list needs an entry for every bad case, and the set of bad cases is open. An allow-list fails closed when it is out of date, which is the direction that hurts least. The same sense applies to the SSRF guard and to the grant of the AppContainer.

Fail-open has one home too, and it is named. `networkEnvFor` leaves a spawn unconfined when the question fails, because a broken helper must not stop every command in the session. That is the opposite direction from the guard, and it is deliberate: the two answers protect different things. The confinement protects the network, and the command protects the work of the user.

The comments also state the measured costs and the run or date that measured them. A comment in this package is a claim that a test or a measurement backs. The figure sits next to the rule, so a regression is visible in the text.

## Known traps

- The quote restyle of `edit.ts` sends a `"mixed"` verdict straight to no restyle. The call-site comment says that the file style is the fallback, and the code does not do that. The two must be read together. That comment stays in the source on purpose.
- The policy half of the `write.ts` comment block says that `buildSandboxPolicy` derives `.git` for every writable root. The code derives it for the workspace and for `project`-kind roots only (`90f6db4`). The block predates that filter, and it stays in the source.
- `os.homedir()` reads only the Win32 environment block. On linux and macOS it reads the real home of the developer, and a fixture that rewrites `HOME` does not reach it. The `source-env-coverage` test is the guard.
- The proxy map keys on the exact policy. The map was once a single unkeyed slot. That shape failed open: the first restricted command of a session became the authority for every later command.
- The AppContainer branch must never fall through to the plain spawn. The old ternary was fail-open in that shape, and the resolver now returns a fifth kind.
- A confined run is synchronous FFI. The abort signal cannot fire during the run, so Esc waits for the timeout. The timeout kill and the abort at entry still work, and both leave `killed` true.
- A confined run hands nothing to `onTimeout`. Background adoption is a spawn-path feature, and the Bash tool text that promises adoption is false under this backend.
- `guardPublicUrl` does not pin the connection. The check and the connect resolve the name twice, and the design note sits at the top of `packages/tools/src/sandbox/proxy.ts`.
- The Grep tool walks a bounded subset of the gitignore syntax, with a JavaScript regular expression. The header once claimed ripgrep. The tool never spawned it, and the description now matches the walk.
- A `.gitignore` read that fails throws in the walker. The presence of `readTextFile` is the flag that turns the support on.
- Write refuses a path with a `.git` segment, with separators normalised on both sides. The refusal also covers a spelling that is `.git` once the dots and spaces at its end are removed. The strip-first option was rejected: a path in the output of `git checkout` can end in a dot.
- The `blockedHint` of a TaskUpdate is never a refusal. A blocked move runs, an unknown dependency counts as open, and the note is the first sign of a typo.
- A spill directory outside `readOnlyRoots` writes a file that the model cannot read back.
- Line references inside comments drift when another file changes. The refs in this document were re-derived at the end. The ones inside the source comments are not all current.
