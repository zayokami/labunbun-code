# Missions and recovery

A mission is the session and everything it is running: the conversation, the background shells, the subagents (`mission-ledger.ts:1-29`). A crash scatters those differently — a subagent dies with the process and leaves only traces, a background shell was started precisely to outlive it — and the session file carries one ledger for each: the `mission` close-out note, which says how the last run ended and what it was still holding; the shell ledger, which pairs `shell_start`/`shell_end` by pid so a surviving shell can be found again; and the subagent ledger, which pairs `subagent_start`/`subagent_end` by sidechain id so a run that died mid-flight is named instead of forgotten. `/tasks` renders the same state as one tree, and the exit guard reads it at the last moment there is still a screen to say anything.

Not every host leaves every trace. Background shells are a REPL feature — the `-p` host contains no background-shell code at all, and an ACP session starts none either — so the shell ledger is written and read only by the REPL (`interactive.ts:611`). The close-out note, by contrast, is written by all three hosts, each at the end of its run under its own control and each with `reason: "exit"`: the REPL at teardown (`interactive.ts:2168-2173`), a `-p` run at every controlled end of its single run (`headless.ts:774-786`, called at `:808` and `:883`), and the ACP host at shutdown, once per open session (`acp.ts:837-857`). A run killed mid-flight writes none, which is how a crash stays distinguishable from an exit (`mission-ledger.ts:20-22`). Subagent entries are written by the REPL and by `-p`, because both run a `Task` (`subagents.ts:659`, `:661-672`, `:803-820`; the `-p` host passes its store getter at `headless.ts:540`); the ACP host builds no `Task`, so there is no spawner to write them (`acp.ts:943-947`). Of the recovery notices, only the subagent orphan notice reaches all three hosts — the REPL prints it (`interactive.ts:580-581`), a `-p` run prints it before its checkpoint resume line (`headless.ts:348-353`), an ACP session prints it on `session/new` and `session/load`, to stderr (`acp.ts:968-969`) — while the mission summary and the shell recovery warning stay REPL-only, because both sentences send the reader to `/ps`, a command neither other host has (`mission-ledger.ts:117-120`).

## The close-out note

`mission-ledger.ts`. One `mission` entry (`MISSION_KIND`, `mission-ledger.ts:32`) records when a run ended, why, and the counts it ended with (`MissionRecord`, `mission-ledger.ts:35-55`): `at`, `reason`, `shellsRunning`, `subagentsLive`, and — only when there were any — `shellsRecovered`, the recovered shells from earlier runs still unended. A zero is dropped rather than written: "the field exists for the case that needs it, and a zero in every record would be noise on a line read once" (`mission-ledger.ts:49-54`, dropped at `:81`).

`writeMissionRecord` (`mission-ledger.ts:77-84`) stamps `at` itself and returns the record as written, so a caller can see exactly what reached the file. The REPL writes its note at teardown (`interactive.ts:2168-2173`), after the REPL unmounts and before the shell ledger is detached — the counts have to describe the state the run actually ended in, not the state its own teardown began dismantling (`interactive.ts:2159-2166`). It is written through the `store` variable, so a `/resume` earlier in the run lands the note in the session the run swapped to. A `-p` run writes its note at each end it reaches under its own control — the run's normal or aborted completion, and a prompt a hook blocked before the model — and nothing else does: a throw out of the run is a crash and stays note-less, like a kill (`headless.ts:774-786`, called at `:808` and `:883`). Its live-subagent count is read from the registry its `Task` tools write to (`headless.ts:522`, `:541`, `:785`); its shell count is the structural zero of a host that starts none. The ACP host writes one note per open session at shutdown, a resumed session's own file included (`acp.ts:837-857`), with both counts structural: it starts no shells, and it builds no `Task` (`acp.ts:830-832`). Best effort, like the ledger writes: "a note that cost the teardown would be worse than a session that closes out in silence" (`mission-ledger.ts:18-20`).

`readMissionRecord` (`mission-ledger.ts:95-104`) scans backwards for the first valid note. The newest wins because a session can end more than once — quit, resume, quit again — and only the latest ending describes the state the next run is actually inheriting (`mission-ledger.ts:86-94`). A note that fails validation costs only itself: `missionRecord` (`:132-145`) requires a numeric `at`, a string `reason` and non-negative integer counts, and a `shellsRecovered` that is not a count is dropped while the note still reads.

`formatMissionSummary` (`mission-ledger.ts:122-129`) turns the record into one line. Shells left are `shellsRunning + shellsRecovered`; the sentence is `previous session left 1 background shell, see /ps` or `previous session left N background shells, see /ps`; a zero yields nothing at all. Shells only — a run that ended with subagents live is already spoken for by the orphan notice, which names each run (`mission-ledger.ts:112-115`). The REPL prints it un-prefixed at startup (`interactive.ts:559-560`), before the recovery notices below because it is the context they belong to (`interactive.ts:553-558`). It is the REPL's line and only its: the sentence sends the reader to `/ps`, so the two hosts without that command — a `-p` run and an ACP session — read the note but never print the summary; they still write notes, because the next REPL to open the session is the reader this line is for (`mission-ledger.ts:117-120`).

## The shell ledger

`shell-ledger.ts`. `shell_start` (`:39`) carries the shell's id, pid, command, cwd, start time and output file; `shell_end` (`:41`) carries the pid — the pairing key — plus a status and exit code that nothing reads, kept because the file is readable by eye (`shell-ledger.ts:62-66`).

The writer is `attachShellLedger` (`shell-ledger.ts:171-207`), which subscribes to the manager's spawn and settle events. A shell with no pid is not written at all — a later run could pair or probe nothing, and "half a ledger is worse than a gap in one" (`:180-183`). The session is read per event rather than captured, for the same reason the shell notices read it that way: a `/resume` mid-session swaps the store, and shells started after the swap belong to the new file (`interactive.ts:611`, comment at `shell-ledger.ts:162-170`). A failed write lands in the manager's own subscriber guard — a ledger that throws must cost neither the shell nor the other subscribers (`:175-178`).

`readShellLedger` (`shell-ledger.ts:219-262`) is a linear scan, not a fold over two maps, because pairing has to be generation-correct: a pid that starts, ends and starts again — the second run's shell behind the first run's number — must come out as one ended shell and one open one, and only the order of the lines can tell those apart (`:209-218`). A second start for an open pid replaces the first, whose output file is no longer the live one (`:229-232`); an end with no start pairs with nothing, and counting it would invent a shell no start ever claimed (`:234-237`). A pid still open at the end of the scan is settled by asking the OS, not the file, because the line that would have ended it may never have been written (`:215-217`).

`probePidState` (`shell-ledger.ts:121-132`) gives the three answers the rest of the module is built on: alive — EPERM included, "the process is there and simply not ours to signal"; dead — ESRCH, "the one answer that is evidence of death"; unknown — anything else, evidence of neither (`:115-120`). A pid open with no end on file and no live process ended while nobody was listening — a crash, a kill, a reboot — and joins the `ended` count, "the whole of what can honestly be said about it" (`:256-258`).

The read answers in three buckets (`ShellRecovery`, `shell-ledger.ts:105-113`): `alive` and `unknown` as `RecoveredShell`s, `ended` as a number only, since a shell seen to end has nothing left to act on (`:109-110`). `RecoveredShell` (`:81-98`) wears the `BackgroundShell` interface with a pid, `recovered: true`, a liveness word and `observedAt`; wearing the same interface is what lets recovered shells ride the `/ps` and `/stop` paths with no branch of their own except where acting on one needs a pid (`:74-79`).

`observeRecoveredShell` (`shell-ledger.ts:280-293`) asks the OS again at the moments the user is about to see the answer — the `/ps` list, the exit guard's count — not on a timer (`:269-272`). `"ended"` is terminal: never probed again, never revived, because the pid can be recycled and a later probe answering "there is a process with this number" is not evidence it is the same shell (`:274-278`). The moment of death is recorded nowhere, so `observedAt` freezes at the last look and the age display stops counting this program's watch instead of the shell's life (`:91-97`). `observeRecoveredShells` (`:295-303`) takes one clock for a batch, so rows asked about together freeze together.

`formatShellRecovery` (`shell-ledger.ts:323-349`) joins up to three sentences — one per bucket — into the startup warning. Alive: `1 background shell from a previous run is still running: pid-4412 — /ps reads its log, /stop ends it.` Unknown: `1 background shell from a previous run is in an unknown state: pid-4412 — the probe could not say whether it is still running; /ps reads its log, /stop tries to end it.` Ended: `1 background shell from a previous run has ended.` Each has a plural form. The ids are in it because they are the handles the very next command takes (`:318-321`).

`excludeManagedShells` (`shell-ledger.ts:365-372`) subtracts pids the current manager is already tracking: a `/resume` can land on a session whose ledger still holds an open start for a shell this process started while that session was live, and without this the shell would show twice — once by id and once by pid — and count twice against the batch being interrupted (`:351-364`). The `ended` count is the file's and stays untouched.

`recoveredShellOutput` (`shell-ledger.ts:380-390`) is the end of the log the start recorded, capped at `RECOVERED_OUTPUT_CHARS = 30_000` (`:50`), with a truncation header naming the full log — and `(the log file is gone)` for a log since deleted, rather than empty output. `/ps` (`interactive.ts:3203-3219`) lists the manager's shells plus the recovered ones and tails through it per shell, saying `No background shells.` when there are none. `/stop` on a recovered shell (`interactive.ts:3221-3242`) has no handle to call, so the kill goes by pid through an awaited `killPidTree`, and only a kill confirmed true earns the splice from the rows; a failed kill asks the pid its state through `recoveredStopFailureMessage` rather than guessing.

## The subagent orphan ledger

`subagent-ledger.ts`. A subagent lives in memory, and dies with the process that spawned it. The ledger pairs `subagent_start` (`:27`) with `subagent_end` (`:29`) by sidechain id — created fresh per spawn, written on both kinds, stable across runs by construction (`:14-18`). The end entry is written on the way out however a run leaves, a throw out of the prompt included (`subagents.ts:661-672`), so a start with no end after it is the one honest trace a dead process leaves: a run that began and was never seen to finish (`:6-12`). Continuations write an end with no start of their own; an end pairs with its sidechain's start wherever the start is, and an end with no start anywhere costs nothing — it invents no run (`subagent-ledger.ts:16-18`, `subagents.ts:803-820`).

`readSubagentLedger` (`subagent-ledger.ts:58-76`) is two passes over the same list: collect starts (first start per id wins — two starts wearing one id are one run) and ends, then orphans are the started minus the ended. `formatSubagentRecovery` (`:88-96`) is one line: `1 subagent run from a previous run never finished: <id> (<type>) — the process it lived in is gone, and a subagent cannot be resumed; start a new Task.`, with the plural variant `N subagent runs from previous runs never finished: <labels> — the process that ran them is gone, and a subagent cannot be resumed; start a new Task.` There is no handle in it to type: the sentence that matters is "cannot be resumed", so nobody waits for a report that cannot arrive (`:78-87`). The REPL prints it as `Warning:` at startup (`interactive.ts:580-581`).

## The startup notices

The REPL's startup reads, in order (`interactive.ts:549-590`), each to stderr before the transcript renders: the damaged-session warning (`:551`, see `checkpoint-ledger.md`), the mission summary (`:559-560`), the shell recovery warning (`:566-568`), the subagent recovery warning (`:580-581`), and the checkpoint resume line (`:589-590`). None of them needs a `--resume` branch of its own: a fresh session reads empty ledgers and says nothing (`interactive.ts:585-586`). The other two hosts draw from the same list, but not all of it. A `-p` run prints the subagent notice and then the checkpoint resume line, to stderr, at startup (`headless.ts:338-354`) — the two it skips are the mission summary and the shell warning, whose sentences point at `/ps` (`headless.ts:343-346`). An ACP session prints the subagent notice on `session/new` and `session/load`, again to stderr: stdout there is frames only, and no notice ever becomes a protocol frame (`acp.ts:959-969`).

## `/tasks`

`task-tree.ts` renders the whole picture as one pure string. The root row is `main  running|idle` (`:78`); under it one branch per subagent and per shell — subagents in the `/subagents` listing's order (running oldest-first), then shells in the order they were started (`:16-18`) — each wearing `├─ ` except the last, `└─ ` (`:42-43`, `:87-89`); an empty tree says `└─(no subagents or background shells this session)` (`:84`). Rows that have ended stay on: "a failed subagent and a killed shell are states of the schedule, and a tree that dropped them would say the work never happened" (`:14-15`). A subagent row reads `agent  <status> <type> <age> <title>  (<sidechainId>)` (`:53-57`); a shell row reads `shell  <status> <age> <command>  (<id>[, from a previous run])` (`:60-70`), the marker explaining the pid-shaped id to someone who never typed it (`:65-69`). The status columns are shared with the `/subagents` listing so the two screens line up as one family (`:45-51`). The command reads all three sources fresh each time (`interactive.ts:3363-3378`).

## The exit guard

`exit-guard.ts`. Every exit request — `/exit`, `/quit`, the idle double Ctrl+C — comes through the guard first, with the screen still up (`:1-13`, wired at `interactive.ts:1944-1966`). `exitConfirmation` (`exit-guard.ts:59-90`) returns null when nothing is active — "a dialog over a quiet session would be a tax on leaving" (`:18-19`) — and otherwise builds `Still active: <clauses>. <fates>`: a run in flight, subagents, background shells; the run and the subagents end with the process, the shells keep running and get the two commands that can find and end them again (`:52-57`). The options lead with `Stay`; the only leaving answer is `EXIT_ANSWER = "Exit anyway"` (`:35-36`, `:85-88`) — any other answer, a dismissal included, stays.

`createExitGuard` (`exit-guard.ts:112-131`) holds two policies: one request at a time — a second request while the question is up is the same request arriving twice, "a Ctrl+C held a beat too long", and is refused rather than replacing the question with its twin — and the picker is dismissed before the question, because both listen on the same keys (`:102-110`). Work is read fresh per request, not captured at construction (`:94-95`), and every failure path settles on leave: "a guard that cannot ask … must not become an app nobody can exit" (`:20-22`, `:124-126`).

The guard's counts are built at the call site (`interactive.ts:1950-1959`): the run's own state, the live subagents, and the running shells plus recovered shells re-observed now and counted unless seen to end — an unknown-state shell is counted, because "the guard must not promise a quiet exit about a shell that may still be running" (`:1957-1958`).

## Deliberate limits

- Every host writes a close-out note, and `reason: "exit"` is the only value any of them writes (`mission-ledger.ts:38-43`); a run that dies mid-flight writes none, and that absence is the other half of the vocabulary.
- Only the REPL attaches the shell ledger and prints the shell recovery warning: the `-p` and ACP hosts start no background shells, so there is nothing for them to recover. That warning and the mission summary both stay REPL-only, because their sentences send the reader to `/ps` (`mission-ledger.ts:117-120`) — the other two hosts read the notes and print the orphan notice, and the next REPL to open the session is the reader the other two lines are for.
- The ACP host writes no `subagent_start`/`subagent_end` entries: an editor session builds no `Task`, so there is no spawner to pair (`acp.ts:943-947`). Its close-out notes read as composed, not observed — both counts are structural (`acp.ts:830-832`).
- A recovered shell is never reattached to a live manager: there is no handle for a process another process started, so the output is a file tail and the stop goes by pid (`shell-ledger.ts:74-79`, `interactive.ts:3223-3235`).
- The subagent orphan line lists runs, not conversations: a report that was never written cannot be continued, and nothing about an orphan can be revived (`subagent-ledger.ts:6-12`).
- The mission summary counts shells only; a subagent-only ending is left to the orphan notice, which names each run, rather than the summary saying "the same news in a smaller voice" (`mission-ledger.ts:112-115`).
