---
name: code-review-truthfulness
description: Check that the words this diff adds — key lists, hints, reports, notices, error text, and the comments describing them — still describe what the code does, since a wrong claim is worse than no claim.
---

A diff that changes behaviour usually changes something that *describes* the behaviour: a key list, a hint line, a report row, a warning, a docstring. Those are promises, and this repo keeps breaking them in the same four places. Check all four; the failure is not that the text is imprecise but that it is confidently false about a mechanism that does not exist.

- **Key lists and overlays** (`packages/tui/src/shortcuts.ts`, the hint line): a row names a key and what it does. The standing example is `Ctrl+R`, which promised history search while the emacs engine *claims* `C-r` in its reserved table and swallows it — so the promise was not merely unavailable, it was false. The distinction that matters is **claimed-and-dropped versus free**: a key the engine reserves is consumed so it cannot leak through as a stray character, and naming it in a key list as though it works is the same lie in a new place. The file's own header says a list that lies is worse than no list; that is the standard to hold it to.
- **Reports and notices** (the migration report, completion lines, the settings "ignored key" notice): these describe what the run did. A report line reading "the credential is read from undefined" is the shape to look for — a sentence about a value or key that the code never actually produced, usually because a config key was assumed rather than read. The same run reported that same key as having no mapping while reading it, so the two halves of the report contradicted each other. Ask of each line: what produced this string, and does that thing exist?
- **Error and skip copy**: when a skip reason is rewritten, the new reason has to be the real one. A plugin skip that said "skills and MCP servers cover the same ground" was replaced because that was not why — and the plugins that were genuinely enabled could be named instead. A reason that is approximately right is still wrong, because it is the reason someone will act on.
- **Comments and docstrings**: the one place a false claim is hardest to catch, because reviewers read comments as ground truth. Two live examples: a `PLAN_MODE_READ_ONLY_TOOLS` entry outliving the tool it named, which the surrounding comment now records explicitly; and a `Tool.checkPermissions` hook that was declared on the interface, implemented by two tools, and called by nothing at all. When a comment describes a guard, a flag, a lifecycle step, or a precedence rule, check the thing it names is still there and still does that.

The test to apply, which is the same one the key list has to pass: **point at the thing the sentence asserts.** If a claim cannot be tied to a specific symbol, branch, or line that implements it, the sentence is describing a mechanism that is not there — go read the code before deciding whether the text or the mechanism is what changed. And when the answer is that the text was describing something that got removed, the finding is that the text is still claiming it, not a request to delete the sentence.

A weaker version of the same check, worth doing on any renamed or removed thing: a test, a comment, or a report row that names an entity should be searched for across the repo in the same pass. A name that outlives its referent is the common shape here, and it is cheap to find and easy to miss.
