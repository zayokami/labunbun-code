---
name: code-review-maintainability
description: Check whether a change keeps files single-concern and consistent with labunbun's existing module boundaries, naming, and comment conventions, rather than growing an already-large file or inventing a new shape.
---

- **The largest files are large on purpose, so "this file is big" is not by itself a finding.** `packages/tui/src/vim.ts` is ~5,400 lines, `packages/coding-agent/src/interactive.ts` ~2,100, `packages/tui/src/emacs.ts` ~2,500. `vim.ts` grew that way through a long series of deliberate, separately-reviewed feature batches, each one a commit in its own right, and none of them would have been easier to review split. The question worth asking is narrower: **did this change add a distinct concern to a file that already had one, or extend the concern that is already there?** The second needs no action. The first is the one worth naming — that is how `permissions.ts`, `hooks.ts` and `compaction.ts` came to exist as single-concern modules pulled out of the loop rather than folded into `session.ts`.
- **The repo has exactly one measured data point on when a file is genuinely too big, and it is worth quoting the number rather than inventing a threshold.** `packages/coding-agent/src/migrate.ts` reached **13,229 lines** before being split into 20 modules, leaving a ~1,300-line hub and no consumer changed. That is the shape of the finding: a file large enough that a single review cannot hold it. The cost is not free and belongs in the recommendation, because a reviewer who proposes a split without it will get it rejected — the split needed 62 added `export`s, 30 deliberate overrides to keep the dependency edges legal, and four separate instruments to prove afterwards that not one declaration or comment had been lost in the move. Anything under roughly a tenth of that size is not asking for this.
- **Comment convention**: existing top-of-file comments state purpose plus a non-obvious invariant or rationale — e.g. `permissions.ts` ("deny rules always win across all sources"), `client.ts`'s `CONNECT_TIMEOUT_MS` rationale, `containment.ts`'s explicit cross-reference to the pattern it mirrors in `permissions.ts`. A new file with no such comment, or a comment that just restates what the code already says, is a gap; flag it, but don't ask for comments that would just repeat the code.
- **Factory + schema pairing naming**: tool constructors are named `create<Name>Tool` (`createBashTool`, `createReadTool`, ...; see `packages/tools/src/index.ts`), and config shapes are named `<Name>Schema` with a derived `type <Name> = z.infer<typeof <Name>Schema>` (`HookMatcherSchema`/`HookMatcher`, `McpServerConfigSchema`/`McpServerConfig`, `CommandHookSchema`/`CommandHook`). A new tool or config shape that doesn't follow this naming makes itself harder to find by grep and breaks the pattern every other module relies on.
- **Justified duplication only**: `packages/tools/src/containment.ts` duplicates `resolveCanonical`/path-matching logic from `packages/agent/src/permissions.ts` because `tools` can't depend on `agent`, and says so directly in its file comment. If a change duplicates existing logic across package boundaries, check it's actually necessary (not just convenient) and that it says why in a comment — an unexplained duplicate is a future divergence waiting to happen.
- **Cross-package export discipline**: see `code-review-api` for the export-boundary check itself; from a maintainability angle, also check that a change doesn't introduce a second way to do something already covered by an existing export (e.g. a new ad hoc path-resolution helper next to `resolveCanonical`), since two near-identical helpers drift apart over time even when neither is wrong on its own.

For each hit, name the existing convention or module it should have matched, not just that the new code "looks inconsistent."
